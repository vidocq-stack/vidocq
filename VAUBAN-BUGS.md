# Vauban bugs identified

## 1. ~~Proxying normal-scoped beans without a no-arg constructor~~ FIXED

**Symptom:** `UnproxyableResolutionException: Normal scoped bean X has no non-private no-arg constructor`

**Context:** An `@ApplicationScoped` bean with only an `@Inject` constructor could not be proxied by Vauban. CDI 4.1 has relaxed this constraint.

**Status:** Fixed in Vauban 0.1.0-SNAPSHOT. Proxies are generated without a no-arg constructor.

---

## 2. ~~Missing `Module.addReads()` in `VaubanLookup`~~ FIXED

**Symptom:** `RuntimeException: Cannot obtain Lookup for X`

**Context:** Vauban called `MethodHandles.privateLookupIn()` without `Module.addReads()` for application Java modules.

**Status:** Fixed in Vauban 0.1.0-SNAPSHOT.

---

## 3. ~~`sun.misc.Unsafe::staticFieldOffset` deprecated~~ FIXED

**Symptom:** `WARNING: A terminally deprecated method in sun.misc.Unsafe has been called`

**Status:** Fixed in Vauban 0.1.0-SNAPSHOT. Migrated to `VarHandle` / `MethodHandles.Lookup`.

---

## 4. ~~BCE `@Enhancement` did not process all matching classes~~ FIXED

**Symptom:** `@Enhancement(types = Object.class, withAnnotations = Path.class)` only processed one class instead of all.

**Status:** Fixed in Vauban 0.1.0-SNAPSHOT. The `BceProcessor` invokes `@Enhancement` for each matching class. Verified functional via `RestScopeExtension` which enriches all `@Path` classes.

---

## 5. ~~VaubanProcessor APT: trigger annotation enrichment not working~~ FIXED

**Symptom:** The APT loaded enrichment rules from `vauban-apt.properties` but did not apply them to `@Path`-annotated classes.

**Status:** Fixed in Vauban 0.1.0-SNAPSHOT. The `VaubanProcessor` APT executes BCEs at compile time, discovers extensions via ServiceLoader, and generates beans.list + _Factory + _ClientProxy for enriched classes. Writes `META-INF/vauban-bce-processed` to avoid re-execution at runtime.

---

## 6. ~~ClientProxy: `invokevirtual` on protected cross-package method rejected by the verifier~~ FIXED

**Symptom:** `VerifyError: Bad access to protected data in invokevirtual` at startup of an application using `@ApplicationScoped` servlets that extend `HttpServlet`.

**Context:** When a normal-scoped bean extends a class with `protected` methods (typical case of `HttpServlet.doGet`, `doPost`, `doHead` which are `protected`), the ClientProxy generated by Vauban overrides these methods and tries to call the super implementation. The emitted bytecode used `invokevirtual` on the superclass (e.g. `HelloServlet.doHead`) instead of `invokespecial` for a super-call, which is rejected by the JVM verifier (protected access outside the same class/package via non-authorised virtual invocation).

**Bytecode details:**
```
Location: fr/vidocq/examples/servlet/HelloServlet_ClientProxy.doHead(...)V @14: invokevirtual
Reason: Type 'fr/vidocq/examples/servlet/HelloServlet' (current frame, stack[0])
        is not assignable to 'fr/vidocq/examples/servlet/HelloServlet_ClientProxy'
Bytecode:
  2ab4 000e b900 1601 00c0 0004 2b2c b600 1bb1
                                     ^^^^ invokevirtual (should be invokespecial for super-call)
```

**Reproduction:**
```java
@ApplicationScoped
@WebServlet("/hello")
public class HelloServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        resp.getWriter().write("hi");
    }
}
```
Launch → immediate `VerifyError`.

**JVMS §4.10.1.9 explanation:** when a `protected` method is declared in a superclass, the verifier requires that the static type of the receiver on the stack be assignable to the current class. The delegate is cast to `HelloServlet` (the bean class), a type that is **not** assignable to `_ClientProxy` (it is the inverse — `_ClientProxy extends HelloServlet`). The same-runtime-package bypass does not apply when the protected method is declared higher up (e.g. `HttpServlet.doHead` in `jakarta.servlet.http`, a package different from the proxy's).

**Delivered fix:** `RuntimeClientProxyGenerator` now emits a dispatch via {@link java.lang.invoke.MethodHandle} for protected (or package-private) methods declared in a superclass located in a different package from the proxy. Each affected method gets a `private static final MethodHandle $$mh_<name>` field initialised in `<clinit>` via `MethodHandles.privateLookupIn(beanClass, MethodHandles.lookup()).findVirtual(...)`. The proxy override invokes `$$mh_<name>.invokeExact(delegate, args)` instead of `invokevirtual`. MethodHandle is not subject to §4.10.1.9 static checks: access is controlled at runtime by the privileged `Lookup`.

**Status:** FIXED in Vauban 0.1.0-SNAPSHOT (`RuntimeClientProxyGenerator`). 4 unit tests added for the protected cross-package case. The `vidocq-servlet-example` now uses `@ApplicationScoped` everywhere without workarounds; startup measured at 48 ms with 3 servlets + 1 filter + 1 listener, all endpoints (including BASIC auth and sessions) responding correctly.
