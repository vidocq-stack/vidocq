= vidocq-runtime-extensions
:description: Built-in extensions shipped with Vidocq Runtime.

[.lead]
`vidocq-runtime-extensions` is the set of extensions shipped out of the box, grouped by domain under five aggregators (`essentials`, `jakartaee-core`, `jakartaee-web`, `microprofile`, `module-repackaged`). Each leaf is an independent Maven artefact, activated by the user simply adding it as a dependency.

== Coordinates

[cols="1,3"]
|===
| Parent artefact | `io.vidocq.runtime.extensions:vidocq-runtime-extensions:{project-version}`
| Source | `vidocq-runtime/vidocq-runtime-extensions/` in the monorepo
|===

[[codegen-bundles]]
== Codegen bundles are jars

A `-codegen` bundle carries no code: it brings an extension's annotation processors to the compiler's `annotationProcessorPaths`. Up to 0.3.0 each bundle was a pom, declared with `<type>pom</type>`. From 0.4.0 each one is a jar holding only an empty `module-info`, and the `<path>` has no `<type>`: IntelliJ's Maven import ignores a processor path of type pom, so IntelliJ's own build used to compile the application without any processor and drop their output (Vidocq/vidocq#237). With jars, IntelliJ resolves each bundle with its dependencies, exactly as Maven does, and its build runs the same processors. The parent's default `vidocq-runtime-core-codegen` path, `vidocq extension add`, the scaffold and `vidocq:checkpom`'s suggestions all use the jar form.

A `<path>` that still says `<type>pom</type>` keeps working with Maven, since every bundle still publishes its pom, and the parent's `dependencyManagement` keeps a version for it. `vidocq:checkpom` warns about it, never fails: remove the `<type>pom</type>` line for IntelliJ.

[[peano-el]]
== Expression Language (Peano)

With the Vidocq runtime parent, declare the provider extension and append its processor
bundle to the inherited compiler configuration:

[source,xml,subs=attributes+]
----
<dependency>
    <groupId>io.vidocq.runtime.extensions.jakartaee.core</groupId>
    <artifactId>vidocq-runtime-peano-el-extension</artifactId>
</dependency>

<!-- maven-compiler-plugin -->
<annotationProcessorPaths combine.children="append">
    <path>
        <groupId>io.vidocq.runtime.extensions.jakartaee.core</groupId>
        <artifactId>vidocq-runtime-peano-el-extension-codegen</artifactId>
        <version>{project-version}</version>
    </path>
</annotationProcessorPaths>
----

`vidocq extension add peano-el` adds these coordinates. The application module requires
`io.vidocq.runtime.extensions.jakartaee.core.peano`; generated accessor classes and
`@ELAccessible` annotations also require `io.vidocq.peano.api`. No package opens are
needed for generated tables. [[peano-auto-accessors]]No annotation is needed for the
beans an expression reaches by name either: the processor also generates the tables of the classes and producer
methods annotated `@Named` or `@Model`, and of the application types their properties hold (and those of the
`@ELAccessible` types). A normal-scoped bean reaches EL as its Vauban client proxy (`<Bean>_ClientProxy`); the
extension provides the `ProxyUnwrapper` that lets the bean's table serve it, so it is not read by reflection. At process-classes, vidocq:generate reads the APT's
META-INF/peano/accessor-providers fragments and merges their provides directives into
the compiled application module descriptor. It preserves existing access and service
directives and does not rewrite module-info.java. Ensure the generate goal is bound
in the application's build lifecycle, as in Vidocq's generated projects.
The extension re-exports Jakarta EL, so applications use
the standard ExpressionFactory/ELProcessor APIs. Provider selection stays with the
Jakarta API and respects explicit application overrides; no global property is changed.

The `el` startup section reports the selected provider module and `peano.reflection`
policy. Selection happens during startup; rendering reads lifecycle facts only. The
processor is confined to the codegen bundle and the expression compiler remains a
separate build-time tool. Optional JavaBeans compatibility
is not pulled into the runtime extension. Peano's own official TCK results describe
the implementation; these wiring tests do not certify the assembled runtime.

[[servlet]]
== Servlet (Foy)

`vidocq-runtime-foy-servlet-extension` serves the application's servlets, filters, listeners, `web.xml`, web fragments and `ServletContainerInitializer`s through xref:foy::index.adoc[Foy], mounted on the same Chappe server as the other extensions. An application with none of them gets no mount: the extension stays inactive.

Declare the extension, and its codegen bundle on the processor path:

[source,xml,subs=attributes+]
----
<dependency>
    <groupId>io.vidocq.runtime.extensions.jakartaee.web</groupId>
    <artifactId>vidocq-runtime-foy-servlet-extension</artifactId>
</dependency>

<!-- maven-compiler-plugin -->
<annotationProcessorPaths combine.children="append">
    <path>
        <groupId>io.vidocq.runtime.extensions.jakartaee.web</groupId>
        <artifactId>vidocq-runtime-foy-servlet-extension-codegen</artifactId>
        <version>{project-version}</version>
    </path>
</annotationProcessorPaths>
----

The bundle generates the factories of the `@WebServlet`, `@WebFilter` and `@WebListener` classes, makes them beans (so they take `@Inject`), and registers the session context. `vidocq extension add foy-servlet` adds both, and `vidocq:checkpom` asks for the bundle when the extension is declared. In a named module, the application `requires io.vidocq.foy.api` for the generated code.

[cols="2,1,3"]
|===
| Key | Default | Description

| `vidocq.servlet.context-path`
| the `web.xml` `<default-context-path>`, else `/`
| Context path of the application, and prefix of its mount.

| `vidocq.servlet.listener`
| `default`
| Chappe listener the application is mounted on.

| `vidocq.servlet.session-timeout`
| `1800`
| Session timeout in seconds, used when no descriptor declares a `<session-timeout>`. Zero or less: sessions never expire.

| `vidocq.servlet.response-character-encoding`
| `UTF-8`
| Default response encoding of the application, used when neither `web.xml` nor a web fragment declares a `<response-character-encoding>`. See <<servlet-response-encoding>>.
|===

[#servlet-response-encoding]
=== Response encoding

The Servlet specification encodes a text response in ISO-8859-1 unless the application names another encoding, so a page with accents, written through `getWriter()`, reaches the browser garbled. Under the runtime, an application that configures nothing answers in **UTF-8**: the extension makes UTF-8 the default response encoding of the `ServletContext`, and `getWriter()` responses carry `charset=UTF-8`.

What the application configures still wins:

* a `<response-character-encoding>` in `web.xml` or in a web fragment;
* `ServletContext.setResponseCharacterEncoding(...)`, called by a `ServletContainerInitializer` or a listener;
* the encoding a servlet sets on its response, with `setCharacterEncoding` or `setContentType("text/html;charset=...")`.

`vidocq.servlet.response-character-encoding` changes the default; `ISO-8859-1` restores the Servlet one. The value must name a character encoding the JDK supports, or the application fails at startup with the key in the message. A declarative `type=servlet` mount takes the same value. The Servlet TCK run on the assembled runtime asserts the Servlet default, so it sets the key to `ISO-8859-1`.

[source,properties]
----
vidocq.servlet.response-character-encoding=ISO-8859-1
----

=== Security

Foy enforces the security constraints of `web.xml` and `@ServletSecurity`, with BASIC, FORM or `HttpServletRequest.login`. It checks credentials against a user base, which the extension supplies:

* an application bean that implements `io.vidocq.foy.spi.security.IdentityStore`: `validate(user, password)` returns the caller's `Identity`, with its roles, or empty to refuse;
* otherwise, users declared in the configuration, for development: `vidocq.servlet.users.<name>.password` and `vidocq.servlet.users.<name>.roles`, a comma-separated list. Foy keeps only a salted digest of each password, but the configuration holds it in clear.

Without either, every login fails. A bean and configured users together fail at startup.

[source,java]
----
@ApplicationScoped
public class Accounts implements IdentityStore {
    @Override
    public Optional<Identity> validate(String user, char[] password) {
        // compare in constant time, never log the password
    }
}
----

[cols="2,1,3"]
|===
| Key | Default | Description

| `vidocq.servlet.users.<name>.password` +
`vidocq.servlet.users.<name>.roles`
| none
| A user of the in-memory store and its comma-separated roles. Not allowed next to an `IdentityStore` bean.

| `vidocq.servlet.confidential-port`
| none
| HTTPS port a `CONFIDENTIAL` or `INTEGRAL` constraint redirects plain HTTP to. Unset: such a request gets 403.

| `vidocq.servlet.rotate-session-id-on-login`
| `true`
| Whether a successful login changes the session id, against session fixation.
|===

=== Request and session scopes

Foy activates the request context around every request, and the session context with the `HttpSession`: a `@SessionScoped` bean lives as long as its session, `HttpSession.invalidate()` or the timeout destroys it and fires `@Destroyed(SessionScoped.class)`. Passivation of session beans is not supported.

[[servlet-built-in-beans]]
=== Injecting the request, the session and the context

A bean injects the `HttpServletRequest` being served (`@RequestScoped`), its `HttpSession` (`@SessionScoped`, created at first use) and the application's `ServletContext` (`@ApplicationScoped`, there from the start of the deployment, so a `ServletContextListener` can use it in `contextInitialized`). Foy's `foy-cdi-vauban`, which the extension brings, provides the three beans: the application declares nothing. Their client proxies are generated when Foy is built, so a packaged application generates no class for them when it starts. Where they work, and their limits: xref:foy::usage.adoc#servlet-built-in-beans[Injecting the request, the session and the context].

=== Next to REST

The REST and Servlet extensions are two mounts of one server. The longest prefix wins: with REST on `/api` and the servlets on `/`, `/api/items` reaches Cassini and every other path reaches Foy. Two mounts on the same prefix of one listener fail at startup, with the extensions and the keys to change named in the message. By default, servlet filters and the `HttpSession` do not apply to REST resources. [[rest-as-servlet]]To run the application's REST resources inside Foy instead (https://codefloe.com/Vidocq/vidocq/issues/215[vidocq#215]), add `cassini-servlet` next to the two extensions: the resources are then served by a servlet that Foy registers at the `@ApplicationPath`, so the context path, the filters and the authentication (Jakarta Security included) apply to them like to any servlet, and `SecurityContext` and `jakarta.ws.rs.core.SecurityContext` answer with the caller Foy authenticated. `vidocq.rest.mode` chooses: `auto` (the default) serves the resources as a servlet when the Foy extension and `cassini-servlet` are both there, and on Chappe otherwise; `chappe` mounts them on Chappe whatever is there; `servlet` fails the start when Foy or `cassini-servlet` is missing. In servlet mode the automatic Chappe mount is not made; the declarative `vidocq.http.mount.<name>.type=restful` mounts stay on Chappe, which is where MicroProfile Health and the other operations endpoints are served, outside the application's security. `cassini-servlet` is not a dependency of the REST extension, so an application without Foy needs no Servlet API.

The REST extension mounts its resources on the `@ApplicationPath` of the application's `Application` subclass, which needs no CDI scope: `cassini-processor`, in the REST codegen bundle, records the path at compile time. `vidocq.rest.context-path` wins over it.

=== Declarative mount

`vidocq.http.mount.<name>.type=servlet` mounts the application on `vidocq.http.mount.<name>.path`, on `vidocq.http.mount.<name>.listener`; `vidocq.http.mount.<name>.session-timeout` overrides `vidocq.servlet.session-timeout`. With such a mount, the extension does not mount the application on its own. A `servlet` mount on an application without any web component fails at startup, and so do a second `servlet` mount, which would start the application twice, and `strip-prefix=true`: the prefix is the context path, and Foy dispatches on the full request path.

=== The `servlet` section of the startup report

The `servlet` section gives the number of servlets and filters and the prefixes they are mounted on, the listener, the context path and the session timeout, then every servlet and filter with what it is mapped to, and the listeners in registration order; or it says that the extension is inactive.

Under `vidocq:dev`, `vidocq-runtime-foy-servlet-extension-dev` makes the section live in the dev console: it plots the active sessions of each servlet deployment. Only `vidocq:dev` adds the module; no binary contains it.

[[foy-websocket]]
== Jakarta WebSocket (Foy)

`vidocq-runtime-foy-websocket-extension` (Java module `io.vidocq.runtime.extensions.jakartaee.web.websocket`) brings Foy's `foy-websocket` module into the application: Jakarta WebSocket 2.2, programmatic server API. Foy puts the `ServerContainer` in the `jakarta.websocket.server.ServerContainer` servlet context attribute; an application adds its endpoints to it, from a `ServletContextListener` (`@WebListener`) for instance, with `ServerContainer.addEndpoint(ServerEndpointConfig)`. The Vaadin extension depends on this extension, so a Vaadin application needs no dependency of its own (<<vaadin>>). `vidocq extension add foy-websocket` adds it to any other application, or declare it:

[source,xml]
----
<dependency>
    <groupId>io.vidocq.runtime.extensions.jakartaee.web</groupId>
    <artifactId>vidocq-runtime-foy-websocket-extension</artifactId>
</dependency>
----

It runs on the Servlet extension, so the application is mounted as described in <<servlet>>. The application module requires `jakarta.websocket` for the API.

[WARNING]
====
On the module path, Foy creates a programmatic `Endpoint` subclass through its Class-File tier, a hidden class defined in the endpoint's package. The application module must open that package to `io.vidocq.foy.core`, or the handshake fails (reflection is only Foy's last resort):

[source,java]
----
opens com.example.app.ws to io.vidocq.foy.core;
----

See `vidocq-runtime-it-foy-websocket` for a complete module.
====

An application stop closes every open WebSocket connection with a Close frame of code 1001 (going away), and calls the endpoint's `onClose` with 1006 (closed abnormally), before the Chappe servers stop. The stop is a close the container initiates, and Jakarta WebSocket 2.2 §2.1.5 gives `onClose` 1006 for those, so the endpoint can tell it from a peer that sent 1001 (Foy BUG-20261115-08). The Servlet extension closes Foy's deployments in a before-stop hook of the Chappe mount point (`ChappeMountPoint.addBeforeStopHook`). Without it the connections dropped with no Close frame and the peer saw 1006 (BUG-20261115-01). `Servlet.destroy()` and `ServletContextListener.contextDestroyed` run while the server still serves, too.

[cols="2,1,3"]
|===
| Key | Default | Description

| `vidocq.websocket.allowed-origins`
| _none_
| Origins allowed to open a WebSocket besides the server's own: comma-separated (`https://admin.example.com, http://localhost:5173`), or `*` for any. Applies to Jakarta WebSocket endpoints and to every WebSocket route of the server, native `type=websocket` mounts included. `*` turns the protection against cross-site WebSocket hijacking off. A malformed entry stops the start.
|===

With no value, or a blank one, only the same origin is allowed. The extension checks the syntax of the key at start and a malformed value stops the start with a message naming `vidocq.websocket.allowed-origins`; it then hands the value to Foy as a servlet context init parameter. Its `websocket` section of the startup report has the summary `Jakarta WebSocket 2.2`; the accepted origins are the `allowed origins` row, shown by the detailed report (`-Dvidocq.startup.report=detailed`): `same origin only`, `any`, or the list.

Annotated `@ServerEndpoint` endpoints, the client API and the official Jakarta WebSocket TCK come later (Vidocq/vidocq#65).

[[ibarra-pages]]
== Jakarta Pages (Ibarra)

`vidocq-runtime-ibarra-pages-extension` serves the application's JSP pages through the Servlet extension. xref:ibarra::index.adoc[Ibarra] compiles them at build time, inside `vidocq:generate`: no page is translated or compiled while the application runs, and the runtime holds no Java compiler. The extension brings the Servlet extension and the Expression Language extension (<<peano-el>>) with it.

[source,xml]
----
<dependency>
    <groupId>io.vidocq.runtime.extensions.jakartaee.web</groupId>
    <artifactId>vidocq-runtime-ibarra-pages-extension</artifactId>
</dependency>
----

The application module reads the APIs its compiled pages use:

[source,java]
----
module com.acme.shop {
    requires io.vidocq.runtime.extensions.jakartaee.web.ibarra;
    requires io.vidocq.ibarra.api;
    requires io.vidocq.peano.api;   // pages with expressions
}
----

`vidocq extension add ibarra-pages` adds the dependency and these directives.

Where the pages go, as Foy serves the web resources of a runtime application:

* pages the client requests under `src/main/resources/META-INF/resources/`: `META-INF/resources/hello.jsp` answers `/hello.jsp`;
* pages only a forward or an include reaches under `src/main/resources/WEB-INF/`: `WEB-INF/views/greet.jsp` is `/WEB-INF/views/greet.jsp` for `getRequestDispatcher`, and a client request for it answers `404`;
* tag library descriptors under `WEB-INF/` (for example `WEB-INF/tlds/strings.tld`), or in the `META-INF/` of a module the application reads; `jsp-config` in `WEB-INF/web.xml`, else `META-INF/web.xml`.

At process-classes, `vidocq:generate` stages them as a web root under `target/ibarra-web` and compiles every page into the application module, whose descriptor gains `provides io.vidocq.ibarra.spi.PageIndex`. A page that does not translate or compile fails the build, with the page named. Pages in a module that does not require `io.vidocq.ibarra.api` are not compiled: the build warns and names the first one. The precompilation runs before the Peano accessor registration, which keeps the page index when it rewrites the descriptor. Bind the generate goal in the build, as Vidocq's generated projects do: `vidocq:run` and `vidocq:dev` then reach it through `process-classes`. Without it, no page is compiled, and the startup report says so.

[[pages-cdi-beans]]A page reads a CDI bean by its name, as Jakarta EE requires: `${cart.total}` is the
`total` of the `@Named` bean `cart`, in its scope (a `@RequestScoped` bean is the one of the current request). Once
the application is deployed, before its first request, the extension adds a resolver of CDI bean names to the
pages' EL context (`JspApplicationContext.addELResolver`); a name no bean has goes on to the request, session and
application attributes as before. A `@Dependent` bean read by name is created for the page and destroyed when the
request ends. A name with dots (`@Named("a.b")`) is not split into a bean name and properties. Vauban implements CDI Lite, which has no `BeanManager.getELResolver()`: the
resolver is built on `BeanManager.getBeans(String)`. Peano reads the bean through the accessor table it generates
for a `@Named` bean, served for its client proxy (xref:#peano-auto-accessors[no `@ELAccessible` needed]), so the
page needs no reflection.

At run time, Foy finds Ibarra's JSP engine and the compiled pages in the application layer. An application made of pages only, with no servlet, filter or listener of its own, is deployed.

The `pages` section of the startup report counts the compiled pages and lists their paths; when none was compiled, it reports an anomaly with the steps above.

[[bodoni-jstl]]
== Jakarta Standard Tag Library (Bodoni)

`vidocq-runtime-bodoni-jstl-extension` lets the pages of <<ibarra-pages>> use the standard tags: `c:` (core), `fmt:` (formatting and internationalisation), `fn:` (functions), `x:` (XML) and `sql:` (relational database access). xref:{page-component-version}@bodoni::index.adoc[Bodoni] implements Jakarta Standard Tag Library 3.0 and depends on its APIs only; this extension assembles the rest. It brings with it the Pages extension (<<ibarra-pages>>, which brings the Servlet extension and <<peano-el>>) and `bodoni-peano`, the accessor tables Peano needs under `-Dpeano.reflection=deny` to read the `varStatus` of `c:forEach`, the items of a `Map` and the `Result` of `sql:query`. An application declares the extension, nothing else of that chain.

[source,xml]
----
<dependency>
    <groupId>io.vidocq.runtime.extensions.jakartaee.web</groupId>
    <artifactId>vidocq-runtime-bodoni-jstl-extension</artifactId>
</dependency>
----

The application module reads Bodoni's tag handlers, which its compiled pages construct, and the APIs of Ibarra and Peano:

[source,java]
----
module com.acme.shop {
    requires io.vidocq.runtime.extensions.jakartaee.web.bodoni;
    requires io.vidocq.bodoni.core;
    requires io.vidocq.ibarra.api;
    requires io.vidocq.peano.api;
}
----

`vidocq extension add bodoni-jstl` adds the dependency and these directives. A page then declares a library with the URI of the specification and uses it as on any Pages container:

[source,jsp]
----
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<%@ taglib prefix="fn" uri="jakarta.tags.functions" %>
<c:forEach items="${names}" var="n" varStatus="s">${s.index}: ${fn:toUpperCase(n)}</c:forEach>
----

`vidocq:generate` compiles the page like any other, at build time: the tag handlers are called directly, no tag library is parsed while the application runs. `sql:` looks a data source up under `java:comp/env`, which <<naming>> provides.

The `jstl` section of the startup report counts the tag libraries found in the module graph and lists their prefixes; when Bodoni is missing, it reports an anomaly that names the `requires` to add.

[WARNING]
====
.Deploying on an application server
The same `bodoni-core` jar is the JSTL implementation in a WAR on Open Liberty (tested by Bodoni's `bodoni-it-openliberty` module): keep the server's own Standard Tag Library feature off for that application, as the Deploying on an application server block of the Bodoni reference page says. The extension is for Vidocq only; on a server, the server assembles Pages, Servlet and Expression Language.

[[naming]]
== JNDI `java:` names

Code written for an application server looks its resources up by name, and the bricks keep doing so: Mansart Data resolves `@Repository(dataStore = "java:comp/env/jdbc/audit")` with `new InitialContext().lookup(…)`, and the Standard Tag Library's `sql:` tags look a data source up under `java:comp/env`. Naming is a service of the platform: `vidocq-runtime-naming-extension` provides it, from the running CDI container, through xref:{page-component-version}@vauban::jndi.adoc[Vauban Naming].

[source,xml]
----
<dependency>
    <groupId>io.vidocq.runtime.extensions.jakartaee.web</groupId>
    <artifactId>vidocq-runtime-naming-extension</artifactId>
</dependency>
----

The extension needs no codegen and no directive in the application's module unless the application looks names up itself or declares some in code, with `requires io.vidocq.runtime.extensions.jakartaee.web.naming`. `vidocq extension add naming` adds the dependency and that directive.

*Declaring names.* Beyond the names of the platform and of the pools, below, Vidocq answers the names the application declares, one key of `vidocq.properties` per name: `vidocq.naming.` followed by the name without `java:`.

[source,properties]
----
# a bean: its type, then its qualifiers; none means @Default
vidocq.naming.comp/env/jdbc/orders   = javax.sql.DataSource @Named("orders")
vidocq.naming.comp/env/jms/audit     = com.acme.AuditQueue
vidocq.naming.comp/env/payment       = com.acme.Payment @com.acme.Primary
vidocq.naming.comp/env/orders/eu     = com.acme.Orders @com.acme.Region("eu") @com.acme.Tier(level = 2)

# a link: another name, such as an alias of a data source
vidocq.naming.comp/env/jdbc/legacy   = java:comp/env/jdbc/orders
vidocq.naming.app/env/jdbc/reporting = java:comp/env/jdbc/orders
----

* *The key* copies into a lookup as it is: `vidocq.naming.comp/env/com.acme.Orders/ds` is `java:comp/env/com.acme.Orders/ds`. A properties key takes `/`; only a `:` would need escaping, and the key has none. A key under `vidocq.naming.` that does not start with `comp/`, `module/`, `app/` or `global/` fails the start, so that `vidocq.naming.comp.env.orders`, with dots for slashes, is not silently ignored.
* *A value starting with `java:`* links to that name. *Any other value* is a bean written as text: `@Named`, `@Default` and `@Any` take their short name, every other qualifier its fully qualified name, and a member is a Java source literal (xref:{page-component-version}@vauban::jndi.adoc#text[the grammar]). A properties file reads `\\` as `\`, so double each backslash of a literal: `@Named("say \"hi\"")` is written `@Named("say \\"hi\\"")` in `vidocq.properties`.
* *The four namespaces are distinct*, as in the Jakarta EE Platform: `java:comp`, `java:module`, `java:app` and `java:global`. A name exists only in the namespace it is declared in, so `java:comp/env/jdbc/orders` does not answer `java:app/env/jdbc/orders`: declare both, or link one to the other.
* *The pools answer by default*, as the data sources of an application server do (Vidocq/vidocq#676): `java:comp/DefaultDataSource` (Jakarta EE Platform, §5.19) is the default pool (`vidocq.pool.url`), and `java:comp/env/<name>` the pool `vidocq.pool.<name>.url`: the pool `orders` answers `java:comp/env/orders`. Any `DataSource` bean does: the `@Default` one and each `@Named` one.
** *With the transactions extension*, the name answers the pool through Mansart's `JtaDataSource`: within a transaction, its connections are the one connection of that transaction and that pool, which the transaction manager alone commits or rolls back, and which a Jakarta Data repository or a JTA persistence unit on the same pool works on too. Outside a transaction, and without the transactions extension, they are the pool's own.
** *A key of `vidocq.properties` that declares the name replaces it*, and binds the pool itself, which never takes part in a transaction: `vidocq.naming.comp/env/jdbc/orders-raw = javax.sql.DataSource @Named("orders")`. This is the `non-jta-data-source` of a JTA persistence unit whose factory the application creates itself.
* *The transaction names of the platform* come with the transactions extension (`vidocq-runtime-mansart-transactions-extension`): `java:comp/UserTransaction` is its `UserTransaction` bean and `java:comp/TransactionSynchronizationRegistry` its `TransactionSynchronizationRegistry` bean, as the Jakarta EE Platform defines them (§5.10, §5.11). Without that extension, neither name is bound. A key of `vidocq.properties` that declares one of them replaces it.
* *Environment variables* override a key already in a file, as MicroProfile Config maps them (`VIDOCQ_NAMING_COMP_ENV_JDBC_ORDERS`), but cannot declare a new name: the `/` of the name cannot be read back from the variable.

*What is checked at startup.* Vauban checks every declared name when the container starts, as it checks an injection point. The start fails, naming the key, when a name is declared twice, when no bean or several beans match a bean, when that bean is `@Dependent` (nobody would destroy the instance a lookup creates; the pools of the Mansart Pool extension are `@Singleton`), when a qualifier is not one, when a link names an undeclared name, or when links loop.

*Installation.* In its `configure` phase, before the container starts, the extension makes Vauban's factory the default of the JVM, through the `java.naming.factory.initial` system property. It sets the property only when the application chose no factory: neither in that property nor in a `jndi.properties` file, which the property would override. `ldap://`, `rmi://` and `dns://` names still reach the JDK's providers, and `new InitialContext(env)` with an explicit `Context.INITIAL_CONTEXT_FACTORY` still gets that factory. When Vidocq stops, the extension clears the property it set.

*A context holds no container.* Each lookup asks the container running at that moment: a context the application kept answers from the new container after a `vidocq:dev` restart, and with no container running a lookup throws `NoInitialContextException`. A bean is resolved at each lookup, and the namespace is read-only: `bind` and the other writes throw `OperationNotSupportedException`. `java:comp/env`, `java:module/env`, `java:app/env` and the parents of a declared name are contexts, in which relative names resolve, as the Standard Tag Library resolves `jdbc/orders` under `java:comp/env`.

The `naming` section of the startup report says which factory answers `java:` names, this extension's or the one the application chose, then lists each name `vidocq.properties` declares with its target.

An application or a library can also declare names in code, with a `JndiBindings` bean, and answer names not known in advance with a `JndiNameProvider` bean: see xref:{page-component-version}@vauban::jndi.adoc[Vauban Naming].

Not covered yet: literal values (`env-entry`), `@Resource` injection, `resource-ref` in `web.xml`, `@DataSourceDefinition`, and the `jms/` names of Tassis, which will come as a `JndiNameProvider` of its extension (vidocq#297).

== Typical lifecycle — Chappe example

The `vidocq-runtime-chappe-webserver-extension` extension illustrates the pattern. Four hook points:

[cols="1,2,1,3"]
|===
| Phase | Actor | Priority | Action

| `configure`
| `ChappeEngineExtension`
| 100
| installs `ChappeMountPoint`

| `onStart`
| Contributors (REST, Servlet)
| 500–9999
| call `mount(...)`

| `onStart`
| `ChappeServerBootstrap`
| 10000
| starts a `Server` per listener

| `onStop`
| `ChappeServerBootstrap`
| 10000
| runs the hooks of `ChappeMountPoint.addBeforeStopHook(Runnable)` while every listener still serves, then shuts servers down cleanly, then runs the `addAfterStopHook` ones
|===

Every listener logs the address it actually bound, not the one it was given: with `port=0`, the line shows the real port.

----
Chappe listener 'default' started on http://localhost:43127/
----

A wildcard host reads `localhost` and an IPv6 address is bracketed, `http://[::1]:8080/`.

`vidocq.chappe.listener.default.port-file` is an internal key of xref:testing.adoc#http-port[`@VidocqTest`], not one for applications: the `default` listener writes the port it bound to that file, in one atomic move, so the test reads it whatever the logging configuration; a file it cannot write is a WARNING, never a failed start.

[#chappe-http-section]
The startup report gets the same addresses in its `http` section, one per listener of the configuration. The sections that declare routes, such as `rest`, then print them as absolute URLs, and the `mcp` section finds the URL of `/mcp` there:

----
http          HTTP (Chappe) | 0 ms
  default http://127.0.0.1:18090/
rest          REST (Cassini) | 1 ms
  1 resource class, 4 routes, 4 providers at /
  POST    http://127.0.0.1:18090/mcp          McpEndpoint#handlePost
----

A listener an extension declares for itself is left to that extension's section: the dev console's is in the `devconsole` section. An extension reads the URL a listener really listens on with `ChappeMountPoint.instance().boundUrl(name)`, from its `contribute` onwards.

[#chappe-websocket-origins]
A native Chappe WebSocket mount (`vidocq.http.mount.<name>.type=websocket`), and any other WebSocket route of the mount point (`ChappeMountPoint.webSocket(...)` or a router an extension adds), takes the same origin rule as the Jakarta WebSocket endpoints of Foy: `vidocq.websocket.allowed-origins` lists the origins allowed besides the server's own, `*` allows any, and a malformed entry stops the start. See <<foy-websocket>>.

[#extension-listeners]
=== A listener of an extension's own

An extension that serves something apart from the application, as the dev console does, declares its own listener from its `onStart`, between priority 100 and 10000, then mounts on it by name like on any other:

[source,java]
----
ChappeMountPoint mp = ChappeMountPoint.instance();
mp.declareListener(ChappeListener.http("dev", "127.0.0.1", 8888),
        new ListenerOptions(true, true, Duration.ofSeconds(1), this::bound));
mp.router("dev").get("/api/snapshot", snapshot);
----

[cols="1,3"]
|===
| `ListenerOptions` | Effect

| `anyPortWhenTaken`
| When the port is in use, listen on a free port instead of failing the boot, and log a WARNING naming both ports. Chappe first retries the bind with a backoff, as for any listener, so falling back costs about one second.

| `quiet`
| Log the `Chappe listener '…' started on …` line at DEBUG, for an extension that prints its own.

| `shutdownGracePeriod`
| How long stopping the server waits for the requests in flight. `null` keeps Chappe's 30 seconds.

| `onBound`
| Called on the boot thread once the server listens, with the address it bound: the real port when the declared one was `0` or taken. Nothing can be mounted any more, and an exception it throws is logged as a WARNING, never fatal.
|===

`ListenerOptions.DEFAULTS` starts the listener like one of the configuration. `ChappeListener.httpUrl(address)` turns the address `onBound` receives into the URL the log line shows.

A listener name has one owner. The extensions' listeners start first, then those of `vidocq.chappe.listeners`, which must not list a name an extension declared: the boot fails with `listener 'dev' is declared by an extension (DevConsoleExtension); remove it from vidocq.chappe.listeners`. The listener named `default` is always the application's.

Other extensions follow comparable scheduling logic with their own priorities.

[#cassini-rest-report]
== The `rest` section of the startup report

`vidocq-runtime-cassini-rest-extension` writes the `rest` section: what the Jakarta REST application exposes, as Cassini resolved it. It covers every Cassini stack mounted during the boot — the automatic mount configured by `vidocq.rest.*`, reported as `vidocq.rest`, and each declarative `vidocq.http.mount.<name>.type=restful` mount, reported by its name.

The summary line counts the resource classes, the routes and the providers, and says where they are mounted. The detailed report then lists the routes **in match order** — when two routes match a request, the one listed first wins — each with the resource class and method that handles it; then each mount, the resource classes, and the `@Provider` classes grouped by the contract they implement. A provider that is both a filter and an exception mapper is listed under both.

.An application serving a langchain4j-cdi MCP server (<<langchain4j-cdi-mcp>>), `-Dvidocq.startup.report=detailed`
[source,text]
----
rest          REST (Cassini) | 0 ms
  1 resource class, 4 routes, 4 providers at /
  POST    /mcp/_listen  McpEndpoint#handleListen
  POST    /mcp          McpEndpoint#handlePost
  GET     /mcp          McpEndpoint#handleGet
  DELETE  /mcp          McpEndpoint#handleDelete
  mount vidocq.rest  listener default, prefix /, 4 routes
  resources          dev.langchain4j.cdi.mcp.server.transport.McpEndpoint
  request filters    dev.langchain4j.cdi.mcp.server.transport.McpListenRoutingFilter,
                     io.vidocq.cassini.cdi.vauban.VaubanRequestScopeFilter
  response filters   dev.langchain4j.cdi.mcp.server.transport.McpSseStreamHeadersFilter,
                     io.vidocq.cassini.cdi.vauban.VaubanRequestScopeFilter
  exception mappers  dev.langchain4j.cdi.mcp.server.transport.McpExceptionMapper
----

A route's path is the one a client requests on the listener: the mount prefix, then the path Cassini matches. A mount declared with `strip-prefix=false` hands Cassini the full path, so its routes are printed as Cassini matches them, and its row says `(not stripped)`. A sub-resource locator whose target class is only known when a request reaches it is printed with `*` as its method and names the locator itself.

The route table names handler classes, as every routing section of the report does; it is printed in the detailed report only, the summary keeps its one line. Every route is declared to the report at every level, so a later section finds the URL of its own resource: the `mcp` section's `endpoint` row reads its URL there. The routes are printed as absolute URLs, joined with the listener the <<chappe-http-section,`http` section>> declares.

The section reads what Cassini computed when each stack was built, through `CassiniStack.routes()` (xref:cassini::usage.adoc#route-table[Reading the route table]): it creates no resource or provider instance, and it keeps names only, never a class of the application, so a dev reload releases the previous application.

[#cassini-rest-live]
=== The `rest` panel in the dev console

The dev console shows the section as the `rest` panel, with the boot facts above, and one card per mount below it, sampled about once a second from the counters each Cassini stack keeps (xref:cassini::usage.adoc#request-statistics[Reading live request figures]):

[cols="1,1,3"]
|===
| Key | Kind | What it is

| `requests`
| counter
| The requests the mount answered since the boot, whatever their status. Plotted as requests per second.

| `status.1xx` to `status.5xx`
| counter
| The same, by status class. The *Responses by status* chart plots `2xx` to `5xx` per second.

| `in-flight`
| gauge
| The requests handed to Cassini and not answered yet.

| `handler-time`
| counter, nanoseconds
| The time spent answering, added up. Its rate is the share of wall time spent in handlers, added up over concurrent requests: 200 % reads as two requests being served at every instant, on average.

| `mean`, `max`
| duration
| The mean and the longest time to answer one request since the boot; absent, `no request served yet`, before the first.
|===

A request is timed from the moment Chappe hands it to Cassini to the moment Cassini has written its response: filters, the resource method, exception mappers and serialisation, not the network. A request no resource matches counts as the `404` it gets. The figures are totals for the whole mount: there is no breakdown per route.

Sampling sums a few counters and creates nothing. The counters are on in every stack Vidocq builds; they cost about 25 ns per request and allocate nothing, as Cassini's `BENCH.md` measures. A stack built without them shows `requests` absent, `counters off`, never a zero.

[#dirac-metrics-panel]
== Dirac metrics in the startup report and the dev console

`vidocq-runtime-dirac-metrics-extension` writes the `metrics` section, titled *Metrics (Dirac)*: what the three MicroProfile Metrics registries of xref:dirac::index.adoc[Dirac] hold. The dev console shows it as the `metrics` panel. Dirac itself needs no Vidocq code; the extension, `DiracMetricsExtension`, only reads what Dirac publishes.

[#dirac-metrics-report]
=== Boot facts

The summary line counts the metrics of each registry, gauges included: `3 application metrics, 13 base, 0 vendor`. The base registry holds the gauges Dirac reads from the JVM. The detailed report then writes:

* one row per registry, `application`, `base` and `vendor`: its counters, timers, histograms and gauges, such as `1 counter, 1 timer, 0 histograms, 1 gauge`;
* a list `<registry> metrics` for each registry that holds a counter, a timer or a histogram: the key each one has in the panel, its kind, then its name and tags, such as `checkout.shop-eu, checkout.shop-eu.mean = timer checkout{shop=eu}`. This is where a key the panel shortened or numbered reads back as the metric it stands for;
* a list `<registry> gauges`: each gauge by its name and tags.

A metric name is not a valid key of the console, so the panel derives one, always the same for the same registry: the name, then each tag in the order of the tag names as `.name-value`; lowercased, every character other than a letter, a digit, a dot or a hyphen replaced with a hyphen, and `m-` in front when it does not start with a letter; cut to 40 characters, less 5 for a timer, whose mean needs `.mean`; and when two metrics end up with the same key, the second gets `-2`, the third `-3`. `com.acme.Shop.placeOrder` with the tag `shop=EU` is `com.acme.shop.placeorder.shop-eu`.

=== The `metrics` panel in the dev console

One card per registry, `application` first, then `base` and `vendor`, sampled about once a second:

[cols="1,1,3"]
|===
| Key | Kind | What it is

| `counters`, `timers`, `histograms`, `gauges`
| gauge
| How many metrics of that kind the registry holds.

| `<key>` of a counter
| counter
| Its count. The page shows how much it grew since the previous poll.

| `<key>` of a timer
| counter
| How many times it was timed.

| `<key>.mean` of a timer
| duration
| Its mean: the time it recorded, added up, divided by its count; absent, `no call yet`, before the first.

| `<key>` of a histogram
| counter
| How many values it recorded.

| `omitted`
| text
| How many metrics of the card did not fit, such as `11 metrics left out: the console shows 64 values per group`. Written only when some did not.
|===

What is never shown:

* **A gauge's value.** A gauge's `getValue()` runs application code, which may do I/O or wait on a lock. A gauge is counted and named in the boot facts, and never called, by the report or by the panel.
* **A timer's longest time, or any percentile.** Dirac's `Timer.getSnapshot()` copies and sorts every value its reservoir holds, too much for a poll that should take well under a millisecond. The panel reads `getCount()` and `getElapsedTime()` only. A histogram shows its count for the same reason.
* **More than 64 values per card.** The four counts and `omitted` leave 59 values for the metrics: counters first, then timers, two values each, then histograms, each kind in the order of its name and tags. Past them, the rest of the card is left out — a timer whole or not at all — and `omitted` says how many metrics were. The application's metrics have a card of their own, so the JVM gauges of the base registry never push them out.

The section and the panel read the registries of the `MetricRegistryProducerBean` instance the application already has: the bean is resolved once when the extension starts, and each sample asks its context for the existing instance, which never creates one. Before anything asked Dirac for a registry or a metric, the section's summary is `registries not created yet` and the panel shows a single `registries` value, absent, `not created yet`. A container with no Dirac producer, or with a second copy of Dirac loaded by the application layer, which the extension cannot read, shows `no Dirac registry in this container`.

[#knock-health-panel]
== Knock health checks in the startup report and the dev console

`vidocq-runtime-knock-health-extension` writes the `health` section, titled *Health (Knock)*: the health checks xref:knock::index.adoc[Knock] registered, by probe, and the last answer of each. The dev console shows it as the `health` panel. Knock itself needs no Vidocq code; the extension, `KnockHealthExtension`, only reads what Knock keeps in memory.

A health check is application code, and may do I/O: neither the section nor the panel ever calls one. Knock remembers the last answer of each check as a probe request ran it, `GET /health`, `/health/live`, `/health/ready` or `/health/started`, and the panel shows that answer. A check that turns DOWN shows DOWN once the next probe request has run it, not before.

[#knock-health-report]
=== Boot facts

The summary line counts the checks of each probe: `3 checks: 1 liveness, 2 readiness, 0 startup`. Then:

* a `Health` link to `GET /health`, at the path the `rest` section declared for Knock's resource: `/api/health` when the application mounts its resources under `/api`, `/health` by default. The console shows it as a button that opens the endpoint, which runs every check;
* in the detailed report, a list per probe that has checks, `liveness`, `readiness` and `startup`: each check by the name the panel shows it under, its simple class name, without the `_ClientProxy` suffix of a scoped bean's proxy: `AppLivenessCheck`.

[#knock-health-live]
=== The `health` panel in the dev console

One card per probe that has at least one check, `liveness`, then `readiness` and `startup`, sampled about once a second. A check with two probe qualifiers is in both cards: Knock runs it, and records its answer, for each.

[cols="1,1,3"]
|===
| Key | Kind | What it is

| `status`
| text
| `UP` when every check of the probe that answered last answered UP, `DOWN` when one did; absent, `never called`, until a probe request runs one.

| `up`, `down`
| gauge
| How many checks of the probe last answered UP and DOWN, out of its checks. The *Checks UP / DOWN* chart plots them over time. Written once a check has answered.

| `<key>` of a check
| gauge
| 1 when the check last answered UP, 0 when DOWN; absent, `never called`, until a probe request runs it.

| `<key>.at` of a check
| text
| When it last answered, in the server's time zone: `2026-09-23 17:22:35`.

| `checks`
| table
| Every check of the probe: the name it is shown under, the name its response carries, its last status, when it answered, and its data, `pool=8, ok=true`.

| `omitted`

The key of a check is derived from its name, always the same for the same checks: its words hyphenated and lowercased, `AppLivenessCheck` is `app-liveness-check`; every character other than a letter, a digit, a dot or a hyphen replaced with a hyphen, and `c-` in front when it does not start with a letter; cut to 37 characters, to leave room for `.at`; and when two checks end up with the same key, the second gets `-2`, the third `-3`.

What is never shown:

* **A check called by the console.** Sampling reads Knock's last results, in memory: a check that no probe request has run is `never called`, and a check that changed since the last request still shows its last answer.

A URL loses its user info (`//user:password@`, Oracle's `user/password@`) and every parameter or setting whose key holds `password`, `passwd`, `pwd`, `secret`, `token` or `credential`: `jdbc:postgresql://audit:s3cret@db.example:5432/audit?sslpassword=k3y&ssl=true` shows as `jdbc:postgresql://db.example:5432/audit?ssl=true`. The user info runs to the last `@` before the first `?` or `;`, whatever the password holds, a `/`, a `//`, a `+`, an `=` or an `@`: `jdbc:oracle:thin:scott/Xy7+//Qp4==@db:1521:orcl` shows as `jdbc:oracle:thin:@db:1521:orcl`. Failing closed there would also hide ordinary URLs such as `;password=P@ss`, so it is left as it is and documented. The error of `xa=true` for a URL whose `XADataSource` cannot be guessed quotes the URL the same way.

One group per pool, read from the pool's own counters, without a lock and without I/O:

[cols="1,1,3"]
|===
| Key | Kind | Value

| `active`, `idle`
| gauge, max `maxSize`
| The connections lent, and those ready to lend.

| `waiting`
| gauge
| The borrowers waiting for a connection, an estimate.

| `borrows`, `timeouts`
| counter
| The borrows so far, and those that gave up after `acquireTimeout`.

[#mansart-pool-sql]
=== Tables and a SQL editor

Under `mvn vidocq:dev`, each pool also has a tab of the *Mansart pools* panel, named after it — `@Default` first, then the named pools in name order — whose list offers five actions. They answer in the dev console's xref:dev-console.adoc#rows-table[table of rows].

* *Tables* lists the tables and views of the pool's catalog and its schemas, the system ones (`information_schema`, `pg_catalog`…) left out, in schema then name order: schema, name, kind (`TABLE`, `BASE TABLE`, `VIEW`…) and number of columns, with a *Describe* and a *Preview* button that fill those forms with the table. The line says `12 tables, 2 views`.
* *Describe* takes one of the tables listed at boot: each column's name, SQL type with its size (`varchar(200)`, `numeric(10,2)`), whether it is nullable, its default, its place in the primary key, and the `table.column` a foreign key refers to; the line names its indexes, `9 columns · indexes: tasks_pkey (id), tasks_status_due_idx (status, due_date)`.
* *Preview* shows the first rows of one, 100 unless you say from 1 to 1000: `SELECT * FROM "public"."tasks"`, the table quoted as the database quotes a name, read in a transaction rolled back.
* *Query* runs a statement that only reads — its first word, comments skipped, is `SELECT`, `WITH`, `VALUES`, `SHOW`, `EXPLAIN` or `TABLE`, anything else refused before it runs: `Query only reads: use Execute` — on a read-only connection, in a transaction always rolled back. It shows 100 rows at most; the line says `3 rows in 12 ms`, or `first 100 rows in 40 ms` when there are more, or when the body had to leave rows out to stay within 256 KiB: the line then counts the rows the table shows (`first 25 rows`), never the rows read.
* *Execute* runs any one statement, asked first (`Runs this SQL on @Default. A DDL statement (CREATE, ALTER, DROP, TRUNCATE…) may be committed by the database itself whatever is chosen.`), in a transaction that its *Transaction* list says to roll back, the default, or to commit; it is always rolled back when the statement fails. It answers the rows the statement returns, an `UPDATE … RETURNING` included, or how many it changed: `3 rows · rolled back`. PostgreSQL rolls a `CREATE TABLE` back; most databases commit a DDL statement whatever is asked.

The form has two fields: `sql`, the statement, in the dev console's query editor with the pool's language (xref:dev-console.adoc#query-sql[SQL]), and `params`, its named parameters as a JSON object, whose schema follows the statement. A `:name` outside a string, a quoted name and a comment is bound with the member `name` of `params`, as `setObject`: a string, a number (an integer as a `long`), a boolean or `null`, and a list as a SQL array where the driver makes one (`WHERE id = ANY(:ids)`); a cast such as `due::text` is no parameter. On PostgreSQL a string is bound untyped, so that the database types it from where it is: `{"day": "2026-10-01"}` is a date in `due_date < :day`, and a time with its offset, a UUID or an enum constant work the same way; a parameter PostgreSQL cannot type, such as `:p` in `:p IS NULL`, makes the statement run again with its strings and its nulls bound as text. A `$$…$$` or `E'…'` string is read as a string, as `'…'` is. A parameter with no member is refused before anything runs, `missing parameter id`, and so is a text of two statements, `one statement at a time`; a last `;` is fine.

[source,text]
----
SELECT t.title, p.name FROM tasks t JOIN projects p ON p.id = t.project_id WHERE t.status = :status
                                                                            params: {"status": "OPEN"}
UPDATE tasks SET priority = 'HIGH' WHERE id = :id RETURNING id, priority      params: {"id": 3}
----

*Values.* A long text and binary are read through their stream, up to what is shown (10 000 characters, 64 bytes) and no further, where the driver streams them; a number is shown as a number, but a `numeric` and an integer past 2^53 as their text, so that nothing is rounded; a date, a time or a timestamp as ISO text, with its offset when it has a zone (`2026-10-01T12:00+02:00`); binary as `0x` and the hex of its first 64 bytes, `…` after when there are more; an array as the JSON of its elements, an array of arrays as nested JSON; a text past 10 000 characters cut with `…`; anything else, a `json`, an `interval`, as the driver writes it.

*Failures.* A statement runs at most 30 seconds, then is cancelled: `the statement ran past 30 s and was cancelled`. A failing statement shows the database's message, on one line, with the pool's URL, its password, its user and the URL's host and port or the path of a file database masked (the user after the word `user`, and wherever it is quoted, `role "app" does not exist`); *Exchange* holds the statement, its parameters, the transaction, the `SQLState` and the vendor code. A pool with no connection to lend answers once its `acquireTimeout` has passed. Every call takes a connection from the pool and gives it back as it was, its auto-commit, read-only flag, schema, catalog and transaction isolation restored (a `SET SCHEMA` or a `SET search_path` through *Execute* does not reach the application). Any other session state a statement sets, such as PostgreSQL's `SET ROLE`, is left to the database's own rollback, which does not undo it once committed.

*A database that does not answer.* The console runs one action at a time per panel, and every pool shares the one `mansart-pool` panel: a call that waits on a database that stopped answering keeps the actions of every pool refused (`409`) until it ends, and a slow *Query* holds the others for up to its 30 seconds. `setQueryTimeout` cannot cancel through a dead socket, and *Tables* and *Describe* read the database's metadata with no timeout of their own: a socket timeout (`socketTimeout` on the PostgreSQL URL, `NETWORK_TIMEOUT` on H2's) is the pool configuration's job, and ends the wait. The boot's own read of foreign keys is the exception: it is bounded to 10 seconds.

*The `sql` language.* What the editor knows of the pool is read once per boot from `DatabaseMetaData` and offered as the language `sql-<pool>` — `sql-default` for `@Default`, a named pool's name in lower case: SQL-92's keywords and the product's (`getSQLKeywords()`), the common functions, the database's identifier quote and how it stores a name written without quotes; each table and view, bare in the current schema and `schema.name` in another, with its columns, their JSON type and `<SQL type> · column`, and a column of a single-column foreign key leading to the table it refers to. On PostgreSQL its `reserved` words, the `R` and `T` words of `pg_get_keywords()`, are the only ones a name is quoted for, and the keywords the editor colours are those and the words of a query's structure: `position`, `comments`, `text`, `date` or `owner` are plain names, as `getSQLKeywords()` alone would make them keywords. The foreign keys are read once per schema, `getImportedKeys(catalog, schema, null)`, where the driver accepts it, one call per table otherwise, on a read-only connection and within 10 seconds, a WARNING saying so when some were left. Past 1 MiB it is written without the details, then without the types, then with the dialect alone, no table at all; past it still, the pool has no language, which a WARNING says. A pool whose tables cannot be read at boot gets that dialect alone too, with `"` as its identifier quote, so that the editor reads SQL as SQL and never falls back to JDQL's words; it has no *Describe* and no *Preview*, which a WARNING says without its URL; *Tables*, *Query* and *Execute* still work. A table created later is listed by *Tables* but known to the editor, *Describe* and *Preview* after the next dev reload only.

[#mansart-pool-001]
=== MANSART-POOL-001 — pre-fill opened nothing

A pool whose `minIdle` asks for connections at boot opened none of them. The pool gives up its pre-fill at the first failure, without a word, and opens connections on demand only, so the first requests pay for them, and fail if the cause is still there:

[source,text]
----
[MANSART-POOL-001] Pool 'ghost' opened none of the 1 connection its minIdle asks for at boot: the pool gave up at the first failure and opens connections on demand only Check vidocq.pool.ghost.url, the credentials and the JDBC driver on the module path
----

Check the URL, the credentials and the JDBC driver of that pool.

[#mansart-pool-002]
=== MANSART-POOL-002 — named pool without its bean

A named pool is open, but no `@Named("<name>") DataSource` bean serves it: the bean is generated at compile time by `vidocq-runtime-mansart-pool-datasources-codegen`, which the application's annotation processor paths lack, or which never saw the name. The processor takes a name from a `vidocq.pool.<name>.url` of the `vidocq.properties` it compiles with, or from `@VidocqDataSources("<name>")`; a name set only in an environment variable or a system property is invisible to it. An injection or a repository routed to that pool fails on its first use:

[source,text]
----
[MANSART-POOL-002] Named pool 'ghost' is open, but no @Named("ghost") DataSource bean serves it: an injection or a repository routed to it fails on first use Add vidocq-runtime-mansart-pool-datasources-codegen to the annotationProcessorPaths of the application, and declare 'ghost' where the build sees it: vidocq.pool.ghost.url in vidocq.properties, or @VidocqDataSources("ghost")
----

When the container cannot say which beans it has, no pool is flagged: the report never guesses.

| The name of one of its constants.

| `LocalDate`; `LocalDateTime`, `Instant`, `OffsetDateTime`, `ZonedDateTime`; `LocalTime`
| ISO text: `2026-09-28`; `2026-09-28T10:15:30` for a `LocalDateTime`, which has no zone, and `2026-09-28T10:15:30Z` or `2026-09-28T10:15:30+02:00` for the three others; `10:15`.

| `UUID`
| Its text.

| An entity of a repository
| An object, one property per column. Its schemasays `required` for a column that cannot be null and whose field is not a primitive, `readOnly` for the generated id and the version, and names each column in `description` (`id of Gizmo, column gizmo_id` for a reference); the console does not enforce it: an absent property keeps what the entity's no-arg constructor sets, so that an absent generated `id` is generated. A reference to another entity takes that entity's id. The entity is built through Mansart's own model, as Mansart builds it from a row.
|===

A boxed type takes `null`, a primitive does not. A value that does not convert fails the call before anything runs, with the parameter and why: `dueDate: not an ISO date`. A method with any other parameter type, such as `PageRequest`, `Sort`, `Limit` or a `List`, is listed under *Monitoring* in `not-runnable`, with the reason, and is not offered.

*Writes.* `save`, `saveAll`, a method whose name starts with `insert`, `update` or `delete`, one annotated `@Insert`, `@Update`, `@Delete` or `@Save`, and a `@Query` that starts with `UPDATE` or `DELETE` are writes. The page asks before running one (`Runs TaskRepository.save against the database.`), and its *Transaction* list offers `rollback`, the default, then `commit`. The console runs the call in a transaction of the application's `jakarta.transaction.TransactionManager`, then rolls it back or commits it; an exception from the method always rolls it back. A rollback undoes only what was done on a connection enlisted in that transaction, which `vidocq-runtime-mansart-transactions-extension` sets up. An application without a `TransactionManager` bean gets `commit` only, and the call then runs as it would outside a transaction. Reads run as they are.

*Results.* The answer is JSON, shown by the page's JSON viewer: an entity as an object, one property per column (a referenced entity as its id, a joined attribute left out), a `List`, `Collection`, `Stream` or array as an array of at most 100 elements, an `Optional` as its value or `null`. The line under the form says what came back and, for a write, what became of the transaction: `3 rows in 12 ms`, `first 100 rows in 40 ms`, `1 row · rolled back`, `42 · committed`, `done`. *Exchange* holds the method, each argument with its type and value, and the transaction asked. A method that throws shows the class of its exception and its message, cut after 500 characters, with a `user:password@` in it masked.

*History.* Each repository tab lists its last 20 calls of the boot, newest first, each with *Replay*, which fills the form again; nothing is sent until you run it. A dev reload starts a new history, and builds the tabs again from the new boot.

*Limits.* The console keeps 128 actions per panel: past them, *Monitoring* says `and N more methods`. A call longer than the console's 60 seconds keeps running, and its outcome shows on a later poll. The repository's package must be open to Vidocq — a Vidocq application is an `open module` by convention, or `opens` the package; otherwise its methods are listed as `package <p> not open to Vidocq`.

[#mansart-data-jdql]
== A JDQL console for Mansart Data

Under `mvn vidocq:dev`, the *Mansart Data* tab of the xref:dev-console.adoc[dev console] ends with a *JDQL* tab, which runs a JDQL statement you type against the application's database: a query to look at data, an `UPDATE` or a `DELETE` to try a change, then roll it back or keep it. Its list offers two actions.

* *Query* runs a `FROM …`, a projection `SELECT a, b FROM …`, a `SELECT COUNT(this) FROM …` or an aggregate such as `SELECT MAX(price) FROM …`, without asking first. An `UPDATE` or a `DELETE` is refused there: `an UPDATE or DELETE: use Update / Delete`; and when the application has a transaction manager, a query runs in a transaction that is always rolled back, so that nothing it could hold is kept.
* *Update / Delete* runs an `UPDATE … SET …` or a `DELETE FROM …`, and nothing else (`not an UPDATE or DELETE: use Query`). The page asks first (`Runs this JDQL statement against the database.`), and its *Transaction* list offers `rollback`, the default, then `commit`, as a repository method's write does (<<mansart-data-run-method>>): the statement runs in a transaction of the application's `TransactionManager`, rolled back unless `commit` is asked, and always rolled back when it fails. Without a `TransactionManager`, `commit` only.

The form has two fields of several lines: `query`, the statement, and `params`, its named parameters as a JSON object. The statement is typed in the dev console's query editor, which colours it, completes the entities after `FROM` and their attributes elsewhere, and underlines an unknown entity or attribute before anything runs (xref:dev-console.adoc#query-editor[Query editor]); `params` in a JSON editor whose schema follows the statement: after `WHERE status = :status`, it offers `status` with the values of its enum, and flags it while it is missing (xref:dev-console.adoc#query-parameters[Its parameters]).

[source,text]
----
FROM Task WHERE status = :status ORDER BY dueDate           params: {"status": "OPEN"}
SELECT title, priority FROM Task WHERE project = :project   params: {"project": "vidocq"}
SELECT COUNT(this) FROM Task WHERE dueDate < :day           params: {"day": "2026-10-01"}
UPDATE Task SET priority = :priority WHERE project = :p     params: {"priority": "HIGH", "p": "vidocq"}
DELETE FROM TaskEvent WHERE type = 'REOPENED'
----

*The entity.* A statement names its entity after `FROM`, `UPDATE` or `DELETE FROM`, by its simple name, or by its full class name when two entities share a simple name, as the catalogue then shows them. A name the catalogue does not know is refused, with the names it knows: `unknown entity Nope; entities: Task, TaskEvent`.

*The `jdql` language*. What the query editor knows comes from the panel, built once per boot from the catalogue and Mansart's models (xref:dev-console.adoc#query-language[A query language for a panel]): the words of Mansart's JDQL, then one entity per entity of the catalogue whose model could be read, under its simple name, with its table, and every attribute of its model but the joined ones, with the JSON type of its Java type and a detail such as `Long · id, generated`, `String · column title` or `→ Project · column project_id`; a reference leads to its entity, so that `project.` completes a project's attributes. An entity whose simple name another shares, which the tab refuses as ambiguous, is left out. *Export CSV*'s statement is typed in the same editor.

*Parameters.* A named parameter `:name` takes the member `name` of `params`; a parameter with no value, or a member no parameter uses, is refused (`:status: no value given`), and so is a positional `?1`. A value compared to an attribute — a parameter, a literal such as `'OPEN'` or `'2026-09-29'`, a value of `SET` — is converted to the attribute's Java type: an enum by the name of a constant, a date or a time as ISO text, a number exactly (`2.5` for an `int` is refused), a `Boolean` from `true` or `false`, a `UUID` from its text. A JSON array feeds an `IN :names`. A value that does not convert fails the statement before it runs: `:status: not a TaskStatus`.

*Results.* The entities as rows of a table, one column per attribute as a repository method returns them (<<mansart-data-run-method>>), each typed from its attribute (`integer`, `string`, `date`…); a projection's columns, a column of entities typed `object` and each written as its JSON; at most 100 rows, fewer when the body would pass 256 KiB, the line saying `3 rows in 12 ms` or `first 100 rows in 40 ms` (`first 25 rows` when the body was cut; xref:dev-console.adoc#rows-table[A table of rows], with *JSON* and *Copy as CSV*). A count is its number, `42`; an aggregate its value, `null` when there is no row; a write the rows it changed, `4 rows · rolled back`. *Exchange* holds the entity, the statement, its parameters and the transaction asked. A statement that does not parse, or fails, shows the class of the exception and its message, cut after 500 characters and with a `user:password@` masked.

*History.* The *JDQL* tab lists its last 20 statements, *Query* or *Update / Delete*, newest first, each with *Replay*, which fills the form again without sending it.

*Limits.* JDQL has no `INSERT`: insert with a repository's `save`, or an `@Insert` method (<<mansart-data-run-method>>). A statement runs on the default data store, the `RepositoryRuntime` bean of the `@Default` datasource: a repository routed elsewhere with `@Repository(dataStore = …)` is not reached. Paths such as `author.name` go as far as Mansart's JDQL does. The whole result is read before the first 100 rows are shown: narrow a large table with a `WHERE`. The console runs Mansart's own `JdqlExecutor.run(jdql, parameters, model, runtime)`, which a tool of yours may call too.

[#mansart-data-csv]
== CSV export and import for Mansart Data

The *JDQL* tab of the *Mansart Data* panel (<<mansart-data-jdql>>) has two more actions, which move rows between the application's database and a CSV file in your browser: *Export CSV* downloads the result of a query, *Import CSV* saves the rows of a file you paste or pick. Nothing is read from, or written to, the project's directory.

*Export CSV* runs a JDQL query as *Query* does and answers its whole result as CSV, shown as text with a *Download* button, which saves it as `jdql.export-20260929-143012.csv`. `FROM Task` exports every attribute of every task; `SELECT title, priority FROM Task WHERE project = :p` some columns of some. An `UPDATE` or a `DELETE` is refused (`an UPDATE or DELETE: export a query`), and the query runs in a transaction that is always rolled back. The header is the entity's attributes in model order, a joined attribute left out, or the columns of a projection; a count is one column `count`, an aggregate one column `value`. The line says `42 rows · 3.1 KiB in 12 ms`. Every row is exported, but the file is at most 256 KiB in UTF-8: a larger one is refused, `larger than 256 KiB: narrow the query`, never cut. No more rows are read from the database than could fit, a SQL `LIMIT`, so a large table is never loaded whole to be refused; *Query* likewise reads one row more than the 100 it shows.

*Import CSV* takes an entity, picked in the list of the catalogue's, and the CSV text: paste it, or *Choose file* to load a file of at most 60 KiB, read as UTF-8 or, when it is not, as Windows-1252 (the line under the input says so), its line ends kept while you leave it unedited. The page asks first (`Saves these CSV rows against the database.`). Its *Transaction* list offers `rollback`, the default, then `commit`: with `rollback` an import is a dry run, every row saved then the transaction rolled back, so that what goes through `rollback` goes through `commit`.

. The file is read completely before anything is saved. Its first line is the header: each name an attribute of the entity, once. A joined attribute, or a name the entity does not have, is refused with the attributes it has (`header: unknown attribute colour; attributes: id, title, priority, dueDate`), and so is an attribute of a type the console does not convert (`header: attachment cannot be imported; …`). Then at least one row, at most 5000 (blank lines at the end of the file do not count), each with as many fields as the header (`line 9: 3 fields, the header has 4`).
. Each row becomes an entity: its no-arg constructor, then each column set, its text converted by the attribute's type as a repository method's argument is (<<mansart-data-run-method>>) — an enum by its constant's name, a date or a time as ISO text, a number exactly, `true` or `false`, a `UUID` as its text, a reference by the referenced entity's id. An attribute without a column keeps the constructor's value; an empty field for a primitive is refused. The first row that does not convert stops the import, nothing saved: `line 7, priority: no constant URGENT in Priority`, the line counted in the text, the header being line 1.
. Every entity is then saved with Mansart's `RepositoryRuntime.save`, in order, in one transaction. A row whose id is empty is inserted, its id generated; a row with an id updates that row, or inserts one with that id. An id of a primitive type, such as `long`, is never generated: the header must then name it (`header: id is a long, which is never generated: give each row its id`). Re-importing an edited export therefore updates the rows it holds; empty its ids to add copies. A save that fails rolls everything back: `line 12: io.vidocq.mansart.data.core.MansartDataException: …`, the message cut and a `user:password@` masked. Without a `TransactionManager`, `commit` only, each row committed as it is saved: a failing row leaves the rows before it, and the line says so (`· 11 rows before it stay committed`).

The result says `42 rows saved · rolled back` or `· committed`; *Exchange* holds the entity, the number of rows, the separator and the transaction, never the file.

*The format* is RFC 4180, written and read by the console itself:

* fields separated by `,`, or by `;` as a spreadsheet of a decimal-comma locale expects: the *separator* of both actions; records ended by `\r\n` when written, by `\r\n` or `\n` when read, the last one with or without; a UTF-8 byte order mark at the start ignored;
* a field holding the separator, a `"`, a line end, or nothing at all is quoted, a `"` doubled;
* `null` is an empty field, `a,,b`, and the empty text `""`, `a,"",b`: an export and an import keep them apart;
* a number as Java writes it, `2.50` whatever the separator (a decimal comma is refused: `line 2, price: not a number`), `true` or `false`, an enum by its name, a date or a time in ISO, a `UUID` as its text, a reference as the referenced entity's id: the text an import reads back. An attribute of another type is exported as its `toString()`, and refused at import.

*History.* Both actions join the *JDQL* tab's history, *Export CSV* and *Import CSV*; an export's *Replay* fills its form again, an import's is empty as soon as its call passes 4 KiB.

*Limits.* A file picked with *Choose file* is at most 60 KiB, and the whole request at most the console's 64 KiB, which a CSV fills a little more than its size once sent as JSON: split a larger file. At most 5000 rows per import, 256 KiB per export: export a large table in slices, `FROM Task WHERE id <= 2000 ORDER BY id`. The default data store only, and no joined attribute, as in the JDQL console.

[#mansart-transactions-jdbc-bridge]
== Mansart Data writes join the transaction

`vidocq-runtime-mansart-transactions-extension` now brings `mansart-transactions-jdbc` itself, as a compile dependency and a `requires` of its module descriptor, alongside `mansart-transactions-cdi`. Adding the extension is enough for `@Transactional` to cover Mansart Data writes — no second dependency to remember.

Mansart Data's JDBC-to-JTA bridge (`io.vidocq.mansart.transactions.jdbc.ConnectionXAResource`) only enlists a repository's JDBC connection in the active JTA transaction when that class can be loaded; `mansart-data-cdi` declares it an optional dependency. Before this fix, an application that depended on this extension alone did not have it on the module path: every repository call still took its own autocommit connection, so a `@Transactional` method began and rolled back a real JTA transaction, but no connection was ever enlisted in it — a write made before a thrown exception stayed committed, silently, with no anomaly in the startup report (Vidocq/vidocq#97).

[source,xml,subs=attributes+]
----
<dependency>
    <groupId>io.vidocq.runtime.extensions.jakartaee.web</groupId>
    <artifactId>vidocq-runtime-mansart-transactions-extension</artifactId>
    <version>{project-version}</version>
</dependency>
----

[#mansart-transactions-request-end]
== A transaction a request leaves active is rolled back

A servlet, a filter or a REST resource that begins a transaction completes it before the response: Jakarta EE 11 Platform §4.2.2 calls returning to the client with an active transaction an error, which the web container detects and aborts. With `vidocq-runtime-mansart-transactions-extension`, a request that ends with the transaction it began still active has that transaction rolled back, and the log says so:

----
WARNING: A request ended with the transaction it began still active: rolled back (Jakarta EE Platform §4.2.2). Commit or roll back a transaction before the response.
----

The check runs when the CDI request context of the request ends, on the thread that served it: Foy and Cassini end it there. A transaction that was already active when the request context started, as one an `@ActivateRequestContext` method runs in, belongs to the code that began it and is left alone. Before this, the transaction stayed associated with a thread that no longer ran, and kept its connection and the locks it held until the process stopped (BUG-20261118-80).

[#kerckhoffs-security]
== Jakarta Security (Kerckhoffs)

`vidocq-runtime-kerckhoffs-security-extension` puts the application's authentication under Jakarta Security 4.0, on xref:kerckhoffs::index.adoc[Kerckhoffs]. `vidocq extension add kerckhoffs-security` adds it with the Servlet extension it runs on; the Vidocq Maven plugin puts its `-codegen` bundle, which carries Kerckhoffs's build compatible extensions, on the compiler's processor path.

[source,xml,subs=attributes+]
----
<dependency>
    <groupId>io.vidocq.runtime.extensions.jakartaee.web</groupId>
    <artifactId>vidocq-runtime-kerckhoffs-security-extension</artifactId>
    <version>{project-version}</version>
</dependency>
----

The application declares a mechanism and an identity store, and protects its servlets as usual:

[source,java]
----
@BasicAuthenticationMechanismDefinition(realmName = "shop")
@Dependent
public class ShopSecurity {
}

@ApplicationScoped
public class UserStore implements IdentityStore {
    @Override
    public CredentialValidationResult validate(Credential credential) { /* ... */ }
}

@WebServlet("/orders")
@ServletSecurity(@HttpConstraint(rolesAllowed = "admin"))
public class OrdersServlet extends HttpServlet {
    @Inject SecurityContext security;
}
----

How it works: the extension finds the `HttpAuthenticationMechanism` bean of the application and hands it to Foy through the `ServletAuthentication` SPI of the Servlet extension. Foy then asks the mechanism for *every* request, protected or not, before it applies the constraint of the resource, so the mechanism replaces the `login-config` of the container. Without a mechanism, the container keeps its own. Two extensions that both take over the authentication fail the start.

* The identity stores are created at start, so a store that cannot be created stops the start instead of the first login (a store bound to a request or session scope is left to its first use).
* `SecurityContext` and `Principal` answer for the request Foy is serving; outside a request, nobody is the caller.
* Also there: `@RememberMe` (the cookie, the application's `RememberMeIdentityStore`, and its `*Expression` attributes, which the extension evaluates with Peano, brought with it) and an application `HttpAuthenticationMechanismHandler`.
* Also there: Jakarta Authorization for web resources. The access to each request is asked of the `Policy` of the `PolicyFactory` as a `WebResourcePermission`; the default policy answers with the security constraints, and a policy the application registers decides in its place (it may delegate to the default one). `PolicyContext.PRINCIPAL_MAPPER` gives it the caller and the roles of the subject.
* Not there yet: an Expression Language expression that reads a bean in the definitions or in `@LoginToContinue` (a string literal is fine), `@RolesAllowed` through Jakarta Authorization, a CDI decorator on a mechanism (Vauban applies no `@Decorator`).
* Out of scope for now: the part of the Jakarta Security 4.0 TCK that needs JSF, an EJB, an LDAP directory or an OpenID provider. Coverage per official TCK application, on this runtime and on the Kerckhoffs container: the `tck` page of xref:kerckhoffs::tck.adoc[Kerckhoffs]; the runtime's own figures are in `vidocq-runtime/vidocq-runtime-integration-tests/TCK.md`.

[#noether-persistence]
== Jakarta Persistence (Noether)

`vidocq-runtime-noether-persistence-extension` runs the persistence units of the application's `META-INF/persistence.xml` and of its xref:#noether-persistence-keys[`vidocq.persistence.*` keys] on xref:noether::index.adoc[Noether], its Jakarta Persistence 3.2 provider. `vidocq extension add noether-persistence` adds it with the two extensions it runs on, Mansart Pool and Mansart Transactions; the Vidocq Maven plugin puts its `-codegen` bundle, which carries Noether's annotation processor, on the compiler's processor path.

[source,xml,subs=attributes+]
----
<dependency>
    <groupId>io.vidocq.runtime.extensions.jakartaee.web</groupId>
    <artifactId>vidocq-runtime-noether-persistence-extension</artifactId>
    <version>{project-version}</version>
</dependency>
----

[source,xml]
----
<persistence xmlns="https://jakarta.ee/xml/ns/persistence" version="3.2">
    <persistence-unit name="ledger" transaction-type="JTA">
        <class>com.acme.ledger.Entry</class>
    </persistence-unit>
</persistence>
----

[source,java]
----
@ApplicationScoped
public class Ledger {

    @PersistenceContext
    EntityManager entries;

    @Transactional
    public void record(String id) {
        entries.persist(new Entry(id));
    }
}
----

*Injection.* `@PersistenceContext` gives a container-managed entity manager, transaction-scoped or extended, synchronized or not, and `@PersistenceUnit` the unit's `EntityManagerFactory`; a unit name may be left out only when the application has one unit. The container owns the factory: `close()` on it throws `IllegalStateException`, and Vidocq closes it when it stops. Each factory an injection point names is created when Vidocq starts, so a unit that cannot start fails the boot, not the first request.

*Several units.* A `persistence.xml` may declare several units, each on a pool of its own, and every injection point then names its unit. A unit manages the classes it lists in `<class>`, and, unless it sets `<exclude-unlisted-classes>`, every entity, embeddable, mapped superclass and converter of its root: for a `persistence.xml` in the application module, every one of the module. Two units of one module that do not exclude their unlisted classes therefore both manage every entity, and with schema generation both create every table, each in its own database. List the classes of each unit and exclude the others:

[source,xml]
----
<persistence xmlns="https://jakarta.ee/xml/ns/persistence" version="3.2">
    <persistence-unit name="ledger" transaction-type="JTA">
        <class>com.acme.ledger.Entry</class>
        <exclude-unlisted-classes>true</exclude-unlisted-classes>
    </persistence-unit>
    <persistence-unit name="archive" transaction-type="JTA">
        <qualifier>com.acme.ledger.Archived</qualifier>
        <jta-data-source>notes</jta-data-source>
        <class>com.acme.ledger.Note</class>
        <exclude-unlisted-classes>true</exclude-unlisted-classes>
    </persistence-unit>
</persistence>
----

[source,java]
----
@PersistenceContext(unitName = "archive")
EntityManager notes;

@PersistenceUnit(unitName = "ledger")
EntityManagerFactory ledger;
----

[#noether-persistence-per-module]
*One `persistence.xml` per module.* A library module of the application, with its entities, may carry its own `META-INF/persistence.xml`, and the application module its own. Noether reads every one of them, and a unit's root is the module whose file declares it, so a unit without a class list manages the entities of its own module and not those of the others: the units need no `<exclude-unlisted-classes>` to stay apart. The library is built for Noether as any module of entities is, with Noether's processor and the `provides` of its accessor (xref:noether::getting-started.adoc[Noether's Getting started]). A unit name is unique in the application: two units of one name, in one file or in two, fail the start with a `PersistenceException` that names every file declaring it, and the build warns that it leaves the build compatible extensions to the start.

[#noether-persistence-keys]
*Units declared with keys*. The `vidocq.persistence.<unit>.*` keys declare a unit without a `persistence.xml`, or point a unit a `persistence.xml` declares at another pool, per deployment. A unit name with a dot is quoted: `vidocq.persistence."com.acme.ledger".datasource`.

[cols="2,4,2",options="header"]
|===
| Key | Meaning | Default
| `vidocq.persistence.<unit>.module` | The Java module whose entities the unit manages: its root | The application module
| `vidocq.persistence.<unit>.packages` | Keeps the unit to these packages of its module, and their sub-packages, comma-separated | Every package
| `vidocq.persistence.<unit>.classes` | The classes the unit manages, alone, comma-separated, as `<class>` with `<exclude-unlisted-classes>` | None
| `vidocq.persistence.<unit>.transaction-type` | `JTA` or `RESOURCE_LOCAL` | `JTA`
| `vidocq.persistence.<unit>.qualifier` | The qualifier annotations of the unit's beans, fully qualified, comma-separated | None: `@Default`
| `vidocq.persistence.<unit>.scope` | The scope annotation of the unit's `EntityManager` bean, fully qualified | Transaction scoped
| `vidocq.persistence.<unit>.datasource` | The Mansart pool of the unit: the `jta-data-source` of a JTA unit, the `non-jta-data-source` of a RESOURCE_LOCAL one | The default pool
| `vidocq.persistence.<unit>.non-jta-datasource` | The pool a JTA unit allocates TABLE identifiers in | The unit's pool
| `vidocq.persistence.<unit>.properties.<name>` | A property of the unit, such as `jakarta.persistence.schema-generation.database.action` | None
|===

[source,properties]
----
vidocq.persistence.journal.classes=com.acme.journal.Memo
vidocq.persistence.journal.properties.jakarta.persistence.schema-generation.database.action=create
----

* *Declaring or overriding.* `module`, `packages`, `classes`, `transaction-type`, `qualifier` and `scope` declare the unit, so a unit of that name in a `persistence.xml` is a duplicate and fails the start. `datasource`, `non-jta-datasource` and `properties.<name>` alone override the unit a `persistence.xml` declares, its properties winning over the file's, and declare it otherwise, on the entities of the application module, as a JTA unit.
* *The default unit.* Without any `vidocq.persistence.*` key, the application has a unit named `default`, JTA on the default pool, of the entities of the application module: it exists only when no `persistence.xml` declares a unit and the module has an entity, so a `@PersistenceContext` without a unit name reaches it. An application that is not a named Java module has none.
* *Build and start.* `vidocq:generate` freezes the beans of each unit at build (xref:{page-component-version}@vauban::concepts.adoc#writing-a-frozen-extension[a frozen extension]), so the build reads the keys of the application's `vidocq.properties` and `application.properties`, and the start reads them from the whole configuration, `-D` and the environment included. The data sources and the properties of a unit may differ at start. A unit declared or gone, or a transaction type, a qualifier or a scope that differs from the build's, would need other beans: the start fails with a `DeploymentException` that names each difference and asks for a rebuild.
* *Environment variables.* The units are found by the names of their keys, which a `vidocq.properties` file or a `-D` gives: an environment variable, such as `VIDOCQ_PERSISTENCE_LEDGER_DATASOURCE`, changes the value of a key one of them names, and does not declare one alone.
* *Errors.* A key that sets nothing a unit has, a module the application does not have, or a transaction type other than `JTA` and `RESOURCE_LOCAL` fails the start, naming the key.

See xref:{page-component-version}@noether::usage.adoc#unit-sources[Units declared by a runtime] in Noether's documentation.

[#noether-persistence-inject]
*Injection with `@Inject`.* Every unit is also a set of CDI beans (Jakarta EE 11 Platform §13.12):

* an `EntityManagerFactory`, application scoped and named after the unit;
* for a JTA unit, an `EntityManager`, transaction scoped, or in the scope the unit's `<scope>` element names;
* the factory's `CriteriaBuilder`, `PersistenceUnitUtil`, `Cache`, `SchemaManager` and `Metamodel`, dependent.

They carry the qualifiers the unit's `<qualifier>` elements name (Jakarta Persistence 3.2 §8.2.1.5), or `@Default` when it names none. With the descriptor above, `@Inject EntityManager` reaches `ledger`, and `@Inject @Archived EntityManager` reaches `archive`, where `Archived` is a `@Qualifier` annotation of the application:

[source,java]
----
@Inject
@Archived
EntityManager notes;

@Inject
@Archived
EntityManagerFactory archive;
----

* *Same unit, same factory.* The beans run on the factory that `@PersistenceContext` and `@PersistenceUnit` inject, so an `@Inject` entity manager and a `@PersistenceContext` of the same unit share the persistence context of a transaction.
* *Proxies generated at build*. The `EntityManager` and `EntityManagerFactory` beans are of normal scopes, so they are injected through client proxies. The extension's jar holds them, generated when it was built (xref:{page-component-version}@vauban::concepts.adoc#synthetic-interface-proxies[Client proxies of synthetic beans]): each call goes straight to the unit's entity manager or factory. They used to be `java.lang.reflect.Proxy` instances built at start, every call going through reflection, and the start printed the _VAUBAN — RUNTIME CODE GENERATION FALLBACK_ warning for them.
* *No `EntityManager` bean for a RESOURCE_LOCAL unit.* A container-managed entity manager is a JTA one, so Vidocq gives that unit no `EntityManager` bean and logs its `<scope>` as ignored.
* *Units without a qualifier.* Each of them gives `@Default` beans, so with two of them an `@Inject EntityManager` is ambiguous and fails the start. Give each unit a `<qualifier>`, or inject with `@PersistenceContext(unitName = ...)`.
* *A pool and a unit of the same name.* The `EntityManagerFactory` bean takes the unit's name, and the `DataSource` bean of a named pool takes the pool's name, so CDI refuses the two and the start fails. Name them differently: the `archive` unit above runs on the pool `notes`.
* *Errors.* A `<qualifier>` or `<scope>` class the application cannot load, or one that is not a qualifier or a scope, fails the start, naming the unit.

See xref:{page-component-version}@noether::usage.adoc#inject-units[Injecting a persistence unit with @Inject] in Noether's documentation.

[#noether-persistence-references]
*References declared on a class*. A component written for a Jakarta EE server may declare its persistence contexts and units on its class, with a name, and look them up instead of having them injected (Jakarta EE 11 Platform §5.13, §5.14). With the xref:#naming[naming extension], each name is bound under `java:comp/env`:

[source,java]
----
@WebServlet("/orders")
@PersistenceContext(name = "persistence/orders", unitName = "orders")
public class OrdersServlet extends HttpServlet {
    // (EntityManager) new InitialContext().lookup("java:comp/env/persistence/orders")
}
----

* *A context reference* is one transaction-scoped entity manager that every lookup shares; *a unit reference* is the unit's factory, the one `@PersistenceUnit` injects. A name that starts with `java:` is bound as it is.
* *Errors.* A reference without a name, an `EXTENDED` context declared on a class and a name two classes declare for different beans fail the start, naming the class.
* *Without the naming extension*, nothing binds the names, and a lookup finds no initial context.

See xref:{page-component-version}@noether::usage.adoc#references[References declared on a class] in Noether's documentation.

*Data sources.* A unit takes its connections from a Mansart pool, never from its own JDBC properties when a pool is there.

* *A JTA unit* uses the pool its `jta-data-source` names, `@Named("orders")` for `<jta-data-source>orders</jta-data-source>` (`vidocq.pool.orders.url`), or the default pool (`vidocq.pool.url`) when it names none. Within a transaction, every connection the unit asks for is the one connection Mansart Transactions keeps for that transaction and that pool, enlisted in the transaction and given back to the pool once it completes: the transaction manager commits or rolls it back, and the unit cannot. The unit's non-JTA data source, which the TABLE identifier generator and schema generation use outside the transaction, is the pool its `non-jta-data-source` names, or else the same pool.
* *A RESOURCE_LOCAL unit* uses the pool its `non-jta-data-source` names, or else the default pool, or else, without a pool, the JDBC properties of the unit.
* *A factory the application creates itself*, with `Persistence.createEntityManagerFactory("orders")`, finds the pool its unit names by a JNDI lookup (Vidocq/vidocq#676): the name as written, then `java:comp/env/<name>`, which the <<naming,naming extension>> answers for each pool, through the application's transactions. So the application needs the naming extension. A `DataSource` object the application passes wins, and a unit that names no data source keeps its JDBC properties. Two differences with a factory the container creates: a JTA unit with a `TABLE` identifier generator must name a `non-jta-data-source` that does not enlist (a `vidocq.naming.*` key bound to the pool bean), and a RESOURCE_LOCAL unit used within a JTA transaction gets that transaction's connection, which it cannot commit.

*A unit of another provider*. A unit whose `<provider>` names another provider than Noether is handed to that provider's `createContainerEntityManagerFactory`, with the pool of its `jta-data-source` or `non-jta-data-source` as above (Jakarta Persistence 3.2, §9.6). The application declares the provider as a service: `provides jakarta.persistence.spi.PersistenceProvider with ...;` in its `module-info.java`, or its jar's `META-INF/services/jakarta.persistence.spi.PersistenceProvider`. The startup report and the dev console list Noether's units only. See xref:{page-component-version}@noether::usage.adoc[Noether's usage page], "With CDI".

A name no pool answers fails the start, naming the key to set (`vidocq.pool.<name>.url`). The pools are declared as for Mansart Data: a named pool is a `vidocq.pool.<name>.url`, and its `@Named("<name>") DataSource` bean is generated at compile time from that key of `vidocq.properties` by `vidocq-runtime-mansart-pool-datasources-codegen`, which the application adds to its annotation processor paths, as the xref:#mansart-pool-002[MANSART-POOL-002] anomaly of the startup report reminds when it is missing. See the named datasources of xref:mansart::usage.adoc[Mansart's usage page].

*Mansart Data in the same transaction.* Within one transaction, a Jakarta Data repository and a JTA unit on the same pool work on the same connection: Mansart keeps one connection per transaction and per data source, which the extension hands the unit through Mansart's `JtaDataSource` over the pool bean the repository takes too (xref:{page-component-version}@mansart::modules/mansart-transactions.adoc#jta-datasource[One connection per transaction and data source]). Each sees what the other wrote before the commit, the unit's writes once it has flushed them (`flush()`, or a query that flushes), and the transaction commits or rolls back the writes of both together. A repository and a unit on two different pools work on two connections, one per pool: when neither can prepare (a single-phase `ConnectionXAResource`), the transaction commits them one after the other, and a failure of the second commit leaves the first one committed.

*The application module.* Noether's processor generates, per package of entities, an accessor (`_NoetherJpaAccess`) that Noether calls instead of reflecting: the package needs no `opens`, and `vidocq:check-module-info` does not ask for one. The accessor implements Noether's SPI, so the module needs `requires io.vidocq.noether.jpa.core;`, which `vidocq extension add noether-persistence` writes with the `requires` of the extension. The processor lists the accessor in `META-INF/services`, and the layer `Vidocq.run` creates for the application turns that file into the `provides` of its module; a test that boots Vidocq without that layer declares it in its `module-info.java`: `provides io.vidocq.noether.jpa.core.spi.ManagedAccessProvider with com.acme.ledger._NoetherJpaAccess;`.

[#noether-persistence-report]
*In the startup report*. The extension writes the section `noether-persistence`, *Noether Persistence*, of the xref:modules/vidocq-runtime-core.adoc#startup-report[startup report]. Its summary counts the units the application injects and their entities, `3 persistence units, 3 entities`, or says `no persistence unit is injected`. In a dev boot, or at `vidocq.startup.report=detailed`, a row per unit gives:

* its transaction type and its pool: `JTA on pool notes`, or `on the default pool` when the unit names none;
* its schema action, `jakarta.persistence.schema-generation.database.action`, or `none` when it sets none;
* how many entities, embeddables, named queries and indexes it declares, a unique constraint counting as an index.

The counts come from the unit's description (xref:{page-component-version}@noether::reference.adoc#tools[Describing a unit for tools]), read once at start, without opening a connection.

=== The Persistence panel in the dev console

Above its tabs, a *Persistence unit* dropdown (xref:dev-console-panels.adoc#selector[a panel selector]) chooses the unit every tab works on. The panel is `vidocq-runtime-noether-persistence-extension-dev`: `vidocq:dev` adds it next to the extension, the application declares nothing, and no package contains it (xref:dev-console-panels.adoc#dev-module[A `-dev` module, never packaged]).

[cols="1,1,3"]
|===
| Tab | Reads | What it does

| *Monitoring*
| Memory
| A card per unit, next to its row of the startup report: how many entities, embeddables, named queries and indexes it declares.

| *Model*
| Memory
| *Show the model* draws the unit (xref:dev-console.adoc#graph-view[a graph]). Each entity, embeddable and mapped superclass is a box, which lists its table and the attributes its class declares, with their columns. An arrow goes from a subclass to what it extends. A relation is one line from its owning side, labelled with its attribute, its cardinality and its inverse attribute: `author *..1 / notes`. An embedded value is a dashed line.

| *JPQL*
| The database
| *Query* runs a SELECT and shows at most 100 rows. *Update / Delete* runs an UPDATE or a DELETE, and *Export CSV* gives the rows of a SELECT as CSV, at most 10,000 rows and 256 KiB. | *DDL*
| Memory
| *Create script* and *Drop script* give the statements Noether writes for the unit's schema, in its dialect, to copy or download as a `.sql` file. Nothing runs against the database.

*Transactions.* Every action that reads the database runs in a transaction of the unit:

* a JTA unit's work runs in a transaction of the application's `TransactionManager`, and the entity manager joins it;
* a RESOURCE_LOCAL unit's work runs in the entity manager's own transaction.

A query, an export, a page and a comparison always roll their transaction back. *Update / Delete* rolls it back too, unless its *Transaction* argument is `commit`: try a statement, read how many rows it changed, then run it again to keep it. The summary says what happened: `3 rows deleted · rolled back`. JPQL has no INSERT.

*A statement.* The *Statement* argument is a JSON object, `{"query": "SELECT n FROM Note n WHERE n.day > :since", "params": {"since": "2026-11-01"}}`. A named parameter takes the member of `params` of its name, converted to the type the query gives the parameter:

* a number, to any numeric type;
* ISO text, to a `LocalDate`, `LocalDateTime`, `LocalTime`, `OffsetDateTime` or `Instant`;
* text, to a `UUID` or to the name of an `enum` constant;
* a list, to a collection parameter, `WHERE n.id IN :ids`, element by element.

A value that does not convert fails the call and names the parameter: `parameter since: "yesterday" is not a LocalDate`.

*Rows.* A row of a query is a value per item of the select list, named as the list writes it, or by its `AS` alias. An entity in the results is expanded to the values it holds: its id, its basic attributes and its version, an embedded value as one column per attribute (`address.city`), and a single-valued relation as its target's id (`author.id`). A collection is left out. An entity next to other items is shown as `Note#12`. Every row is read through one more query per 500 ids.

*From a page to a write.* When the entity has a simple id, its rows offer a menu (xref:dev-console.adoc#rows-menu[a menu on the selected rows]). Select rows, right-click them, and choose *Delete these rows* or *Update these rows*. The *JPQL* tab opens with the statement filled for the selected ids, `DELETE FROM Note e WHERE e.id IN (12, 15)`; an update sets the first basic attribute to itself, for you to edit. Review it, then run it. An entity with a composite id has no menu, and its page is sorted by the values of its id.

*Indexes.* Each declared index gets a status:

* `same`: the database has it, with the same columns and the same uniqueness;
* `different`: the database has it with other columns, or another uniqueness;
* `missing in the database`: the database does not have it.

A database index that no declared index matches is `extra in the database`. A declared index is matched first by its name and its columns, then by its columns, then by its name. Names are compared ignoring case, since a database stores an unquoted name in its own case: H2's `IDX_NOTE_TITLE` is the mapping's `idx_note_title`. The indexes a database creates for a primary key or a foreign key are left out. The database's indexes come from the JDBC metadata of the connection (`DatabaseMetaData.getIndexInfo`).

[#schema-migration]
== Schema migration

`vidocq-runtime-migration-extension` migrates each datasource at boot, in `beforeStart`, before the pools open, with the one backend on the path: `vidocq-runtime-flyway-migration-extension` or `vidocq-runtime-liquibase-migration-extension`. It migrates the `@Default` datasource whenever `vidocq.pool.url` is set, and a named datasource only when `vidocq.migration.<name>.locations` is set. A migration that fails stops the boot.

[#schema-migration-backends]
=== What each backend brings

A backend brings its engine into the application, with the engine's own dependencies:

* `vidocq-runtime-flyway-migration-extension`: Flyway 13.9.0 (`flyway-core`, `flyway-database-postgresql` and `flyway-database-cockroachdb`), Apache 2.0. Of Jackson, only `jackson-annotations` comes with it: since Flyway 13.5, `jackson-databind` serves Flyway's TOML and JSON configuration files only, which the extension does not read.
* `vidocq-runtime-liquibase-migration-extension`: Liquibase 4.33.0 and its libraries, Apache 2.0, with commons-lang3 3.20.0 in place of the 3.17.0 Liquibase declares (CVE-2025-48924). The backend stays on Liquibase 4: 4.33.0 is the last release under the Apache 2.0 licence, as Liquibase 5 moved to the Functional Source License (FSL-1.1-ALv2).

[#flyway-prefixes-warning]
NOTE: Under Maven 3.10, the Maven of the wrapper `vidocq create` writes, a build with the Flyway backend prints `[WARNING] Could not transfer metadata /.meta/prefixes.txt from/to flyway-community-db-support (https://maven.pkg.github.com/flyway/flyway-community-db-support): HTTP Status: 401`, and goes on. It is harmless. Maven 3.10 reads the list of prefixes of every repository the resolution meets. `flyway-parent`, up to 13.9.0, declares a GitHub Packages repository that refuses anonymous reads. Nothing is downloaded from it: Maven Central serves every Flyway artifact. Maven 3.9 printed nothing (BUG-20261108-02).

| `vidocq.migration.engine`
| the one backend

| `vidocq.migration.locations`

[#schema-migration-layer]
=== Scripts in the application layer

`vidocq:dev`, `vidocq:run` and the launcher `vidocq:package` writes by default boot the application in a module layer of its own. Its class loader serves a script by name, but lists no directory. The backends used to scan `classpath:db/migration` with a loader, and found nothing there: Flyway logged `No migrations found. Are your locations set up correctly?`, the boot went on with an empty schema, and the first query failed with `Table "…" not found`. Liquibase stopped the boot, the changelog not found.

The backends now list `classpath:` locations from the application's own modules, through `ApplicationLayer` (xref:modules/vidocq-runtime-spi.adoc#application-layer[Listing the application's files]), and read each file by name:

* Flyway: SQL scripts, SQL callbacks and Java migrations such as `V3__Backfill.class`, from a directory (`vidocq:dev`) or a jar (the `app/` of a distribution). A script keeps the name Flyway's own scanner gives it, so a schema history written by a flat launch, or through `filesystem:`, stays valid. Flyway instantiates a Java migration itself, so its package must stay open to it, as the `opens db.migration;` that `vidocq:check-module-info` requires.
* Liquibase: the changelog, every file it includes, and the directories of `includeAll`.

A `@VidocqMain` trampoline launched from the IDE re-layers the application in `Vidocq.run()`, so this launch takes this path too. A launch that leaves the application module in the JVM's boot layer keeps the backend's own scanning: a jlink image, `-Dvidocq.dev.layer=false` or `vidocq.package.layer=false`, with or without a trampoline (xref:modules/vidocq-runtime-maven-plugin.adoc#layer-off[no application layer]), a class-path launch, and the tests. Flyway locations that mix `classpath:` with `filesystem:` are left to Flyway's scanner, which cannot list the `classpath:` ones in the application layer. The migration logs a warning saying so: keep the locations all `classpath:` or all `filesystem:`.

[#schema-migration-liquibase-analytics]
=== Liquibase analytics stay off

Since 4.30, Liquibase sends usage data to Liquibase by default for open-source users (`liquibase.analytics.enabled`, with its settings fetched from `config.liquibase.com`). The extension runs every migration, listing and clean with that option off, unless a value is configured where Liquibase reads its configuration: `-Dliquibase.analytics.enabled=true`, `LIQUIBASE_ANALYTICS_ENABLED`, or a defaults file. A configured value, `true` or `false`, is kept as it is.

| Line | Value

| summary
| The engine, then each datasource: `flyway: default 2 applied, version 2`, or `default not migrated` when nothing was found. With no datasource, `idle: no vidocq.pool[.<name>].url`; turned off, `disabled: vidocq.migration.enabled=false`.

| `<datasource>`

[#vidocq-mig-001]
=== VIDOCQ-MIG-001 — no migration found

A datasource's migration found no migration at its locations, and its schema history records none: the schema was not migrated at all, and the first query on it will fail. It is a warning in every launch mode:

[source,text]
----
[VIDOCQ-MIG-001] datasource default: no migration found in [classpath:db/migration] and none in its schema history; the schema was not migrated Check vidocq.migration.locations and that the scripts are in the application
----

Check the key the hint names, and that the scripts are packaged with the application under that path. In a launch that leaves the application module in the boot layer (<<schema-migration-layer>>), also check that `module-info.java` opens their package (`opens db.migration;`). A schema whose history holds a migration, a repeatable one included, is never flagged, so an up-to-date restart is not an anomaly. `vidocq.migration.failOnMissingLocations=true` turns an empty Flyway location into a boot failure instead.

[#schema-migration-actions]
=== The `migration` panel and its actions

The dev console shows the section as the `migration` panel, with the boot facts above and one card per migrated datasource below:

[cols="1,1,3"]
|===
| Key | Kind | What it is

| `version`
| text
| The version the schema is at after the last run: `2`, `(none)`, or `(liquibase)`, which numbers no version.

| `last-run`
| text
| What ran last and how many migrations it applied: `boot: 2 applied`, `migrate: 1 applied`, `clean-and-migrate: 3 applied`, or `migrate: failed (FlywayValidateException)`, by the exception's class only, when an action failed.

| `clean`
| text
| `allowed`, or `disabled: vidocq.migration.cleanDisabled=false allows it`, naming the key of that datasource.

| `applied`, `pending`
| table
| The migrations the schema history records, the latest 100, and those still to run, the first 100: version, description, type, installed on and state, as Flyway's `info` gives them. Liquibase numbers no version: a changeset's id stands in the version column, its author in the description. Absent, `listed in a dev launch only`, outside a `dev` launch.
|===

The migrations are listed once after the boot's migration, in a `dev` launch only, and again after each action: listing opens a connection, and the page's polls never do.

In a `dev` launch the panel offers two actions (xref:dev-console.adoc#security[the console runs them for its own page only]), each on one migrated datasource, picked from a list:

* *Migrate now*, `migrate`, applies the migrations added since the boot, as the boot does, without a restart: `default: 1 migration applied, schema at version 3`. Its outcome replaces the one the panel shows.
* *Clean and migrate*, `clean-and-migrate`, asks first: _Drop every object in the schema of the chosen datasource, then migrate it again? This cannot be undone._ It then drops every table, view and sequence of the schema, its history included, with Flyway's `clean` or Liquibase's `dropAll`, and migrates it from scratch: `default: schema cleaned, 3 migrations applied, schema at version 3`. It is refused unless the datasource's `cleanDisabled` key is `false`, and then drops nothing: `default: clean refused, nothing dropped; set vidocq.migration.cleanDisabled=false to allow it`. Flyway itself refuses too, since the extension passes it that same setting.

Actions on one datasource run one after the other. An action runs while the application runs: a query on the datasource at the same time may fail, which the developer who clicked accepts. The answer and the log line name the datasource and counts, never its URL or password. A backend written for an older SPI, without `info` or `clean`, shows its tables absent, `flyway cannot list the migrations` for instance, and answers `clean-and-migrate` with `default: flyway cannot clean a schema, nothing dropped`.

[[start-time-code]]
== Declaring start-time code

`vidocq:dev` compares each recompile with the output the application runs, and swaps the application layer when a
change touches code that ran at start: that code ran once, and will not run again until a swap
(xref:usage.adoc#dev-reload-reasons[why a change reloads]). The plugin knows two things on its own: static
initializers, and every application method that start-time code calls. The rest depends on the technology, and each
extension declares it in a file of its main jar, `META-INF/vidocq/dev/start-time.properties`. Only `vidocq:dev` reads
the file, and nothing reads it in a packaged application. A third-party jar can carry one too, and so can the
application, under `src/main/resources`: the plugin reads it again after each recompile.

[cols="1,3",options="header"]
|===
| Key | What it names
| `long-lived-annotations` | Annotations of classes whose instances live from the start: their constructors, field
initializers and initializer methods ran at start. `jakarta.enterprise.context.ApplicationScoped`.
| `long-lived-types` | Supertypes of such classes, found through the application, its jars and the JDK.
`jakarta.servlet.Servlet`.
| `start-annotations` | Annotations of methods that run at start, on any class: `jakarta.annotation.PostConstruct`,
`jakarta.enterprise.inject.Produces`.
| `observer-annotations` | Annotations of an observer's event parameter: `jakarta.enterprise.event.Observes`.
| `start-events` | Events fired at start, as the parameter's type or a qualifier on it:
`jakarta.enterprise.event.Startup`, `jakarta.enterprise.context.Initialized`.
| `start-callbacks` | Methods a container calls at start, as `owner#name(descriptor)`, matched on the classes that
extend or implement the owner: `jakarta.servlet.Servlet#init(Ljakarta/servlet/ServletConfig;)V`.
| `build-files` | Files of the class output that a build tool writes for its own use, as paths relative to the output;
a path ending with `/` names a directory. A change to them alone reloads nothing, as for the build info of
`META-INF/vidocq/build-info/`: `META-INF/VAADIN/config/flow-build-info.json`.
|===

Each value is a comma-separated list; a line ends with `\` to go on. The extensions of this repository declare their
technology:

[cols="1,3",options="header"]
|===
| Jar | Declares
| `vidocq-runtime-core` | CDI: `ApplicationScoped`, `SessionScoped` and `jakarta.inject.Singleton` classes;
`VidocqExtension`; `@PostConstruct` and `@Produces` methods; observers of `Startup` and `@Initialized`.
| `vidocq-runtime-foy-servlet-extension` | Servlet: servlets, filters, context, session and request listeners, container
initializers; `Servlet#init(ServletConfig)`, `GenericServlet#init()`, `Filter#init(FilterConfig)`,
`ServletContextListener#contextInitialized`, `ServletContainerInitializer#onStartup`.
| `vidocq-runtime-cassini-rest-extension` | JAX-RS: `@Provider` classes and `Application` subclasses;
`Application#getClasses`, `getSingletons` and `getProperties`, `Feature#configure`, `DynamicFeature#configure`.
|===

The Vaadin extension, in https://codefloe.com/VidocqCodeUniverse_VCU/vidocq_vcu_extension_vaadin[its own repository],
declares Vaadin's: the Vaadin CDI scopes, `@PreserveOnRefresh` classes, `VaadinServiceInitListener#serviceInit` and the
build file `flow-build-info.json`.

The constructors of other objects, such as a Vaadin view, a `@Dependent` or `@RequestScoped` bean or a plain object,
are not start-time: the next instance runs the new constructor. A declared type that no dependency has is never
matched. An unknown key, or an entry that cannot be read (a callback without `#`, a bad descriptor, a build file
that leaves the output), logs a warning
naming the jar and the entry, `Hot swap: <jar>: ...`, and is skipped: it never fails the build or the session. A
supertype found in no dependency warns once, and the classes that extend it count as long-lived, which is the safe
side.
