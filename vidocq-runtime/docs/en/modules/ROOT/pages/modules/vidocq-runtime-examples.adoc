= vidocq-runtime-examples
:description: Tour of shipped examples.

[.lead]
`vidocq-runtime-examples` groups the demo applications used as living oracles for validation and documentation. Each example is an independent Maven module, packageable via the `vidocq-runtime-maven-plugin`.

== Coordinates

[cols="1,3"]
|===
| Reactor | `vidocq-runtime/vidocq-runtime-examples/` in the monorepo
| Build | From the root of the monorepo: `./mvnw -ntp -pl vidocq-runtime/vidocq-runtime-examples/<example> -am package`
|===

An example builds from the root of the monorepo, with its wrapper: there is no `mvnw` in the examples' folders.
The root build declares `vidocq-runtime-maven-plugin` in `pluginManagement` only, so the `vidocq:` prefix does not
resolve there: install the reactor once (`./mvnw -ntp install -DskipTests`), then name the plugin by its group and
artifact, `io.vidocq.runtime:vidocq-runtime-maven-plugin:<goal>`, as the quick starts below do.

No example has a main class. Each pom declares `vidocq.mainModule` only, and the runtime's own
main boots the module under `vidocq:dev`, `vidocq:run`, the `vidocq:package` launchers and the `vidocq:jlink` /
`vidocq:jpackage` images (see
xref:modules/vidocq-runtime-maven-plugin.adoc#jlink-without-main-class[jlink without a main class]). A main class
is for an application that wants a right-click Run in the IDE or logic after boot: see
xref:usage.adoc[the `@VidocqMain` trampoline].

== Catalogue

[cols="2,3"]
|===
| Example | Description

| `vidocq-runtime-cassini-rest-example`
| Minimal REST application — two Jakarta REST resources and a third from `vidocq-runtime-external-rest-lib`, packageable in jlink/jpackage/docker. Serves as the canonical reference to test the Maven plugin and the extension mechanism on the Chappe + Vauban + Cassini triplet.

| `vidocq-runtime-mansart-h2-example`
| Complete REST + CDI + persistence application via xref:mansart::index.adoc[Mansart] on H2 in-memory. Demonstrates `@Transactional`, `BasicRepository<T, K>`, `@Inject`. The recommended example in xref:getting-started.adoc[Getting started].

| `vidocq-runtime-cervantes-jwt-example`
| REST application secured with MicroProfile JWT via `vidocq-runtime-cervantes-jwt-extension` — token validation and `@RolesAllowed` on Jakarta REST resources.

| `vidocq-runtime-knock-health-example`
| MicroProfile Health via `vidocq-runtime-knock-health-extension` — custom `@Liveness`/`@Readiness` checks exposed on `/api/health` (`/live`, `/ready`, `/started`).

| [[cyrano-rest-client-example]]`vidocq-runtime-cyrano-rest-client-example`
| MicroProfile Rest Client via `vidocq-runtime-cyrano-rest-client-extension` and its `-codegen` bundle — `/api/relay` calls the application's own `/api/greeting` through an `@Inject @RestClient` interface. Its `dist` profile links it with `vidocq:jlink`.

| [[foy-servlet-example]]`vidocq-runtime-foy-servlet-example`
| Jakarta Servlet 6.1 via `vidocq-runtime-foy-servlet-extension` and its `-codegen` bundle — the Vidocq Bistro: servlets, a filter and a session listener, all CDI beans, a `@SessionScoped` basket, a `@RequestScoped` ticket shared by the filter and the servlet of a request, and a kitchen page protected by `@ServletSecurity` with FORM login;JSP pages compiled by Ibarra, with Peano expressions on `@ELAccessible` records.

| `vidocq-runtime-petstore-example`
| The largest example — Cassini + Mansart + Champollion + H2 petstore combining REST, persistence and JSON binding.

| [[noether-persistence-example]]`vidocq-runtime-noether-persistence-example` [.tag-new]#NEW#
| Jakarta Persistence 3.2 via `vidocq-runtime-noether-persistence-extension` — a reading notebook: books, their authors and reading notes, kept by xref:noether::index.adoc[Noether] in one JTA unit on the default Mansart pool (H2 in memory), and served by Cassini. See <<noether-persistence-example-quick-start>>.

| `vidocq-runtime-external-rest-lib`
| External library consumed by the examples — illustrates the case where a Java Modules-named dependency provides its own CDI beans. Useful for validating multi-module APT composition.
|===

== `vidocq-runtime-cassini-rest-example` — quick start

[source,bash]
----
# from the root of the monorepo; the dist profile builds the jlink image
./mvnw -ntp -Pdist -pl vidocq-runtime/vidocq-runtime-examples/vidocq-runtime-cassini-rest-example -am package -DskipTests

# standalone jlink image
./vidocq-runtime/vidocq-runtime-examples/vidocq-runtime-cassini-rest-example/target/dist/bin/todo-app

# UI on http://127.0.0.1:8080/
# API on http://127.0.0.1:8080/api/todos
----

== `vidocq-runtime-mansart-h2-example` — quick start

[source,bash]
----
# from the root of the monorepo, after ./mvnw -ntp install -DskipTests
./mvnw -ntp -pl vidocq-runtime/vidocq-runtime-examples/vidocq-runtime-mansart-h2-example \
    package io.vidocq.runtime:vidocq-runtime-maven-plugin:package

# vidocq:package produced a bin/ + lib/ distribution (also zipped as *-dist.zip)
./vidocq-runtime/vidocq-runtime-examples/vidocq-runtime-mansart-h2-example/target/vidocq-runtime-mansart-h2-example-<version>/bin/vidocq-runtime-mansart-h2-example.sh

curl -X POST http://localhost:8080/api/products \
     -H 'Content-Type: application/json' \
     -d '{"name":"cables","price":12.50}'

curl http://localhost:8080/api/products
----

In dev mode, the plugin's `dev` goal (`io.vidocq.runtime:vidocq-runtime-maven-plugin:dev`), the example also serves the xref:dev-console.adoc[dev console]: it logs `Vidocq dev console: http://127.0.0.1:8888/`, a page with the startup report, the two pools, `@Default` and `audit`, live, and the JVM. Its `DevConsoleSnapshotTest` boots the example in a dev launch, reads that URL from the log, and checks the snapshot the page polls: both pools, the heap, and no pool password anywhere in it.

The example demonstrates the `@TransactionScoped` scope and the xref:mansart::index.adoc[Mansart] transactional bridge. It also served as the reproduction harness for bug VAU-INJ-001 (normal-scope proxy resolution) — see `vidocq-components/vidocq-components-jakartaee/vidocq-components-jakartaee-core/vauban/BUG.md`.

[[foy-servlet-example-quick-start]]
== `vidocq-runtime-foy-servlet-example` — quick start

[source,bash]
----
# from the root of the monorepo, after ./mvnw -ntp install -DskipTests
./mvnw -pl vidocq-runtime/vidocq-runtime-examples/vidocq-runtime-foy-servlet-example \
    io.vidocq.runtime:vidocq-runtime-maven-plugin:dev

# menu and basket on http://localhost:8080/
# kitchen on http://localhost:8080/kitchen, sign in as chef, password chef
# receipt (a JSP) on http://localhost:8080/receipt, about page on http://localhost:8080/about.jsp
----

**JSP pages, with Ibarra and Peano.** `ReceiptServlet` builds a `Receipt` from the basket and forwards to `WEB-INF/views/receipt.jsp`, which a client cannot request; `about.jsp`, `specials.jsp` and `tally.jsp`, under `META-INF/resources`, are requested directly. `specials.jsp` reads the `@Named("specials")` `@RequestScoped` bean by its name; `tally.jsp` reads a `@Named("tally")` `@Dependent` bean, whose `@PreDestroy` counts each time a page lets one go, so the next request shows that it ran. `vidocq:generate` compiles the four pages into the application module with Ibarra (xref:modules/vidocq-runtime-extensions.adoc#ibarra-pages[Jakarta Pages]). The receipt reads `${line.dish}` on `@ELAccessible` records, whose accessors Peano generates at build time; `BistroPagesTest` runs the pages with `-Dpeano.reflection=deny` to prove no expression falls back to reflection. Ibarra has no JSTL: the example writes its own `<bistro:each>` tag and two functions in `WEB-INF/tlds/bistro.tld`. The module requires `io.vidocq.runtime.extensions.jakartaee.web.ibarra`, `io.vidocq.ibarra.api` and `io.vidocq.peano.api`, and the pom adds the Peano codegen bundle.

The other pages are written by servlets. `TicketFilter` and the servlet of one request inject the same `@RequestScoped` `RequestTicket`: its id is both the `X-Request-Id` header and the one in the page footer, and the next request gets a new one. The `@SessionScoped` `Basket` lives in the HTTP session, and `SessionCounter`, a `@WebListener`, counts the open sessions for the kitchen page. `KitchenServlet` carries `@ServletSecurity(@HttpConstraint(rolesAllowed = "chef"))`, and `META-INF/web.xml` holds only a FORM `login-config`: Foy forwards a visitor to `LoginServlet`'s form, which posts to `j_security_check`, and checks the user that `vidocq.servlet.users.chef.*` declares in `vidocq.properties`. The identity lives in the HTTP session, so it ends at *Sign out*, a POST to `LogoutServlet`, or after `vidocq.servlet.session-timeout` without a request; BASIC authentication, Foy's default without a `login-config`, would leave the credentials in the browser until it closes. The `module-info.java` has no exports, no opens and no hand-written `provides`. Under `vidocq:dev`, the dev console plots the active sessions.

[[noether-persistence-example-quick-start]]
== `vidocq-runtime-noether-persistence-example` — quick start [.tag-new]#NEW#

[source,bash]
----
# from the root of the monorepo, after ./mvnw -ntp install -DskipTests
./mvnw -pl vidocq-runtime/vidocq-runtime-examples/vidocq-runtime-noether-persistence-example \
    io.vidocq.runtime:vidocq-runtime-maven-plugin:dev

curl -X POST http://localhost:8080/api/books \
     -H 'Content-Type: application/json' \
     -d '{"title":"Invisible Cities","isbn":"978-0-15-645380-6","author":"Italo Calvino"}'

curl http://localhost:8080/api/books
curl http://localhost:8080/api/authors/Italo%20Calvino/books

# the notebook's page on http://localhost:8080/
----

*The model.* Three entities: a `Book` has an `Author` (`@ManyToOne`) and its `ReadingNote`s (`@OneToMany`, the inverse side of the note's `@ManyToOne`). Named queries find a book by ISBN, an author by name, and an author's books sorted by title. The identifiers are `@GeneratedValue`, which Noether draws from a generator table at `persist()`; an `IDENTITY` key would be known only at the flush.

*The unit.* `META-INF/persistence.xml` declares one JTA unit, `library`, with no data source and no class: it takes the default Mansart pool (`vidocq.pool.url`) and manages every entity of the module. Noether creates the tables at the start (`drop-and-create`), without Flyway, so a restart begins with an empty notebook.

*The work.* `Library` is an `@ApplicationScoped` bean with a `@PersistenceContext EntityManager` and `@Transactional` methods. They return records, built inside the transaction: the API never writes an entity, whose relations point back to each other. Cataloguing a book finds or creates its author, then refuses an ISBN already catalogued by throwing: the transaction rolls back, and the author created for the refused book goes with it (the API answers 409).

*The module.* `module-info.java` requires the three extensions and `io.vidocq.noether.jpa.core`, which the entity accessor of Noether's processor implements: the entity package has no `opens`, and no hand-written `provides` (xref:modules/vidocq-runtime-extensions.adoc#noether-persistence[Jakarta Persistence (Noether)]). The pom adds the Noether and Mansart Transactions `-codegen` bundles to the processor path.

*Tests.* `ReadingNotebookTest` starts the application with `@VidocqTest` and checks the `noether-persistence` section of the startup report (`1 persistence unit, 3 entities`), a book and its notes read back, an author kept once for all their books, and the rollback of a refused book.

*Dev console.* Under `vidocq:dev`, the *Noether Persistence* tab shows the unit: its counts, a graph of the three entities and their relations, JPQL queries on the notebook, its rows and the create and drop scripts (xref:modules/vidocq-runtime-extensions.adoc#noether-persistence-dev[the Persistence panel]).
