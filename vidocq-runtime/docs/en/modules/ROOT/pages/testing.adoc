= Testing an application
:description: @VidocqTest starts the application in its own JVM for a test class and sends it HTTP requests.

[.lead]
`@VidocqTest` starts the application before the first test of a class and stops it after the
last one. A test then sends it HTTP requests, as a client would, through the `VidocqApplication` it receives as a
parameter. `vidocq create` writes such a test for a REST application (Vidocq/vidocq#350).

== Setting it up

Two test dependencies, versioned by `vidocq-runtime-bom` and `junit-bom`, which the pom `vidocq create` writes
imports, as xref:migration.adoc#application-parent[`vidocq-runtime-parent`] does:

[source,xml]
----
<dependency>
    <groupId>io.vidocq.runtime</groupId>
    <artifactId>vidocq-runtime-junit</artifactId>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <scope>test</scope>
</dependency>
----

Nothing goes into `module-info.java`: the tests are patched into the application module, which reads the test
dependencies on the class path.

== A first test

[source,java]
----
import io.vidocq.runtime.junit.VidocqApplication;
import io.vidocq.runtime.junit.VidocqResponse;
import io.vidocq.runtime.junit.VidocqTest;
import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertEquals;

@VidocqTest
class HelloResourceTest {

    @Test
    void saysHello(VidocqApplication application) {
        VidocqResponse response = application.get("/hello");

        assertEquals(200, response.status(), application.log());
        assertEquals("Hello from Vidocq!", response.body());
    }
}
----

`mvn test`, `vidocq test` and the IDE run it alike.

== What it does

* **Once per test class**, the application starts in a JVM of its own, as `vidocq:run` starts it: the runtime's
  own main boots the application module from the module path of the tests (`jdk.module.path`). Under Surefire
  that path holds `target/classes` and the main dependencies; JUnit and the other test dependencies stay on the
  class path, so the application never sees them. A `@Nested` class shares the application of the class that
  carries `@VidocqTest`.
* [[application-layer]]**The application layer is the one of `vidocq:run`** [.tag-new]#NEW#. That path is divided
  as `vidocq:run` divides it: the application module and, under `vidocq.app.layer=all`, the default, its libraries
  go to the application layer through `vidocq.app.path`, and the runtime, the bricks and what they read stay on the
  module path (see xref:usage.adoc#app-layer-dependencies[the application layer]). `vidocq.app.layer` and
  `vidocq.app.layer.keep` are read from `properties` below, and from nowhere else: a value the pom sets for the goals
  does not reach the test (xref:modules/vidocq-runtime-maven-plugin.adoc#app-layer-where[where each launch reads
  them]). A default `all` that cannot be honoured falls back to `classes` with a warning, as in `vidocq:run`. The
  application module used to stay on the module path as well: the JVM loaded it twice, once in the boot layer, and a
  `ServiceLoader` found each `provides` of its
  `module-info.java` twice, so Vaadin refused to start with _multiple eligible instantiator implementations_
  (BUG-20261114-07).
* [[runtime-dependencies]]**Every runtime dependency** reaches the application, on its module path or in its
  application layer, and every module is resolved, as under `vidocq:dev` and in the packaged application: a JDBC driver in
  `runtime` scope, which no module requires, is found without `requires org.postgresql.jdbc`. Surefire leaves such a
  jar on the class path of the tests; `vidocq:test-path`, which `vidocq-runtime-parent` binds to
  `process-test-classes`, names the runtime dependencies in `vidocq.test.runtimePath`, and the parent hands that
  property to Surefire. An application without the parent gets both from the plugin, a build extension
  (xref:modules/vidocq-runtime-maven-plugin.adoc#parentless[Vidocq/vidocq#380]); one that declares the plugin
  without `<extensions>true</extensions>` binds the goal and passes the property itself:
+
[source,xml]
----
<plugin>
    <artifactId>maven-surefire-plugin</artifactId>
    <configuration>
        <systemPropertyVariables>
            <vidocq.test.runtimePath>${vidocq.test.runtimePath}</vidocq.test.runtimePath>
        </systemPropertyVariables>
    </configuration>
</plugin>
----
+
[[from-the-ide]]A test an IDE starts gets no property from Surefire [.tag-new]#NEW#: `vidocq:test-path` also writes the
same path to `target/vidocq-test-runtime-path`, and `@VidocqTest` reads it, next to the test classes, when the property
is not set. The application then starts from the IDE instead of stopping on `Module io.vidocq.runtime.core not found`.
The file is the one the last Maven build wrote, and an IDE that compiles by itself writes none: run
`mvn process-test-classes` (or any later phase) once before the first test, and again after a change of dependencies.
`mvn test-compile` is not enough: `vidocq:test-path` runs in the phase after it. Without the file, `@VidocqTest` stops
before it starts the application and names that build. A property the IDE sets, as the Vidocq IntelliJ plugin does,
wins over the file. Where VS Code's Java extension compiles into a folder of its own, `target-ide/`, a test it starts
does not read the file, which that folder does not hold: the application starts on the module path the extension
builds for the launch (xref:modules/vidocq-runtime-maven-plugin.adoc#ide-output[what an IDE compiles, and where]).
The same is expected of Eclipse. A project the extension compiles into `target/`, an application of several modules
without the `ide-output` profile or one that sets `vidocq.ide.output.skip`, reads the file there, as before.
* [[dev-services]]**The dev services of the run** reach the application. `vidocq test`, `vidocq dev`
  and, under a plain `mvn test`, the `vidocq-runtime-devservices-junit` listener (see
  xref:dev-services.adoc[Dev services]) put the keys their containers publish, `vidocq.pool.url` or
  `mp.jwt.verify.issuer` for instance, in the system properties of the tests. The application gets each of them, as
  `vidocq:dev` gives them to its application, so it migrates and queries the dev database rather than the one
  `vidocq.properties` names. A key set by hand in the test JVM stays there; `properties` below wins over a dev
  service's key. Without that listener on the test class path, a plain `mvn test` starts no dev service, and the
  application uses what `vidocq.properties` points to.
* [[http-port]]**Its HTTP listener** is the `default` Chappe listener, on `127.0.0.1` and port `0`
  (`vidocq.chappe.listener.default.host` and `.port`, which win over `vidocq.properties`) [.tag-new]#NEW#: the system
  picks a free port as the listener binds it, so no other process can take it first. A port that
  `@VidocqTest(properties)` names as `vidocq.chappe.listener.default.port=9090` wins and stays as given.
  `VIDOCQ_HTTP_PORT` is not honoured, nor is its `vidocq.http.port`: the listener key the test passes outranks both
  aliases, so a port exported for `vidocq dev` in the same shell never puts the tested application on the port of the
  dev one.
* **The test starts** once the listener listens: it writes the port it bound to a file that `@VidocqTest` reads,
  whatever the logging configuration of the application, and the URL of the application takes that port. If the
  process exits first, or after 60 seconds, the class fails with the application's output.
* **After the last test** the application is stopped as Ctrl+C would stop it, then forcibly after ten seconds.

== The application in a test

A test method declares any of these parameters:

[cols="1,3"]
|===
| Parameter | What it is

| `VidocqApplication application`
| `get(path)`, `post(path, contentType, body)` and `request(method, path, contentType, body)` send a request and
  return a `VidocqResponse` (`status()`, `body()` read as UTF-8, `header(name)`, `headers()`); `url()` and
  `url(path)` give the URL; `log()` gives what the application wrote so far.
  [[request-headers]]`get(path, headers)` and `request(method, path, headers, contentType, body)` add request
  headers, an `Authorization: Bearer …` for a `@RolesAllowed` endpoint for one. The test cannot send the request
  itself: patched into the application module, it does not read `java.net.http`.

| `@VidocqUrl URI base` or `@VidocqUrl String base`
| `http://127.0.0.1:<port>`.
|===

NOTE: A test patched into the application module reads what that module reads, and an application module does not
read `java.net.http`: an `HttpClient` in a test fails with `IllegalAccessError`. `VidocqApplication` sends the
requests from its own jar, which reads it.

== Settings

[cols="1,3"]
|===
| `@VidocqTest` attribute | Effect

| `properties`
| System properties of the application, `key=value` each, such as
  `@VidocqTest(properties = "vidocq.greeting=hi")`; they win over `vidocq.properties`.

| `module`
| The application module. By default the module of the test class, which Surefire and the IDEs patch into the
  application module, else `-Dvidocq.mainModule`.

| `startupTimeoutSeconds`
| How long the application may take to listen; 60 by default.
|===

== Limits

* The application needs an HTTP listener (`vidocq-runtime-chappe-webserver-extension`, which every web extension
  brings): the start waits for its port.
* The tests run on the module path: an application without `module-info.java`, or a Surefire configured with
  `useModulePath=false`, has no `jdk.module.path` to start from, and `@VidocqTest` says so.
* Each test class starts its own application.
