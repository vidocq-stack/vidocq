== Maven coordinates

[cols="1,3"]
|===
| Artefact | Role

| `io.vidocq.runtime:vidocq-runtime-parent:{project-version}`
| Parent POM of an application (Model 4.0.0). [[parent-pom-versions]]It imports `vidocq-runtime-bom`, sets Java 25 and UTF-8, puts the Vauban indexer (`vidocq-runtime-core-codegen`) on the compiler's processor path, pins the Maven plugins and `vidocq-runtime-maven-plugin` at the runtime version written out literally, and binds `checkpom`, `build-info`, `generate`, `check-module-info`, `test-path` and `package` to the application that declares the plugin. Until 0.4.0 it was the reactor root, `vidocq-runtime-build` now: see xref:migration.adoc#application-parent[the migration note]. Since 0.4.0 an application needs no parent: the plugin, declared with `<extensions>true</extensions>`, gives its build the same (xref:modules/vidocq-runtime-maven-plugin.adoc#parentless[Vidocq/vidocq#380]); `vidocq create` writes that pom, `--with-parent` this one.

| `io.vidocq.runtime.extensions.jakartaee.web:vidocq-runtime-foy-websocket-extension:{project-version}`

[#flattened-poms]
NOTE: `vidocq-runtime-bom` and `vidocq-runtime-parent` are built with `io.vidocq:vidocq-parent`, for the release,
and published without it: `org.codehaus.mojo:flatten-maven-plugin` writes the pom the release deploys, with no
parent, no profile and no `distributionManagement`, so an application inherits or imports what these two files
declare and nothing of the repository's own build. It is a build tool of this reactor and never reaches an
application.

Every other module with code is installed and published flattened too, by the `flatten-published` profile of
`io.vidocq:vidocq-parent`: no parent, each dependency at its resolved version. A patch release (`0.4.1`, `0.4.2`,
...) publishes only the modules that changed, and a module of a patch release would otherwise take the versions of
its dependencies from a parent published with an earlier release. An application sees the same dependencies as
before.

[#sbom]
== Software bill of materials (CycloneDX)

Every artifact a release publishes on Maven Central carries its CycloneDX SBOM (Vidocq/vidocq#270):

* In the `release` profile of `io.vidocq:vidocq-parent`, `org.cyclonedx:cyclonedx-maven-plugin` (`makeBom`, bound to
  `package`) writes `<artifactId>-<version>-cyclonedx.json` and attaches it with the classifier `cyclonedx` and the
  type `json`. `maven-gpg-plugin` signs it at `verify` like the jars, so Central holds
  `-cyclonedx.json` and `-cyclonedx.json.asc` next to them. The SBOM lists what the artifact ships: the compile and
  runtime dependencies, not the test, provided or system ones. Every repository whose parent is `vidocq-parent` inherits it
  with its next release, with no change of its own.
* `vidocq:package` writes `<name>-<version>-cyclonedx.json` at the root of the distribution (so inside the `-dist.zip`),
  and `vidocq:jlink` writes it at the root of the image (`target/dist/`). It lists the jars the distribution ships, as they
  ship (an enriched or modularized copy is hashed, not the jar on Central), with their SHA-256 and their Maven
  coordinates. The plugin writes it itself: no dependency.

NOTE: `cyclonedx-maven-plugin` is build tooling: it runs on the build machine at release and never reaches an application.
It is the plugin the CI already runs to feed the dependency scan (Vidocq/vidocq#269), at the same version, so no rewriting of
what exists elsewhere.

[#configuration-key-descriptions]
== Configuration key descriptions

A jar that reads configuration says which keys it reads, in two files under `META-INF/vidocq/`. A tool then knows
the keys of an application from the jars it uses, without running it.

[cols="2,2,3"]
|===
| File | Written by | Holds

| `config-user-keys.properties`
| the author of the jar, in `src/main/resources`
| the keys the jar's code reads by program, and what an annotation cannot say about a key

| `config-keys.properties`
| a build, from the MicroProfile Config annotations
| the keys `@ConfigProperty` and `@ConfigProperties` declare
|===

A jar has one, both or neither. Both files have the same format.

NOTE: The reader of the format is the module `vidocq-runtime-config-keys` (`io.vidocq.runtime.config.keys`, no
dependency). In this version the doctor reads the files of the project and of its jars
(<<key-descriptions-doctor>>). Nothing generates `config-keys.properties` yet, the startup audit does not read the
files, and no Vidocq extension ships its own: these come next. Until then the doctor has something to say for a
project, or a library, that writes its file.

=== A file

One fact per line, the key, a bar, the attribute: `<key>|<attribute>=<value>`. The first fact is the version of the
format.

[source,properties]
----
format=1
vidocq.devconsole.port|type=int
vidocq.devconsole.port|default=8888
vidocq.devconsole.port|doc=Port the dev console listens on.
----

The file is UTF-8. Blank lines and lines that start with `#` or `!` are skipped; a fact is split at its first `=`
and the white space around each side is dropped. It is a `.properties` file kept to what every tool reads the same
way: a fact holds no backslash, so there is no escape and no continuation line, and the part before the `=` holds no
white space and no colon. An attribute is written in lower case.

[cols="1,4"]
|===
| Attribute | Value

| `type`
| `string` (when absent), `boolean`, `int`, `long`, `double`, `duration`, `list:<type>`, or a qualified Java type
name such as `java.net.URI`

| `default`
| the value the key takes when the application gives none

| `required`
| `true` when the application must give the key

| `values`
| the allowed values, separated by commas; a value is compared with them without regard to case

| `doc`
| one line of documentation

| `when`
| `<sibling>=<value>[,<value>]`: the key exists only when the key next to it, the same key with its last segment
replaced by `<sibling>`, has one of these values

| `ref`
| a family: the value, or each item of a list, is a name of that family

| `deprecated`
| `true` when the key should no longer be used

| `source`
| the class and the member that declare the key, in a generated file
|===

=== Patterns

A key is often not one key: the application chooses a name in the middle of it.

[cols="2,3,3"]
|===
| In a key | Meaning | Example

| `<family>`
| one segment the application chooses, a name of that family
| `vidocq.chappe.listener.<listener>.port`

| `[<family>]`
| the same, and the segment may be absent
| `vidocq.pool.[<datasource>].url` is `vidocq.pool.url` and `vidocq.pool.audit.url`

| a final `+*+`
| one segment or more, whatever they are
| `+vidocq.persistence.<unit>.properties.*+`
|===

A key starts with a literal segment. A name that holds a dot is written between double quotes in the application's
configuration: `vidocq.persistence."my.unit".datasource`; a quoted segment is a name, never a literal.

A pattern has 64 segments at most, and 8 names that may be absent at most. Beyond, it is a pattern the reader cannot
read: the line is reported and skipped.

When several patterns match the key an application writes, the most precise one describes it:

. a pattern that describes the key wins over one that covers it with a final `+*+`;
. then a literal segment wins over a name: `vidocq.chappe.listener.default.port` over
`vidocq.chappe.listener.<listener>.port`;
. then, of two final `+*+`, the one that starts further in the key: `+a.<x>.*+` over `+a.*+`;
. then a key wins over its optional twin: `vidocq.pool.url` over `vidocq.pool.[<datasource>].url`;
. and of two patterns still equal, the first in the order of their text.

=== Families

A family is named by what its names are: `datasource`, `listener`, `mount`, `unit`. It is shared by every jar: one
jar describes `vidocq.pool.[<datasource>].url`, another refers to the same family with `ref=datasource`. A line on
the family itself gives the names that exist without being written in the application's configuration, and its
documentation:

[source,properties]
----
<listener>|names=default
<listener>|doc=A listener of the web server.
----

=== Several files

In a jar, the file its author wrote is read before the generated one. Jars are read one after the other. Two
descriptions are of the same key when their patterns are written the same: `a.<x>.b` and `a.<y>.b` are two keys.

* `values`, and the `names` of a family, add up. A jar adds a value to a key another jar describes by writing that
key's `values` with the value it adds.
* For every other attribute the first fact read is kept: what an author writes wins over what a build generates.
* Two jars must agree on the `type` and the `default` of a key they both describe.

[source,properties]
----
# one jar
vidocq.http.mount.<mount>.type|values=static,websocket
vidocq.http.mount.<mount>.classpath|when=type=static

# another jar, which adds a kind of mount and its key
vidocq.http.mount.<mount>.type|values=restful
vidocq.http.mount.<mount>.include-packages|when=type=restful
----

[#key-descriptions-problems]
=== What a reader reports

A reader never fails on what a file holds: it reports what is wrong, with the file and the line, and reads the
rest. A key exists from the first fact that names it, even a fact the reader skips.

* In a file: a line that is not a fact, a pattern it cannot read, a fact written twice (the first is kept), a value
an attribute cannot have, a file whose first fact is not `format=1`.
* Between files: a `type` or a `default` two jars disagree on, a written `default` that contradicts the generated
one, a `default` that is not of the `type` of its key, a `default` outside the `values`, a `when` on a sibling or on
a value no file describes, a `ref` to a family no file describes and no key names. A `default` is of a `type` as a
value of the application is (<<key-descriptions-doctor>>). The `default` of a `list:` is compared item by item, an
empty `default` is no value to compare, and a `default` that holds an expression, `${PORT:8080}`, is compared
neither with the `type` nor with the `values`: only the runtime expands it.
* An attribute it does not know is reported apart and skipped, and a file whose `format` is above the one it knows is
not read: both are expected from a jar built with a later version. A new attribute does not change `format`; a change
of meaning does.

[#key-descriptions-doctor]
=== What the doctor checks

xref:modules/vidocq-runtime-cli.adoc#doctor[`vidocq doctor`] and
xref:modules/vidocq-runtime-maven-plugin.adoc#report-goals[`vidocq:doctor`] read the files of the project, then
those of the jars it runs with, its runtime dependencies, in the order Maven resolves them. Of the project, the
file its author writes is the one in `src/main/resources`, or the copy in `target/classes` when the sources have
none, and the generated file is the one in `target/classes`. The project is read first: what it writes of a key
wins over what a jar says.

Two checks follow. Both warn and neither fails the doctor.

`Key descriptions` reports what is wrong in the files (<<key-descriptions-problems>>), with the file and the line: the
first ten, then how many more. An attribute the reader does not know, or a `format` above the one it knows, is a
warning in a file of the project, where it is a mistake to fix, and is only counted in a jar, which may be built
with a later version. A jar that cannot be opened is reported by its path: it is damaged, and is fetched again once
deleted from the local repository. When nothing is wrong, the check says how much was read:
`2 files, 3 keys described`.

`Config values` takes each key of the project's `vidocq.properties` that a file describes, and reports, in the
order of the keys, the first ten findings then how many more:

* a value that is not of the `type` of its key: `vidocq.sample.port=eighty — is not an int`;
* a value that is not one of its `values`, compared without regard to case: `… — is not one of fast, safe`;
* a key that is `deprecated`, whatever its value, with the documentation of the key, which says what to use.

[cols="1,4"]
|===
| Type | A value fits when it is

| `boolean`
| `true`, `yes`, `y`, `on`, `1`, `false`, `no`, `n`, `off` or `0`, in any case

| `int`, `long`
| a whole number of that size: `8080`, `-1`

| `double`
| a number: `0.5`, `1e3`

| `duration`
| an ISO-8601 duration: `PT30S`, `PT5M`

| `list:<type>`
| items of that type separated by commas; `+\,+` is a comma inside an item, and an empty item is left out

| `string`, a Java type name
| anything: the value is not checked
|===

The value is the one the runtime reads from the file, the escapes of a `.properties` file undone and the white
space around it dropped. A finding prints the first 40 characters of a value, and the hint of a finding says in
which file and at which line the key is described.

When `vidocq doctor` cannot resolve the dependencies of the project, offline for one, it reads the files of the
project alone and checks the values against them. Each check then ends with a warning: the jars of the project could
not be read, and the values were not checked against them. Neither says that no jar describes a key.

What is not checked:

* an empty value, and a value that holds an expression, `${PORT:8080}`: a tool cannot expand it;
* a key no file describes: nothing is said of it here, the `Config` check still reports a `vidocq.*` key outside the
namespaces it knows;
* a key under a profile prefix, `%dev.vidocq.sample.port`;
* `required`, `when` and `ref`: the doctor reads one file, and the application may give a key elsewhere, in the
environment or in a system property.

== Public SPI (`vidocq-runtime-spi`)

Source: `vidocq-runtime-spi/src/main/java/io/vidocq/runtime/spi/`.

[cols="1,3"]
|===
| Type | Role

| `VidocqExtension`
| Lifecycle interface — `name()`, `priority()` (lower runs first, default 1000), `configure(VidocqConfiguration)`, `beforeStart(VaubanContainerBuilder)`, `onStart(ExtensionContext)`, `onStop()`, `configKeys()`. Registered with `provides … with …` in `module-info.java` (or `META-INF/services`), discovered via `ServiceLoader`.

| `ExtensionContext`
| Passed to `onStart` — `container()`, `beanManager()`, `configuration()` (legacy), `config()` (typed), `launchMode()`, `startupReport()`.

| `VidocqConfiguration`
| String-property configuration passed to `configure` — `property(key)` returns `Optional<String>`, `property(key, default)`, `portFor(extensionName, defaultPort)`.

| `config.VidocqConfig`
| Typed configuration API aligned with MicroProfile Config concepts — `getValue(key, type)` returns `Optional<T>`, `getValues(key, elementType)`; extensible via `config.ConfigSource`, `config.ConfigSourceProvider` and `config.Converter<T>`.

| `VidocqApp`
| Interface for the application entry class re-loaded inside the Vauban application layer by `Vidocq.run(Class, args)`.

| `@VidocqMain`
| Annotation for the optional trampoline `main` — a right-click Run in the IDE, or a `VidocqApp` after boot; boots the runtime in the Vauban layer. An application needs none: the runtime's own main boots `vidocq.mainModule`.

| `ApplicationLayer`
| The module layer Vidocq boots the application in, when it has one of its own — `current()` — the application module the startup banner names — `applicationModule()` — and the files of a directory of its modules — `list(layer, directory)`: what a library that scans the application reads, since the layer's class loader lists no directory. See xref:modules/vidocq-runtime-spi.adoc#application-layer[Listing the application's files].

| `report.StartupReportContributor`
| Adds a section to the startup report. Implemented by an extension, or declared as a service with `provides … with …` in `module-info.java` and `META-INF/services`. See xref:modules/vidocq-runtime-spi.adoc#startup-report-contributors[Contributing to the startup report].

| `report.StartupReportContext` / `report.StartupReportSection`
| What a contributor reads (level, launch mode, beans, routes) and where it writes (summary line, rows, lists, secrets, listeners, routes, anomalies).

| `report.Verbosity` / `report.LaunchMode`
| `OFF`, `SUMMARY`, `DETAILED`; `DEV`, `TEST`, `PROD`.

| `report.StartupReportView`
| The startup report of the running boot, read-only, from `ExtensionContext.startupReport()`: launch mode and reason, anomalies, sections, the detailed text, and the contributors the boot called. See xref:modules/vidocq-runtime-spi.adoc#startup-report-view[Reading the startup report].

| `report.ReportAnomaly` / `report.ReportSection` / `report.ReportLine`
| Its text-only records: an anomaly (code, message, hint, source), a section (id, headline, summary, lines), a line (key, values).

| xref:modules/vidocq-runtime-core.adoc#vidocq-cfg-002[`VIDOCQ-CFG-002`]

| xref:modules/vidocq-runtime-core.adoc#vidocq-rpt-001[`VIDOCQ-RPT-001`]

| xref:dev-console.adoc#vidocq-devc-002[`VIDOCQ-DEVC-002`]

== Architecture rules

`io.vidocq.runtime:vidocq-runtime-architecture-tests` is a **test-only** module, never released. It runs the runtime's
architecture rules on the classes of `vidocq-runtime-spi`, `vidocq-runtime-core` and every delivered extension (with
its `-dev` companion; the CRaC extension, which builds only with a CRaC JDK, is left out): the dependencies of the SPI and of the core (Vauban and the Jakarta CDI APIs, nothing else), the
layers (the SPI reads nothing of the runtime, nothing reaches the core or an extension), extensions on the runtime SPI
only (none reads the core, the tooling, the Maven plugin, the CLI or the dev services), no reflection outside the
documented fallbacks, no `ThreadLocal`, and no platform thread but three. The reflective fallbacks are the launch of the
application (main method and module layer known by name), the optional classes looked up by name, the type currency of
the Jakarta APIs, and the dev console panels that run a repository's methods; the three platform threads are the JVM
shutdown hook, the dev console's history ticker, and the workers of the common pool that
xref:internals.adoc#common-pool[Vidocq's thread factory] makes. Each is listed with its reason in the test's `ArchitectureRules`,
and a test fails when an entry is no longer needed. The rules come from `io.vidocq:vidocq-archrules`, the shared build
and test library of `vidocq-parent`, in test scope; it brings ArchUnit (Apache-2.0), also test scope. A change that
breaks a rule fails the build.
