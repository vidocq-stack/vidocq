= What's new
:description: Everything that changed in this component since the {release-version} release.

[.lead]
New in the `{project-version}` development line — everything listed here landed **after the {release-version} release** and is not part of it. Every entry links to the section that documents it, and those sections carry the [.tag-new]#NEW# badge. Each brick of the suite keeps its own page of this kind; xref:home::whats-new.adoc[the ecosystem index] gathers them. When the next release train ships, this page is frozen with it and restarts empty on the dev line.

* xref:reference.adoc#config-validated-at-start[The JWT configuration is checked by a `Startup` observer] [.tag-new]#NEW# — `JwtConfigurationCheck`, a bean of `cervantes-cdi-vauban`, observes `Startup` and fails the start with a `DeploymentException` naming the property and its value when the `mp.jwt.*` configuration is invalid. The check was a phase of `CervantesClaimExtension` that did nothing at build: it now holds when Vauban runs the extensions at build only and does not run them again at start, and on Weld and Open Liberty as well (Vidocq/cervantes#52).
* xref:reference.adoc#config-validated-at-start[A cleartext remote JWKS location fails the start] [.tag-new]#NEW# — an `http://` `mp.jwt.verify.publickey.location` to a host that is not loopback is refused when the container starts, with a `DeploymentException` that names the location and `io.vidocq.cervantes.jwks.allowHttp`. The refusal came at the first validation, and every request got a bare `401`. Upgrading from `0.3.0`, which fetched such a location: see xref:migration.adoc#upgrading-from-0-3-0[the migration note] (CERV-012).
