= What's new
:description: Everything that changed in this component since the {release-version} release.

[.lead]
New in the `{project-version}` development line — everything listed here landed **after the {release-version} release** and is not part of it. Every entry links to the section that documents it, and those sections carry the [.tag-new]#NEW# badge. Each brick of the suite keeps its own page of this kind; xref:home::whats-new.adoc[the ecosystem index] gathers them. When the next release train ships, this page is frozen with it and restarts empty on the dev line.

* xref:internals.adoc#definition-errors[Definition errors are compile errors] [.tag-new]#NEW# — `heisenberg-processor` reports the Fault Tolerance 4.1 definition errors of every method an interceptor guards as compile errors, with the messages of `FaultToleranceDefinitionException`, and the container start no longer validates a class whose companion it checked. It also checks inherited methods, which the start did not: an application that started may now fail to compile. A class compiled without the processor is validated at start, as before (vidocq-workspace#40).
* xref:internals.adoc#interceptor-priority[`mp.fault.tolerance.interceptor.priority` is applied at start] [.tag-new]#NEW# — a new build compatible extension, `InterceptorPriorityExtension`, gives `FaultToleranceInterceptor` the configured priority when the container starts, never at build, from the configuration the deployment starts with. Under Vauban a value other than `3850` did not move the interceptor, and a container started after another one in the same JVM could keep the first one's priority. `FaultTolerancePriority3850Interceptor` is gone: one interceptor serves every priority (BUG-019, BUG-020, Vidocq/heisenberg#66).
