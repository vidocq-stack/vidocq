[#final]
== Added in 0.4.0 (since 0.4.0-RC2)

* xref:reference.adoc#bindings-and-inherited-metrics[Metrics on inherited methods are registered] [.tag-new]#NEW# — a bean that inherits a `@Counted` or `@Timed` method from a superclass, of a dependency jar too, or a default method from an interface, and does not override it, carries that metric, named after the class or interface that declares the method. Each call threw `IllegalStateException: Counter metric was removed from registry`. An interface of the deployment no longer registers metrics of its own, which never moved. A superclass that cannot be linked at run time, because a method names a type of an absent optional dependency, ends the walk with a `WARNING`, and the bean keeps its own metrics, where the whole bean was skipped (DRC-011, DRC-012).
* xref:reference.adoc#bindings-and-inherited-metrics[Metrics carried by an interceptor binding count] [.tag-new]#NEW# — a method, constructor or class counted or timed through an application interceptor binding annotated `@Counted` or `@Timed`: the interceptors now name the metric as the scan registered it. A method threw `IllegalStateException: Counter metric was removed from registry` on every call, and the counter of a constructor or a class never moved (DRC-014).
* xref:usage.adoc#inherited-gauges[Inherited gauges] [.tag-new]#NEW# — a `@Gauge` method a bean inherits from a superclass, of a dependency jar too, or as a default method of an interface, is registered and read on the bean, under the name its declaring class gives it; it was never registered. Two unrelated beans that carry one gauge id give one gauge, read on the bean whose class name comes first, with a `WARNING` naming both, where one was picked at random (DRC-013, DRC-012).
* xref:usage.adoc#gauge-bean[A gauge is read on one reference of its bean] [.tag-new]#NEW# — the bean of a gauge is found whatever its qualifiers, and for a class with a bounded type variable, including one that declares a producer, which never runs for a read. Each read of these gauges failed with `DiracException: Unable to read gauge value`. A `@Dependent` bean is created once, at the first read, and destroyed when the container stops; each read created one, which Weld kept until the container stopped (DRC-015 to DRC-018, Vidocq/vidocq#652).

[#rc2]
== Added in 0.4.0-RC2 (since 0.4.0-RC1)

* xref:internals.adoc#generated-code[Generated code and reflective fallback] — one table lists what Dirac generates at build (the `$$DiracMetrics` companions, what its extension records), what uses it at run time and what runs when it is missing, followed by when the annotation scan still runs.
* xref:internals.adoc[Metrics registered once when the extension runs twice] — when `DiracExtension` runs at build time (the Vidocq Metrics codegen bundle) and again when the container starts, the metrics of both runs are registered once, instead of the start-up failing on two `DiscoveredMetrics` beans (DRC-008).

[#rc1]
== Brought by 0.4.0-RC1 (since 0.3.0)

=== CDI containers other than Vauban

* **Explicit bean archives** — `dirac-cdi-vauban` and `dirac-rest` now ship a `META-INF/beans.xml` (`bean-discovery-mode="annotated"`) (DRC-003, dirac#23). `0.3.0` shipped none, so the jars were implicit bean archives: Weld SE, which does not scan those by default, saw neither the `@Counted` / `@Timed` interceptors nor the `MetricRegistry` producer nor the `GET /metrics` resource, and metrics silently stayed empty. Nothing changes under Vauban. xref:reference.adoc#bean-archives[Bean archives].
* **Proven on Weld and Open Liberty** — two new test modules run the Dirac jars, unchanged, without Vauban: `dirac-it-weld` on Weld SE 6.0 (class path, plus two containers in one JVM) and `dirac-it-openliberty` as a WAR on Open Liberty 26.0.0.10 (MicroProfile 7, CDI 4.0) with Liberty's own `mpMetrics` off. Neither is published (dirac#23). xref:reference.adoc#other-containers[Other CDI containers].
* **`vauban-api` is now a runtime dependency** of `dirac-cdi-vauban` and `dirac-rest` — it was `provided`, so outside Vauban the registry producer, the gauge registration and the `/metrics` resource could not be loaded, and the deployment failed (DRC-004). It no longer brings the CDI API: an application that compiled against CDI through Dirac alone now declares `jakarta.enterprise.cdi-api` itself (the Vidocq runtime is not affected). xref:reference.adoc#other-containers[Other CDI containers].
* **Two containers keep their metrics apart** — the metrics `DiracExtension` discovers used to live in `static` sets, shared by every container of the class loader: two applications starting together on one server could register each other's gauges. They now belong to each container (DRC-005). xref:internals.adoc[Internals].
* **Open Liberty can deploy an application with Dirac** — the extension also visits the server's own beans there, and reported every one it could not load as an error, which failed the deployment. Those classes are now skipped (DRC-006). xref:reference.adoc#other-containers[Other CDI containers].
