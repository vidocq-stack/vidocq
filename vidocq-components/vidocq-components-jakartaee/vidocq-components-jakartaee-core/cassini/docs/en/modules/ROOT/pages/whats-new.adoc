= What's new
:description: Everything that changed in this component since the {release-version} release.

[.lead]
New in the `{project-version}` development line — everything listed here landed **after the {release-version} release** and is not part of it. Every entry links to the section that documents it, and those sections carry the [.tag-new]#NEW# badge. Each brick of the suite keeps its own page of this kind; xref:home::whats-new.adoc[the ecosystem index] gathers them. When the next release train ships, this page is frozen with it and restarts empty on the dev line.

* xref:usage.adoc#unmapped-exceptions[An unmapped exception answers a bare `500`] [.tag-new]#NEW# — an exception or an error that no `ExceptionMapper` handles answers `500` with an empty body; its message, which may carry SQL text or request values, stays in the `ERROR` log with the stack trace instead of going to the client (CASSINI-046).
* xref:usage.adoc#locator-exceptions[A sub-resource locator's exception reaches the mappers] [.tag-new]#NEW# — an exception that a sub-resource locator throws goes through the application's `ExceptionMapper`s, as one from a resource method does; it skipped them and answered `500` unless it was a `WebApplicationException` (CASSINI-047).
* xref:reference.adoc#free-port[`SeBootstrap` binds a free port itself] [.tag-new]#NEW# — with `FREE_PORT` or no port, the server binds a free port of `127.0.0.1` and the instance's configuration reports it; the port was picked first and bound once the application was built, so another process could take it in between (CASSINI-049).
* xref:reference.adoc#configuration[`SeBootstrap` listens on the configured host] [.tag-new]#NEW# — on the Chappe and JDK transports, `host("0.0.0.0")` listens on every address, any other host on that host, and the instance's configuration reports it; the Chappe transport listened on `127.0.0.1` whatever the host, the JDK transport on `127.0.0.1` or on every address depending on the port, and both reported `localhost` (BUG-20261123-52, BUG-20261123-63).
* xref:usage.adoc#locator-filters[Filters run on the sub-resources of a locator that returns `Object`] [.tag-new]#NEW# — the request and response filters, global or name-bound, run on a resource method reached through a sub-resource locator that returns `Object`, and the global response filters on the mapped failure of such a locator; none ran (CASSINI-050).
* xref:usage.adoc#locator-filters[The post-matching filters run after the sub-resource locators] [.tag-new]#NEW# — with a locator that returns a typed sub-resource, the post-matching request filters ran before the locators, and the response to a failing locator went through the filters bound to the method it would have led to; the locators now run first, as with a locator that returns `Object`, and only the global response filters process their failure (CASSINI-051).
* xref:usage.adoc#locator-filters[A `DynamicFeature` runs once for each resource method a locator leads to] [.tag-new]#NEW# — the features also run for the methods of a class a locator returns as `Object`, at the first request that reaches one; a method several typed locators lead to is configured once, where its filters were bound, and ran, once per locator; and a locator returning `Object` is no longer handed to the features as a resource method of `Object` (CASSINI-052).
* xref:usage.adoc#unmatched-filters[The global response filters run on a `404`, `405`, `415` or `406`] [.tag-new]#NEW# — a request the matching rejects gets its answer through the global response filters, mapped or not, so CORS or security headers reach these answers too; no response filter ran on them (CASSINI-053).
* xref:usage.adoc#unmatched-filters[A response filter's `@Context` fields follow the request it filters] [.tag-new]#NEW# — on a response with no matched resource method (a pre-matching abort, a rejected request, a locator's failure), a filter's injected `HttpHeaders`, `UriInfo` and `ResourceInfo` describe that request, with no resource method; they described the last matched request the filter had seen (CASSINI-054).
* xref:usage.adoc#locator-classes[A locator that returns `Object` reads the returned class as a typed one does] [.tag-new]#NEW# — the `@Path` of the class an `Object` locator returns is ignored, and its class `@Produces` and `@Consumes` apply to its methods; the class `@Path` was added to the sub-resource's path, and the class media types were ignored (CASSINI-055).
* xref:usage.adoc#filter-changes[The resource method gets the request as the request filters left it] [.tag-new]#NEW# — headers, entity, security context, and the method and URI a pre-matching filter sets reach the resource method's parameters and contexts, and a post-matching filter may call `setEntityStream` and `setSecurityContext`; the resource method got the request the client sent, and those two calls failed with a `500` (CASSINI-056).
* xref:usage.adoc#argument-failures[The response filters run when the arguments of a resource method fail] [.tag-new]#NEW# — the answer to a parameter that does not convert or an entity that does not read goes through the global response filters and those bound to the method; none ran on a parameter's failure, nor on an entity's unless the application had a pre-matching filter (CASSINI-057).
* xref:usage.adoc#automatic-options[The global response filters run on the automatic `OPTIONS` answer] [.tag-new]#NEW# — the `200` with an `Allow` header that answers an `OPTIONS` request to a resource with no `@OPTIONS` method goes through the global response filters, so a CORS filter adds its headers to a preflight request's answer; no response filter ran on it (CASSINI-058).
* xref:usage.adoc#filter-changes[A pre-matching filter can move the application under a new base URI] [.tag-new]#NEW# — after `setRequestUri(URI, URI)`, the request is matched on its path relative to the new base, and `UriInfo.getBaseUri()`, `getPath()`, `resolve()` and a relative `Location` follow that base; the request was matched relative to the context path of the transport, and the base URI stayed the one the client sent (CASSINI-059).
* xref:usage.adoc#locator-classes[A locator that returns `Object` gets the automatic `OPTIONS` answer] [.tag-new]#NEW# — an `OPTIONS` request to a sub-resource with no `@OPTIONS` method answers `200` with an `Allow` header that names its methods, through the global response filters, when a locator returns the sub-resource as `Object` too; it answered `405` (CASSINI-060).
* xref:internals.adoc#generic-default-scope[A generic `@Path` class without a scope gets `@Dependent`] [.tag-new]#NEW# — `CassiniScopeExtension` gives a generic resource or `Application` subclass without a scope `@Dependent`, the only scope CDI 4.1 §3.1 allows a generic managed bean; it gave `@RequestScoped` or `@ApplicationScoped`, which Vauban now refuses at start as Weld does. The resource is still created for each request (CASSINI-065).
* xref:internals.adoc#dependent-resource-release[A `@Dependent` resource is destroyed when its request ends] [.tag-new]#NEW# — its `@PreDestroy` runs at the end of each request, on Vauban, which never ran it, and on Weld, which kept every instance until shutdown. A `BeanProvider` can end what it made for a request with the new `getRequestBean` (CASSINI-062).
* xref:internals.adoc#provider-behind-a-proxy[A provider behind a client proxy keeps its annotations] [.tag-new]#NEW# — Cassini reads a provider's `@PreMatching`, `@Priority`, name bindings, media types and type argument on the class it registered, not on the instance's class, which a CDI client proxy may not extend. On Vauban, a normal-scoped provider or resource whose class has a `final` method is a CDI bean again: it was made with `new`, nothing injected; on Weld, the stack failed to build (CASSINI-066).
* xref:usage.adoc#running-as-a-servlet[`cassini-servlet`: a Jakarta REST application runs as a Servlet] [.tag-new]#NEW# — a new module: its `ServletContainerInitializer` registers a servlet for each `Application` subclass with `@ApplicationPath` (Jakarta REST 4.0 §2), so the container's context path, filters, security constraints and authentication apply to the resources. The Servlet API is `provided`. `SecurityContext` now answers with the principal, roles and scheme the transport authenticated when no Cassini authentication was recorded; it read only Cassini's own.
* xref:usage.adoc#header-names[Request header names are case-insensitive] [.tag-new]#NEW# — `ContainerRequestContext.getHeaderString` and `getHeaders`, `HttpHeaders.getRequestHeaders`, the headers a `MessageBodyReader` gets, and the response context's `getHeaderString` and `getStringHeaders` find a header whatever the case of its name; a filter that read `Authorization` missed an `authorization` header, as HTTP/2 sends it, and answered `401` to a valid token (CASSINI-045).
* xref:internals.adoc#request-scope-end[The CDI request scope ends with the request] [.tag-new]#NEW# — the scope filters of `cassini-cdi` and `cassini-cdi-vauban` hand Cassini an end-of-request action that runs once the dispatch is over: a `MessageBodyWriter`, a `WriterInterceptor` or a `StreamingOutput` sees the `@RequestScoped` beans, and the scope ends once on every path, a `404`, an unmapped failure and an async response included, where it was never ended. The properties of a request are one store, shared by its filters and its reader and writer interceptors; each context had its own (CASSINI-007).
* xref:usage.adoc#response-filter-context[A response filter gets its `@Context` fields] [.tag-new]#NEW# — they are injected before a `ContainerResponseFilter` runs; they were `null` (CASSINI-037).
* xref:usage.adoc#if-match-strong[`If-Match` compares entity tags strongly] [.tag-new]#NEW# — `Request.evaluatePreconditions(EntityTag)` answers a `412` builder when the `If-Match` tag or the current tag is weak, as RFC 9110 §13.1.1 requires; `If-Match: W/"a"` met the precondition (CASSINI-017).
* xref:usage.adoc#context-resolver-parameter[A `@Context ContextResolver` parameter fails clearly] [.tag-new]#NEW# — it ends in `Unsupported @Context type: jakarta.ws.rs.ext.ContextResolver`, answered `500`, like any type outside §9.2; it received the `Providers` and failed with a `ClassCastException` (CASSINI-008).
* xref:internals.adoc#bounded-generic-beans[A resource or provider of a bounded generic class is served as its bean] [.tag-new]#NEW# — a class such as `NumberWriter<T extends Number>`, whose raw type resolves no bean under CDI 4.1 §5.2.4, is looked up by its bean class. On Weld, Cassini built it itself, with no injection and no `@PostConstruct`; on Vauban, a scope-less generic `@Path` class that read a `@Context` field answered `500` (CASSINI-061).
* xref:internals.adoc#dependency-jar-resources[A resource of a dependency jar gets its adapter at build under Vidocq] [.tag-new]#NEW# — `cassini-processor` ships the hints with which `vidocq:generate` runs it over a dependency jar whose classes use `@Path`: such a resource class, compiled without the processor, no longer has its adapter generated at each start (Vidocq BUG-20261118-05).
* xref:usage.adoc#client-rx-tls[Client: `rx()`, and the TLS settings of `ClientBuilder` applied] [.tag-new]#NEW# — `Invocation.Builder.rx()` returns a `CompletionStageRxInvoker` and `rx(Class)` asks a registered `RxInvokerProvider`; both threw `UnsupportedOperationException`. `keyStore`, `trustStore` and `hostnameVerifier` now apply; they were ignored. The executor of `ClientBuilder.executorService` runs the async and reactive invocations, no longer the `HttpClient` (CASSINI-024).
* xref:usage.adoc#client-conformance[Client: targets, features, close, filters and entities follow the Client API] [.tag-new]#NEW# — `WebTarget.register` and `property` no longer change the `Client`; a registered `Feature` is configured; a closed `Client`'s targets and builders throw `IllegalStateException`; client filters read headers case-insensitively and can wrap the entity stream; `Response` derives its cookies, dates, entity tag, allowed methods and links from the headers; cookies are joined with `; `; an `InputStream`, `Reader`, `File` or `StreamingOutput` entity is sent as its content (CASSINI-024).
