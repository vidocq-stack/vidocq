[#final]
== Added in 0.4.0 (since 0.4.0-RC2)

* xref:usage.adoc#unmapped-exceptions[An unmapped exception answers a bare `500`] [.tag-new]#NEW# — an exception or an error that no `ExceptionMapper` handles answers `500` with an empty body; its message, which may carry SQL text or request values, stays in the `ERROR` log with the stack trace instead of going to the client (CASSINI-046).
* xref:usage.adoc#locator-exceptions[A sub-resource locator's exception reaches the mappers] [.tag-new]#NEW# — an exception that a sub-resource locator throws goes through the application's `ExceptionMapper`s, as one from a resource method does; it skipped them and answered `500` unless it was a `WebApplicationException` (CASSINI-047).
* xref:reference.adoc#free-port[`SeBootstrap` binds a free port itself] [.tag-new]#NEW# — with `FREE_PORT` or no port, the server binds a free port of `127.0.0.1` and the instance's configuration reports it; the port was picked first and bound once the application was built, so another process could take it in between (CASSINI-049).
* xref:reference.adoc#configuration[`SeBootstrap` listens on the configured host] [.tag-new]#NEW# — on the Chappe and JDK transports, `host("0.0.0.0")` listens on every address, any other host on that host, and the instance's configuration reports it; the Chappe transport listened on `127.0.0.1` whatever the host, the JDK transport on `127.0.0.1` or on every address depending on the port, and both reported `localhost` (BUG-20261123-52, BUG-20261123-63).
* xref:usage.adoc#locator-filters[Filters run on the sub-resources of a locator that returns `Object`] [.tag-new]#NEW# — the request and response filters, global or name-bound, run on a resource method reached through a sub-resource locator that returns `Object`, and the global response filters on the mapped failure of such a locator; none ran (CASSINI-050).
* xref:usage.adoc#locator-filters[The post-matching filters run after the sub-resource locators] [.tag-new]#NEW# — with a locator that returns a typed sub-resource, the post-matching request filters ran before the locators, and the response to a failing locator went through the filters bound to the method it would have led to; the locators now run first, as with a locator that returns `Object`, and only the global response filters process their failure (CASSINI-051).
* xref:usage.adoc#locator-filters[A `DynamicFeature` runs once for each resource method a locator leads to] [.tag-new]#NEW# — the features also run for the methods of a class a locator returns as `Object`, at the first request that reaches one; a method several typed locators lead to is configured once, where its filters were bound, and ran, once per locator; and a locator returning `Object` is no longer handed to the features as a resource method of `Object` (CASSINI-052).
* xref:usage.adoc#unmatched-filters[The global response filters run on a `404`, `405`, `415` or `406`] [.tag-new]#NEW# — a request the matching rejects gets its answer through the global response filters, mapped or not, so CORS or security headers reach these answers too; no response filter ran on them (CASSINI-053).
* xref:usage.adoc#unmatched-filters[A response filter's `@Context` fields follow the request it filters] [.tag-new]#NEW# — on a response with no matched resource method (a pre-matching abort, a rejected request, a locator's failure), a filter's injected `HttpHeaders`, `UriInfo` and `ResourceInfo` describe that request, with no resource method; they described the last matched request the filter had seen (CASSINI-054).
* xref:usage.adoc#locator-classes[A locator that returns `Object` reads the returned class as a typed one does] [.tag-new]#NEW# — the `@Path` of the class an `Object` locator returns is ignored, and its class `@Produces` and `@Consumes` apply to its methods; the class `@Path` was added to the sub-resource's path, and the class media types were ignored (CASSINI-055).
* xref:usage.adoc#filter-changes[The resource method gets the request as the request filters left it] [.tag-new]#NEW# — headers, entity, security context, and the method and URI a pre-matching filter sets reach the resource method's parameters and contexts, and a post-matching filter may call `setEntityStream` and `setSecurityContext`; the resource method got the request the client sent, and those two calls failed with a `500` (CASSINI-056).
* xref:usage.adoc#argument-failures[The response filters run when the arguments of a resource method fail] [.tag-new]#NEW# — the answer to a parameter that does not convert or an entity that does not read goes through the global response filters and those bound to the method; none ran on a parameter's failure, nor on an entity's unless the application had a pre-matching filter (CASSINI-057).
* xref:usage.adoc#automatic-options[The global response filters run on the automatic `OPTIONS` answer] [.tag-new]#NEW# — the `200` with an `Allow` header that answers an `OPTIONS` request to a resource with no `@OPTIONS` method goes through the global response filters, so a CORS filter adds its headers to a preflight request's answer; no response filter ran on it (CASSINI-058).
* xref:usage.adoc#filter-changes[A pre-matching filter can move the application under a new base URI] [.tag-new]#NEW# — after `setRequestUri(URI, URI)`, the request is matched on its path relative to the new base, and `UriInfo.getBaseUri()`, `getPath()`, `resolve()` and a relative `Location` follow that base; the request was matched relative to the context path of the transport, and the base URI stayed the one the client sent (CASSINI-059).
* xref:usage.adoc#locator-classes[A locator that returns `Object` gets the automatic `OPTIONS` answer] [.tag-new]#NEW# — an `OPTIONS` request to a sub-resource with no `@OPTIONS` method answers `200` with an `Allow` header that names its methods, through the global response filters, when a locator returns the sub-resource as `Object` too; it answered `405` (CASSINI-060).
* xref:internals.adoc#generic-default-scope[A generic `@Path` class without a scope gets `@Dependent`] [.tag-new]#NEW# — `CassiniScopeExtension` gives a generic resource or `Application` subclass without a scope `@Dependent`, the only scope CDI 4.1 §3.1 allows a generic managed bean; it gave `@RequestScoped` or `@ApplicationScoped`, which Vauban now refuses at start as Weld does. The resource is still created for each request (CASSINI-065).
* xref:internals.adoc#dependent-resource-release[A `@Dependent` resource is destroyed when its request ends] [.tag-new]#NEW# — its `@PreDestroy` runs at the end of each request, on Vauban, which never ran it, and on Weld, which kept every instance until shutdown. A `BeanProvider` can end what it made for a request with the new `getRequestBean` (CASSINI-062).
* xref:internals.adoc#provider-behind-a-proxy[A provider behind a client proxy keeps its annotations] [.tag-new]#NEW# — Cassini reads a provider's `@PreMatching`, `@Priority`, name bindings, media types and type argument on the class it registered, not on the instance's class, which a CDI client proxy may not extend. On Vauban, a normal-scoped provider or resource whose class has a `final` method is a CDI bean again: it was made with `new`, nothing injected; on Weld, the stack failed to build (CASSINI-066).
* xref:usage.adoc#running-as-a-servlet[`cassini-servlet`: a Jakarta REST application runs as a Servlet] [.tag-new]#NEW# — a new module: its `ServletContainerInitializer` registers a servlet for each `Application` subclass with `@ApplicationPath` (Jakarta REST 4.0 §2), so the container's context path, filters, security constraints and authentication apply to the resources. The Servlet API is `provided`. `SecurityContext` now answers with the principal, roles and scheme the transport authenticated when no Cassini authentication was recorded; it read only Cassini's own.
* xref:usage.adoc#header-names[Request header names are case-insensitive] [.tag-new]#NEW# — `ContainerRequestContext.getHeaderString` and `getHeaders`, `HttpHeaders.getRequestHeaders`, the headers a `MessageBodyReader` gets, and the response context's `getHeaderString` and `getStringHeaders` find a header whatever the case of its name; a filter that read `Authorization` missed an `authorization` header, as HTTP/2 sends it, and answered `401` to a valid token (CASSINI-045).
* xref:internals.adoc#request-scope-end[The CDI request scope ends with the request] [.tag-new]#NEW# — the scope filters of `cassini-cdi` and `cassini-cdi-vauban` hand Cassini an end-of-request action that runs once the dispatch is over: a `MessageBodyWriter`, a `WriterInterceptor` or a `StreamingOutput` sees the `@RequestScoped` beans, and the scope ends once on every path, a `404`, an unmapped failure and an async response included, where it was never ended. The properties of a request are one store, shared by its filters and its reader and writer interceptors; each context had its own (CASSINI-007).
* xref:usage.adoc#response-filter-context[A response filter gets its `@Context` fields] [.tag-new]#NEW# — they are injected before a `ContainerResponseFilter` runs; they were `null` (CASSINI-037).
* xref:usage.adoc#if-match-strong[`If-Match` compares entity tags strongly] [.tag-new]#NEW# — `Request.evaluatePreconditions(EntityTag)` answers a `412` builder when the `If-Match` tag or the current tag is weak, as RFC 9110 §13.1.1 requires; `If-Match: W/"a"` met the precondition (CASSINI-017).
* xref:usage.adoc#context-resolver-parameter[A `@Context ContextResolver` parameter fails clearly] [.tag-new]#NEW# — it ends in `Unsupported @Context type: jakarta.ws.rs.ext.ContextResolver`, answered `500`, like any type outside §9.2; it received the `Providers` and failed with a `ClassCastException` (CASSINI-008).
* xref:internals.adoc#bounded-generic-beans[A resource or provider of a bounded generic class is served as its bean] [.tag-new]#NEW# — a class such as `NumberWriter<T extends Number>`, whose raw type resolves no bean under CDI 4.1 §5.2.4, is looked up by its bean class. On Weld, Cassini built it itself, with no injection and no `@PostConstruct`; on Vauban, a scope-less generic `@Path` class that read a `@Context` field answered `500` (CASSINI-061).
* xref:internals.adoc#dependency-jar-resources[A resource of a dependency jar gets its adapter at build under Vidocq] [.tag-new]#NEW# — `cassini-processor` ships the hints with which `vidocq:generate` runs it over a dependency jar whose classes use `@Path`: such a resource class, compiled without the processor, no longer has its adapter generated at each start (Vidocq BUG-20261118-05).
* xref:usage.adoc#client-rx-tls[Client: `rx()`, and the TLS settings of `ClientBuilder` applied] [.tag-new]#NEW# — `Invocation.Builder.rx()` returns a `CompletionStageRxInvoker` and `rx(Class)` asks a registered `RxInvokerProvider`; both threw `UnsupportedOperationException`. `keyStore`, `trustStore` and `hostnameVerifier` now apply; they were ignored. The executor of `ClientBuilder.executorService` runs the async and reactive invocations, no longer the `HttpClient` (CASSINI-024).
* xref:usage.adoc#client-conformance[Client: targets, features, close, filters and entities follow the Client API] [.tag-new]#NEW# — `WebTarget.register` and `property` no longer change the `Client`; a registered `Feature` is configured; a closed `Client`'s targets and builders throw `IllegalStateException`; client filters read headers case-insensitively and can wrap the entity stream; `Response` derives its cookies, dates, entity tag, allowed methods and links from the headers; cookies are joined with `; `; an `InputStream`, `Reader`, `File` or `StreamingOutput` entity is sent as its content (CASSINI-024).

[#rc2]
== Added in 0.4.0-RC2 (since 0.4.0-RC1)

* xref:internals.adoc#generated-code[Generated code and reflective fallback] — one table lists what Cassini generates (adapters, route tables, provider and application descriptors), which tool generates it and when, what uses it at run time and what runs when it is missing, followed by when the fallback runs and how to tell which path ran.
* On Vauban, the `@Path` and `@Provider` beans are found from the annotations the deployment's index read in their class files, instead of two reflective reads per bean at startup; a class outside the index is still read by reflection.
* xref:internals.adoc[Internals] — a generated route names its method's parameter types and the class that carries its annotations: Cassini finds the method with one lookup at startup instead of resolving each type by name and scanning annotations. Routes generated by an older processor are resolved as before.
* xref:internals.adoc[Internals] — `cassini-processor` also generates the adapter of the `@BeanParam` classes and sub-resource classes a resource reaches, when they are compiled in the same build: they no longer get one generated at run time on their first request. A sub-resource locator is called through the adapter of its class instead of `Method.invoke`, and a `@BeanParam` parameter is created and filled through its build-time adapter; without one, both keep the reflective path.
* xref:internals.adoc[Internals] — `cassini-processor` generates a `$$CassiniProvider` descriptor for each `@Provider` class: its priority, media types, pre-matching, constraint, name bindings and entity type. Cassini reads it at startup instead of the annotations, and reads the annotations, as before, for a provider without one. A provider in a named module on the boot layer is found through `provides io.vidocq.cassini.spi.gen.ProviderDescriptor with ...`; the Vidocq application layer adds it from `META-INF/services`.
* xref:usage.adoc#_filters_and_interceptors[Filters and interceptors] — a `@PreMatching` filter runs once per request, before routing. Until 0.4.0-RC1 it ran a second time before negotiation, with a fresh `ContainerRequestContext`: a filter that counts, sets a property or activates a scope saw two requests where there was one.
* The request path recomputes less per request, with no API change: the base URI is built once per listener and host, media types are parsed once and shared, provider selection reads what it resolved at registration, routing checks the verb before the template regex and compares literal templates without one, a request entity is read with a buffer of its `Content-Length`, and the JSON provider no longer probes the module path for `jakarta.activation.DataSource` on every `isWriteable` / `isReadable` call.
* xref:internals.adoc#_virtual_threads_and_async[Virtual threads and async] — on Chappe, with a request scope hook such as the Vidocq runtime's, a deployment without Server-Sent Events dispatches each request on the virtual thread of its connection instead of starting one per request. `CassiniHttpAdapter.mayStream()` tells a transport whether it may.
* The arguments of a resource method are resolved from what its parameter annotations say, read once per method instead of on every request, with no API change. The JDK takes a lock on every `Parameter.getAnnotation` and parses the class file again on every `Parameter.getAnnotations()`: a method with a `@PathParam` and an entity paid both on every call.
* xref:internals.adoc[Internals] — a reader, writer or filter whose class declares no `@Context` field gets no adapter: the first JSON request no longer generates one at run time for Cassini's own JSON-B provider, nor for the filters of bricks built without `cassini-processor`, and the `RUNTIME CODE GENERATION FALLBACK` warning no longer names them.
* A resource whose class declares no `@Context`, `@BeanParam` or `@*Param` field skips the field injection on each request and, under CDI, the extra bean resolution that looked up the instance behind the client proxy.
* On Vauban, the bean provider resolves a resource or provider class once instead of on every request: a normal-scoped bean is served by the client proxy the container always hands out for it, a `@Dependent` one is still created on each lookup.
* On Chappe, a request header is looked up by name in Chappe's own headers, and the map of all of them is built at most once per request; it was rebuilt, with a list per name, on each of the half-dozen reads of a request.
* `CassiniHttpExchange.writeResponseBody(byte[])` hands a whole response body to the transport in one call; by default it writes it to `responseBody()`. On Chappe, the exchange keeps the array of an entity written at once instead of copying it into a growing stream and copying that again for Chappe.
* The default scope `CassiniScopeExtension` gives a resource (`@RequestScoped`), a provider (`@Dependent`) or an `Application` subclass (`@ApplicationScoped`) is logged at DEBUG: run at every build of an application, it was an INFO line per class.
* xref:internals.adoc[An adapter generated at run time is announced] — when a resource or provider adapter is generated at run time instead of by `cassini-processor` at build time, Cassini logs a framed `CASSINI — RUNTIME CODE GENERATION FALLBACK` warning naming the classes, at start-up or on first use. A build-time adapter is recognised by its class file, without loading it; the Maven plugin writes its own adapters again on every run; no `newInstance()` is generated for an abstract or inner resource.
* *Jakarta REST conformance fixes* — the multipart part name is read when `filename` comes first (CASSINI-026); `EntityPart.Builder` follows its contract (CASSINI-027); the stack's `Application` is exposed to its requests (CASSINI-028); `UriInfo` keeps `+` in paths and parses matrix parameters (CASSINI-029), and `relativize` and the filter view work (CASSINI-031); `SseBroadcaster` follows its close contract (CASSINI-030); each adapter's method ids are read from the adapter itself (CASSINI-032); one §3.6 rule for every way routes are built; `UriBuilder` keeps URI templates in query and matrix parameters, takes positional values in URI order, percent-encodes supplementary characters as one UTF-8 sequence and leads a relative path with a slash after the authority; `ResponseBuilder.status(int, String)` reports its reason phrase; a wildcard locale answers a request without `Accept-Language`; response filters see a non-null status and delegate-converted header strings; `VariantListBuilder` resets after `build()`; a streamed response whose queue is full ends on Chappe.
* *Client fixes* — typed invocations throw `WebApplicationException` on error statuses; async failures are unwrapped and invocation callbacks typed; `readEntity` follows its contract on closed and unreadable responses; response header names are looked up case-insensitively; request properties are scoped to the request and null ones removed; the default `Jsonb` is created on the first JSON entity only.
* *Hot reload no longer keeps the previous application layers in memory* — the default JSON-B instances of the built-in reader/writer and of the client are dropped with the route and adapter caches when the host stops a layer (`CassiniMaintenance.resetDiscoveryCaches()`, which the Vidocq Cassini extension calls), so a `vidocq dev` session no longer grows by a layer at every reload. Modules built on Cassini can add their own reset with `CassiniMaintenance.onReset`.

[#rc1]
== Brought by 0.4.0-RC1 (since 0.3.0)

=== Request entities

* **An unreadable request entity is a 400, not a 500** — malformed JSON, an empty body, a JSON value of the wrong shape or type for the Java type: the resource method is not called and Cassini answers `400 Bad Request`, with an empty body unless the application maps `BadRequestException`. The application's `ExceptionMapper` for the exception the reader threw still runs first. Up to 0.3.0, these requests answered `500` with the parser's message (cassini#39). xref:usage.adoc#unreadable-entities[Unreadable request entities].
* **`NoContentException` becomes a `BadRequestException`** — whatever reader throws it, the application's included, as Jakarta REST §4.2.4 requires; the built-in JSON reader now throws it for an empty entity. xref:usage.adoc#unreadable-entities[Unreadable request entities].
* **No ERROR log for a client's malformed entity** — one line at `DEBUG` on the `io.vidocq.cassini.entity` logger, and the stack trace at `TRACE`, where each such request used to log a full stack trace at `ERROR`. A type the JSON-B provider cannot reach, its package not exported to it, remains a server error logged at `ERROR`. xref:usage.adoc#unreadable-entities[Unreadable request entities].

=== Response headers

* **A response header Chappe refuses is a clear 500** — a header whose value holds CR, LF, a control character or a character above `U+00FF` (a raw UTF-8 file name in `Content-Disposition`, typically), whose name is not a token, or whose value is `null`. Cassini answers `500` and logs one `ERROR` line that names the header, never its value, and points to the RFC 8187 encoding. A streamed response in that case now releases the thread writing its entity instead of leaving it blocked (cassini#56). xref:usage.adoc#non-latin1-headers[Response headers with non-Latin-1 text].

* **`cassini-jdk-http` answers an empty 500 and refuses the same headers** — a request that fails on the JDK `HttpServer` transport used to answer `500` with the exception's message as its body, which could carry request or header values to the client. It now answers an empty `500` and logs one `ERROR` line with the exception's class only. A response header the wire cannot carry answers `500` as on Chappe, with a line that names the header and never its value; the JDK only refused CR and LF and sent anything else mangled (cassini#58). xref:usage.adoc#non-latin1-headers[Response headers with non-Latin-1 text].

=== Embedding

* **A host can read the route table** — `CassiniStack.routes()` returns the routes a stack resolved, in match order, as `RouteDescription` values: HTTP method, path template, resource class and method names, produced and consumed media types. A host such as Vidocq can list what an application exposes without reaching into `cassini-core` (cassini#41). xref:usage.adoc#route-table[Reading the route table].
* **Live request figures** — `CassiniStack.statistics()` returns the counters a stack keeps: requests answered, in flight, by status class, and the total and longest time spent answering them. Reading them creates nothing and takes no lock; updating them allocates nothing and costs about 25 ns per request, so they are on by default, and `statistics(false)` removes them (cassini#42). xref:usage.adoc#request-statistics[Reading live request figures].

=== Code generation

* **`@ApplicationPath` without CDI** — `cassini-processor` generates an `ApplicationDescriptor` for each `Application` subclass annotated with `@ApplicationPath`, found by `ServiceLoader`. A host reads the path of an `Application` that has no CDI scope, which a container in `annotated` discovery mode never discovers (vidocq#219). xref:internals.adoc#_static_resource_codegen[Static resource codegen].

=== Other CDI containers

* **`cassini-core` no longer brings Champollion** — it depends on the JSON-P and JSON-B APIs only, and the application, or its runtime, picks the implementation: the Vidocq REST extension brings Champollion, so nothing changes in a Vidocq application. A standalone application that relied on `cassini-core` for JSON adds `champollion-jsonb` (or another JSON-B implementation). Without one, the stack still starts and only a JSON entity fails (vidocq-workspace#17). xref:getting-started.adoc#json-implementation[Getting started].
* **`cassini-cdi`, a container-neutral `BeanProvider`** — Cassini resolves its resources and providers as beans of any CDI 4 container, through `CDI.current()`, the `BeanManager` and `RequestContextController`, and activates the request context around each request. `cassini-it-weld` proves it on Chappe with Weld SE: injection, a `@RequestScoped` bean per request, interceptors on resources (cassini#53). xref:reference.adoc#other-containers[Other CDI containers].
* **`CassiniScopeExtension` leaves interfaces alone** — a `@Path` or `@Provider` interface, a MicroProfile Rest Client contract typically, no longer gets a default scope: a container that ran the extension at build time generated a client proxy for the interface, and the application did not compile. Only classes get `@RequestScoped` or `@Dependent` (cassini#59). xref:internals.adoc[Internals].
* **`CassiniScopeExtension` moved to `cassini-cdi`** — the BCE that gives `@Path` and `@Provider` classes their default scope is now `io.vidocq.cassini.cdi.CassiniScopeExtension`; `cassini-cdi-vauban` depends on `cassini-cdi` and keeps its own, faster provider, which outranks the neutral one when Vauban runs. Nothing changes for a Vidocq application. Code that named the class `io.vidocq.cassini.cdi.vauban.CassiniScopeExtension` uses the new package. xref:reference.adoc#java-modules[Java modules].
