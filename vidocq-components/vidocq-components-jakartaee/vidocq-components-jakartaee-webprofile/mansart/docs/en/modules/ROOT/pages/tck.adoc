== Jakarta Data 1.0 — detail

Runner: `mansart-jakarta-data/mansart-data-tck`, **out of reactor** (standalone POM Model 4.0.0, no `<parent>`).
This decouples the implementation and official TCK release cycles. The historical Maven Model 4.1.0 parsing
constraint no longer applies since the move to Maven 3.9.x and Model 4.0.0.

Harness architecture:

* Arquillian + ShrinkWrap for the official TCK fixtures.
* Mansart adapter: `MansartRuntimeProducer` injects a `RepositoryRuntime` from a test H2 in-memory `DataSource`.
* `MansartTckArchiveAppender` + `VaubanArquillianExtension` enrich TCK archives with the Mansart implementations generated by APT.

Local reproduction:

[source,bash]
----
# from the root of the monorepo
cd vidocq-components/vidocq-components-jakartaee/vidocq-components-jakartaee-webprofile/mansart/mansart-jakarta-data/mansart-data-tck
./run-official-tck-data-1.0.sh all
----

In CI: a pull request runs no TCK. Mansart's root `pom.xml` declares `EntityTests` and `SignatureTests` (74 tests, H2 in memory) in `ci.tck.command`, which the `TCK nightly` workflow of the monorepo (`.forgejo/workflows/tck-nightly.yml`) runs in Mansart's folder once a day, on demand on a branch (dispatched with the `MANSART` tag), and for a release: `mvn -f mansart-jakarta-data/mansart-data-tck/pom.xml -Ptck-run,tck-sig test`, with `mansart.version` set to the version of the build, since the runner is outside the reactor and would otherwise test the published snapshot. A single failing test fails the run; it takes under a minute on a fresh runner. `jakarta.data:jakarta.data-tck:1.0.1` is public on Maven Central.

Major historical bug: `BUG-20260505-01` (TCK entities not metamodelled because compiled without the processor in the APT classpath). Resolved by the M7 runtime runner (`MansartRuntimeRepoCreator`). See link:{repo-vidocq}/src/branch/main/vidocq-components/vidocq-components-jakartaee/vidocq-components-jakartaee-webprofile/mansart/mansart-jakarta-data/BUG.md[BUG.md].

== Jakarta Transactions 2.0 — detail

Runner: `mansart-transactions/`, see link:{repo-vidocq}/src/branch/main/vidocq-components/vidocq-components-jakartaee/vidocq-components-jakartaee-webprofile/mansart/mansart-transactions/TCK.md[TCK.md].

The official TCK distributed by Eclipse is a historical **Sun tsharness** harness:

* `bin/build.xml` Apache Ant.
* `bin/ts.jte` ~80 properties (JAVA_HOME, SUT classpath, hostnames, ports).
* Tests under `src/com/sun/ts/tests/jta/ee/` compiled in place by `ant build` then executed via `ant runclient`.

No Surefire-scannable jar exists — `dependenciesToScan` against `jtatck.jar` only finds support classes, not tests.

Status:

* ✅ **M6** smoke wiring 5/5 (`./run-official-tck-transactions-2.0.sh smoke`).
* ✅ **M6b** profile `full-tck`: `ant build.all.tests` `BUILD SUCCESSFUL` on the ~7 JTA EE directories + signature tests.
* ⏳ **M6c** leaf-by-leaf driving + tsharness HTML report parsing.

Manual reproduction:

[source,bash]
----
# from the root of the monorepo
cd vidocq-components/vidocq-components-jakartaee/vidocq-components-jakartaee-webprofile/mansart/mansart-transactions
./install-tck.sh                           # download + unpack
cd .tck-cache/transactions-tck/bin
$EDITOR ts.jte                             # JAVA_HOME, jta.classes, Mansart provider
ant build && ant runclient
xdg-open ../dist/index.html
----

Not run in CI. The official suite is not a Maven artifact: `install-tck.sh` downloads the zip from `download.eclipse.org` and the suite runs under Ant. Until M6c drives it leaf by leaf and parses its report, a run cannot fail on a test, so it would gate nothing. The smoke mode checks the adapter's wiring only, and is run by hand.
