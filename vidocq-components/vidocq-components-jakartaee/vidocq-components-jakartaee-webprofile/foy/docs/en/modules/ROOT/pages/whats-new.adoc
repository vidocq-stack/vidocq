[#final]
== Added in 0.4.0 (since 0.4.0-RC2)

* **Jakarta WebSocket 2.2, lot 1** — the programmatic server API in the new optional `foy-websocket` module: `ServerContainer.addEndpoint(ServerEndpointConfig)`, the RFC 6455 handshake, a same-origin policy with the `io.vidocq.foy.websocket.allowed-origins` init parameter, sessions with limits, timeouts and close codes. Annotated endpoints and the client API come in later lots. xref:usage.adoc#websocket[Usage], xref:reference.adoc#websocket-module[reference].
* **WebSocket origin messages name the configured setting** — the init parameter `io.vidocq.foy.websocket.allowed-origins.setting-name` lets a runtime that fills the origins from its own key (Vidocq: `vidocq.websocket.allowed-origins`) have the refusal WARNING and the malformed-entry error name that key. xref:usage.adoc#websocket-origins[Usage], xref:reference.adoc#websocket-module[reference].
* **Takeover SPI** — `io.vidocq.foy.spi.websocket` (`WebSocketUpgradeHandler`, `WebSocketListener`, `WebSocketPeer`) and the `ComponentInstantiator` context attribute let a WebSocket implementation run on Foy without reaching into `foy-core`. xref:reference.adoc#websocket-spi[Reference].
* **`@Inject HttpServletRequest`, `HttpSession` and `ServletContext` on Vauban** — the beans CDI requires of a Servlet container, `@RequestScoped`, `@SessionScoped` and `@ApplicationScoped`, produced by `foy-cdi-vauban` with client proxies generated at its build; the application declares nothing. They work wherever the request context does, `AsyncListener` callbacks and `AsyncContext.start` tasks included. An application's own producer of one of these types now makes an ambiguous dependency. xref:usage.adoc#servlet-built-in-beans[Usage], xref:internals.adoc#servlet-built-in-beans[Internals], xref:migration.adoc#servlet-built-in-beans[Behaviour changes].
* **`FoyChappeBoot.Builder.initParameter`** — sets a servlet-context init parameter from code. xref:reference.adoc#foychappeboot[Reference].
* **Fix: dynamic filter mappings honour `isMatchAfter`** (BUG-20261114-01). xref:migration.adoc[Behaviour changes].
* **Undeploy in order** (BUG-20261114-08, BUG-20261115-01 to -06) — closing a deployment refuses new requests and WebSocket handshakes with `503 Service Unavailable` and `Retry-After: 3` (the undeploy's bound, in seconds), never with an error page of the application; it closes the upgraded connections (a WebSocket peer gets its 1001 Close; one that does not read, while a send to it holds that Close past 2 s, has its connection cut, and the blocked send fails with an `IOException`), lets the requests in service finish for up to 2 s, refuses cross-context dispatches into the application, then destroys it. Close the deployment before you stop the server. xref:migration.adoc[Behaviour changes], xref:reference.adoc#foychappeboot[`Mounted.close()`].
* **`getContext` follows one rule for every caller** (BUG-20261115-07) — the longest context path the URI lies under, on a segment boundary, wins, and the root application holds every URI no other application does (section 4.8): another application is now found by a URI below its path (`getContext("/b/x")`), and, when a root application is deployed, a URI no other application holds returns the root application. During its undeploy an application still finds itself. xref:migration.adoc[Behaviour changes].
* **A WebSocket close the container initiates reaches `onClose` as 1006** (BUG-20261115-08, Jakarta WebSocket 2.2 section 2.1.5) — the undeploy, the idle and send timeouts, a message over the limit, a failed `onOpen`, a protocol violation of the peer and an `Error` from a message handler give `Endpoint.onClose` 1006 with a reason naming the cause, while the peer still reads the Close frame's own code (1001, 1009, 1011, ...). A close of the peer keeps the peer's code, a `Session.close(...)` of the application its own. xref:usage.adoc#websocket-close-codes[Close codes], xref:migration.adoc[Behaviour changes].
* **A WebSocket close crossed by the peer's Close hears the Close that went out first** (BUG-20261115-08) — when a Close of the peer, or the undeploy's, goes out just before a close of the session (`Session.close(...)`, a timeout, a message over the limit, a failed `onOpen`) or of the undeploy, `Endpoint.onClose` hears that first Close, no longer this side's own reason, as Jakarta WebSocket 2.2 section 2.1.5 asks. `WebSocketPeer.close` of the takeover SPI returns whether the call sent the Close frame, from Chappe's `WebSocket.sendClose`, a new method (`close` is unchanged): this Foy needs a Chappe of the same line. xref:usage.adoc#websocket-close-codes[Close codes], xref:reference.adoc#websocket-spi[reference], xref:internals.adoc#websocket-takeover[Internals].
* **An `Error` from a WebSocket listener's `onClose` is logged, never thrown into Chappe's thread** (BUG-20261116-01) — whichever thread delivers `onClose`, the takeover logs what the listener throws once at WARNING and still calls `destroy()`; an `Error` from `onOpen` reaches Chappe as an `IOException` carrying it. xref:internals.adoc#websocket-takeover[Internals].
* **HTTP sessions survive a dev swap** — `Mounted.closeExportingSessions()` undeploys like `close()` but exports the live sessions, and `Mounted.importSessions(byte[])` imports them into the next deployment before it is mounted: same `JSESSIONID`, same attributes, no `sessionCreated` or `sessionDestroyed`. A session whose attributes cannot all be written or read stays behind whole; a CDI adapter binds its container through the new `CdiContextListeners.aroundSessionImport` default method. xref:internals.adoc#sessions-across-redeploy[Internals], xref:reference.adoc#foychappeboot[`Mounted`].
* **CDI session state moves with the session on Vauban** — when Foy runs on Vauban, a dev swap moves the `@SessionScoped` beans with their state, the client proxies they hold, which read back as the new container's, and the injected built-ins (`Event`, `Instance`, `Provider`, `BeanManager`), so an `@Inject HttpSession` no longer keeps its session behind. A session that holds an intercepted or non-`Serializable` `@SessionScoped` instance still stays behind whole. xref:internals.adoc#sessions-across-redeploy[Internals], xref:vauban::internals.adoc#session-swap[Vauban internals].
* **Fix: a session class without `serialVersionUID` that gains a method keeps its session** (BUG-20261117-01) — adding a method or a constructor changed the JDK's default `serialVersionUID`, so the import dropped every session holding such a class, a `@SessionScoped` bean included. The import now reads it with the new version when neither version declares a `serialVersionUID` or `writeObject`, neither is `Externalizable`, and the serializable fields, the superclass and the interfaces are the same; otherwise the session is dropped as before, and the WARNING line now ends with the reason (`first cause: class <name>: <reason>`). The export format moves to version 2. xref:internals.adoc#session-class-changed[Internals], xref:reference.adoc#foychappeboot[`Mounted.importSessions`].
* xref:reference.adoc#request-authentication[A `RequestAuthentication` hook for a Jakarta Authentication runtime] [.tag-new]#NEW# — `FoyChappeBoot.Builder.requestAuthentication(RequestAuthentication)` hands the authentication of every request, protected or not, to a runtime such as Kerckhoffs, in place of the `login-config` mechanism: `validateRequest` is asked with `mandatory` set when a constraint protects the resource. It fails closed: an anonymous caller of a protected resource gets `403`, and an exception from the hook fails the request. `HttpServletRequest.authenticate` asks the hook, `login(user, password)` throws `ServletException`, and `logout` calls `cleanSubject`.
* xref:reference.adoc#access-control[An `AccessControl` decision for a Jakarta Authorization runtime] [.tag-new]#NEW# — `FoyChappeBoot.Builder.accessControl(AccessControl)` hands the access decision of every request, once the caller is known, to a runtime such as Kerckhoffs: `permits(path, method, caller, constraints)` replaces the security constraints, which it can still read through `constraints`. `false` answers `403`; an exception fails closed.
* xref:reference.adoc#current-request[`CurrentRequest`] [.tag-new]#NEW# — `io.vidocq.foy.spi.security.CurrentRequest.get()` returns the request the current thread serves, for code that is not handed it, such as a security context that answers `getCallerPrincipal()`. Foy binds it around the whole processing of a request, listeners, filters and servlet; it is empty outside a request and on a thread the application started itself.
* xref:reference.adoc#cdi-context-listeners[`CdiContextListeners.requestContextListeners`] [.tag-new]#NEW# — a CDI adapter returns from this default method, empty unless overridden, the request listeners that need the CDI request context; Foy registers them right behind the listener that activates it, so they hear a request once the context is active, on the threads of `AsyncContext.start` too. `foy-cdi-vauban` uses it to bind the request it serves as a bean.
* xref:concepts.adoc#web-components-through-cdi[A `web.xml` servlet whose class is a bean is injected] [.tag-new]#NEW# — with a `BeanManager`, a component that `web.xml` declares or that the application registers by its class (`addServlet(String, Class)`, `createFilter`, an upgrade handler, ...) is created through CDI when its class is a bean of its own, so its injection points are filled (Servlet 6.1 §15.5). It was created by its no-argument constructor, with no injection even when its class was `@Dependent`; a class that is no bean still is (BUG-20261118-62).
* xref:usage.adoc#jlink-image-resources[A jlink image serves its modules' static resources] [.tag-new]#NEW# — the `META-INF/resources/` of a module linked into a run-time image is served by the default servlet and found by `ServletContext.getResource`, `getResourceAsStream` and `getResourcePaths`. Nothing there was found, so Vaadin's theme stylesheet `aura/aura.css` answered 404 in a `vidocq:jlink` image while the same application served it from jars (BUG-20261111-01).
* xref:reference.adoc#_java_modules_and_exports[`foy-chappe` runs without CDI on the module path] [.tag-new]#NEW# — `io.vidocq.foy.chappe` reads `jakarta.cdi` with `requires static`, as `FoyChappeBoot.Builder.beanManager` is optional; an application without the CDI API failed to start with `Module jakarta.cdi not found`. `foy-api` and `foy-core` no longer bring `jakarta.annotation-api` to the application: Foy never loads its classes, so it is `provided`, and an application that uses `@PostConstruct` or `@Resource` gets it from its CDI API or its server, as the Vidocq Servlet extension does (BUG-20261123-56).

[#rc1]
== Brought by 0.4.0-RC1 (since 0.3.0)

=== CDI

* **The request context is active for each request** — when `FoyChappeBoot` is given a `BeanManager`, Foy activates the CDI request context around each request, through the standard `RequestContextController`, so `@RequestScoped` beans work in servlets, filters and listeners, and the container fires the request context events. 0.3.0 activated it under no container, Vauban included: a `@RequestScoped` bean failed with `ContextNotActiveException` (BUG-20261010-01). The session context is not activated. xref:reference.adoc#other-containers[Other CDI containers]. Under Vauban too, since Vauban provides the built-in `RequestContextController` (link:https://codefloe.com/Vidocq/vauban/issues/147[vauban#147]): concurrent requests each get their own request-scoped instances.
* **Proven on Weld SE** — the new `foy-it-weld` module, never published, runs Foy on Chappe with Weld SE 6.0 without `foy-cdi-vauban`: servlets, filters and listeners get injection, request-scoped beans live per request (foy#18). xref:reference.adoc#other-containers[Other CDI containers].
* **`@SessionScoped` on Vauban** — the session context is active for each request: `@SessionScoped` beans live in the `HttpSession` and are destroyed with it, with the `@Initialized`, `@BeforeDestroyed` and `@Destroyed(SessionScoped.class)` events. Vauban's new `vauban-webcontexts` provides the context and `foy-cdi-vauban` drives it; nothing to configure. A session-scoped bean used to fail with `ContextNotActiveException` (foy#21). xref:reference.adoc#other-containers[Other CDI containers].
* **The contexts reach error pages, denials and async threads** — error pages, `onComplete`, security denials and the error pages of refused paths run before `requestDestroyed`, and an `AsyncContext.start()` thread gets the context listeners bound: a `@RequestScoped` or `@SessionScoped` bean used there no longer fails with `ContextNotActiveException` (BUG-20261010-07, BUG-20261010-08, BUG-20261011-07). xref:reference.adoc#other-containers[Other CDI containers].
* **`CdiContextListeners`, a service for the adapters of CDI implementations** — Foy registers the listeners a provider gives for the `BeanManager` it is given, ahead of the application's listeners. xref:reference.adoc#other-containers[Other CDI containers].
* **Weld's servlet integration runs on Foy** — `weld-servlet-core`'s initializer starts Weld, which manages the request and session contexts itself. `foy-it-weld-servlet` uses it as the reference for the session scope, and `foy-it-vauban-session` runs the same scenarios on Vauban. xref:reference.adoc#other-containers[Other CDI containers].

=== Boot

* **`FoyChappeBoot.Builder.applicationLayer(ModuleLayer)`** — the layer the JSP engine is looked up in (default `ModuleLayer.boot()`), in named modules and their ancestors only. xref:reference.adoc#optional-jsp-engine-service[JSP-engine service].
* **JSP-only applications are deployed** — `JspEngine.hasPages(ModuleLayer)`, a new default method answering `true`, is asked when the application has no servlet, filter, listener, descriptor content or initializer. `build()` is empty only when there is no engine, or it answers `false`. xref:reference.adoc#optional-jsp-engine-service[JSP-engine service].
* **`FoyChappeBoot.Builder.componentSource(Function<Class<?>, URL>)`** — attributes discovered classes to their real jar, so the exclusions of an absolute ordering and of `metadata-complete`, the application roots and the initializers hold when a harness loads several jars from one class loader (BUG-20261012-01, vidocq#228). xref:usage.adoc#native-layout-descriptors-fragments-and-resources[Native layout].
* **Requests run with the application's class loader as context class loader** — filters, servlets, pages, listeners and async runnables used to see the loader the server thread inherited, so `ResourceBundle`, `ServiceLoader` and JSTL `fmt:message` lookups through the context loader missed the application's modules outside the Vidocq runtime. The loader given to `FoyChappeBoot.Builder.classLoader` (or `DeployOptions.defaults`) is now installed for the request, at deployment and undeployment, and in a cross-context target, and the thread's own loader restored afterwards. `ServletContext.getClassLoader()` now returns that web application class loader, as the Servlet 6.1 Javadoc defines it, instead of the caller's context class loader (BUG-20261022-06, Vidocq/bodoni BOD-002). xref:reference.adoc#public-api-foychappeboot[Public API].
* **`FoyChappeBoot.Builder.defaultResponseCharacterEncoding(String)`** — the response encoding of an application whose descriptors declare none, for a runtime that wants UTF-8 by default (the Vidocq runtime does); `<response-character-encoding>` and `ServletContext.setResponseCharacterEncoding` still win. xref:reference.adoc[Reference].

=== Observability

* **`Mounted.activeSessions()` and `Mounted.listenerClassNames()`** — two read-only accessors on `FoyChappeBoot.Mounted` for dev consoles and monitoring, without reading foy-core: the live session count and the registered listeners' class names. xref:reference.adoc[Reference].

=== Security

* **The Servlet security model is enforced** — `<security-constraint>` from `web.xml` and its fragments, `@ServletSecurity` and `setServletSecurity` apply per url-pattern before any filter or servlet runs, with `<deny-uncovered-http-methods/>`, the transport guarantee (`403`, or a redirect to `confidentialPort`), `security-role-ref` and `declareRoles`. 0.3.0 parsed the descriptor constraints without enforcing them. xref:usage.adoc#application-security[Application security].
* **BASIC and FORM login** — `login-config` BASIC (realm `Restricted` by default) and FORM (`j_security_check`, server-side saved target, session id rotation); `login()`, `logout()` and `authenticate()` follow the configured mechanism. CLIENT-CERT is covered below; DIGEST is unsupported and fails closed. xref:reference.adoc#security[Security reference].
* **`IdentityStore` replaces `SecurityProvider` (API break)** — declare users with `FoyChappeBoot.builder().user(...)` (salted SHA-256 in memory) or plug an `IdentityStore`. `SecurityProvider` and `AuthenticatedUser` are removed. xref:migration.adoc#security-behaviour-changes[Migration].
* **TCK** — the `spec.security.*` family passes 59 of its 59 tests (Phase 5 exit: 22). xref:tck.adoc[TCK].

* **CLIENT-CERT authentication** — `login-config` CLIENT-CERT authenticates from the TLS client certificate: `FoyChappeBoot.Builder.certificateUser(subjectDn, roles...)` maps a subject DN (compared strictly, ignoring spacing and case) to application roles, or an `IdentityStore` overrides the new default method `validate(X509Certificate[])`. The principal name is the leaf subject in RFC 1779 form. A missing or unmapped certificate answers `403`. The listener asks for the certificate with chappe's `Server.Builder.tls(SSLContext, ClientAuth)`. xref:usage.adoc#client-cert[Client certificates].
* **The Servlet 6.1 section 3.10 TLS attributes** — `X509Certificate`, `cipher_suite`, `key_size`, `ssl_session_id` and the new `secure_protocol` are seeded on a TLS request, without firing attribute listeners. xref:reference.adoc#request-identity-and-connection[Request identity and connection].

* **The `sendError` message is escaped** — the container's error page used to write the message of `sendError(sc, msg)` as is, so an application passing a request value got a reflected cross-site scripting hole; it is now HTML-escaped (BUG-20261022-01, found by the nightly OWASP ZAP scan). xref:usage.adoc#response-semantics[Response semantics].
* **The session cookie is `SameSite=Lax`** — the session cookie carried no `SameSite` attribute, so browsers that do not default to `Lax` sent it on cross-site requests; Foy now adds `SameSite=Lax` unless the application sets a `SameSite` attribute on `SessionCookieConfig` (BUG-20261022-02, found by the nightly OWASP ZAP scan). xref:usage.adoc#sessions[Sessions].

=== TCK

* **Every test of the Servlet TCK that runs passes** — 1707 of 1714 tests run, 7 skipped (HTTP/2 server push), 0 errors (CLIENT-CERT exit: 1702). `foy-tck` now runs the JSP pages of the TCK wars with Ibarra (Jakarta Pages 4.0) plugged into Foy's JSP-engine service: it compiles them at deployment and hands Foy the engine and the layer of the compiled pages. The 3 JSP tests of `ServletContext40Tests` and the 2 FORM tests whose error page is a JSP now pass (BUG-20261011-04). Foy itself still does not depend on Ibarra. xref:tck.adoc#jsp-pages[JSP pages].

=== Streaming

* **What was flushed before an exception reaches the client** — when a servlet throws after `flushBuffer()`, the head and the bytes it had flushed are delivered before the body is aborted. They could be dropped when the abort came before the connection read them, and the client then saw the connection close before the status line (BUG-20261021-01). xref:usage.adoc#streaming-and-response-buffering[Streaming and response buffering].
* **A static text file no longer claims ISO-8859-1** — a `text/*` response written as bytes through `getOutputStream()`, as the default servlet serves files, used to carry `charset=ISO-8859-1` although the container does not know the file's encoding; the header overrode the page's own `<meta charset>` and showed UTF-8 text garbled. The `Content-Type` now names a charset only when one was set, configured with `<response-character-encoding>`, or fixed by `getWriter()`; `getCharacterEncoding()` still answers `ISO-8859-1` by default (BUG-20261022-03, found by the nightly OWASP ZAP scan). xref:usage.adoc#response-semantics[Response semantics].
* **A `Content-Type` set as a header keeps its type** — after `setHeader("Content-Type", "text/html")`, `getContentType()` could answer `null;charset=...`, and `getWriter()` could put back the type of an earlier `setContentType` on the wire. The header's media type is now recorded as `setContentType` records it (BUG-20261022-05). xref:usage.adoc#response-semantics[Response semantics].

=== Multipart and request bodies

* **Multipart is streamed** — `getParts()` parses the body while it streams in (RFC 7578): a part stays in memory up to `fileSizeThreshold`, then goes to an owner-only temporary file under the multipart `location`, deleted at the end of the request (async cycle included). `maxFileSize` and `maxRequestSize` are enforced while streaming. 0.3.0 buffered the whole body in memory and ignored the location and the threshold. xref:usage.adoc#file-upload[File upload].
* **`<multipart-config>` and `setMultipartConfig` reach the request**, like `@MultipartConfig`, and a configuration is now required: without one, `getParts()` throws `IllegalStateException`. xref:migration.adoc#request-body-behaviour-changes[Migration].
* **Form fields of a multipart body are request parameters**, with the part, request, `_charset_`, ISO-8859-1 charset order. xref:usage.adoc#file-upload[File upload].
* **An over-cap request body is no longer drained without bound** — chappe bounds the drain it performs after the response with `maxDrainSize` (1 MiB by default), so an endless chunked body is cut off (BUG-20261011-11, fixed by chappe#28).
* **Container request body limits** — `FoyChappeBoot.Builder` gains `maxChunkedRequestBodySize` (10 MiB), `maxFormBodySize` (2 MiB), `maxMultipartParts` (50) and `maxMultipartPartHeaderSize` (8 KiB); an uncaught limit answers `413` on a synchronous dispatch. xref:reference.adoc#request-body-limits[Request body limits].
* **TCK** — `PartTests` and `Part1Tests` pass 14 of 14 (Phase 6 exit: 6); the full suite then passed 1702 of 1714 tests run, 7 skipped (99.3 %), and the API signature test passes. xref:tck.adoc[TCK].
