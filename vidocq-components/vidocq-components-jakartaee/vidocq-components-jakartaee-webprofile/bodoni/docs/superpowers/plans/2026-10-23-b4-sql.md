# Bodoni B4 — `sql:` SQL library — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement the Jakarta Standard Tag Library 3.0 `sql:` library (spec §10): six classic tag handlers on the JDK's `java.sql` and `java.naming` only, their TLDs under `jakarta.tags.sql` and the legacy `http://java.sun.com/jsp/jstl/sql` URI, data-source resolution (object, JNDI relative path, JDBC parameter string), a disconnected `Result`, a Peano accessor table for `Result`, and proof that real pages using them render on Ibarra against an in-memory H2 database.

**Architecture:** JDBC plumbing with no tag tree lives in `io.vidocq.bodoni.core.internal`: the JDBC parameter string (`JdbcParameters`), an unpooled `DriverManagerDataSource` that finds drivers through the thread context class loader, string resolution JNDI-then-JDBC (`DataSources`) and the materialised result (`QueryResult implements Result`). The handlers live in the exported `io.vidocq.bodoni.core.tags.sql`; `sql:query` and `sql:update` share a package-private `ExecutionTagSupport` (statement, parameters, connection, export), and the configuration-setting and data-source glue is in a package-private `SqlSupport`. `bodoni-peano` gains a `Result` accessor table, sharing a read-only base with the `LoopTagStatus` table.

**Tech Stack:** Java 25 (`java.sql`, `javax.sql`, `javax.naming`, `java.util.ServiceLoader`), Java Modules, Maven 3.9.16, JUnit 6, H2 2.3.232 (test scope only), `jakarta.servlet.jsp.jstl-api` 3.0.2 (compile), Pages 4.0 / Servlet 6.1 / EL 6.0 APIs (provided), Peano SPI (`bodoni-peano` only).

**Spec:** `PLAN.md` (design of record: "`sql:` — DataSource resolution", "Reflection, threads", milestone B4, open questions 7 and 8) and the Jakarta Standard Tag Library 3.0 specification, §2.2, §2.8, §10 (§10.1–§10.9), <https://jakarta.ee/specifications/tags/3.0/jakarta-tags-spec-3.0.html>, with the Javadoc of `jakarta.servlet.jsp.jstl.sql.Result` and `SQLExecutionTag`. Each task cites the sections it implements; read them before writing the test.

- **No `synchronized`, no `ThreadLocal`, no platform threads.** Handler state is per instance; no `DataSource` cache, no connection pool.

## Rulings of this plan

| Topic | Ruling | Why |
|---|---|---|
| H2 in `bodoni-core` unit tests | H2 2.3.232 at test scope instead of hand-written `ResultSet` / `ResultSetMetaData` doubles; small hand-written doubles stay where a double is the better test (`CountingDataSource`, `RecordingConnection`) | `ResultSet` doubles would be large and would not check real JDBC behaviour (types from `getObject`, labels, cursor). |
| `java.sql` | `requires transitive java.sql` | Pages and application code hand `javax.sql.DataSource` objects to the actions (attribute, `Config`) and read `java.sql.Date` / `Time` / `Timestamp` values from `Result` rows; as for `java.xml` in B3, Bodoni does not rely on the API descriptor for a module it uses directly (open question 3). |
| `java.naming` | `requires java.naming` (not transitive) | Only `internal.DataSources` uses `javax.naming`; no exported signature exposes a `javax.naming` type (`dataSource` setters take `Object`). |
| Driver discovery | `uses java.sql.Driver`. `DriverManagerDataSource` captures a loader at construction: the thread context class loader, else its own class loader. Construction loads the named driver with `Class.forName(driver, true, loader)`. `getConnection` asks `ServiceLoader.load(Driver.class, loader)` for the first driver whose `acceptsURL(url)` is true and whose `connect` returns non-`null`; otherwise `DriverManager.getConnection(url, properties)` (drivers registered by hand, or visible to Bodoni's loader). A pre-JDBC 4 driver without `META-INF/services/java.sql.Driver`, in a loader Bodoni cannot see, is unsupported (documented) | `DriverManager` hands out a driver only to a caller whose loader can load it (Task 1 probe), so a WAR driver is refused when Bodoni sits in the server's lib; the same rule as Mansart's pool (mansart#42); no reflective instantiation. |
| No suitable driver | Bodoni's own `SQLException`, SQLState `08001`, **no cause** | `DriverManager`'s message repeats the full URL, which may carry `;PASSWORD=` (Task 1 probe). Driver failures after `connect` keep the driver's exception as cause. |
| String resolution | JNDI first for every string, as §10.2 orders; any `NamingException` falls back to the JDBC form; a name bound to something that is not a `DataSource` fails; a blank string fails before any lookup; another type fails | Spec order; a wrong binding is a configuration error, not "not found". |
| `sql:setDataSource` | Resolves eagerly (JNDI lookup or driver class loaded, no connection opened) and exports the resolved `DataSource`, as `var` or as `Config.SQL_DATA_SOURCE`. `dataSource` wins over `url`; neither → `JspException` | TCK `negativeSetDataSourceDataSourceAttributeDriverManagerTest` expects the exception at `sql:setDataSource`; a `DataSource` export never exposes the password as a string. |
| `Result` | Own `internal.QueryResult`, not `ResultSupport.toResult` | `ResultSupport` has no `startRow`, and how it moves the cursor is not documented. |
| Columns | Names from `ResultSetMetaData.getColumnLabel` (an `AS` alias wins); values from `getObject`; rows are unmodifiable `TreeMap`s with `String.CASE_INSENSITIVE_ORDER` (Javadoc of `Result.getRows`); a duplicated label keeps the first column in the row map; the three arrays are copied on every call | JDBC 4 labels are what page authors write; the result is a disconnected, read-only view. |
| `maxRows` / `startRow` | `maxRows` attribute, else `Config.SQL_MAX_ROWS`, else `-1`. `Statement.setMaxRows(startRow + maxRows + 1)` only when `maxRows != -1` and the `long` sum is in `[1, Integer.MAX_VALUE]`; `startRow` rows are skipped on the cursor; at most `maxRows` rows are kept, and one more row is read only to learn whether the limit cut the result. `limitedByMaxRows` is true when `maxRows != -1` and such an extra row exists (a table of exactly `maxRows` rows is not limited). Controller ruling, 2026-10-23: the spec's "limited by a maximum row setting" read literally; test both the exact and the exceeding case in Task 4. `maxRows < -1` and `startRow < 0` → `JspTagException` | §10.3: "a maximum of startRow + maxRows rows are retrieved"; `setMaxRows(0)` means "no limit" in JDBC. |
| `maxRows` setting conversion (§2.8) | `Integer` / other `Number` → `intValue()`; `String` → `Integer.parseInt(trim)`, blank → no limit; any other type, a non-integer string or a value below `-1` → `JspTagException` naming the setting and the value | A context parameter is always a `String`; an empty one means unset. |
| Statement text | `sql` attribute when set (a body then only runs nested parameter actions, its text is ignored), else the trimmed body; `null` or blank → `JspTagException` | Spec syntaxes 1–3. |
| `null` parameter | `setNull(index, type)`, `type` from `getParameterMetaData().getParameterType(index)`, `Types.NULL` when that call throws `SQLException` | §10.7 "set to the SQL value NULL"; `setObject(i, null)` is not portable. |
| Translation-time constraints | Checked at run time (no TLV, B1 precedent): `scope` without `var`, an empty `var`, and a `dataSource` attribute on `sql:query` / `sql:update` inside `sql:transaction` → `JspTagException` | TCK `negativeQueryNoVarAttributeTest`, `negativeQueryVarAttributeTest`, `negativeTx*DataSourceAttributeTest` expect a failing page. |
| `isolation`, `type` values | Exact lowercase as the spec lists them; invalid → `JspTagException` before any connection is opened | Spec §10.5, §10.8. |
| `sql:transaction` cleanup | `doFinally` restores isolation, then auto-commit, then closes, each step in its own `try`; a failure there goes to `ServletContext.log(message, cause)`, never thrown; the connection is always closed | `TryCatchFinally.doFinally` cannot throw. |
| Exceptions | Data-source and SQL failures: `JspException` with the cause; attribute errors: `JspTagException` | §10.3–§10.6 "Null & Error Handling". |
| JNDI in the IT | Not in `bodoni-it-ibarra`: unit tests cover it with the test `InitialContextFactory` | Foy has no naming implementation; a host-side one would have to reach the driver of the application layer (the split-loader case of Task 1) and prove less than the unit tests. Vidocq's naming extension (#297) brings its own IT. |

## Review Focus

1. **The JDBC password leaks into a message.** A JDBC string `jdbc:h2:mem:x;PASSWORD=s3cret,org.nope.Driver,sa,s3cret`, a `sql:setDataSource password="s3cret"` and a URL `jdbc:x://u:s3cret@h/db?password=s3cret`: no `JspException` message, cause chain Bodoni builds, `toString()` of the exported `DataSource` or `${e}` contains `s3cret`. Tests in Tasks 1, 2 and 5.
2. **SQL injection through the body.** `sql:param value="' OR '1'='1"` against `WHERE title = ?` matches no row (bound as a value); the Reference's CAUTION block shows the concatenated form as the unsafe one. Test in Task 5, block in Task 9.
3. **A resource left open on a failure path**: a syntax error, a binding error (an unsupported parameter object), a failure while reading the result, a failed `commit`, `TRANSACTION_NONE`. Every connection, statement and result set the action opened is closed. Tests in Task 4 (`RecordingConnection` counts every `close`).
4. **A handler instance reused across invocations** (Jasper and Open Liberty pool classic handlers): the parameters of the previous `sql:query`, the body of the previous invocation when the next one is an empty element, the saved isolation and auto-commit of the previous `sql:transaction`. Each stateful handler's test runs it twice on the same instance.
5. **`maxRows="0"` and a huge `startRow`**: `maxRows="0"` gives an empty `Result` (never "no limit"), `startRow=2147483647 maxRows="10"` neither overflows into a negative `setMaxRows` nor fails. Test in Task 4.
