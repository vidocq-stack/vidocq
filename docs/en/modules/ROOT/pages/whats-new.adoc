= What's new
:description: Everything that changed in this component since the {release-version} release.

[.lead]
New in the `{project-version}` development line — everything listed here landed **after the {release-version} release** and is not part of it. Every entry links to the section that documents it, and those sections carry the [.tag-new]#NEW# badge. Each brick of the suite keeps its own page of this kind; xref:home::whats-new.adoc[the ecosystem index] gathers them. When the next release train ships, this page is frozen with it and restarts empty on the dev line.

* xref:modules/vidocq-runtime-cli.adoc#extension-settings[The pool writes its connection; `config set` uncomments] — `vidocq extension add mansart-pool` and `vidocq create -x mansart-pool` append the pool's URL, user and password, commented, for everywhere the PostgreSQL dev service does not run; `vidocq config set` on a key such a block wrote commented uncomments that line in place, under its comment, instead of adding a second one at the end of the file.
* xref:modules/vidocq-runtime-cli.adoc#extension-settings[Extensions write their settings] — `vidocq extension add` and `vidocq create -x` append, once, the settings an extension needs to `vidocq.properties`: the service name, the SDK switch and a local collector for Telemetry; for JWT, commented hints for production and for a dev realm of your own, as the Keycloak dev service sets the verification keys itself. A key you set is never overwritten, and `remove` leaves the file alone. `vidocq doctor` warns about an application with JWT and no verification key.
* xref:modules/vidocq-runtime-cli.adoc#doctor-project[`vidocq doctor` checks the `opens` the build checks] — the _Module directives_ check asks for the `opens` of the resource packages an extension reads, such as Flyway's `opens db.migration`, and, once the application is compiled, those of the packages the runtime reaches by reflection (entities, REST types, interceptors), with the code `vidocq:check-module-info` runs; `--fix` writes them, the latter in the block `vidocq:complete-module-info` writes: `doctor` no longer says ✔ on a project the build then fails. Its line names no count of extensions next to the _Extensions_ check's.
* xref:modules/vidocq-runtime-maven-plugin.adoc#docker-linux-image[`vidocq build docker` on macOS and Windows] — the Dockerfile links the runtime image inside a Linux JDK when the build host is not Linux, so the image starts in its container; the CLI builds it when Docker answers (`Docker image built.`) and says the image is not built otherwise, instead of a bare _Done._. The entry point runs the image's `java`, which the shell-less distroless base needs.
* xref:modules/vidocq-runtime-cli.adoc#doctor-project[`vidocq doctor` checks the `opens` the build checks] — the _Module directives_ check asks for the `opens` of the resource packages an extension reads, such as Flyway's `opens db.migration`, as `vidocq:check-module-info` does, and `--fix` writes it: `doctor` no longer says ✔ on a project the build then fails.
* xref:modules/vidocq-runtime-extensions.adoc#flyway-opens-migrations[Flyway's folder opened at once] — `vidocq extension add flyway-migration` and `vidocq create -x flyway-migration` create `src/main/resources/db/migration` with a `README.md` and write `opens db.migration;` right away, instead of a warning asking to add the extension again once the first script exists.
* xref:modules/vidocq-runtime-maven-plugin.adoc#check-module-info-dev[`vidocq dev` opens a new package itself] — a package the runtime reaches by reflection that `module-info.java` does not open, a new package of entities or DTOs for instance, no longer stops `vidocq dev`: `check-module-info` writes the `opens` line in `module-info.java` and in the compiled descriptor, prints it and the application starts. Outside dev the failure names `vidocq doctor --fix` and `./mvnw vidocq:complete-module-info`.
* xref:modules/vidocq-runtime-maven-plugin.adoc#check-module-info-uncompiled[`check-module-info` after a compile error] — under `vidocq dev`, a compile error no longer makes the goal report a module without `module-info.java`: it says the module is not compiled yet and checks it once it is. Its messages say _Java module_, not _JPMS_.
* xref:modules/vidocq-runtime-maven-plugin.adoc#check-module-info-interceptors[Interceptor packages checked at build time] — Vauban calls interceptor methods through the provider generated in their package, so the tutorial's package-private `AuditedInterceptor` needs no `opens` any more (it failed the first request with an `IllegalAccessException`); `vidocq:check-module-info` asks for the `opens` of an interceptor's package only when a method its container calls is `private`, and `vidocq:complete-module-info` now writes every `opens` the check asks for, the JSON-B and JPA packages included.
* xref:dev-services.adoc#declared-for-you[Dev services declared for you] — `vidocq extension add`, `vidocq create` and `vidocq doctor --fix` write what the dev service of the pool, JWT or Telemetry needs: the provider on `vidocq-runtime-maven-plugin`, the provider and `vidocq-runtime-devservices-junit` in test scope for a plain `mvn test`, and the PostgreSQL driver for the pool. `vidocq doctor` and `vidocq:checkpom` warn about a missing piece; a pool without a URL and without the driver logs a `[WARNING]`, and its boot error names both ways out instead of only asking whether `vidocq.pool.url` is set.
* xref:continuous-testing.adoc[`vidocq test` reads the application's configuration] — it runs `process-classes` before `vidocq:test`, so the dev services see `vidocq.properties` on a clean project too (the Keycloak dev service started on realm `master` instead of the configured one).
* xref:modules/vidocq-runtime-maven-plugin.adoc#jlink-modularize[jlink and docker with Flyway or a JDBC driver] — `vidocq:jlink` gives the automatic modules of the dependencies their module descriptor before linking, so an application with Flyway or the PostgreSQL driver builds its image without a hand-run `vauban:modularize`; `vidocq build docker` builds that image first.
* xref:modules/vidocq-runtime-extensions.adoc#mansart-data-dialects[Mansart Data brings its SQL dialects] — the H2 and PostgreSQL dialects come with `vidocq-runtime-mansart-data-extension`, so the application no longer declares one; a database without a dialect fails the boot with a message naming it, not the first query.
* xref:dev-console.adoc[JDQL examples name your entities] — the Mansart Data panel's query editor and CSV export show `FROM <your first entity> ORDER BY <its id>` as their example, instead of a `Product` entity few applications have.
* xref:dev-services.adoc[Startup report under `vidocq dev`] — without any dev service, the section says _no dev service configured_ instead of _not started by vidocq:dev_.
* xref:modules/vidocq-runtime-extensions.adoc#mansart-data-apis[Entities and tracing compile without extra `requires`] — the Mansart Data extension brings the Jakarta Persistence API and exports it with Jakarta Data, and the Telemetry extension exports the OpenTelemetry API and `@WithSpan`: a created application no longer adds `jakarta.persistence-api`, `requires jakarta.persistence`, `requires io.opentelemetry.api` or `requires io.opentelemetry.instrumentation_annotations` by hand.
* xref:continuous-testing.adoc#terminal[Failed tests named under `vidocq dev`] — a red run prints each failed test, the reason and the line of the test where it failed, then the log, instead of the counts alone; `vidocq:test` adds the line too.
* xref:modules/vidocq-runtime-maven-plugin.adoc#first-build[`vidocq dev` survives a first build that does not compile] — it reports the error and builds again on the next change, instead of exiting.
* xref:modules/vidocq-runtime-extensions.adoc#jdbc-telemetry[Database spans] — with Telemetry and the JDBC pool, each SQL statement is a span in the request's trace, named and described per the OpenTelemetry database conventions; the new `vidocq-runtime-mansart-pool-telemetry-extension` (`jdbc-telemetry`) comes with the pair when `vidocq extension add` or `vidocq create` sees both.
* xref:modules/vidocq-runtime-extensions.adoc#mansart-pool-connection-decorators[A hook on every JDBC connection] — `JdbcConnectionDecorator`, a service of the Mansart Pool extension, wraps each connection the Vidocq DataSources hand out; the first step towards database spans in traces.
* xref:modules/vidocq-runtime-maven-plugin.adoc#check-module-info-reflected[A package JSON-B or JPA needs is checked at build time] — `vidocq:check-module-info` reads the compiled classes and fails the build, with the `opens` line to add, when a package holding an entity or a type a REST resource returns is neither opened nor exported; it used to fail at the first request.
* xref:modules/vidocq-runtime-cli.adoc[`--help` on every command] — `vidocq build --help`, `vidocq extension add --help`… show the command's help instead of refusing the option. The start-up list of extensions also names the extensions that bring only a CDI extension (JWT, Rest Client, Fault Tolerance, Config), marked _CDI only_.
* xref:modules/vidocq-runtime-extensions.adoc[No test library in a packaged application] — the Telemetry extension no longer brings `opentelemetry-sdk-testing`: Humboldt maps its spans to its own `SpanData`, and the jar leaves the `lib/` of `vidocq build`.
* xref:modules/vidocq-runtime-cli.adoc#create-snapshot[SNAPSHOTs also on maven.vidocq.dev] — every build of `main` publishes the Vidocq SNAPSHOTs to `https://maven.vidocq.dev/snapshots/`, copied every 10 minutes to `maven.bak.vidocq.dev`, which takes over when the first is down, then to Central's snapshot repository as before. `vidocq create` declares our two repositories, and `vidocq update` reads the first. A project that declares `central-snapshots` changes nothing. Releases stay on Maven Central.
* xref:migration.adoc#metrics-openapi-codegen[JWT gets a codegen bundle; the Metrics and OpenAPI bundles complete] — `vidocq-runtime-cervantes-jwt-extension-codegen` puts Cervantes' Build Compatible Extension on the processor path, and the Metrics and OpenAPI bundles now bring `DiracExtension` and `GrimmExtension`: an application with these extensions builds without Vauban's warning that their extensions _will not run_. `vidocq:checkpom` asks for the JWT bundle; `vidocq extension add` writes it.
* xref:testing.adoc#dev-services[`@VidocqTest` uses the dev services] — the application a test starts gets the keys of the dev services `vidocq test`, `vidocq dev` or the `vidocq-runtime-devservices-junit` listener started, so it runs on the dev database instead of the one `vidocq.properties` names.
* xref:dev-services.adoc[Keycloak dev service coordinates] — `target/vidocq-dev-services.properties` and the console block list `keycloak.issuer`, `keycloak.token-url` and `keycloak.admin-console`; `vidocq.dev.keycloak.port` pins the port, so the issuer stays the same across starts; the startup report and the dev console show the token endpoint and the admin login. See `DEV_SERVICES.md`, "Connection information".
* xref:modules/vidocq-runtime-extensions.adoc#flyway-opens-migrations[`extension add flyway-migration` opens `db.migration`] — once the project has a migration; before that it says where the migrations go.
* xref:modules/vidocq-runtime-maven-plugin.adoc#launcher-java-opts[`JAVA_OPTS` in the launchers] — `bin/<app>.sh` and `.cmd` pass `JAVA_OPTS` to the JVM, so a packaged application takes `-Xmx` or a `-D` without editing the script.
* xref:testing.adoc#request-headers[`@VidocqTest` requests with headers] — `VidocqApplication.get(path, headers)` and `request(method, path, headers, contentType, body)` send a bearer token or any other header.
* xref:migration.adoc#metrics-openapi-codegen[Fault Tolerance needs its codegen bundle] — `vidocq-runtime-heisenberg-fault-tolerance-extension-codegen` runs Heisenberg's processor on the application: the Fault Tolerance annotations are read from build-time companions, not by reflection, and the start-up warning _read by reflection_ goes away. `vidocq:checkpom` asks for it; `vidocq extension add` writes it.
* xref:testing.adoc#runtime-dependencies[`@VidocqTest` sees the runtime dependencies] — the application a test starts gets every `runtime`-scope jar on its module path, as `vidocq:dev` does: a JDBC driver is found without `requires`. The new `vidocq:test-path` goal, bound by `vidocq-runtime-parent`, names them for Surefire.
* xref:dev-services.adoc#host-log[Dev services log through the build] — under `vidocq dev`, `vidocq:run`, `vidocq:test` and a plain `mvn test` (the `vidocq-runtime-devservices-junit` listener), a dev service logs one `[INFO]` line like the rest of the build, instead of the JDK's two-line format in the machine's language.
* xref:migration.adoc#metrics-openapi-codegen[Metrics and OpenAPI need their codegen bundle] — the Metrics and OpenAPI extensions ship a `-codegen` bundle that runs Dirac's and Grimm's processors on the application: metrics and the OpenAPI document come from build-time companions instead of a scan by reflection at start-up. `vidocq:checkpom` asks for both bundles.
* xref:dev-services.adoc[Dev services] — `vidocq-runtime-devservice-otel` starts an OpenTelemetry collector with Grafana (`grafana/otel-lgtm`) for an application with MicroProfile Telemetry, and publishes `otel.exporter.otlp.endpoint`; Grafana's URL is in the startup report and the dev console.
