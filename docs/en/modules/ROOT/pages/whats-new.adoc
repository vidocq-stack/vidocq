= What's new
:description: Everything that changed across the Vidocq ecosystem since the {release-version} release.

[.lead]
New in the `{project-version}` development line — everything listed here landed **after the {release-version} release** and is not part of it. Sections carrying the [.tag-new]#NEW# badge across the documentation point to these features. When the next release train ships, this page is frozen with it and restarts empty on the dev line.

== Vidocq Runtime

* **Startup banner with the exact Vidocq version** — every boot tells which Vidocq starts, once per JVM, before anything later can fail: `Vidocq 0.4.0-SNAPSHOT (9beafc47+dirty, built 2026-09-17T14:02:11Z)`, then the Java version, the profile or dev launch, and the application. A terminal, a dev profile or IntelliJ's Run console get the art on standard output; containers, CI, pipes and tests get one log line. `vidocq.banner.mode=auto|console|log|off`, a custom `vidocq-banner.txt` with placeholders, and `VidocqBootstrap.banner(BannerMode.OFF)` for embedders. `vidocq dev` now starts its spinner after the banner. xref:modules/vidocq-runtime-core.adoc#startup-banner[Startup banner].
* **The launch mode, and the debugger, in the startup identity** — every boot says which of `dev`, `test` and `prod` it is, with the signal it was read from: `Java 25+36-LTS | dev (IntelliJ agent) | debug *:5005 | mcp-time-server 0.1.0-SNAPSHOT`. `prod` never shows without `(no dev or test signal)`, since nothing proves it. A JVM started with `-agentlib:jdwp=…` shows the address a debugger has to attach to, in every mode, and repeats it on a `Vidocq debugger: attach to …` record when the 80 columns of the banner could not hold it. Neither the mode nor the address is ever lost to the JVM vendor, which the line gives up first. `vidocq.launch.mode=dev|test|prod` forces the mode; it changes what is printed, nothing else. xref:modules/vidocq-runtime-core.adoc#launch-mode[Launch mode].
* **Build identity in every jar** — `vidocq-parent` writes `META-INF/vidocq/build-info/<artifactId>.properties` (version, abbreviated commit, dirty flag, commit time, and build time outside releases, which stay reproducible), so two snapshots with the same version are told apart. xref:modules/vidocq-runtime-core.adoc#build-identity[Build identity].
* **Every Java 25 main shape starts the application** — when Vidocq picks the main itself, it now picks the one `java` would: `main(String[])` and `main()`, static or an instance method, public or not, declared in the class, inherited from a superclass, or a `default` method of an implemented interface. The selection mirrors the launcher's, down to the parts nobody guesses — a declared main ends the search even when it cannot be used, so a `private main(String[])` sends the launch to `main()`. An IDE on JDK 25 flags the `public` of a main as an unnecessary modifier: following that advice no longer makes `vidocq:run` fail. A `private` or non-`void` main is named as such, with the class that declares it, instead of being reported as a missing main (Vidocq/vidocq#88). xref:modules/vidocq-runtime-core.adoc#main-shapes[Which main methods are accepted].
* **Readable console logs by default** — when the application has not configured logging, Vidocq replaces the JDK's two-line records on standard error (red in an IDE) with one aligned line per record on standard output: `[LEVEL][timestamp][thread][class#method] : message`, with a coloured level on a terminal or in IntelliJ's Run console. Any logging setup of the application wins (`logging.properties`, an SLF4J or Log4j bridge, `vidocq.log.console=jdk`); `vidocq.console.color` and `NO_COLOR` control the colours. The examples no longer carry their own copies of a stdout handler and formatter. xref:modules/vidocq-runtime-core.adoc#console-logging[Console logging].

== Vauban

Client proxies for third-party produced types, without `opens` (vauban#42, the jakartaee/cdi#1015 case):

* **Java SE launcher and placed proxies** — `java -p mods --add-modules ALL-MODULE-PATH -m io.vidocq.vauban.classloader/io.vidocq.vauban.classloader.Launch app/app.Main` runs the application inside a Vauban layer (`--add-modules` is required: with `-m`, the launcher is the only root module). There, a client proxy that must live in a third-party type's package is *placed* into it by the loader that now owns that package — zero `opens`, no agent, no rewritten jar — and the third-party constructors do not run for the proxy (vauban#24, extended to types you do not compile). Unwoven beans are woven at definition, so IDE runs no longer need the load-time agent. xref:vauban::se.adoc[Vauban in Java SE], xref:vauban::internals.adoc#proxy-strategies[client-proxy strategies].
* **`Vidocq.run` places proxies too** — the trampoline re-layers with the launcher's policy: every module moves except the Vidocq bricks, the platform and Jakarta modules, automatic modules, modules with a `javax.`, `sun.` or `com.sun.` package, and what those kept modules read. A CDI-agnostic library that only the application reads now moves with it, so its in-package proxies are placed as well; before, only modules carrying a beans list moved (vauban#53). xref:usage.adoc[Usage].
* **Build-time proxies for cross-module producers** — a fully-public class or an interface produced from a CDI-agnostic module gets its proxy at compile time in the producer's package; no `java.lang.reflect.Proxy` on the build-time path. The eligibility check covers inherited members.
* **`vauban:enhance-dependencies`** (opt-in) — a copy of a dependency jar with the proxy co-located in the type's package; the copy records its provenance in the manifest (`Vauban-Enhanced-From`, `Vauban-Enhanced-Digest`) and drops the inherited signature. The AOT path when a placed class cannot be defined at runtime.
* **Boot-time opens are opt-in** — `-Dvauban.opens.auto=true`; left off, the container refuses and names every remedy, the launcher first. xref:vauban::reference.adoc[Reference].

== Vidocq Runtime

* **`vidocq:run`** — one run of the application, in a JVM forked as the production launcher does, after the goal has forked the lifecycle up to `process-classes`: `mvn vidocq:run` alone compiles, completes the bean index with `vidocq:generate` and starts the application. Ctrl+C stops it, its exit code is the goal's result, `-Dvidocq.run.debug=true` opens a JDWP agent, and a `-Dvidocq.*` of the command line reaches the application. xref:modules/vidocq-runtime-maven-plugin.adoc#run[The `vidocq:run` goal].
* **Maven's colours reach the forked JVM** — `vidocq:run` and `vidocq:dev` pass Maven's own colour policy to the application as `-Dvidocq.console.color`. In an IDE's Maven console, which is neither a terminal nor an IntelliJ Run console, the runtime used to drop its colours while Maven's `[INFO]` lines kept theirs. An explicit `vidocq.console.color` and `NO_COLOR` still win. xref:modules/vidocq-runtime-maven-plugin.adoc#run-colours[Colours in the forked JVM].
* **`vidocq:idea`** (experimental) — one IntelliJ IDEA shared run configuration per application of the reactor, written into `.run/` from what the poms already declare. By default it is a **Maven** run of `vidocq:run` on the application's pom (`vidocq.idea.kind=application` writes the Application run of the main class, with Make and `vidocq:generate` before launch): clicking Run then compiles, indexes and starts the application through Maven, because the IDE's own build never runs `vidocq:generate` (Vidocq/vidocq#83). It never overwrites a file you wrote or edited, never touches `.idea/`, and `-Dvidocq.idea.check=true` fails a CI build when `.run/` no longer matches the poms (`=strict` also fails on the files you wrote or edited). xref:modules/vidocq-runtime-maven-plugin.adoc#idea[The `vidocq:idea` goal].
