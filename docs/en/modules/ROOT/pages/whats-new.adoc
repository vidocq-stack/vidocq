== Added in 0.4.0-RC2 (since 0.4.0-RC1)

* xref:crac.adoc[Checkpoint and restore (CRaC)] — a page on starting an application from a snapshot of a warmed-up process: the JDK and extension it takes, how to take a checkpoint and restore it, what Vidocq lets go of and in which order, and what an image does not keep.
* xref:crac.adoc#application-events[`Checkpoint` and `Restore` events] — the application lets go of its own resources before a checkpoint (a client, an open file) and takes them back after the restore, by observing two CDI events of `vidocq-runtime-spi`, with no `jdk.crac` in its code. They run after the HTTP server stopped taking requests and while the pool is still open (vidocq#496).
* xref:modules/vidocq-runtime-extensions.adoc#ravel-config-release[`vidocq dev` frees the configuration of a stopped layer] — the Config extension takes the layer's MicroProfile Config out of Ravel's registry at stop, so a hot reload no longer keeps the previous application layer in memory.
* xref:continuous-testing.adoc#once[`vidocq test --once`] — runs every test once and exits with the verdict (status 1 when a test fails), for CI and scripts, instead of watching the sources.
* xref:internals.adoc#generated-code[Generated code and reflective fallback] — what Vidocq does so the bricks' generators run on every build (the codegen bundles on the processor path, `vidocq:generate` for the dependency jars, the generate stamp), a table of every bundle with the processors it brings and a link to the matching section of each brick, and how to tell which path ran.
* xref:modules/vidocq-runtime-extensions.adoc#pages-cdi-beans[A JSP reads a `@Named` CDI bean by name] — `${cart.total}` resolves the bean `cart` in its scope, as Jakarta EE requires; it went unresolved before (BUG-20261102-05).
* xref:modules/vidocq-runtime-extensions.adoc#mansart-data-catalogue[No Mansart Data catalogue in production] — the catalogue of repositories and entities, read by reflection, is built only when the dev console or a startup report in dev or at `detailed` asks for it; a production boot reports the number of repositories. The pool's `DataSource` holder and the Telemetry holder are created by a registered factory instead of their constructor by reflection.
* xref:modules/vidocq-runtime-extensions.adoc#peano-auto-accessors[EL without reflection for named beans] — Peano generates the accessor tables of the `@Named` and `@Model` beans an expression reaches and of the types their properties hold, without `@ELAccessible`; the Peano EL extension lets a normal-scoped bean's table serve its Vauban client proxy (BUG-20261102-03).
* xref:ravel::cdi-integration.adoc#generated-code[`@ConfigProperties` and implicit converters without reflection] — the Config codegen bundle now runs Ravel's processor: each `@ConfigProperties` class of the application gets a generated factory and each injected type with a `parse`, `of` or `valueOf` method a generated converter, so Ravel fills and converts them with plain code and their packages need no `opens`. A class the processor cannot handle keeps the reflective path, unchanged.
* xref:java-modules.adoc#entities[Entities and repositories need no `opens`] — Mansart reaches the entity models, the repository implementations and the records a JDQL query projects into through code its processor generates (mansart#74), so `vidocq:check-module-info` and `vidocq doctor` no longer ask to open a package of entities that has a generated model; they still ask when Mansart would fall back to reflection, and call such a class an _entity (Jakarta Data)_, not a _JPA entity_.
* xref:modules/vidocq-runtime-maven-plugin.adoc#generate[`vidocq:generate` on every build] — `vidocq-runtime-parent` runs the goal on every build of an application, so the dependency jars get the code their bricks generate for them — beans, `@Repository` implementations, servlets — with no goal to declare; `@VidocqTest` starts the application on the enriched copies too. `-Dvidocq.generate.skip` turns it off; `vidocq doctor` reports whether the build runs it, and `vidocq:checkpom` names an execution of the pom that declares it again.
* xref:modules/vidocq-runtime-maven-plugin.adoc#brick-processors[`@Repository` interfaces from a library] — `vidocq:generate` runs Mansart's processor over the dependency jars that ship Jakarta Data repositories: their implementations go into the jar's enriched copy, as for the application's own (mansart#40).
* xref:java-modules.adoc#json-b-at-build-time[CDI beans as JSON-B adapters, checked at build] — the REST extension brings Champollion's `champollion-jsonb-cdi`: the generated bindings and the runtime get adapters, serializers and deserializers from the application's container, one per application and destroyed when it stops, and an adapter that injects without being a bean, or an ambiguous one, fails the build.
* xref:java-modules.adoc#limits[The entity of a `Response` is no longer a surprise at the first request] — the entity a resource or an exception mapper gives `Response.ok(…)`, `ResponseBuilder.entity(…)` or a `GenericEntity<T>` gets its JSON-B binding at build time, and the module check opens its package when no binding can be generated: a production build no longer passes with an endpoint that fails on its first call.
* xref:java-modules.adoc#json-b-at-build-time[JSON-B without reflection for the DTOs of a library] — the types of a dependency jar that your resources take or return get their JSON-B binding at build time too: `vidocq:generate` runs Champollion's processor over that jar and writes the bindings into its enriched copy, so the library needs no `opens` for JSON-B. Bricks can now select dependency jars from a list the application's compilation writes (`application-classes` in `dependency-codegen.properties`).
* xref:java-modules.adoc#json-b-at-build-time[More DTOs without reflection] — date and number formats, arrays, `@JsonbTypeAdapter`, `@JsonbTypeSerializer`/`@JsonbTypeDeserializer`, `@JsonbCreator` and `@JsonbTypeInfo` on a sealed interface over records are now generated too, with no `opens`.
* xref:java-modules.adoc#json-b-at-build-time[JSON-B without reflection for plain classes too] — the classes a resource exchanges get their JSON-B binding generated even when they are not `final` or extend a base class: a classic `Product extends BaseEntity` with getters and setters needs no `opens` any more. A subclass returned under its declared type needs nothing either.
* xref:java-modules.adoc#json-b-at-build-time[JSON-B without reflection for records and final classes] — the REST codegen bundle now runs Champollion's processor: the records and final classes a resource takes or returns get their JSON-B binding at build time, so JSON-B maps them with no reflection, their packages need no `opens`, and `vidocq:check-module-info` and `vidocq doctor` no longer ask for one. A type that keeps the reflective mapping is named in the build output with the reason.
* xref:java-modules.adoc#what-is-detected[The build check follows superclasses and implementations] — a DTO or an entity that extends a class of another package of the application, or a field typed by an application interface or abstract class, now gets the packages of that superclass or of those implementations opened, where the first request used to fail.
* xref:modules/vidocq-runtime-cli.adoc#extension-required[`extension add mansart-data` brings the pool] — Mansart Data reads the pool's DataSource, so `vidocq extension add mansart-data` and `vidocq create -x mansart-data` add `mansart-pool` with its dev service, driver and test block; `remove` keeps the pool and says how to drop it; `vidocq doctor` warns when it is missing.
* xref:java-modules.adoc#open-module[`vidocq create --open-module`] — the application can be an `open module`, which opens every package to reflection: no `opens` line is ever written or asked for, by `extension add`, `vidocq dev`, `doctor --fix`, `vidocq:complete-module-info` or the build check. `vidocq doctor --fix` removes the `opens` lines of a module made open by hand, which javac refuses.
* xref:java-modules.adoc#runtime-message[A clear error for any package a library cannot reach] — when a library fails to reach a package of the application by reflection at run time (JSON-B called by hand, a third-party library: cases the build check cannot see), the logged failure is followed by one error naming the package and the `opens` line to add; under `vidocq dev` the plugin writes the line and the application reloads. A new page, xref:java-modules.adoc[Java modules in a Vidocq application], explains what the tooling detects and writes, and what it cannot see.
* xref:modules/vidocq-runtime-cli.adoc#module-info-layout[One layout for `module-info.java`] — the packages opened for reflection go in one block, last, each line marked `// vidocq:reflection`, which `doctor --fix`, `vidocq:complete-module-info` and `vidocq dev` extend; `vidocq extension add` puts its lines with the other extensions'. A file with several blocks, from earlier versions, is merged on the next write.
* xref:modules/vidocq-runtime-cli.adoc#extension-settings[The pool writes its connection; `config set` uncomments] — `vidocq extension add mansart-pool` and `vidocq create -x mansart-pool` append the pool's URL, user and password, commented, for everywhere the PostgreSQL dev service does not run; `vidocq config set` on a key such a block wrote commented uncomments that line in place, under its comment, instead of adding a second one at the end of the file.
* xref:modules/vidocq-runtime-cli.adoc#extension-settings[Extensions write their settings] — `vidocq extension add` and `vidocq create -x` append, once, the settings an extension needs to `vidocq.properties`: the service name, the SDK switch and a local collector for Telemetry; for JWT, commented hints for production and for a dev realm of your own, as the Keycloak dev service sets the verification keys itself. A key you set is never overwritten, and `remove` leaves the file alone. `vidocq doctor` warns about an application with JWT and no verification key.
* xref:modules/vidocq-runtime-cli.adoc#doctor-project[`vidocq doctor` checks the `opens` the build checks] — the _Module directives_ check asks for the `opens` of the resource packages an extension reads, such as Flyway's `opens db.migration`, and, once the application is compiled, those of the packages the runtime reaches by reflection (entities, REST types, interceptors), with the code `vidocq:check-module-info` runs; `--fix` writes them, the latter in the block `vidocq:complete-module-info` writes: `doctor` no longer says ✔ on a project the build then fails. Its line names no count of extensions next to the _Extensions_ check's.
* xref:modules/vidocq-runtime-maven-plugin.adoc#docker-linux-image[`vidocq build docker` on macOS and Windows] — the Dockerfile links the runtime image inside a Linux JDK when the build host is not Linux, so the image starts in its container; the CLI builds it when Docker answers (`Docker image built.`) and says the image is not built otherwise, instead of a bare _Done._. The entry point runs the image's `java`, which the shell-less distroless base needs.
* xref:modules/vidocq-runtime-extensions.adoc#flyway-opens-migrations[Flyway's folder opened at once] — `vidocq extension add flyway-migration` and `vidocq create -x flyway-migration` create `src/main/resources/db/migration` with a `README.md` and write `opens db.migration;` right away, instead of a warning asking to add the extension again once the first script exists.
* xref:modules/vidocq-runtime-maven-plugin.adoc#check-module-info-dev[`vidocq dev` opens a new package itself] — a package the runtime reaches by reflection that `module-info.java` does not open, a new package of entities or DTOs for instance, no longer stops `vidocq dev`: `check-module-info` writes the `opens` line in `module-info.java` and in the compiled descriptor, prints it and the application starts. Outside dev the failure names `vidocq doctor --fix` and `./mvnw vidocq:complete-module-info`.
* xref:modules/vidocq-runtime-maven-plugin.adoc#check-module-info-uncompiled[`check-module-info` after a compile error] — under `vidocq dev`, a compile error no longer makes the goal report a module without `module-info.java`: it says the module is not compiled yet and checks it once it is. Its messages say _Java module_, not _JPMS_.
* xref:modules/vidocq-runtime-maven-plugin.adoc#check-module-info-interceptors[Interceptor packages checked at build time] — Vauban calls interceptor methods through the provider generated in their package, so the tutorial's package-private `AuditedInterceptor` needs no `opens` any more (it failed the first request with an `IllegalAccessException`); `vidocq:check-module-info` asks for the `opens` of an interceptor's package only when a method its container calls is `private`, and `vidocq:complete-module-info` now writes every `opens` the check asks for, the JSON-B and entity packages included.
* xref:dev-services.adoc#declared-for-you[Dev services declared for you] — `vidocq extension add`, `vidocq create` and `vidocq doctor --fix` write what the dev service of the pool, JWT or Telemetry needs: the provider on `vidocq-runtime-maven-plugin`, the provider and `vidocq-runtime-devservices-junit` in test scope for a plain `mvn test`, and the PostgreSQL driver for the pool. `vidocq doctor` and `vidocq:checkpom` warn about a missing piece; a pool without a URL and without the driver logs a `[WARNING]`, and its boot error names both ways out instead of only asking whether `vidocq.pool.url` is set.
* xref:continuous-testing.adoc[`vidocq test` reads the application's configuration] — it runs `process-classes` before `vidocq:test`, so the dev services see `vidocq.properties` on a clean project too (the Keycloak dev service started on realm `master` instead of the configured one).
* xref:modules/vidocq-runtime-maven-plugin.adoc#jlink-modularize[jlink and docker with Flyway or a JDBC driver] — `vidocq:jlink` gives the automatic modules of the dependencies their module descriptor before linking, so an application with Flyway or the PostgreSQL driver builds its image without a hand-run `vauban:modularize`; `vidocq build docker` builds that image first.
* xref:modules/vidocq-runtime-extensions.adoc#mansart-data-dialects[Mansart Data brings its SQL dialects] — the H2 and PostgreSQL dialects come with `vidocq-runtime-mansart-data-extension`, so the application no longer declares one; a database without a dialect fails the boot with a message naming it, not the first query.
* xref:dev-console.adoc[JDQL examples name your entities] — the Mansart Data panel's query editor and CSV export show `FROM <your first entity> ORDER BY <its id>` as their example, instead of a `Product` entity few applications have.
* xref:dev-services.adoc[Startup report under `vidocq dev`] — without any dev service, the section says _no dev service configured_ instead of _not started by vidocq:dev_.
* xref:modules/vidocq-runtime-extensions.adoc#mansart-data-apis[Entities and tracing compile without extra `requires`] — the Mansart Data extension brings the Jakarta Persistence API and exports it with Jakarta Data, and the Telemetry extension exports the OpenTelemetry API and `@WithSpan`: a created application no longer adds `jakarta.persistence-api`, `requires jakarta.persistence`, `requires io.opentelemetry.api` or `requires io.opentelemetry.instrumentation_annotations` by hand.
* xref:continuous-testing.adoc#terminal[Failed tests named under `vidocq dev`] — a red run prints each failed test, the reason and the line of the test where it failed, then the log, instead of the counts alone; `vidocq:test` adds the line too.
* xref:modules/vidocq-runtime-maven-plugin.adoc#first-build[`vidocq dev` survives a first build that does not compile] — it reports the error and builds again on the next change, instead of exiting.
* xref:modules/vidocq-runtime-extensions.adoc#jdbc-telemetry[Database spans] — with Telemetry and the JDBC pool, each SQL statement is a span in the request's trace, named and described per the OpenTelemetry database conventions; the new `vidocq-runtime-mansart-pool-telemetry-extension` (`jdbc-telemetry`) comes with the pair when `vidocq extension add` or `vidocq create` sees both.
* xref:modules/vidocq-runtime-extensions.adoc#mansart-pool-connection-decorators[A hook on every JDBC connection] — `JdbcConnectionDecorator`, a service of the Mansart Pool extension, wraps each connection the Vidocq DataSources hand out; the first step towards database spans in traces.
* xref:modules/vidocq-runtime-maven-plugin.adoc#check-module-info-reflected[A package JSON-B or JPA needs is checked at build time] — `vidocq:check-module-info` reads the compiled classes and fails the build, with the `opens` line to add, when a package holding an entity or a type a REST resource returns is neither opened nor exported; it used to fail at the first request.
* xref:modules/vidocq-runtime-cli.adoc[`--help` on every command] — `vidocq build --help`, `vidocq extension add --help`… show the command's help instead of refusing the option. The start-up list of extensions also names the extensions that bring only a CDI extension (JWT, Rest Client, Fault Tolerance, Config), marked _CDI only_.
* xref:modules/vidocq-runtime-extensions.adoc[No test library in a packaged application] — the Telemetry extension no longer brings `opentelemetry-sdk-testing`: Humboldt maps its spans to its own `SpanData`, and the jar leaves the `lib/` of `vidocq build`.
* xref:modules/vidocq-runtime-cli.adoc#create-snapshot[SNAPSHOTs also on maven.vidocq.dev] — every build of `main` publishes the Vidocq SNAPSHOTs to `https://maven.vidocq.dev/snapshots/`, copied every 10 minutes to `maven.bak.vidocq.dev`, which takes over when the first is down, then to Central's snapshot repository as before. `vidocq create` declares our two repositories, and `vidocq update` reads the first. A project that declares `central-snapshots` changes nothing. Releases stay on Maven Central.
* xref:migration.adoc#metrics-openapi-codegen[JWT gets a codegen bundle; the Metrics and OpenAPI bundles complete] — `vidocq-runtime-cervantes-jwt-extension-codegen` puts Cervantes' Build Compatible Extension on the processor path, and the Metrics and OpenAPI bundles now bring `DiracExtension` and `GrimmExtension`: an application with these extensions builds without Vauban's warning that their extensions _will not run_. `vidocq:checkpom` asks for the JWT bundle; `vidocq extension add` writes it.
* xref:testing.adoc#dev-services[`@VidocqTest` uses the dev services] — the application a test starts gets the keys of the dev services `vidocq test`, `vidocq dev` or the `vidocq-runtime-devservices-junit` listener started, so it runs on the dev database instead of the one `vidocq.properties` names.
* xref:dev-services.adoc[Keycloak dev service coordinates] — `target/vidocq-dev-services.properties` and the console block list `keycloak.issuer`, `keycloak.token-url` and `keycloak.admin-console`; `vidocq.dev.keycloak.port` pins the port, so the issuer stays the same across starts; the startup report and the dev console show the token endpoint and the admin login. See `DEV_SERVICES.md`, "Connection information".
* xref:modules/vidocq-runtime-extensions.adoc#flyway-opens-migrations[`extension add flyway-migration` opens `db.migration`] — once the project has a migration; before that it says where the migrations go.
* xref:modules/vidocq-runtime-maven-plugin.adoc#launcher-java-opts[`JAVA_OPTS` in the launchers] — `bin/<app>.sh` and `.cmd` pass `JAVA_OPTS` to the JVM, so a packaged application takes `-Xmx` or a `-D` without editing the script.
* xref:testing.adoc#request-headers[`@VidocqTest` requests with headers] — `VidocqApplication.get(path, headers)` and `request(method, path, headers, contentType, body)` send a bearer token or any other header.
* xref:migration.adoc#metrics-openapi-codegen[Fault Tolerance needs its codegen bundle] — `vidocq-runtime-heisenberg-fault-tolerance-extension-codegen` runs Heisenberg's processor on the application: the Fault Tolerance annotations are read from build-time companions, not by reflection, and the start-up warning _read by reflection_ goes away. `vidocq:checkpom` asks for it; `vidocq extension add` writes it.
* xref:testing.adoc#runtime-dependencies[`@VidocqTest` sees the runtime dependencies] — the application a test starts gets every `runtime`-scope jar on its module path, as `vidocq:dev` does: a JDBC driver is found without `requires`. The new `vidocq:test-path` goal, bound by `vidocq-runtime-parent`, names them for Surefire.
* xref:dev-services.adoc#host-log[Dev services log through the build] — under `vidocq dev`, `vidocq:run`, `vidocq:test` and a plain `mvn test` (the `vidocq-runtime-devservices-junit` listener), a dev service logs one `[INFO]` line like the rest of the build, instead of the JDK's two-line format in the machine's language.
* xref:migration.adoc#metrics-openapi-codegen[Metrics and OpenAPI need their codegen bundle] — the Metrics and OpenAPI extensions ship a `-codegen` bundle that runs Dirac's and Grimm's processors on the application: metrics and the OpenAPI document come from build-time companions instead of a scan by reflection at start-up. `vidocq:checkpom` asks for both bundles.
* xref:dev-services.adoc[Dev services] — `vidocq-runtime-devservice-otel` starts an OpenTelemetry collector with Grafana (`grafana/otel-lgtm`) for an application with MicroProfile Telemetry, and publishes `otel.exporter.otlp.endpoint`; Grafana's URL is in the startup report and the dev console.

== Brought by 0.4.0-RC1 (since 0.3.0)

=== Runtime

* **A SNAPSHOT build of a Vaadin application needs `<pluginRepositories>`** — `vidocq-runtime-maven-plugin` is a build extension, which Maven resolves from the plugin repositories only: a pom, or a `settings.xml`, that declares `central-snapshots` under `<repositories>` alone finds the parent and then stops with _Unresolveable build extension_ on a machine whose `~/.m2` does not hold the plugin yet. The Vaadin guide shows both blocks and says it concerns SNAPSHOTs only; a release comes from Maven Central. xref:vaadin.adoc#snapshot-repositories[Building against a SNAPSHOT].
* **The parent manages `vauban-maven-plugin`** — `vidocq-runtime-parent` pins `vauban:modularize` to the Vauban the runtime is built on and defines `vauban.version` again, which it lost when it stopped being the reactor's root (Vidocq/vidocq#348): a `vidocq:jlink` profile that wrote `<version>${vauban.version}</version>` no longer made the pom unreadable. An application now declares the plugin without a version (BUG-20261025-02). xref:modules/vidocq-runtime-maven-plugin.adoc#modularize[`modularize` moved to the Vauban plugin], xref:vaadin.adoc#jlink[Vaadin in a jlink image].
* **An extension is one dependency: the plugin wires its codegen bundle** — `vidocq-runtime-parent` loads `vidocq-runtime-maven-plugin` as a build extension, which puts the Vauban indexer and the codegen bundle of each extension the application depends on on the compiler's processor path. The `maven-compiler-plugin` block of an application goes away; `vidocq create` and `vidocq extension add` no longer write it under a 0.4.0 parent, and a path already in the pom is kept, not doubled. IntelliJ IDEA's Maven import runs the plugin too, so its build gets the same processors. An application with a parent of its own declares the plugin with `<extensions>true</extensions>` (Vidocq/vidocq#339). xref:modules/vidocq-runtime-maven-plugin.adoc#codegen-wiring[The plugin wires the codegen bundles].
* **`@VidocqTest`** — `vidocq-runtime-junit`, in test scope, starts the application in a JVM of its own for a test class, on a free port, and stops it after the last test; a test sends it requests through the `VidocqApplication` parameter (`get`, `post`, `log`). The examples' hand-written launchers are no longer needed. xref:testing.adoc[Testing an application] (Vidocq/vidocq#350).
* **A Vaadin extension: an app shell works in a jlink image** — in a jlink image an `AppShellConfigurator` made the first request fail with `ServiceConfigurationError: … module flow.server does not declare 'uses'`: Vaadin's lookup asks `ServiceLoader` for the application's own class from `flow.server`, whose descriptor cannot name it. `vidocq-runtime-vaadin-extension` ships a Vaadin `LookupInitializer` whose lookup loads services from a module of its own after `Module.addUses`; the application adds the dependency, `requires io.vidocq.runtime.extensions.jakartaee.web.vaadin`, and nothing else (`vidocq extension add vaadin`). A Vidocq jar can now ask for the application layer with the `Vidocq-Application-Layer: true` manifest attribute, which the extension does to stay with Vaadin (BUG-20261023-06). xref:modules/vidocq-runtime-extensions.adoc#vaadin[Vaadin], xref:vaadin.adoc#jlink-app-shell[An app shell in a jlink image].
* **Servlet applications answer in UTF-8 by default** — the Servlet specification encodes a text response in ISO-8859-1 unless the application names another encoding, so a page with accents written through `getWriter()` was shown garbled. The Servlet extension now makes UTF-8 the default response encoding of the `ServletContext` when the application configures none: a `<response-character-encoding>` in `web.xml` or a fragment, and a `setResponseCharacterEncoding` call by an initializer or a listener, still win. `vidocq.servlet.response-character-encoding` changes the default, and `ISO-8859-1` restores the Servlet one. xref:modules/vidocq-runtime-extensions.adoc#servlet-response-encoding[Response encoding].
* **Flyway 13 and Liquibase 4.33 behind the migration backends** — `vidocq-runtime-flyway-migration-extension` moves from Flyway 11.1.0 to 13.9.0 and no longer brings `jackson-databind` into the application: `jackson-annotations` alone remains. `vidocq-runtime-liquibase-migration-extension` moves from Liquibase 4.31.1 to 4.33.0, the last release under the Apache 2.0 licence. xref:modules/vidocq-runtime-extensions.adoc#schema-migration-backends[What each backend brings].
* **The Bistro example shows JSP pages** — `vidocq-runtime-foy-servlet-example` gains a receipt page forwarded to by a servlet and an about page, compiled by Ibarra, with Peano expressions on `@ELAccessible` records, a custom tag and tag library functions; its test runs them with reflection denied. xref:modules/vidocq-runtime-examples.adoc#foy-servlet-example-quick-start[Bistro quick start].
* **JNDI `java:` names** — `vidocq-runtime-naming-extension` answers `new InitialContext().lookup("java:comp/env/jdbc/audit")` from the running container, through Vauban Naming, with the names `vidocq.properties` declares: `vidocq.naming.comp/env/jdbc/audit = javax.sql.DataSource @Named("audit")` binds a bean, a value starting with `java:` links to another name, in four distinct namespaces, checked at startup. Mansart Data now resolves `@Repository(dataStore = "java:comp/env/jdbc/…")` under Vidocq, where no initial context existed before. The extension sets `java.naming.factory.initial` only when the application chose no factory, and its contexts follow a `vidocq:dev` restart (vidocq#297). xref:modules/vidocq-runtime-extensions.adoc#naming[JNDI java: names].
* **JSP pages, through Ibarra** — `vidocq-runtime-ibarra-pages-extension` serves the application's JSP pages through the Servlet extension. `vidocq:generate` compiles them with Ibarra into the application module, at build time; a page that does not compile fails the build. The Servlet extension now hands Foy the application layer, where it finds the engine and the pages, and an application made of pages only is deployed. `vidocq extension add ibarra-pages` (vidocq#232). xref:modules/vidocq-runtime-extensions.adoc#ibarra-pages[Jakarta Pages (Ibarra)].
* **The listeners of an excluded web fragment stay out** — the Servlet extension tells Foy which jar each component class comes from: the jar the application's loader finds its class file in. A `@WebListener` in a jar that `<absolute-ordering>` leaves out is no longer registered when the class was loaded from elsewhere, as the TCK harness does; the Servlet TCK on the assembled runtime then passed 1699 of 1714 (BUG-20261018-01, vidocq#228). xref:tck.adoc[TCK].

* **The application layer can hold the application's dependencies (`vidocq.app.layer=all`)** — with `all`, the dependencies outside the runtime's closure move into the application layer, as `WEB-INF/lib` does in a servlet container, and a framework that looks up resources through its own loader sees the whole application. `vidocq.app.layer.keep` pins modules in the parent layer; `classes` stays the default (Vidocq/vidocq#247). xref:usage.adoc#app-layer-dependencies[Dependencies in the application layer].
* **`vidocq:generate` runs the brick processors over dependency jars** — a library compiled without a brick's annotation processor, such as a `@WebListener` or a `ServletContainerInitializer` in a plain jar, now works: the Foy processors run over the jars Foy selects, the output goes into the jar's enriched copy, and the build logs one line per jar. A failure names the jar, the brick, the member and the `scanExcludes` fix; the output is cached in `~/.cache/vidocq/depgen` (`vidocq.generate.cacheDir`); signed jars are skipped; `vidocq:analyze-deps` shows `selected by a brick`, and the startup report counts the `enriched` libraries. A brick declares its hints in `META-INF/vidocq/dependency-codegen.properties` (Vidocq/vidocq#246). xref:modules/vidocq-runtime-maven-plugin.adoc#brick-processors[Brick processors on dependency jars], xref:modules/vidocq-runtime-maven-plugin.adoc#brick-authors[For brick authors].
* **`vidocq:jlink` names the resource directories several jars share, and can merge them** — such a directory is a split package that `jlink` refused with a list of packages; the goal now stops before `jlink` with one line naming the jars and the directory. `-Dvidocq.jlink.mergeSharedResources=true` moves the files into one module of the image, which is what Vaadin's `flow-server` and `flow-react` need (Vidocq/vidocq#256). xref:modules/vidocq-runtime-maven-plugin.adoc#jlink-shared-resources[Resource directories several jars share].
* **A JDK module that only the application requires is resolved** — `vidocq:run`, `vidocq:dev` and the `vidocq:package` launchers add the JDK modules the application modules require to `--add-modules`. An explicit module of the application layer that requires `java.sql`, such as Vaadin's `flow-data` once modularized, failed with `Module java.sql not found`: only the boot layer can define a JDK module. A launch written by hand gets a message that names the option to add (Vidocq/vidocq#254). xref:usage.adoc#app-layer-jdk-modules[JDK modules].
* **`vidocq:package` keeps a brick-selected jar automatic** — a jar a brick selects and that has no module descriptor ships as the automatic copy `vidocq:generate` wrote, so it may use any service. `vidocq:package` used to rebuild it on the descriptor `vauban:modularize` synthesizes, which can miss a `uses`; a packaged Vaadin application then failed at boot. `vidocq:jlink` still rebuilds it, since it refuses automatic modules (Vidocq/vidocq#251). xref:modules/vidocq-runtime-maven-plugin.adoc#brick-automatic-packaging[Brick processors on dependency jars].
* **An application built without Vauban's processor says so** — an application module compiled without the annotation processor, as by VS Code's Java extension on its own Java 21 runtime, started without its beans and answered 404 with no warning. The boot now logs `VIDOCQ-GEN-002` when the module has bean classes and no Vauban index, and says how to build it. xref:modules/vidocq-runtime-core.adoc#vidocq-gen-002[`VIDOCQ-GEN-002`].
* **An IDE build no longer answers 404 for the beans of a dependency** — the beans of a dependency compiled without Vauban's processor, such as langchain4j-cdi's MCP server, were indexed by `vidocq:generate` only, which an IDE build never runs: the application started and answered 404 to everything (Vidocq/vidocq#83). `vidocq:generate` now stamps the index it leaves, and a boot whose stamp is missing or stale, as after an IDE build or an IDE's incremental build, scans the `beans.xml` archives that no build step indexed and says so, `VIDOCQ-GEN-001`, naming them (Vidocq/vidocq#241). xref:modules/vidocq-runtime-core.adoc#vidocq-gen-001[`VIDOCQ-GEN-001`].

* **The Servlet TCK on the assembled runtime** — `vidocq-runtime-tck-foy-servlet` runs the official Jakarta Servlet 6.1 TCK through the Servlet extension, each WAR deployed by the runtime with Foy and Vauban: 1704 of 1714 pass, the JSP tests included since the harness compiles each war's pages with Ibarra at deployment, every difference with Foy's own runner explained. * **`@ApplicationPath` on an `Application` without scope** — the REST extension used to find the `Application` among the CDI beans, so a subclass without a scope, no bean under `annotated` discovery, was missed and REST landed on `/`. It now reads the descriptor `cassini-processor` generates, and the bean only for a class compiled without the processor (vidocq#219). xref:modules/vidocq-runtime-extensions.adoc#servlet[Servlet (Foy)].
* **REST resources need no scope** — the REST codegen bundle now carries `cassini-cdi`, so Vauban's processor runs `CassiniScopeExtension` at compile time: a `@Path` class without a scope becomes `@RequestScoped`, and a `@Provider` class `@Dependent`. Before, such a resource was no bean and answered 404; Rest Client interfaces are left alone (cassini#59).
* **Mounts routed longest prefix first; a duplicate prefix fails** — a mount on `/` used to answer every path of the mounts registered after it, and a second mount on a prefix was silently unreachable. Mounts are now routed longest prefix first, whatever the order the extensions mounted in, and two mounts on the same prefix of one listener fail at startup, naming both extensions and the keys that move them. An explicit `vidocq.http.mount.<name>.priority` still goes first, and a trailing slash no longer hides a mount's subpaths (`/api/` serves `/api/items`). xref:reference.adoc[Configuration reference].
* **Startup banner with the exact Vidocq version** — every boot tells which Vidocq starts, once per JVM, before anything later can fail: `Vidocq 0.4.0-SNAPSHOT (9beafc47+dirty, built 2026-09-17T14:02:11Z)`, then the Java version, the profile or dev launch, and the application. A terminal, a dev profile or IntelliJ's Run console get the art on standard output; containers, CI, pipes and tests get one log line. `vidocq.banner.mode=auto|console|log|off`, a custom `vidocq-banner.txt` with placeholders, and `VidocqBootstrap.banner(BannerMode.OFF)` for embedders. `vidocq dev` now starts its spinner after the banner. xref:modules/vidocq-runtime-core.adoc#startup-banner[Startup banner].
* **The launch mode, and the debugger, in the startup identity** — every boot says which of `dev`, `test` and `prod` it is, with the signal it was read from: `Java 25+36-LTS | dev (IntelliJ agent) | debug *:5005 | mcp-time-server 0.1.0-SNAPSHOT`. `prod` never shows without `(no dev or test signal)`, since nothing proves it. A JVM started with `-agentlib:jdwp=…` shows the address a debugger has to attach to, in every mode, and repeats it on a `Vidocq debugger: attach to …` record when the 80 columns of the banner could not hold it. Neither the mode nor the address is ever lost to the JVM vendor, which the line gives up first. `vidocq.launch.mode=dev|test|prod` forces the mode; it changes what is printed, and the runtime itself behaves the same in every mode. xref:modules/vidocq-runtime-core.adoc#launch-mode[Launch mode].
* **Build identity in every jar** — `vidocq-parent` writes `META-INF/vidocq/build-info/<artifactId>.properties` (version, abbreviated commit, dirty flag, commit time, and build time outside releases, which stay reproducible), so two snapshots with the same version are told apart. xref:modules/vidocq-runtime-core.adoc#build-identity[Build identity].
* **Every Java 25 main shape starts the application** — when Vidocq picks the main itself, it now picks the one `java` would: `main(String[])` and `main()`, static or an instance method, public or not, declared in the class, inherited from a superclass, or a `default` method of an implemented interface. The selection mirrors the launcher's, down to the parts nobody guesses — a declared main ends the search even when it cannot be used, so a `private main(String[])` sends the launch to `main()`. An IDE on JDK 25 flags the `public` of a main as an unnecessary modifier: following that advice no longer makes `vidocq:run` fail. A `private` or non-`void` main is named as such, with the class that declares it, instead of being reported as a missing main (Vidocq/vidocq#88). xref:modules/vidocq-runtime-core.adoc#main-shapes[Which main methods are accepted].
* **Readable console logs by default** — when the application has not configured logging, Vidocq replaces the JDK's two-line records on standard error (red in an IDE) with one aligned line per record on standard output: `[LEVEL][timestamp][thread][class#method] : message`, with a coloured level on a terminal or in IntelliJ's Run console. Any logging setup of the application wins (`logging.properties`, an SLF4J or Log4j bridge, `vidocq.log.console=jdk`); `vidocq.console.color` and `NO_COLOR` control the colours. The examples no longer carry their own copies of a stdout handler and formatter. xref:modules/vidocq-runtime-core.adoc#console-logging[Console logging].
* **A startup report at the end of every boot** — one INFO record, just before `Vidocq - Started in`, says what has just started: the launch mode and the signal it was read from, the application layer and its modules, the configuration sources and the audited namespaces (never a value), the extensions and the time of each `onStart`, and the section of every library that contributes one. One line per section by default, everything on the first boot of a dev launch, nothing for an embedded deployment such as the TCK; `vidocq.startup.report=auto|off|summary|detailed` chooses. Every anomaly is its own WARNING record, its code first, logged even with the report `off`: `VIDOCQ-CFG-001` for an invalid `vidocq.startup.report` or `vidocq.launch.mode`, `VIDOCQ-CFG-003` for a key read by nothing — `vidocq.startup.reprot` included, and `vidocq doctor` now knows the `vidocq.startup.*` keys — `VAUBAN-009` for load-time weaving that could not be prepared, `VIDOCQ-RPT-001` and `VIDOCQ-RPT-002` for a contributor that fails or takes an id already used. A boot that fails logs one warning naming what was running, the time spent and the codes already logged, with the partial report in a dev launch, then lets the same exception through, untouched. A library adds its section with `StartupReportContributor`, in the new package `io.vidocq.runtime.spi.report` of `vidocq-runtime-spi`: an extension only implements it, any other library declares it as a service, and nothing needs `vidocq-runtime-core`. Extensions read the launch mode with `ExtensionContext.launchMode()`. xref:modules/vidocq-runtime-core.adoc#startup-report[Startup report], xref:modules/vidocq-runtime-spi.adoc#startup-report-contributors[Contributing to the startup report].
* **Chappe listeners say where they really listen, and an extension can bring its own** — every listener now logs the address it bound, so `port=0` prints the real port and an IPv6 address is bracketed. An extension declares a listener of its own with `ChappeMountPoint.declareListener(listener, options)`: it may fall back to a free port when its port is taken, log quietly, stop with a short grace period, and is handed the address it bound. `vidocq.chappe.listeners` can no longer list such a listener, nor silently replace it. xref:modules/vidocq-runtime-extensions.adoc#extension-listeners[A listener of an extension's own].
* **The dev console** — run `mvn vidocq:dev`, which adds the console itself (see the dev tools entry below): `Vidocq dev console: http://127.0.0.1:8888/` opens a read-only page, on a loopback listener of its own, with the startup report of the running boot, its anomalies first, then one tab per extension, and the JVM last. The Mansart pools show live: the active, idle and waiting connections of each pool, borrows and timeouts per second, leaks, the mean borrow time. It is on in a dev launch only (`vidocq.devconsole.enabled=auto|true|false`), listens on `vidocq.devconsole.host` and `vidocq.devconsole.port`, `0` for a free port that the dev reloads keep, and the banner promises it: `devconsole :8888`. A port already taken never stops the application: the console takes a free one and says so loudly, in a boxed warning, as `VIDOCQ-DEVC-004` and on the page. It answers only a request that names its own address, never shows a secret, a JVM argument or a system property, and warns when it is on outside development or off the loopback address (`VIDOCQ-DEVC-001` to `VIDOCQ-DEVC-005`). An extension shows its section of the startup report live by implementing `DevConsolePanel`, from the new `vidocq-runtime-devconsole-spi`, in its own runtime extension: boot facts once, values sampled from memory on every poll, and the charts to draw. `ExtensionContext.startupReport()` gives an extension the report of its boot. The Mansart pool extension's section also names its pools, their sizes and checks, and raises `MANSART-POOL-001` for a `minIdle` pre-fill that opened nothing and `MANSART-POOL-002` for a named pool that no `@Named` datasource serves. xref:dev-console.adoc[Dev console], xref:dev-console-panels.adoc[Writing a dev console panel].
* **A langchain4j-cdi MCP server in one dependency** — `vidocq-runtime-langchain4j-cdi-mcp-extension` brings langchain4j-cdi's MCP server, its CDI 4.1 invoker, the Jakarta REST runtime and the server's bean list: an application drops its two langchain4j-cdi dependencies, `parsson`, `yasson` and `scanDependencies`, and an IDE launch finds `/mcp` without a Maven step. The server stays in the boot layer in every launch shape, the application layer holds the application alone, and nine `vidocq.mcp.*` keys configure it. The startup report gets an `mcp` section (tools, prompts, resources, protocols, configuration, never the request-state secret), and five codes, `VIDOCQ-MCP-001` to `VIDOCQ-MCP-005`, name what the extension can see going wrong. * **The `mcp` section of the startup report is live in the dev console** — `vidocq-runtime-langchain4j-cdi-mcp-extension` now implements `DevConsolePanel` too: besides the boot facts, which stay, the `mcp` panel samples seven values about once a second — the sessions the server holds, the SSE streams and the `subscriptions/listen` streams open, the requests it is still waiting a client's answer of, and the three counters of the CDI 4.1 invoker — and plots *Connections* and *Server-to-client requests*. `invoker.matches` and `invoker.misses` count **distinct methods, not calls**: a server of four MCP methods reads `4` after six calls and still `4` after six hundred, which is why no chart plots them. The panel never creates a bean — it asks each bean's `Context` for the instance it already has, since creating `McpSessionManager` would start its `mcp-session-cleanup` thread, once a second, on an application that has served no request — and a bean with no instance is shown `absent` with its reason, `no request served yet`, `not created yet`, `reflection` or `built at the first call`, never a zero that would claim a measure the panel does not have (Vidocq/vidocq#94). xref:modules/vidocq-runtime-extensions.adoc#langchain4j-cdi-mcp-live[The `mcp` panel in the dev console].
* **An MCP inspector in the dev console** — in a `dev` launch, the `mcp` tab lists the application's MCP tools, prompts and resources and calls them through its own `/mcp`: a *Monitoring* sub-tab and one per kind, a list to pick the item, a form from its input schema, the result in a block of its own through a JSON viewer that colours and folds it, the exact JSON-RPC exchange, the kind's last calls with a replay, secrets masked. * **The dev console's curves survive a hidden tab** — the five minutes of history behind every chart moved from the page to the server, where a thread of the console's own, `vidocq-devconsole-history`, fills it once a second for the life of the boot, whether or not a page is open. The page used to keep it, one point per poll, and a browser stops the timers of a hidden tab — on macOS, Chrome counts a window another application covers as hidden — so every curve had a hole covering exactly the minutes you had left the console to go and cause something, which is the interval you came back to look at. A poll now asks for what it is missing, `GET /api/snapshot?since=<its newest point>`, and a tab that comes back after three minutes away redraws a complete curve in one document. The holes that are true are kept: a tick where a panel wrote `absent` keeps its place on the axis with a null value, and a tick the server itself missed — a long pause, a suspended process, a laptop that slept — leaves no point and breaks the curve, as before. The ring is bounded and the bound is a number: 256 series of 300 points, measured full at 1,966,960 bytes, 1.88 MB, whatever the panels do and however long the run; a series arriving past the cap keeps its live value and gets no curve, and the snapshot says `historyTruncated` (Vidocq/vidocq#107). xref:dev-console.adoc#history[Where the history lives].

* **A query editor for JDQL in the dev console** — the statement of the *Mansart Data* panel's *JDQL* tab, in *Query*, *Update / Delete* and *Export CSV*, is typed in the dev console's code editor in a new query mode: keywords, functions, the entity, its attributes, strings, numbers and parameters each coloured; `Ctrl+Space` completes the entities after `FROM`, their attributes with their Java type and column in `SELECT`, `WHERE`, `ORDER BY` and `SET` — `FROM` written after the caret included — and a reference's attributes after `project.`; an unknown entity or attribute, a path through an attribute that is no reference, an unterminated string or an unbalanced parenthesis is underlined before anything runs; *Format* puts each clause on its line. Its `params` become a JSON editor whose schema follows the statement as you type: `WHERE status = :status` offers `status` with the values of its enum and flags it missing. A panel publishes such a vocabulary with `DevConsolePanel.languages()` (or `LivePanel`'s), `PanelLanguage` records the page fetches once at `GET /api/language/<panel>/<id>` in a `dev` launch, and names it from a `json` argument's schema with `"contentMediaType": "text/x-query"`, `"x-language"` and `"x-parameters-of"`. xref:dev-console.adoc#query-editor[Query editor], xref:modules/vidocq-runtime-extensions.adoc#mansart-data-jdql[A JDQL console for Mansart Data].
* **Tables and a SQL editor for each Mansart pool, and a table of rows in the dev console** — under `mvn vidocq:dev`, the *Mansart pools* panel gives each pool a tab: *Tables* lists its tables and views with their columns' number, *Describe* a table's columns, types, keys and indexes, *Preview* its first rows, *Query* runs a statement that only reads in a transaction always rolled back, and *Execute* any one statement, asked first and rolled back unless committed; 30 seconds at most, `:name` parameters bound from `params`, the pool's URL and password never shown. The SQL is typed in the query editor, which now reads SQL: aliases, joins, several tables, quoted names, comments, the columns of every table in scope completed with their table, an unknown alias flagged and an ambiguous column warned, `LEFT JOIN … ON` formatted on one line; its vocabulary, the language `sql-<pool>`, is read from `DatabaseMetaData` at boot. A result of rows is now a table — the type of each column under its name, `NULL` dimmed, *Table* / *JSON* and *Copy as CSV* — which the *JDQL* tab's *Query* answers too; a panel answers one with `PanelAction.ActionResult.rows(…)`. xref:modules/vidocq-runtime-extensions.adoc#mansart-pool-sql[Tables and a SQL editor], xref:dev-console.adoc#rows-table[A table of rows], xref:dev-console.adoc#query-sql[SQL].
* **Dev service containers are named `vidocq-dev-…`** — the PostgreSQL and Keycloak dev services used to leave their containers to Docker's random names; each is now `<prefix><application>-<service>[-<datasource>]-<suffix>`, such as `vidocq-dev-mcp-tasks-server-postgres-3f9a2c01`, the prefix `vidocq-dev-` unless `vidocq.dev.container-prefix` says otherwise. The suffix is random, or for a reused container a digest of the application and the configuration, so reuse keeps finding it. Three labels, `io.vidocq.dev`, `io.vidocq.dev.app` and `io.vidocq.dev.service`, let `docker ps --filter label=io.vidocq.dev` list them. A provider of its own names its containers the same way with `DevContainers.name` and `DevContainers.labels`, from the SPI. xref:dev-services.adoc#container-names[Container names and labels].
* **The PostgreSQL dev service starts only for an application on PostgreSQL** — with `vidocq-runtime-devservice-postgres` on the plugin, an application whose `vidocq.properties` says `vidocq.pool.url=jdbc:h2:…` (or MySQL, or any other database) no longer gets a PostgreSQL container whose URL replaced its own: the provider reads which database the application's file names and, with no URL at all, starts a container only when `org.postgresql.Driver` is on the application's class path. A PostgreSQL URL in the file (or a wrapper driver's, such as `jdbc:otel:postgresql:`) still gets its container: it is the production one. An application with no URL and the driver in test scope only now needs its URL in `vidocq.properties` to keep the container under `vidocq:dev` and `vidocq:run`. A provider that does not start says why — `not started: vidocq.pool.url is jdbc:h2, not PostgreSQL`, the scheme only — in the log, the state file, the startup report and the *Dev services* panel. The `DevServiceContext` SPI gains `applicationProperty(key)` and `onApplicationClasspath(className)`, and `DevService` gains `skipReason(ctx)`, all `default`. xref:dev-services.adoc#postgres-only-for-postgres[A PostgreSQL container only for a PostgreSQL application].
* **Dev services are visible, `vidocq.properties`-aware, and available to `vidocq:run` and to tests** — a dev service's coordinates used to reach only the application's `-D` arguments, invisible to the boot itself: the startup report now has a `devservices` section, host `vidocq:dev`/`vidocq:run`/`test`, image and endpoints per service, its injected keys, a secret always `configured`; the dev console shows the same, live, as its own panel. A `vidocq.dev.*` tuning key — `vidocq.dev.postgres.port`, `vidocq.dev.reuse`, `vidocq.dev.devServices` — is now also read from `vidocq.properties`/`application.properties`, so the stable-port recipe works without a `-D` on every run; an opt-out key such as `vidocq.pool.url` still never comes from those files. `vidocq:run` starts no container unless asked, with the same `vidocq.dev.devServices=true`. Every host reads that key the same way, first match wins: the explicit value (`-D`, the goal's configuration, a system property), then the application's files, then the host's default (on for `vidocq:dev` and tests, off for `vidocq:run`), so `-Dvidocq.dev.devServices=false` overrides a `true` in `vidocq.properties` for one run. A test adds `vidocq-runtime-devservices-junit` and a provider, both `test` scope, and a `LauncherSessionListener` starts one set of containers for the whole run, no annotation needed. An unreadable state file is `VIDOCQ-DEVS-001`, which names its path; the boot goes on. The state file is the project's, shared by every host: `mvn test` while `vidocq:dev` runs overwrites it, then marks it `stopped`, host `test`. `target/vidocq-dev-services.properties` still keeps a password in clear text, local to the machine, for `psql`/DataGrip — the JSON state file the application reads never does (Vidocq/vidocq#123). xref:dev-services.adoc[Dev services].
* **Continuous testing, in `vidocq:dev` and in a new `vidocq:test` goal** — `vidocq:dev` now runs the application's tests after every reload, or alone after a test-only change, without reloading the application, and the dev console's new `tests` panel shows the last run: its counts, its failures with the first line of their message, a chart, and the buttons *Run all tests* and *Rerun failed tests*, which never name a test. `vidocq:test` runs the same loop without the application, with a summary in the terminal and `r`, `f` and `q` when a console is attached. A run is Surefire itself (`mvn test-compile surefire:test`), a new change cancels the run in flight, and the result is in `target/vidocq-dev-tests.json`, the output in `target/vidocq-dev-tests.log`; a run that fails before any test is `compile-error` when the compiler failed, `error` otherwise, such as Surefire's provider missing offline (Vidocq/vidocq#138). The tests reuse the dev services containers, and share their database. `vidocq.dev.continuousTesting=false` turns it off; it is on when the project has `src/test/java` (Vidocq/vidocq#122). xref:continuous-testing.adoc[Continuous testing].
* **Dev tools only under `vidocq:dev`; the `-dev` panel modules, never packaged** — the dev console and each extension's live panel are development tools: nothing to declare any more, `mvn vidocq:dev` adds the console itself the moment the application has `vidocq-runtime-chappe-webserver-extension`, and each extension's `-dev` companion module with it, so its tab is live. `vidocq:run`, `vidocq:package`, `vidocq:jlink`, `vidocq:jpackage` and `vidocq:docker` never contain any of it, even when a project still declares it: every dev-only jar is dropped, with a warning naming it, and `vidocq:checkpom` warns about the same declaration earlier, outside `test` scope. A test that reads the console, or a live panel, declares both at `test` scope. The six extensions that had a live panel of their own — Mansart pools, Knock health, Cassini REST, Dirac metrics, schema migration, the langchain4j-cdi MCP server — each move it to a new `-dev` module next to the runtime extension; the older, all-in-one `DevConsolePanel` form still works, for an extension that keeps it, and the console SPI it requires, an ordinary API jar, ships in the binary with it. `vidocq:idea` now writes a matching Dev, `(packaged)` and `(debug)` file for each application (Vidocq/vidocq#143). xref:dev-console.adoc#getting-it[Getting it], xref:modules/vidocq-runtime-maven-plugin.adoc#dev-tools[Dev tools and binaries].
* **A code editor for JSON arguments, and a form for an entity** — in the dev console, every `json` argument of an action, an MCP tool's arguments as a Mansart Data repository method's, is typed in a code editor written for the page: colours, line numbers, the first syntax error and then what the argument's JSON Schema says at every depth (a missing required key, a wrong type, a value outside its enum, a key the schema does not list, a date that does not look like one), underlined with its message; completion of keys and values with `Ctrl+Space`; *Format* (`Shift+Alt+F`), which keeps numbers and strings as written; brackets and quotes closed as you type; one `Ctrl+Z` per edit it makes. The generated form takes one level of nesting, so `TaskRepository.save(entity: Task)` gets fields: the required ones starred and refused by their path when empty, the generated id marked `(generated)`, dates with the shape they expect. Mansart Data's entity schema now says which attributes are `required` and `readOnly`, and names each column. xref:dev-console.adoc#json-editor[JSON editor], xref:dev-console.adoc#json-form[The generated form].
* **CSV export and import for Mansart Data** — under `mvn vidocq:dev`, the *Mansart Data* panel's *JDQL* tab gains *Export CSV*, which runs a query and downloads its whole result as a CSV file, and *Import CSV*, which saves the rows of a file you paste or pick as entities, in a transaction rolled back unless you commit it: a header of attribute names, `null` apart from `""`, `,` or `;` as separator, at most 5000 rows, the first bad line named before anything is saved. The console gains a `text/csv` action result, shown with a *Download* button, and a *Choose file* input for a CSV field. xref:modules/vidocq-runtime-extensions.adoc#mansart-data-csv[CSV export and import for Mansart Data].
* **A JDQL console for Mansart Data** — under `mvn vidocq:dev`, the *Mansart Data* tab ends with a *JDQL* tab that runs a statement you type against the application's database: *Query* for a `FROM`, a projection, a count or an aggregate, *Update / Delete* for a write, asked first and rolled back unless you commit it; named parameters as a JSON object, converted to the attributes' types; the result as JSON, with the last 20 statements and a replay. Mansart gains `JdqlExecutor.run` for it, and a JSON argument's form now shows a string of `"format": "textarea"` as a field of several lines. xref:modules/vidocq-runtime-extensions.adoc#mansart-data-jdql[A JDQL console for Mansart Data].
* **Run a Mansart Data repository method from the dev console** — under `mvn vidocq:dev`, the *Mansart Data* tab gets one tab per repository, which runs any of its methods against the application's database: the arguments as JSON, converted to the method's types, an entity built through Mansart's own model; the result as JSON, with the last 20 calls and a replay. A write asks first and runs in a transaction rolled back by default, or committed. xref:modules/vidocq-runtime-extensions.adoc#mansart-data-run-method[Running a repository method from the dev console].
* **A Mansart Data catalogue in the startup report and the dev console** — `vidocq-runtime-mansart-data-extension` writes a `mansart-data` section: the application's entities with their table and columns, as Mansart's own model gives them, and its repositories with each declared method's kind, `@Query` text, parameters and return type, plus the methods they inherit from Jakarta Data. Under `mvn vidocq:dev` its new companion `vidocq-runtime-mansart-data-extension-dev` shows it as the *Mansart Data* tab, one card per entity with its repositories inside. It reads names only: no connection, no query. An entity whose model Mansart cannot build keeps its place and raises `MANSART-DATA-001`. xref:modules/vidocq-runtime-extensions.adoc#mansart-data-catalogue[The Mansart Data catalogue].
* **The MCP request state is encrypted** — with langchain4j-cdi's MCP server, the `REPLAY` request state that carries a tool's elicitation and sampling answers between rounds was signed but readable by anyone holding it; it is now encrypted and authenticated with AES-256-GCM, its key derived from `vidocq.mcp.requestStateSecret`. Only this format is read: no released version ever issued the signed one (langchain4j/langchain4j-cdi#303, langchain4j/langchain4j-cdi#305). xref:modules/vidocq-runtime-extensions.adoc#langchain4j-cdi-mcp[langchain4j-cdi MCP server].
* **MicroProfile 7.2** — the runtime now targets MicroProfile 7.2: JWT Auth 2.2 (Cervantes), OpenAPI 4.2 (Grimm) and Telemetry 2.2 (Humboldt, on OpenTelemetry 1.66). The TCKs of the seven MicroProfile 7.2 component specs, and that of Metrics 5.1 (not part of the 7.2 platform), are green on the assembled runtime (1888 tests). Only the OpenAPI and Telemetry runs use release-candidate TCKs, published on Maven Central and byte-identical to the finals; the JWT Auth 2.2 TCK is final. The 7.2 platform release is still under ballot, and the two runs will be repeated on the finals once they are published. What you will notice: JWT accepts RS256 and ES256 (all RS/ES key sizes) when `mp.jwt.verify.publickey.algorithm` is unset, rejects an unrecognised value at startup, and enforces the algorithm family when it is set; `@WithSpan` spans carry `code.function.name` and `@WithSpan(inheritContext = false)` starts a new trace; OpenAPI treats unknown `Schema` properties as extensions, reads `@Header.example`/`examples` and method-level `@ExternalDocumentation`, maps Bean Validation `@Digits` to `multipleOf`/`pattern`, and writes decimals in plain notation. See xref:tck.adoc#microprofile-tcks-on-the-assembled-runtime[the TCK page].
* **Buttons in the dev console, and the Swagger UI one click away** — a section can now offer to open something the application serves: `StartupReportSection.link(label, listener, path)`. The log prints the absolute URL; the console shows a button under the panel's title that opens it in a new tab. The Swagger UI and the OpenAPI document get one in the `rest` panel and in the new `openapi` section, which also counts the operations of the document; a `GET` route with no template variable is a link in the route table. A panel never writes a URL: Vidocq builds it from a listener the report declared and a path, and the page only opens `http` and `https`. An extension offers a page it serves with `ChappeMountPoint.advertise(listener, label, path)` (Vidocq/vidocq#113). xref:dev-console-panels.adoc#links[Links].
* **The `rest` panel is live in the dev console** — one card per mount, sampled about once a second from the counters Cassini now keeps, `CassiniStack.statistics()`: requests per second, responses by status class, requests in flight, the share of time spent in handlers, and the mean and longest time to answer. The counters cost about 25 ns per request and allocate nothing; there is no breakdown per route (Vidocq/vidocq#103, Vidocq/cassini#42). xref:modules/vidocq-runtime-extensions.adoc#cassini-rest-live[The `rest` panel in the dev console].
* **A boot that fails stops what it started** — when `beforeStart`, the container build or an `onStart` threw, the extensions already started stayed started: a Mansart pool kept its connections open, and under `vidocq:dev` a failed reload left the dev console's live panels on the values of that boot. Every extension whose `beforeStart` was called now gets its `onStop`, in reverse order, and the container is closed; a failing `onStop` is logged, the next one still runs, and the exception of the boot goes through untouched. An extension's `onStop` must therefore work when its `onStart` never ran (Vidocq/vidocq#145). xref:concepts.adoc#failed-boot[When a boot fails].
* **`@Transactional` now covers Mansart Data writes with one dependency** — `vidocq-runtime-mansart-transactions-extension` brings `mansart-transactions-jdbc` itself, the JDBC-to-JTA bridge that `mansart-data-cdi` declares optional: without it on the module path, a repository call took its own autocommit connection, so a `@Transactional` method could begin and roll back a real JTA transaction while a write it made just before throwing stayed committed, with no anomaly reported. Adding the extension is now enough (Vidocq/vidocq#97). xref:modules/vidocq-runtime-extensions.adoc#mansart-transactions-jdbc-bridge[Mansart Data writes join the transaction].
* **Schema migrations run where the application does** — under `vidocq:dev`, `vidocq:run` and the launcher `vidocq:package` writes by default, the application boots in a module layer of its own, whose class loader lists no directory: Flyway found none of the scripts in `classpath:db/migration`, logged one warning, and the boot went on with an empty schema until the first query failed with `Table "…" not found`, and Liquibase did not find its changelog. Both backends now list `classpath:` locations from the application's own modules, Flyway's Java migrations and Liquibase's `includeAll` included, and a schema history written by a flat launch stays valid. `vidocq.migration.locations` in `vidocq.properties` or as a `-D` no longer stops the boot with a `StringIndexOutOfBoundsException`. A datasource that finds no migration on an empty history is now the anomaly `VIDOCQ-MIG-001`, a warning in every mode. The new `migration` section of the startup report says what each datasource did, an up-to-date restart logs the version the schema is at instead of `version=(none)`, `vidocq.migration.failOnMissingLocations=true` makes an empty Flyway location stop the boot, and a mistyped `vidocq.migration.*` key is reported as `VIDOCQ-CFG-003`. An extension reads the application layer with `ApplicationLayer`, new in `vidocq-runtime-spi` (Vidocq/vidocq#96). xref:modules/vidocq-runtime-extensions.adoc#schema-migration[Schema migration], xref:modules/vidocq-runtime-spi.adoc#application-layer[Listing the application's files].

* **Clear errors when the application stays in the boot layer** — when `Vidocq.run()` finds no application module to move into the Vauban layer, it cannot export the `VidocqApp` class's package to itself, and the boot used to fail with a bare `IllegalAccessException`. The message now names the class, its package and the two fixes: an `exports <package> to io.vidocq.runtime.core;` in `module-info.java`, or a CDI bean (Vidocq/vidocq#201). xref:usage.adoc#app-in-boot-layer[When the application stays in the boot layer].
* **`@Inject @RestClient` works, and a Rest Client application links** — the new `vidocq-runtime-cyrano-rest-client-extension-codegen` bundle runs Cyrano's extension and generates each client's proxy in the compiler: without it, `@Inject @RestClient` was unsatisfied at boot. `vidocq:checkpom` now fails an application that declares the Rest Client extension without the bundle, and prints the `<path>` to add; `vidocq extension add cyrano-rest-client` writes it. `vidocq:jlink` links such an application, since Cyrano no longer requires `org.reactivestreams`, an automatic module (Vidocq/cyrano#30). **When upgrading**, add the bundle to the compiler's `annotationProcessorPaths`. The new `vidocq-runtime-cyrano-rest-client-example` shows the whole setup (Vidocq/vidocq#207). xref:modules/vidocq-runtime-extensions.adoc#cyrano-rest-client-codegen[The Rest Client extension], xref:migration.adoc#config-rest-client-codegen[Config and Rest Client need their codegen bundle], xref:modules/vidocq-runtime-examples.adoc#cyrano-rest-client-example[the example].
* **An extension brings what its brick leaves to the runtime** — a brick now depends on APIs, and its Vidocq runtime extension picks the implementations (vidocq-workspace#17). The Rest Client extension brings the Jakarta REST API and Champollion's JSON-B implementation: an application with the Rest Client and no REST server used to fail on the first JSON response, with no JSON-B provider (BUG-20261010-02). The Telemetry extension brings the Jakarta REST API, which `humboldt-rest` now leaves `provided`. xref:modules/vidocq-runtime-extensions.adoc#cyrano-rest-client-apis[Rest Client extension], xref:modules/vidocq-runtime-extensions.adoc#humboldt-telemetry-apis[Telemetry extension].
* **`@Inject @ConfigProperty` compiles with validation on** — the new `vidocq-runtime-ravel-config-extension-codegen` bundle puts Ravel's extension on the processor path, so the Vauban processor sees the beans it synthesises: an application used to get `Unsatisfied dependency` at compile time, and the only way out was `-Avauban.validation=false`. `vidocq:checkpom` requires the bundle wherever the Config extension is declared. **When upgrading**, add it to `annotationProcessorPaths` (Vidocq/ravel#21). xref:modules/vidocq-runtime-extensions.adoc#ravel-config-codegen[The Config extension], xref:migration.adoc#config-rest-client-codegen[Config and Rest Client need their codegen bundle].
* **`/openapi` in a sealed packaged application** — the OpenAPI extension requires Grimm's named module instead of the automatic one, which `cassini:generate` could fold into the application module, losing every Grimm bean: `/openapi` answered 404 (Vidocq/grimm#15). xref:modules/vidocq-runtime-extensions.adoc#grimm-named-module[The OpenAPI extension].
* **Liquibase's usage analytics stay off** — Liquibase 4.30+ sends usage data to Liquibase by default for open-source users. The Liquibase backend now runs every migration, listing and clean with that option off, unless a system property, the environment or a Liquibase defaults file sets it. xref:modules/vidocq-runtime-extensions.adoc#schema-migration-liquibase-analytics[Liquibase analytics stay off].

=== Maven plugin

* **`vidocq:dev` builds a project nobody built** — from an empty `target/`, after `mvn clean` for instance, `vidocq:dev` used to start with no class at all: no bean, no route, 404 on every request, with or without Vaadin. It now runs one `mvn process-classes` first, as every reload does, and warns that it does. For Vaadin, `vidocq:run` also starts from an empty `target/` once `build-frontend` is bound to `process-classes` in the pom. xref:vaadin.adoc#dev-and-run[`vidocq:dev` and `vidocq:run` with Vaadin].
* **An application parent and a BOM** — `vidocq-runtime-parent` is now the parent of an application, and nothing else: it imports the new `vidocq-runtime-bom`, which versions every Vidocq artifact, sets Java 25, puts the Vauban indexer on the processor path, and binds `checkpom`, `check-module-info` and `package` when the application declares the plugin. It no longer hands the application the SonarQube, TCK and dependency settings of the runtime's own reactor, whose root is `vidocq-runtime-build`. An application with a parent of its own imports the BOM. xref:migration.adoc#application-parent[What to change] (Vidocq/vidocq#339).
* **`vidocq:doctor -Dvidocq.doctor.fix`** — the goal checks the project as `vidocq doctor` does, and repairs it first with `-Dvidocq.doctor.fix` (Vidocq/vidocq#339). xref:modules/vidocq-runtime-maven-plugin.adoc#report-goals[The report goals].
* **`vidocq:doctor` and `vidocq:list-extensions`** — the reports of `vidocq doctor` and `vidocq extension list`, in a build that has Maven and no CLI. Both tools now gather the facts and run the checks of `vidocq-runtime-tooling`, so they diagnose the same project the same way (Vidocq/vidocq#314). xref:modules/vidocq-runtime-maven-plugin.adoc#report-goals[The report goals].
* **`vidocq:create`** — scaffolds a new project without the CLI: `mvn io.vidocq.runtime:vidocq-runtime-maven-plugin:0.4.0-RC1:create -Dname=my-api -Dextensions=cassini-rest`. It writes the project `vidocq create` writes, from the same scaffolder, moved into `vidocq-runtime-tooling` (Vidocq/vidocq#314). xref:modules/vidocq-runtime-maven-plugin.adoc#create-goal[The `vidocq:create` goal].
* **`vidocq:add-extension` and `vidocq:remove-extension`** — `mvn vidocq:add-extension -Dextensions=cassini-rest,knock-health` adds the dependency, the codegen bundle's processor path and the `module-info.java` directives, as `vidocq extension add` does; `remove-extension` undoes it. The CLI and the plugin run the same code, moved into a new module, `vidocq-runtime-tooling`, so either gives the same edit (Vidocq/vidocq#314). xref:modules/vidocq-runtime-maven-plugin.adoc#extension-goals[The extension goals].
* **`vidocq:checkpom` reads the codegen bundle from the extension** — an extension that ships `META-INF/vidocq/extension.properties` names its codegen bundle there, or names none, so `checkpom` no longer guesses it from the extension's name and no longer resolves the guess to know whether it exists. The Vidocq CLI reads the same descriptors, so the two cannot disagree on which bundle an extension needs. An extension without the descriptor, such as a third-party one, is checked by naming convention as before (Vidocq/vidocq#314). xref:modules/vidocq-runtime-maven-plugin.adoc#goals[Goals].
* **`vidocq:jlink` and `vidocq:jpackage` link an application without a main class** — both goals required `vidocq.mainClass`, so an application that the runtime's own main boots, as `vidocq:dev`, `vidocq:run` and `vidocq:package` already allowed, could not be linked: `The parameters 'mainClass' ... are missing or invalid`. `vidocq.mainModule` is now the only setting they need. Without a main class, the launcher runs `io.vidocq.runtime.core/io.vidocq.runtime.core.Vidocq` and the image carries `--add-modules=<mainModule>` and `-Dvidocq.app.module=<mainModule>`; the new `vidocq.app.module` property makes `Vidocq.main` re-layer that module as a `@VidocqMain` trampoline does, so the application boots in the same Vauban layer, a Vaadin application included. `vidocq:jpackage` passes the same options as `--java-options`. With a main class, the image is unchanged. xref:modules/vidocq-runtime-maven-plugin.adoc#jlink-without-main-class[Without an application main class], xref:modules/vidocq-runtime-core.adoc#app-module-property[the `vidocq.app.module` property].
* **`vidocq-runtime-parent` no longer hands Maven's own dependency versions to applications** — the parent imported the Arquillian BOM, which imports, through ShrinkWrap Resolver's, the dependency management of Maven itself: an application inheriting it got commons-lang3 3.12.0, commons-io 2.11.0 and guava 31.1-jre whatever its dependencies declared, all three with known vulnerabilities. With the Liquibase backend, that was also a commons-lang3 older than the 3.13.0 Liquibase needs. The import has moved to the integration tests, the only modules that use Arquillian, and an application now gets the versions its dependencies declare.
* **Dev services on Testcontainers 2** — the PostgreSQL and Keycloak providers run on Testcontainers 2.0.5 instead of 1.21.4, and JUnit 4 has left the plugin's class path, as only Testcontainers 1 needed it. A provider of your own moves to Testcontainers 2 with them, whose modules are now named `testcontainers-<module>`, such as `testcontainers-postgresql`. xref:dev-services.adoc[Dev services].
* **Codegen bundles are jars, so IntelliJ's build runs the annotation processors** — every `-codegen` bundle was a pom, declared with `<type>pom</type>`, which IntelliJ's Maven import ignores: its build compiled the application without any processor. Each bundle is now a jar holding an empty `module-info`, declared without `<type>`; IntelliJ resolves it with its dependencies as Maven does. The parent's default path, `vidocq extension add`, the scaffold and `checkpom` use the new form; an old `<type>pom</type>` path still builds and `checkpom` warns about it (Vidocq/vidocq#237). xref:modules/vidocq-runtime-extensions.adoc#codegen-bundles[Codegen bundles are jars].
* **An IDE build no longer starts an application without its generated code** — an IDE build that skips the annotation processors (IntelliJ's, with a `-codegen` bundle still declared as a pom) compiles `target/classes` without the generated code, and `maven-compiler-plugin` then finds nothing to recompile: the Servlet example started with no servlet. `vidocq:run` and `vidocq:dev` now compare the compiler's `createdFiles.lst` with `target/classes` before launching and, on a gap, warn, reset the compiler's incremental state and recompile once; the `(dev)` configuration of `vidocq:idea` runs `process-classes vidocq:dev`, as `vidocq dev` does (Vidocq/vidocq#237). xref:modules/vidocq-runtime-maven-plugin.adoc#compiler-output-check[An output compiled without the processors].
* **`vidocq:dev` passes `-Dvidocq.*` on to the application** — a `-Dvidocq.*` of the Maven command line used to stop at Maven: `mvn vidocq:dev -Dvidocq.chappe.listener.default.port=8081` still listened on the default port, silently, and `-Dvidocq.devconsole.port` never moved the dev console. The goal now forwards the same keys as `vidocq:run`, by the same rule: every `vidocq.*` key that is not a setting of the plugin. xref:modules/vidocq-runtime-maven-plugin.adoc#run[The properties the application sees].
* **`vidocq:dev` says which dev service provided a key** — each key that the application gets from a dev service is marked with `-Dvidocq.dev.provided.<key>=<provider id>`, such as `vidocq.dev.provided.vidocq.pool.audit.url=postgres`, so that the application can tell a dev-service datasource from one configured by hand: the Mansart pool section of the startup report and the dev console show `dev service postgres, localhost:54213`. The marker names the provider, never a value, and a key that an explicit value kept is not marked. The dev services report no longer takes the user info of a JDBC URL for its host. xref:modules/vidocq-runtime-extensions.adoc#mansart-pool-panel[Mansart pools in the startup report and the dev console].
* **`vidocq:run`** — one run of the application, in a JVM forked as the production launcher does, after the goal has forked the lifecycle up to `process-classes`: `mvn vidocq:run` alone compiles, completes the bean index with `vidocq:generate` and starts the application. Ctrl+C stops it, its exit code is the goal's result, `-Dvidocq.run.debug=true` opens a JDWP agent, and a `-Dvidocq.*` of the command line reaches the application. xref:modules/vidocq-runtime-maven-plugin.adoc#run[The `vidocq:run` goal].
* **The debugger listens on this machine only** — `vidocq:dev`, and `vidocq:run` with `-Dvidocq.run.debug=true`, used to start the JDWP agent with `address=*:5005`: every machine that could reach the port could attach, and a JDWP agent runs whatever code its debugger asks. The agent now listens on `127.0.0.1:5005`, which a debugger on the same machine reaches as before. `-Dvidocq.dev.debugHost='*'` (`vidocq.run.debug.host` for `vidocq:run`; quote the `*`, or zsh stops the command with "no matches found") opens it on every interface again, `0.0.0.0` too, and another address or host name on that interface; the goal then logs a warning that the debugger is reachable from the network. The connection hint of `vidocq dev --debug` prints `address=127.0.0.1:5005` as well. xref:modules/vidocq-runtime-maven-plugin.adoc#debugger[The debug agent].
* **Maven's colours reach the forked JVM** — `vidocq:run` and `vidocq:dev` pass Maven's own colour policy to the application as `-Dvidocq.console.color`. In an IDE's Maven console, which is neither a terminal nor an IntelliJ Run console, the runtime used to drop its colours while Maven's `[INFO]` lines kept theirs. An explicit `vidocq.console.color` and `NO_COLOR` still win. xref:modules/vidocq-runtime-maven-plugin.adoc#run-colours[Colours in the forked JVM].
* **`vidocq:idea`** (experimental) — IntelliJ IDEA shared run configurations per application of the reactor, written into `.run/` from what the poms already declare. By default it is three **Maven**/Remote files: a run of `vidocq:dev` suffixed ` (dev)` (the one a developer runs day to day), one of `vidocq:run` suffixed ` (run)`, and a Remote JVM Debug one suffixed ` (debug)` that attaches to `vidocq:dev`'s own debug agent (`vidocq.idea.kind=application` still writes a single Application run of the main class instead, with Make and `vidocq:generate` before launch, and no console or debug file of its own). Because the IDE's own build never runs `vidocq:generate`, the `(dev)` and `(run)` files compile, index and start the application entirely through Maven (Vidocq/vidocq#83). An application without a main class of its own, which declares `vidocq.mainModule` only and lets the runtime's main boot it, gets them too, named after its artifactId. It never overwrites a file you wrote or edited, never touches `.idea/`, and `-Dvidocq.idea.check=true` fails a CI build when `.run/` no longer matches the poms (`=strict` also fails on the files you wrote or edited). xref:modules/vidocq-runtime-maven-plugin.adoc#idea[The `vidocq:idea` goal].
* **Generated code for third-party CDI jars** — `vidocq:generate` now scans, besides `<scanDependencies>`, the jars an extension declares in its manifest and every CDI bean archive (`vidocq.generate.autoScan`, on by default), and gives each scanned jar the code the Vauban processor gives a project: `_VaubanComponents`, client proxies, intercepted subclasses. They ship in an enriched copy of the jar — given an `open module` first when it has no descriptor — that `dev`, `run`, `package` and `jlink` use in place of the original. The langchain4j-cdi MCP server's beans move from reflection to generated code. `mvn vidocq:analyze-deps` explains which jars are scanned and why (Vidocq/vidocq#186). Both goals resolve the runtime-scope dependencies as well as the compile-scope ones, so a class that only a runtime-scope extension makes a bean — a JAX-RS `@Provider` of a scanned jar, under Cassini's — gets generated code too (Vidocq/vidocq#188). xref:modules/vidocq-runtime-maven-plugin.adoc#generate[The `vidocq:generate` goal].

* **`vidocq:modularize` is now `vauban:modularize`** — the goal moved to `io.vidocq.vauban:vauban-maven-plugin`, with its properties renamed `vauban.modularize.*` and its output in `target/vauban-modularized/`, which `vidocq:dev`, `vidocq:jlink` and `vidocq:package` read. **When upgrading**, change the plugin in the pom. xref:modules/vidocq-runtime-maven-plugin.adoc#modularize[`modularize` moved to the Vauban plugin], xref:migration.adoc#modularize-moved[migration].
* **The legacy `vidocq:package` layout starts** — with `vidocq.package.layer=false`, the launchers passed a class name to `--module` and the JVM stopped on a `FindException`. They now launch `<vidocq.mainModule>/<vidocq.mainClass>`, or the runtime's own main when the application has none, and a plain main class without `vidocq.mainModule` fails the build with a message that says what to set (Vidocq/vidocq#198). xref:modules/vidocq-runtime-maven-plugin.adoc#package-legacy-layout[The legacy layout].
* **`vidocq:docker` checks that the image is Linux** — `vidocq:jlink` links against the build machine's JDK, so on macOS or Windows the image holds a Mach-O or PE `bin/java` that no Linux container starts. `vidocq:docker` reads it: it warns and still writes the `Dockerfile`, or, with `vidocq.docker.build=true`, fails before `docker build` (Vidocq/vidocq#199). xref:modules/vidocq-runtime-maven-plugin.adoc#docker-linux-image[The `vidocq:docker` goal].
* **`vidocq:checkpom` prints the `<path>` to add** — a missing codegen bundle used to be reported as a fall back to reflection, which only Cassini does; the message now gives the `<path>` entry to paste into `annotationProcessorPaths`, with its group and version. A `-dev` companion module is no longer asked for the codegen bundle of the extension it reads (Vidocq/vidocq#147). xref:modules/vidocq-runtime-maven-plugin.adoc#goals[Goals].
* **`vidocq:checkpom` fails when the Vauban indexer is gone** — an application whose `annotationProcessorPaths` has no `combine.children="append"` replaces the parent's entry, `vidocq-runtime-core-codegen`: it compiled, but its beans got no generated factory, and `checkpom` said "all aligned". It now fails such a build wherever an extension is declared, and says to add the attribute. xref:modules/vidocq-runtime-maven-plugin.adoc#goals[Goals].
* **The dev console follows the application's runtime version** — `vidocq:dev` used to resolve the console at the plugin's version, whatever runtime the application ran. It now takes the version of the application's Chappe extension, warns when the plugin's differs, and also looks in the plugin repositories, where a snapshot repository may be declared alone (Vidocq/vidocq#148). xref:dev-console.adoc#getting-it[Getting it].
* **An application can declare its own version** — `vidocq-runtime-parent` managed the Vidocq artifacts and the plugin at `${project.version}`, which Maven reads in the child: an application with a `<version>` of its own looked for the plugin and every extension at that version and could not build. The parent now writes the runtime version out. xref:reference.adoc#parent-pom-versions[Maven coordinates].

=== CLI

* **A CLI that says less and helps more** — `vidocq info` gives the environment and, in a project, its main module, runtime version, number of extensions and active profile, read from its files without running Maven; the detailed list stays in `vidocq extension list`. `vidocq config set` warns at once on a `vidocq.*` key no module reads and names the key meant (`vidocq.htpp.port` → `vidocq.http.port`), where only `vidocq doctor` saw it. Once a day at most, on a terminal, an installed CLI says after a command that `vidocq update` has a newer build (`VIDOCQ_NO_UPDATE_CHECK=1` turns it off). `vidocq extension list --available` and `mvn vidocq:list-extensions -Dvidocq.extensions.available` list the catalog by family (Jakarta EE, MicroProfile, Data, Web), which each extension's descriptor now names; the CLI no longer queries `registry.vidocq.dev`, which never existed, nor says "offline" (Vidocq/vidocq#353). xref:modules/vidocq-runtime-cli.adoc#update-notice[The update notice].
* **`vidocq create` writes a finished project** — with `-x cassini-rest`, a first test that starts the application with `@VidocqTest` and calls `GET /hello`, so `vidocq test` has something to run on day one; a `.gitignore` and a `README.md` with the commands that work. Without `--name`, on a terminal, it asks for the name, the group id and the extensions. `vidocq-runtime-it-create` builds what it writes with `mvn verify vidocq:jlink` on every pull request, and fails on any warning but the three javac ones documented as expected. xref:modules/vidocq-runtime-cli.adoc#create[`vidocq create`] (Vidocq/vidocq#339).
* **`vidocq doctor` checks the project, and `--fix` repairs it** — besides the machine, `doctor` now checks a Vidocq project from its sources, before any compile: the codegen bundle of each extension, the Vauban indexer, the `module-info.java` directives each extension needs, the Maven the wrapper runs and whether the HTTP port is free. `vidocq doctor --fix` wires a missing codegen bundle and removes a stale one, makes `annotationProcessorPaths` append to the parent's, adds the missing directives, writes a missing wrapper and upgrades an older one; every fixable line ends with the command that fixes it. A project `vidocq create` has just written reports no warning, and an application without an extension is no longer one (Vidocq/vidocq#339). xref:modules/vidocq-runtime-cli.adoc#doctor-project[The project checks].
* **No Vidocq version to write any more** — under a `vidocq-runtime-parent` from 0.4.0, or in a pom that imports `vidocq-runtime-bom`, `vidocq create` and `vidocq extension add` (and `vidocq:create`, `vidocq:add-extension`) write the Vidocq dependencies and codegen paths without a `<version>`: the BOM gives it. A created pom names two versions, its parent's and its own. xref:migration.adoc#application-parent[The application parent].
* **The CLI and the Maven plugin, side by side** — a table gives the goal of every command and how the two agree: the commands that edit or check the project and their goals run the same `vidocq-runtime-tooling` code (Vidocq/vidocq#314). xref:modules/vidocq-runtime-cli.adoc#cli-and-plugin[The CLI and the Maven plugin].
* **`vidocq vscode`** — writes `.vscode/` for VS Code's Java extension: its language server on Java 25, which Vauban's annotation processors need, with its automatic build off, so that `vidocq dev` alone writes `target/classes`; tasks for `vidocq dev`, `run` and `test`; a debug configuration attached to `vidocq dev`. `mvn vidocq:vscode` does the same, and `--check` verifies the files in CI (Vidocq/vidocq#339). xref:modules/vidocq-runtime-maven-plugin.adoc#vscode[The `vidocq:vscode` goal].
* **`vidocq eclipse`** — writes `.eclipse/` for Eclipse IDE 2026-09: Maven builds of `vidocq dev`, `run` and `test` and a debug configuration attached to `vidocq dev`, listed under Run Configurations. `mvn vidocq:eclipse` does the same, and `--check` verifies the files in CI. `vidocq-runtime-parent` now turns m2e's annotation processing on (`m2e.apt.activation`): without it, Eclipse's build wrote an application with no bean index (BUG-20261025-06). xref:modules/vidocq-runtime-maven-plugin.adoc#eclipse[The `vidocq:eclipse` goal].
* **`vidocq test` and `vidocq idea`** — the two plugin goals the CLI had no command for: `vidocq test` runs `mvn vidocq:test`, the tests on every change without the application; `vidocq idea [--check|--strict] [--kind application]` runs `mvn vidocq:idea`, the IntelliJ run configurations. Both complete in the shell (Vidocq/vidocq#314). xref:modules/vidocq-runtime-cli.adoc#test[`vidocq test`], xref:modules/vidocq-runtime-cli.adoc#idea[`vidocq idea`].
* **`vidocq create` writes a project of its own** — the application has its own version, `1.0.0-SNAPSHOT`, instead of the runtime's, which moved with every Vidocq upgrade (BUG-20261024-06); it gets the Maven wrapper of the Vidocq repositories, so it builds with the ecosystem's Maven and `vidocq doctor` no longer warns on the project `create` has just written (BUG-20261024-08); its pom no longer carries the `jvmArgs` and `<mainClass>` workarounds of 0.2.0 bugs fixed since (BUG-20261024-07); and `--main` names the trampoline of `demo-app` `DemoApp`, not `DemoAppApp` (BUG-20261024-09). `create` ends with `vidocq dev`, `vidocq build` and `vidocq start`, and `vidocq:create` with `./mvnw vidocq:dev`. xref:modules/vidocq-runtime-cli.adoc#create[`vidocq create`].
* **An unknown extension id is refused** — `vidocq extension add`, `vidocq create -x` and their goals turned an id outside the catalog into `io.vidocq.runtime:vidocq-runtime-<id>-extension`, a coordinate no Vidocq extension has, so the next build failed to resolve it (BUG-20261024-04). They now refuse it, name the closest catalog ids (`mansart-persistence` → `mansart-data, mansart-pool, mansart-transactions`) and write nothing; an extension outside the catalog is added as `groupId:artifactId`. The runtime parent now manages `vidocq-runtime-grimm-openapi-extension` and `vidocq-runtime-grimm-openapi-ui-extension`, so a pom declares them without a version like the others (BUG-20261024-05); the catalog describes `mansart-data` as Jakarta Data 1.0 repositories, not Jakarta Persistence (BUG-20261024-03); and `add` no longer warns about the Vauban indexer in a pom that lists it itself, as one without the Vidocq parent does (BUG-20261024-02). xref:modules/vidocq-runtime-cli.adoc#extension[`vidocq extension`].
* **No `provides` advice on every build** — Vauban's processor told every application to add `provides io.vidocq.vauban.api.VaubanComponentProvider with <pkg>._VaubanComponents;` to its `module-info.java`, which a Vidocq application does not need: the application layer declares it when it loads the module (BUG-20261024-10). The runtime parent passes `-Avauban.providesHint=false`, so the note only says what was generated.
* **`vidocq create` writes the extensions in the order given** — two runs of the same command could write the dependencies and codegen paths of the pom in two different orders (BUG-20261024-01). xref:modules/vidocq-runtime-cli.adoc#create[`vidocq create`].
* **`vidocq extension add` declares the dependency where Maven reads it** — on a pom whose `<dependencyManagement>` comes before its `<dependencies>`, the usual order, `add` wrote the extension into the managed list, so it was never a dependency of the application, although `add` said it was added (BUG-20261023-08). It now writes into the project's own `<dependencies>`, and `remove` drops that element when it leaves it empty (BUG-20261023-07). xref:modules/vidocq-runtime-cli.adoc#extension[`vidocq extension`].
* **The extensions describe themselves to the CLI** — each first-party extension ships `META-INF/vidocq/extension.properties`: its short id, description, codegen bundle, and the `module-info.java` directives `vidocq extension add` and `vidocq create -x` write. The CLI's catalog is built from those descriptors, and a test fails when the two no longer match, so the CLI can no longer miss a codegen bundle that the extension gained. The catalog now lists the extensions sorted by id (Vidocq/vidocq#314). xref:modules/vidocq-runtime-cli.adoc#extension-descriptor[For extension authors].
* **`vidocq create` writes no main class unless asked** — the runtime's own main boots the application from `vidocq.mainModule`, under `vidocq dev`, `vidocq start` and the launchers of `mvn package`, so the scaffold no longer writes an `…App` class, a `vidocq.mainClass` or the `<mainClass>` of the `vidocq:package` execution, and `module-info.java` no longer requires `io.vidocq.runtime.core`. `--main` brings the `@VidocqMain` trampoline back, for a right-click Run in the IDE or logic after boot (a `VidocqApp`); `vidocq:jlink` and `vidocq:jpackage` link the main-less project as it is. With `-x cassini-rest` the scaffold writes a `HelloResource` (`GET /hello`): the module can only open a package that holds a class, and the JVM refused one with no class ("Package … not found in module"). For the same reason, `create` and `vidocq extension add` no longer open an application package that has no class yet, and say to add the `opens` once it has one. xref:modules/vidocq-runtime-cli.adoc#create[`vidocq create`].
* **A scaffolded application runs the same everywhere** — `vidocq create` now writes a `@VidocqMain` class whose `main` is `Vidocq.run(args)`, as the examples do. The `VidocqBootstrap` main it wrote before booted in place: in a jlink image the application stayed in the boot layer, where the build-time generated `_VaubanComponents` is not seen without a `provides`, and Vauban fell back to reflection, so a bean with an interceptor (a `@Retry` method, for instance) failed with `IllegalAccessException` unless the package was exported. An application scaffolded with `0.3.0` can replace its `main` by the new one. `create` also refuses a name or `--package` that is not a valid Java package name (`ft-030` gave the module `io.example.ft.030`, which does not compile). xref:modules/vidocq-runtime-cli.adoc#getting-started[Getting started].
* **Scaffold against a SNAPSHOT** — when the parent version is a SNAPSHOT, `vidocq create` writes the Central snapshot repository into the generated `pom.xml`, for dependencies and plugins, so `--parent-version 0.4.0-SNAPSHOT`, or a CLI installed with `VIDOCQ_VERSION=snapshot`, gives a project that builds as is. See xref:modules/vidocq-runtime-cli.adoc#create-snapshot[Trying a SNAPSHOT].
* **`vidocq dev` and `vidocq start` run the project** — both booted the runtime inside the CLI's own JVM, which holds neither the project's classes nor its extensions, so nothing listened. They now run `mvn process-classes vidocq:dev` and `mvn vidocq:run`, through `./mvnw` when there is one, and behave as the goals do: live reload, dev console, debug agent. `--port` outranks the project's `vidocq.http.port`. xref:modules/vidocq-runtime-cli.adoc#dev[`vidocq dev`], xref:modules/vidocq-runtime-cli.adoc#start[`vidocq start`].
* **`vidocq extension add` declares the module too** — besides the dependency and the codegen bundle, `add` writes the extension's directives into `module-info.java` (its `requires`, and what Cassini and Mansart Data leave to the application), each marked `// vidocq:<id>`, and pins the parent's version on what it adds; `remove` takes all of it back, the codegen path included. The catalog lists the OpenAPI, Swagger UI and migration extensions, and knows the Config and Rest Client codegen bundles. `vidocq extension list`, `vidocq info` and `vidocq doctor` resolve the project's dependencies with Maven, so they see its extensions, transitive ones marked `(transitive)`, instead of none. xref:modules/vidocq-runtime-cli.adoc#extension[`vidocq extension`].
* **`vidocq extension add` wires the codegen bundle where the build reads it** — it used to edit the first `annotationProcessorPaths` of the file, which could be a profile's or `pluginManagement`'s; to declare a second `maven-compiler-plugin` next to the one the pom had, which Maven warns about; and to leave a block that replaced the parent's, without the Vauban indexer. It now fills the compiler plugin of the project's build, and makes its block append to the parent's. `vidocq help create` gives catalog ids in its example. xref:modules/vidocq-runtime-cli.adoc#extension-codegen-path[Where the codegen path goes].
* **Completion for the whole command line** — sub-commands, options and values: the extensions not yet in the pom after `extension add`, those it declares after `extension remove`, the keys of `vidocq.properties` after `config get|set`, all without starting a JVM. `vidocq completion install` sets it up in `~/.zshrc` or `~/.bashrc`, and an installed script follows the CLI that runs. xref:modules/vidocq-runtime-cli.adoc#completion[`vidocq completion`].
* **`vidocq update`** — updates the CLI itself, a release to the latest release, a SNAPSHOT to the latest SNAPSHOT build; `--check` only reports. A SNAPSHOT CLI also prints its build time next to its version. xref:modules/vidocq-runtime-cli.adoc#update[`vidocq update`], xref:modules/vidocq-runtime-cli.adoc#command-reference[Command reference].

=== Other bricks

* **Vauban** — client proxies for third-party produced types, without `opens`: the Java SE launcher places them, `Vidocq.run` re-layers with the same policy, and boot-time opening stays opt-in. xref:dev@vauban::whats-new.adoc[What's new in Vauban].
* **Cassini** — an unreadable request entity answers 400, not 500, and a host reads the route table and live request figures. xref:dev@cassini::whats-new.adoc[What's new in Cassini].
* **Mansart** — enums stored as `@Enumerated` says, a stricter JDQL parser, and the Jakarta Data core the dev console's tools use. xref:dev@mansart::whats-new.adoc[What's new in Mansart].
* **Heisenberg** — fallback methods reached on a strict module path, with no `opens`. xref:dev@heisenberg::whats-new.adoc[What's new in Heisenberg].
