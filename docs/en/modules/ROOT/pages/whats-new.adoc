= What's new
:description: Everything that changed in this component since the {release-version} release.

[.lead]
New in the `{project-version}` development line — everything listed here landed **after the {release-version} release** and is not part of it. Every entry links to the section that documents it, and those sections carry the [.tag-new]#NEW# badge. Each brick of the suite keeps its own page of this kind; xref:home::whats-new.adoc[the ecosystem index] gathers them. When the next release train ships, this page is frozen with it and restarts empty on the dev line.

== Jakarta EE web

* xref:cassini::internals.adoc#dependent-resource-release[A `@Dependent` REST resource ends with its request on a filtered mount too] [.tag-new]#NEW# — a mount with `include-packages` or `exclude-packages` now hands Cassini what ends a `@Dependent` resource after its request, so its `@PreDestroy` runs there as on an unfiltered mount (BUG-20261118-01).
* xref:mansart::migration.adoc#mapped-names-unquoted[Mansart Data no longer quotes table and column names] [.tag-new]#NEW# — a repository writes a mapped name as the mapping gives it, as Jakarta Persistence does, so a repository and a Noether persistence unit that share an entity name the same table. *An H2 schema created with quoted lower-case names breaks*: H2 reads the unquoted `products` as `PRODUCTS`, and the first repository call fails with `The table products of entity … does not exist`, caused by H2's `Table "PRODUCTS" not found (candidates are: "products")`. Two ways out: remove the quotes from the DDL (`CREATE TABLE products (...)`), or write the mapped name with quotes (`@Table(name = "\"products\"")`, `@Column(name = "\"name\"")`). On PostgreSQL an unquoted name folds to lower case, so tables created without quotes need nothing. The two examples that ship a schema (`vidocq-runtime-mansart-h2-example`, `vidocq-runtime-petstore-example`) now create their tables without quotes (MANSART-067).

* xref:modules/vidocq-runtime-extensions.adoc#servlet-built-in-beans[`@Inject HttpServletRequest`, `HttpSession` and `ServletContext`] [.tag-new]#NEW# — with the Servlet extension, a bean injects the request being served, its session and the application's context, which Foy provides as `@RequestScoped`, `@SessionScoped` and `@ApplicationScoped` beans (Vidocq/foy#107). An application that declares its own producer of one of these types now fails at start with an ambiguous dependency: remove it.
* xref:modules/vidocq-runtime-extensions.adoc#foy-websocket[Jakarta WebSocket 2.2 (Foy)] [.tag-new]#NEW# — `vidocq-runtime-foy-websocket-extension` brings Foy's programmatic WebSocket server API into the application, and `vidocq-runtime-vaadin-extension` brings it to a Vaadin application, so `@Push(transport = Transport.WEBSOCKET_XHR)` works (Vidocq/vidocq#65). The `vidocq.websocket.allowed-origins` key lists the origins allowed to open a WebSocket besides the server's own, and it also applies to native `type=websocket` mounts, which now refuse another origin with a 403: see xref:migration.adoc#websocket-origins[the migration note].
* xref:modules/vidocq-runtime-extensions.adoc#foy-websocket[Refused WebSocket origins name your key] [.tag-new]#NEW# — the WARNING logged when a handshake from another origin is refused names `vidocq.websocket.allowed-origins`, for native Chappe routes and Jakarta WebSocket endpoints alike, no longer `Router.Builder.webSocketOrigins` or Foy's init parameter (BUG-20261114-13).
* xref:modules/vidocq-runtime-extensions.adoc#foy-websocket[WebSocket connections closed with 1001 at stop] [.tag-new]#NEW# — an application stop closes Foy's deployments before the Chappe servers stop: every open WebSocket gets a Close frame of code 1001 and `onClose` with 1006, a close the container initiates (Jakarta WebSocket 2.2 §2.1.5, Foy BUG-20261115-08), without `onError`, and `Servlet.destroy()` runs while the server still serves. Extensions can run work at that point with `ChappeMountPoint.addBeforeStopHook` (BUG-20261115-01).
* xref:modules/vidocq-runtime-extensions.adoc#bodoni-jstl[Jakarta Standard Tag Library 3.0 (Bodoni)] [.tag-new]#NEW# — `vidocq-runtime-bodoni-jstl-extension` gives the pages Ibarra compiles the `c:`, `fmt:`, `fn:`, `x:` and `sql:` tags (official Tags TCK 541/541 on Bodoni + Ibarra + Foy + Peano, not a certification), with Ibarra, the Servlet extension and Peano; `vidocq extension add bodoni-jstl` wires it (Vidocq/vidocq#266).
* xref:modules/vidocq-runtime-extensions.adoc#noether-persistence[Jakarta Persistence 3.2 (Noether)] [.tag-new]#NEW# — `vidocq-runtime-noether-persistence-extension` runs the units of `persistence.xml` on the application's Mansart pools, with `@PersistenceContext` and `@PersistenceUnit` injected and JTA units in `@Transactional`, which share the connection of a transaction with the Mansart Data repositories on the same pool (Vidocq/mansart#103); `vidocq extension add noether-persistence` wires it with Mansart Pool and Mansart Transactions (Vidocq/noether#45).
* xref:modules/vidocq-runtime-extensions.adoc#noether-persistence-inject[Persistence units injected with `@Inject`] [.tag-new]#NEW# — every unit of `persistence.xml` is also an `EntityManagerFactory` bean named after it, a transaction-scoped `EntityManager` bean for a JTA unit, and its `CriteriaBuilder`, `PersistenceUnitUtil`, `Cache`, `SchemaManager` and `Metamodel`, under the qualifiers and the scope its `<qualifier>` and `<scope>` elements name (Jakarta EE 11 Platform §13.12, Vidocq/noether#72). A unit and a named pool of the same name now fail the start, as two beans of one name: rename one of them.
* xref:modules/vidocq-runtime-extensions.adoc#noether-persistence-report[Persistence units in the startup report] [.tag-new]#NEW# — the `noether-persistence` section counts the injected units and their entities, and in a dev boot or a detailed report gives each unit's transaction type, pool, schema action and declared entities, embeddables, named queries and indexes.
* xref:modules/vidocq-runtime-extensions.adoc#noether-persistence-dev[A Persistence panel in the dev console] [.tag-new]#NEW# — under `vidocq:dev`, a *Persistence unit* dropdown above six tabs: the units' counts, a graph of the model, JPQL queries and writes (rolled back unless asked to commit), a paged view of an entity whose selected rows open a DELETE or an UPDATE, the declared indexes against the database's, and the create and drop scripts.
* xref:modules/vidocq-runtime-extensions.adoc#noether-persistence-inject[Persistence beans proxied without reflection] [.tag-new]#NEW# — the `@Inject` `EntityManager` and `EntityManagerFactory` go through client proxies generated when the Noether extension is built, no longer through a `java.lang.reflect.Proxy` built at start, and the start no longer warns of a run-time code generation fallback for them (Vauban BUG-20261113-19).
* xref:modules/vidocq-runtime-extensions.adoc#noether-persistence-per-module[One `persistence.xml` per module] [.tag-new]#NEW# — a library module may declare its units next to its entities, and each unit manages the entities of its own module. Two units of one name now fail the start, naming every file that declares it (Vidocq/noether#78): rename one of them.
* xref:modules/vidocq-runtime-extensions.adoc#noether-persistence-keys[Persistence units declared with keys] [.tag-new]#NEW# — the `vidocq.persistence.<unit>.*` keys declare a unit without a `persistence.xml` (`module`, `packages`, `classes`, `transaction-type`, `qualifier`, `scope`), or set the pool and the properties of a unit a `persistence.xml` declares (`datasource`, `non-jta-datasource`, `properties.<name>`). Without any key and any `persistence.xml` unit, the entities of the application module make a unit named `default`. The build reads the keys of `vidocq.properties` for the beans it freezes, and a start whose keys would need other beans fails and asks for a rebuild (Vidocq/vidocq#551, Vidocq/noether#87).

== Build

* xref:modules/vidocq-runtime-maven-plugin.adoc#frozen-extensions[Build compatible extensions frozen at build] [.tag-new]#NEW# — `vidocq:generate` runs the build compatible extensions of the application once and records what they did; the start loads the record instead of running them, 30 to 40 ms less on a 425 ms start of an application with eleven extensions. The startup report says `cdi extensions  10 extensions frozen at build`. `-Dvidocq.freezeExtensions=false` keeps the former behaviour (Vidocq/vauban#288). What an extension author must do: xref:internals.adoc#frozen-bce[Build compatible extensions, frozen at build]. What an extension of another project reads while a phase runs is the build's (xref:modules/vidocq-runtime-maven-plugin.adoc#frozen-extensions-of-another-project[an extension of another project]), and a library module that runs the goal sets `freezeExtensions` to `false` (xref:modules/vidocq-runtime-maven-plugin.adoc#frozen-extensions-library[a record belongs to an application]).
* xref:modules/vidocq-runtime-core.adoc#vidocq-gen-003[A refused record names what differs] [.tag-new]#NEW# — a production start that finds the record of another deployment, and so runs the build compatible extensions, warns with `VIDOCQ-GEN-003` and names the bean classes added, removed or changed since the build; `vidocq.startup.require-frozen-extensions=true` makes it fail.
* xref:modules/vidocq-runtime-maven-plugin.adoc#nothing-to-freeze[Extensions that all ran at compile do not run again at start] [.tag-new]#NEW# — a packaged application whose bean archives were all processed at compile, such as one with the Servlet extension alone, ran its build compatible extensions at every start, and refused to start with `vidocq.startup.require-frozen-extensions=true` (BUG-20261115-05, Vauban BUG-20261115-07). It now runs none: `vidocq:generate` says `nothing to freeze: every build compatible extension of the deployment ran at compile`, no longer that the deployment has no build compatible extension, and the startup report has no `cdi extensions` row.
* xref:usage.adoc#app-layer-dependencies[`vidocq.app.layer=all` is the default] [.tag-new]#NEW# — the application layer holds the application and its libraries, outside the runtime and the bricks, in `vidocq:run`, `vidocq:dev`, an IDE launch and `vidocq:package` alike (Vidocq/vidocq#247). It was `classes`. An application that worked keeps working: where `all` cannot be honoured and was not asked for, the build warns and falls back to `classes`. Vaadin no longer needs the property. Opt out with `vidocq.app.layer=classes`; see xref:usage.adoc#app-layer-migration[the migration note].
* xref:modules/vidocq-runtime-maven-plugin.adoc#parentless[An application without `vidocq-runtime-parent`] [.tag-new]#NEW# — `vidocq create` writes a pom that imports the BOM and declares the plugin as a build extension; the plugin gives the build what the parent carried (the executions, the Java release, the source encoding, the compiler argument, the lifecycle plugin versions, the Surefire property, the m2e switch), once, and leaves what the pom has. A company parent stays. `--with-parent` writes the previous style (Vidocq/vidocq#380).
* xref:modules/vidocq-runtime-cli.adoc#pom-convert[`vidocq pom convert --to parentless|parent`] [.tag-new]#NEW# — turns an existing pom from one style into the other, idempotently, keeping everything else where it is; the diff first, `--check` for CI.
* xref:modules/vidocq-runtime-cli.adoc#pom-upgrade[`vidocq pom upgrade [--to <version>|--release|--snapshot] [--check]`] [.tag-new]#NEW# — moves an application to another Vidocq version in either pom style, or in a pom written before 0.4.0; the diff first, `--check` for CI, versions that disagree reported and never aligned.
* xref:modules/vidocq-runtime-maven-plugin.adoc#build-info[`vidocq:build-info`] [.tag-new]#NEW# — the build identity the banner reads, written by the plugin itself from `.git` (plain repository, worktree, submodule, shallow clone), with no third-party plugin, with `vidocq-runtime-parent` as without it: the parent's `git-commit-id-maven-plugin` named the main checkout's commit for an application built from a linked worktree (BUG-20261117-06). Without a repository the commit reads `unversionned` and the build goes on; without a `git` command that answers, the dirty flag and the commit time are left out and the log line says so.
* xref:modules/vidocq-runtime-maven-plugin.adoc#jlink-every-module[A jlink image resolves every staged module] [.tag-new]#NEW# — `vidocq:jlink` linked every module but rooted only the application's: a module that nothing `requires`, such as Vaadin's `flow.push`, `vaadin.lumo.theme` and `vaadin.aura.theme`, was in the image and never resolved, and its `META-INF/resources` answered 404. The image now roots every staged module, in both launch shapes; `vidocq:jpackage` does the same for the image it packages.
* xref:modules/vidocq-runtime-maven-plugin.adoc#layer-off[The application loaded once by every launcher] [.tag-new]#NEW# — the `vidocq:package` launchers under `vidocq.app.layer=classes` hand `app/` to the runtime as under `all`, and the launches without a layer (`vidocq.package.layer=false`, `vidocq.dev.layer=false`) pass `-Dvidocq.app.layer.off=true`, which a `@VidocqMain` trampoline honours. With a trampoline main, both used to load the application module twice, in the boot layer and in the application layer: a `ServiceLoader` found each of its providers twice (BUG-20261114-10).
* xref:modules/vidocq-runtime-maven-plugin.adoc#docker-jdk-kind[A Docker image on a JDK base] [.tag-new]#NEW# — `vidocq:docker -Dvidocq.docker.kind=jdk` copies the `vidocq:package` distribution onto `eclipse-temurin:<version>-jre` and starts it with its own launcher: the application keeps its application layer, so an encrypted jar works there, and a library that is not a named module is used as it is. The default kind, `jlink`, is unchanged; the choice is explicit (Vidocq/vidocq#580). A new page, xref:shipping.adoc[Choosing how to ship], says which form fits which situation, and why.
* xref:modules/vidocq-runtime-maven-plugin.adoc#jlink-one-layer[A jlink image has one layer] [.tag-new]#NEW# — the image of `vidocq:jlink`, the `vidocq:jpackage` application and the `vidocq:docker` image start as a plain modular application, with no application layer: one copy of each module, by construction. They used to hold the application module in the boot layer and in the application layer, and a `ServiceLoader` found each of its providers twice (BUG-20261114-11). Before linking, the build adds to the staged modules the `provides` their services files declare, which the application layer promotes at start elsewhere; `vidocq.app.layer` no longer applies to an image, and an encrypted jar needs a `vidocq:package` distribution: `vidocq:jlink` fails with a message that names it (Vidocq/vidocq#580).
* xref:modules/vidocq-runtime-core.adoc#vidocq-lay-001[`VIDOCQ-LAY-001`: an IDE run loads the application twice] [.tag-new]#NEW# — a `@VidocqMain` trampoline run from the IDE, with the application on the module path, loads it again into the application layer; the start now warns and names the modules held twice, and points to the `(dev)` and `(run)` configurations of `vidocq:idea`, which load it once (BUG-20261114-10).
* xref:modules/vidocq-runtime-maven-plugin.adoc#parentless[`vidocq:checkpom` and the Java release] [.tag-new]#NEW# — warns when `maven.compiler.release` came from the plugin: IntelliJ IDEA reads the language level from the pom alone.
* xref:modules/vidocq-runtime-extensions.adoc#humboldt-telemetry-codegen[A codegen bundle for the Telemetry extension] [.tag-new]#NEW# — `vidocq-runtime-humboldt-telemetry-extension-codegen` puts Humboldt's Build Compatible Extension on the processor path, so the interceptor binding of each `@WithSpan` class and method is written into the build instead of being added again at each start; the plugin wires it, and a pom that lists its bundles by hand adds it, as xref:migration.adoc#metrics-openapi-codegen[the migration note] says (BUG-20261113-02, Vidocq/vidocq#546).

== Dev services

* xref:dev-services.adoc#test-run-files[A test run has files of its own] [.tag-new]#NEW# — the JUnit listener writes `target/vidocq-dev-services-test.json` and `-test.properties`, `vidocq test` and the tests of `vidocq dev` a pair each of their own, so a test run beside `vidocq dev` no longer overwrites the dev session's files, and the next reload no longer reports the test run's container as the application's, `stopped` (BUG-20261106-03). A `mvn test` beside `vidocq test` or `vidocq dev` no longer rewrites their tests' files either (BUG-20261114-08).
* xref:dev-services.adoc#test-run-files[A test run never lands on the application's container] [.tag-new]#NEW# — `mvn test`, `vidocq test` and the tests of `vidocq dev` reuse no container and pin no host port, whatever `vidocq.dev.reuse` and the `vidocq.dev.<service>.port` keys say. With `vidocq.dev.reuse=true`, a test run beside `vidocq dev` got the application's container back by its name, and a test that empties a table emptied the application's (BUG-20261114-08).

== Testing

* xref:testing.adoc#application-layer[`@VidocqTest` starts the application layer of `vidocq:run`] [.tag-new]#NEW# — the application module and, under `vidocq.app.layer=all`, its libraries reach the runtime through `vidocq.app.path` and leave the module path. The application module was on both: the JVM loaded it twice, a `ServiceLoader` found each `provides` of its `module-info.java` twice, and a Vaadin application whose module provides an `InstantiatorFactory` answered 500, _multiple eligible instantiator implementations_, while its packaged distribution started (BUG-20261114-07). `vidocq.app.layer` and `vidocq.app.layer.keep` are read from `@VidocqTest(properties)`.
* xref:testing.adoc#http-port[`@VidocqTest` lets the system pick the port] [.tag-new]#NEW# — the application's listener binds port `0`, then writes the port it got to a file the start reads, whatever the logging configuration of the application. The extension picked a free port, closed it, and gave it to the application, which bound it later: another process could take it in between, and the application then failed to start (BUG-20261114-09). A port `@VidocqTest(properties)` names now works: the start waited for the port it had picked and timed out.

== Dev mode

* xref:usage.adoc#dev-swap-sessions[HTTP sessions survive a layer swap] [.tag-new]#NEW# — a change that swaps the application layer under `vidocq dev` no longer invalidates the HTTP sessions: the servlet deployment writes them out at the stop, and the new one reads them back before it serves, `Hot reload - kept 1 HTTP session across the reload`. A Vaadin page keeps its UI. `vidocq dev` drops them, and says why, when a changed serializable class gained, lost or retyped an instance field, its serializable lambdas or anonymous classes moved, or its `serialVersionUID` moved where Java would refuse to read it back: a method added to a view keeps them, a declared `serialVersionUID` given another value drops them (BUG-20261117-04); `-Dvidocq.dev.keepSessions=false` drops them at every swap. CDI session state moves too: the `@SessionScoped` beans with their state, the client proxies they hold, and the `@Inject HttpSession` bean.
* xref:usage.adoc#dev-reload-reasons[`vidocq dev` says why a change reloads] [.tag-new]#NEW# — after each recompile, `vidocq dev` compares the compiled output with the one the application runs. An unchanged output, for instance after an edited comment, reloads nothing, and the tests of the change still run. Any other change names its reason on both sides of the log: `Hot reload - restarting on a fresh application layer: MainView gained a method lambda$new$1`. The extensions xref:modules/vidocq-runtime-extensions.adoc#start-time-code[declare their start-time code] in `META-INF/vidocq/dev/start-time.properties`. With a runtime that declares none, the reload is unchanged.
* xref:continuous-testing.adoc#dev-services[The tests of `vidocq dev` keep off the application's data] [.tag-new]#NEW# — continuous testing gets dev services of its own, opened at the first test run and stopped with `vidocq dev`, so a test's `TRUNCATE … RESTART IDENTITY` no longer wipes what the running application just stored in the same PostgreSQL. They reuse no container and pin no host port, whatever `vidocq.dev.reuse` and `vidocq.dev.postgres.port` say; dev services off for `vidocq dev` still means none for the tests. The cost is a second set of containers and a slower first run (BUG-20261114-08).
* xref:modules/vidocq-runtime-maven-plugin.adoc#debugger-port-busy[A second `vidocq dev` on the machine starts] [.tag-new]#NEW# — the debug port is checked before the application JVM is forked: left at its default and held by another session, it moves to a free port with a warning that names both; set with `vidocq.dev.debugPort`, busy, it fails the goal at once, naming the port and the property. The JVM died at start with `transport error 202: bind failed`, and nothing said the debug port was the cause (BUG-20261114-03). `vidocq:run -Dvidocq.run.debug=true` does the same with `vidocq.run.debug.port`.
* xref:continuous-testing.adoc#when-tests-run[An application that dies before it is ready is reported down] [.tag-new]#NEW# — when the application JVM stops before it is ready, `vidocq dev` no longer speaks of a reload at the first start: its warning says that the application's output above gives the reason, and that the next change starts it again (BUG-20261114-04).
* xref:continuous-testing.adoc#terminal[A failed test class is named by its class] [.tag-new]#NEW# — when a test class fails as a whole, in an `@BeforeAll` or while the application starts, `vidocq dev` and `vidocq:test` name it `com.acme.HelloResourceTest`, not `com.acme.HelloResourceTest#` with an empty method (BUG-20261114-06).
* xref:continuous-testing.adoc#terminal[The line of a failed test, at last] [.tag-new]#NEW# — `vidocq dev` and `vidocq:test` print where a test failed, `(OrderServiceTest.java:31)`, for the tests of a Vidocq application too: they run in a named module, whose frames the JDK prints as `com.acme@1.0.0/com.acme.OrderServiceTest…`, and the line was never found (BUG-20261106-02).
* xref:continuous-testing.adoc#limits[The first test run under `vidocq dev` downloads what the tests need] [.tag-new]#NEW# — a continuous-testing run that misses a test-scope jar or Surefire's JUnit provider offline runs again once online, so `vidocq dev` on a new project no longer reports a failed run, with `Cannot access central in offline mode` in its log, before any test ran (BUG-20261106-01).
* xref:continuous-testing.adoc#who-builds[A save just after a reload is applied] [.tag-new]#NEW# — the test runs of `vidocq dev` no longer compile the main sources: the recompile of the dev loop alone builds `target/classes`, and a run that a change stops loses what it wrote before the next one starts, under `vidocq:test` too. A run started just after a save compiled the main sources itself, and the change stopped it while javac wrote its classes: the recompile then found nothing to compile and failed on a generated class that was missing, `Missing compiled Peano accessor provider`, as did every recompile until a Java source was saved again (BUG-20261117-01).
* xref:usage.adoc#dev-preload-classes[The application keeps its classes while a recompile runs] [.tag-new]#NEW# — the application reads its classes from `target/classes` when it first uses them, and the compiler plugin removes the classes it created before it compiles the module again: they stay out while a save does not compile. A page whose classes no request had asked for yet answered 500 with a `NoClassDefFoundError`, and kept answering 500 once the class was back, until the next layer swap. `vidocq dev` now loads every class of the application's directories as soon as the application layer starts, without running their static initializers. `-Dvidocq.dev.preloadClasses=false` gives the previous behaviour (BUG-20261117-09).
* xref:usage.adoc#dev-save-while-starting[A save made while `vidocq dev` starts is applied] [.tag-new]#NEW# — `vidocq dev` watches the sources last, after the build and the dev services. A file saved before that began no recompile: the application started without the save, and kept running without it until another save. `vidocq dev` now looks, once it watches, for the files saved since Maven started, compiles them before the application starts, and names them: `Menu.java was saved while vidocq:dev started: compiling it before the application starts.` A start with no save compiles nothing more (BUG-20261117-05).
* xref:usage.adoc#dev-changed-while-stopped[`mvn vidocq:dev` builds what changed while it did not run] [.tag-new]#NEW# — `mvn vidocq:dev` alone runs no phase of the build, and started the application from the classes of the last build: a source edited, added or deleted since was not in them, and nothing said so. The goal now compares the watched files with the record the compiler keeps of its last run, builds the project first when one is newer or when a compiled source is gone, and names it: `Since the last build, Menu.java changed: building the project first (mvn process-classes).` A source your IDE compiled, or one saved while the last build compiled it, has a class that looks up to date: it loses that class first, so that the build compiles it with the annotation processors (BUG-20261117-08). A start with no change builds nothing, and `vidocq dev`, which builds first, is as before (BUG-20261117-07).
* xref:usage.adoc#dev-save-while-compiling[A save made while a recompile runs is applied] [.tag-new]#NEW# — javac reads every source, then writes the classes. A source saved in between got a class newer than itself, compiled from what javac had read, and Maven took it for compiled: the save showed only once another Java source was saved. `vidocq dev` now deletes that class when the next recompile starts, and names the source: `Menu.java was saved since the previous recompile started and its class is not older: compiling it again.` The test runs of `vidocq dev` and of `vidocq:test` do the same for the sources they compile. A class your IDE compiled after the recompile stays (BUG-20261117-03).

== Dev console

* xref:dev-console-panels.adoc#action-result[A SQL result] [.tag-new]#NEW# — an action can answer `ActionResult.SQL`, `application/sql`: the page shows the script as text with a *Download* button, which saves it as a `.sql` file without a request.
* xref:dev-console.adoc#graph-view[A graph result] [.tag-new]#NEW# — an action can answer `ActionResult.ofGraph(summary, nodes, edges)`, which the page lays out as boxes and lines, with a parent above its subclass and a box's facts listed on a click.
* xref:dev-console.adoc#rows-menu[A menu on the selected rows] [.tag-new]#NEW# — a result of rows can offer entries that fill another action's form with the ticked rows' values, such as `DELETE FROM Note e WHERE e.id IN (1, 3)`. A right-click opens them at the pointer, and nothing is sent until you submit.
* xref:dev-console-panels.adoc#selector[One choice above a panel's sub-tabs] [.tag-new]#NEW# — a panel that writes one group per item, such as a persistence unit, can return a `PanelSelector` from `selector()`. The page then draws a dropdown of the groups above the panel's sub-tabs, shows the chosen group alone in *Monitoring*, and sends the choice to every action that declares the selector's argument, in place of a form field.
* xref:modules/vidocq-runtime-maven-plugin.adoc#dev-tools[The Mansart Data panel without JTA] [.tag-new]#NEW# — `vidocq dev` no longer resolves a `-dev` module's optional dependencies, so an application with Mansart Data and no `mansart-transactions` keeps its live Mansart Data panel, instead of `… needs jakarta.transaction:jakarta.transaction-api, which the application does not have; its panel shows its boot facts only` (BUG-20261106-04).
