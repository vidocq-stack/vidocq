= What's new
:description: Everything that changed in this component since the {release-version} release.

[.lead]
New in the `{project-version}` development line — everything listed here landed **after the {release-version} release** and is not part of it. Every entry links to the section that documents it, and those sections carry the [.tag-new]#NEW# badge. Each brick of the suite keeps its own page of this kind; xref:home::whats-new.adoc[the ecosystem index] gathers them. When the next release train ships, this page is frozen with it and restarts empty on the dev line.

== Jakarta EE web

* xref:modules/vidocq-runtime-extensions.adoc#bodoni-jstl[Jakarta Standard Tag Library 3.0 (Bodoni)] [.tag-new]#NEW# — `vidocq-runtime-bodoni-jstl-extension` gives the pages Ibarra compiles the `c:`, `fmt:`, `fn:`, `x:` and `sql:` tags (official Tags TCK 541/541 on Bodoni + Ibarra + Foy + Peano, not a certification), with Ibarra, the Servlet extension and Peano; `vidocq extension add bodoni-jstl` wires it (Vidocq/vidocq#266).
* xref:modules/vidocq-runtime-extensions.adoc#noether-persistence[Jakarta Persistence 3.2 (Noether)] [.tag-new]#NEW# — `vidocq-runtime-noether-persistence-extension` runs the units of `persistence.xml` on the application's Mansart pools, with `@PersistenceContext` and `@PersistenceUnit` injected and JTA units in `@Transactional`, which share the connection of a transaction with the Mansart Data repositories on the same pool (Vidocq/mansart#103); `vidocq extension add noether-persistence` wires it with Mansart Pool and Mansart Transactions (Vidocq/noether#45).
* xref:modules/vidocq-runtime-extensions.adoc#noether-persistence-inject[Persistence units injected with `@Inject`] [.tag-new]#NEW# — every unit of `persistence.xml` is also an `EntityManagerFactory` bean named after it, a transaction-scoped `EntityManager` bean for a JTA unit, and its `CriteriaBuilder`, `PersistenceUnitUtil`, `Cache`, `SchemaManager` and `Metamodel`, under the qualifiers and the scope its `<qualifier>` and `<scope>` elements name (Jakarta EE 11 Platform §13.12, Vidocq/noether#72). A unit and a named pool of the same name now fail the start, as two beans of one name: rename one of them.
* xref:modules/vidocq-runtime-extensions.adoc#noether-persistence-inject[Persistence beans proxied without reflection] [.tag-new]#NEW# — the `@Inject` `EntityManager` and `EntityManagerFactory` go through client proxies generated when the Noether extension is built, no longer through a `java.lang.reflect.Proxy` built at start, and the start no longer warns of a run-time code generation fallback for them (Vauban BUG-20261113-19).
* xref:modules/vidocq-runtime-extensions.adoc#noether-persistence-per-module[One `persistence.xml` per module] [.tag-new]#NEW# — a library module may declare its units next to its entities, and each unit manages the entities of its own module. Two units of one name now fail the start, naming every file that declares it (Vidocq/noether#78): rename one of them.
* xref:modules/vidocq-runtime-extensions.adoc#noether-persistence-keys[Persistence units declared with keys] [.tag-new]#NEW# — the `vidocq.persistence.<unit>.*` keys declare a unit without a `persistence.xml` (`module`, `packages`, `classes`, `transaction-type`, `qualifier`, `scope`), or set the pool and the properties of a unit a `persistence.xml` declares (`datasource`, `non-jta-datasource`, `properties.<name>`). Without any key and any `persistence.xml` unit, the entities of the application module make a unit named `default`. The build reads the keys of `vidocq.properties` for the beans it freezes, and a start whose keys would need other beans fails and asks for a rebuild (Vidocq/vidocq#551, Vidocq/noether#87).

== Build

* xref:modules/vidocq-runtime-maven-plugin.adoc#frozen-extensions[Build compatible extensions frozen at build] [.tag-new]#NEW# — `vidocq:generate` runs the build compatible extensions of the application once and records what they did; the start loads the record instead of running them, 30 to 40 ms less on a 425 ms start of an application with eleven extensions. The startup report says `cdi extensions  10 extensions frozen at build`. `-Dvidocq.freezeExtensions=false` keeps the former behaviour (Vidocq/vauban#288). What an extension author must do: xref:internals.adoc#frozen-bce[Build compatible extensions, frozen at build].
* xref:modules/vidocq-runtime-core.adoc#vidocq-gen-003[A refused record names what differs] [.tag-new]#NEW# — a production start that finds the record of another deployment, and so runs the build compatible extensions, warns with `VIDOCQ-GEN-003` and names the bean classes added, removed or changed since the build; `vidocq.startup.require-frozen-extensions=true` makes it fail.
* xref:usage.adoc#app-layer-dependencies[`vidocq.app.layer=all` is the default] [.tag-new]#NEW# — the application layer holds the application and its libraries, outside the runtime and the bricks, in `vidocq:run`, `vidocq:dev`, an IDE launch and `vidocq:package` alike (Vidocq/vidocq#247). It was `classes`. An application that worked keeps working: where `all` cannot be honoured and was not asked for, the build warns and falls back to `classes`. Vaadin no longer needs the property. Opt out with `vidocq.app.layer=classes`; see xref:usage.adoc#app-layer-migration[the migration note].
* xref:modules/vidocq-runtime-maven-plugin.adoc#parentless[An application without `vidocq-runtime-parent`] [.tag-new]#NEW# — `vidocq create` writes a pom that imports the BOM and declares the plugin as a build extension; the plugin gives the build what the parent carried (the executions, the Java release, the source encoding, the compiler argument, the lifecycle plugin versions, the Surefire property, the m2e switch), once, and leaves what the pom has. A company parent stays. `--with-parent` writes the previous style (Vidocq/vidocq#380).
* xref:modules/vidocq-runtime-cli.adoc#pom-convert[`vidocq pom convert --to parentless|parent`] [.tag-new]#NEW# — turns an existing pom from one style into the other, idempotently, keeping everything else where it is; the diff first, `--check` for CI.
* xref:modules/vidocq-runtime-cli.adoc#pom-upgrade[`vidocq pom upgrade [--to <version>|--release|--snapshot] [--check]`] [.tag-new]#NEW# — moves an application to another Vidocq version in either pom style, or in a pom written before 0.4.0; the diff first, `--check` for CI, versions that disagree reported and never aligned.
* xref:modules/vidocq-runtime-maven-plugin.adoc#build-info[`vidocq:build-info`] [.tag-new]#NEW# — the build identity the banner reads, written by the plugin itself from `.git` (plain repository, worktree, submodule, shallow clone), with no third-party plugin; without a repository the commit reads `unversionned` and the build goes on.
* xref:modules/vidocq-runtime-maven-plugin.adoc#jlink-every-module[A jlink image resolves every staged module] [.tag-new]#NEW# — `vidocq:jlink` linked every module but rooted only the application's: a module that nothing `requires`, such as Vaadin's `flow.push`, `vaadin.lumo.theme` and `vaadin.aura.theme`, was in the image and in no layer, and its `META-INF/resources` answered 404. The image now bakes `--add-modules` for every staged module, in both launch shapes, and `vidocq:jpackage` passes the modules of the image it packages.
* xref:modules/vidocq-runtime-maven-plugin.adoc#layer-off[The application loaded once by every launcher] [.tag-new]#NEW# — the `vidocq:package` launchers under `vidocq.app.layer=classes` hand `app/` to the runtime as under `all`, and the launches without a layer (`vidocq.package.layer=false`, `vidocq.dev.layer=false`) pass `-Dvidocq.app.layer.off=true`, which a `@VidocqMain` trampoline honours. With a trampoline main, both used to load the application module twice, in the boot layer and in the application layer: a `ServiceLoader` found each of its providers twice (BUG-20261114-10).
* xref:modules/vidocq-runtime-maven-plugin.adoc#parentless[`vidocq:checkpom` and the Java release] [.tag-new]#NEW# — warns when `maven.compiler.release` came from the plugin: IntelliJ IDEA reads the language level from the pom alone.
* xref:modules/vidocq-runtime-extensions.adoc#humboldt-telemetry-codegen[A codegen bundle for the Telemetry extension] [.tag-new]#NEW# — `vidocq-runtime-humboldt-telemetry-extension-codegen` puts Humboldt's Build Compatible Extension on the processor path, so the interceptor binding of each `@WithSpan` class and method is written into the build instead of being added again at each start; the plugin wires it, and a pom that lists its bundles by hand adds it, as xref:migration.adoc#metrics-openapi-codegen[the migration note] says (BUG-20261113-02, Vidocq/vidocq#546).

== CLI

* xref:modules/vidocq-runtime-cli.adoc#create-parentless[`vidocq create` without a parent, `--with-parent`, `--vidocq-version`] [.tag-new]#NEW# — the project builds on the BOM and the plugin by default; the parent on request (Vidocq/vidocq#380).
* xref:modules/vidocq-runtime-cli.adoc#update-channel[`vidocq update --release` and `vidocq update --snapshot`] [.tag-new]#NEW# — switch the CLI to the latest release or the latest SNAPSHOT build whatever channel is installed (a `0.4.0-SNAPSHOT` CLI can move to the latest release, a release to the latest SNAPSHOT). They are mutually exclusive, combine with `--check`, and complete after `vidocq update`.

== Configuration

* xref:usage.adoc#property-expressions[Property expressions in every key] [.tag-new]#NEW# — `vidocq.chappe.listener.default.port=${DASHBOARD_PORT:8080}` and the other `${key}` and `${key:default}` expressions of MicroProfile Config are expanded for the Vidocq keys too, with or without Ravel. The start failed with a `NumberFormatException` on the expression as written (BUG-20261114-01).

== Dev services

* xref:dev-services.adoc#test-run-files[A test run has files of its own] [.tag-new]#NEW# — `vidocq test` and the JUnit listener write `target/vidocq-dev-services-test.json` and `-test.properties`, so a test run beside `vidocq dev` no longer overwrites the dev session's files, and the next reload no longer reports the test run's container as the application's, `stopped` (BUG-20261106-03).

== Testing

* xref:testing.adoc#application-layer[`@VidocqTest` starts the application layer of `vidocq:run`] [.tag-new]#NEW# — the application module and, under `vidocq.app.layer=all`, its libraries reach the runtime through `vidocq.app.path` and leave the module path. The application module was on both: the JVM loaded it twice, a `ServiceLoader` found each `provides` of its `module-info.java` twice, and a Vaadin application whose module provides an `InstantiatorFactory` answered 500, _multiple eligible instantiator implementations_, while its packaged distribution started (BUG-20261114-07). `vidocq.app.layer` and `vidocq.app.layer.keep` are read from `@VidocqTest(properties)`.

== Dev mode

* xref:modules/vidocq-runtime-maven-plugin.adoc#debugger-port-busy[A second `vidocq dev` on the machine starts] [.tag-new]#NEW# — the debug port is checked before the application JVM is forked: left at its default and held by another session, it moves to a free port with a warning that names both; set with `vidocq.dev.debugPort`, busy, it fails the goal at once, naming the port and the property. The JVM died at start with `transport error 202: bind failed`, and nothing said the debug port was the cause (BUG-20261114-03). `vidocq:run -Dvidocq.run.debug=true` does the same with `vidocq.run.debug.port`.
* xref:continuous-testing.adoc#when-tests-run[An application that dies before it is ready is reported down] [.tag-new]#NEW# — when the application JVM stops before it is ready, `vidocq dev` no longer speaks of a reload at the first start: its warning says that the application's output above gives the reason, and that the next change starts it again (BUG-20261114-04).
* xref:continuous-testing.adoc#terminal[The line of a failed test, at last] [.tag-new]#NEW# — `vidocq dev` and `vidocq:test` print where a test failed, `(OrderServiceTest.java:31)`, for the tests of a Vidocq application too: they run in a named module, whose frames the JDK prints as `com.acme@1.0.0/com.acme.OrderServiceTest…`, and the line was never found (BUG-20261106-02).
* xref:continuous-testing.adoc#limits[The first test run under `vidocq dev` downloads what the tests need] [.tag-new]#NEW# — a continuous-testing run that misses a test-scope jar or Surefire's JUnit provider offline runs again once online, so `vidocq dev` on a new project no longer reports a failed run, with `Cannot access central in offline mode` in its log, before any test ran (BUG-20261106-01).

== Dev console

* xref:modules/vidocq-runtime-maven-plugin.adoc#dev-tools[The Mansart Data panel without JTA] [.tag-new]#NEW# — `vidocq dev` no longer resolves a `-dev` module's optional dependencies, so an application with Mansart Data and no `mansart-transactions` keeps its live Mansart Data panel, instead of `… needs jakarta.transaction:jakarta.transaction-api, which the application does not have; its panel shows its boot facts only` (BUG-20261106-04).
