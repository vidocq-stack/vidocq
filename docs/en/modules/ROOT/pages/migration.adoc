== From Quarkus

Vidocq Runtime explicitly borrows the Quarkus extension pattern.

[cols="1,1,2"]
|===
| Quarkus | Vidocq Runtime | Note

| Quarkus deployment build steps + recorders (`io.quarkus.deployment`)
| `io.vidocq.runtime.spi.VidocqExtension` lifecycle (`configure` / `beforeStart` / `onStart` / `onStop`)
| Simpler model — `ServiceLoader` discovery, ordered by `priority()`, no build-step graph

| Gizmo bytecode generation (ASM)
| APT + Class-File API (JEP 484) at compile time
| No ASM — standard JDK bytecode

| ArC (runtime CDI)
| xref:vauban::index.adoc[Vauban]
| Build-time in both cases

| RESTEasy Reactive
| xref:cassini::index.adoc[Cassini] on xref:chappe::index.adoc[Chappe]
| No Vert.x — virtual threads

| Hibernate Reactive / ORM
| xref:mansart::index.adoc[Mansart]
| JDBC + virtual threads, no Vert.x SQL Client

| Jackson
| xref:champollion::index.adoc[Champollion]
| JSON-B 3.0 / JSON-P 2.1 implementation
|===

The forthcoming `compare-to/` workspace examples will illustrate migrating a simple extension.

== From Helidon MP

* Helidon SE (Web) → xref:chappe::index.adoc[Chappe] + xref:cassini::index.adoc[Cassini].
* Helidon MP → Vidocq Runtime directly.
* `application.yaml` → MicroProfile Config (`vidocq.properties` or env).
* Helidon Níma already uses virtual threads — the transition is conceptually transparent.

== From Spring Boot

Spring Boot does not naturally align with the MicroProfile model, and migration touches the programming model.

[cols="1,1,2"]
|===
| Spring Boot | Vidocq Runtime | Note

| `@SpringBootApplication`
| `vidocq.mainModule` in the pom
| No application class required: the runtime's own main boots the module (xref:usage.adoc#entry-point[entry point])

| `@RestController`
| `@Path` + `@GET/@POST`
| Standard Jakarta REST

| `@Service`, `@Component`
| `@ApplicationScoped`
| CDI Lite

| `@Autowired`
| `@Inject`
| Constructor injection preferred

| `@ConfigurationProperties`
| `@ConfigProperty` injection
| MicroProfile Config via `vidocq-runtime-ravel-config-extension`

| `application.yml`
| `vidocq.properties` + MP profiles
| `%<profile>.` prefix

| Spring Data JPA
| xref:mansart::index.adoc[Mansart] (Jakarta Data 1.0)
| APT-generated repositories
|===

== From Open Liberty / WildFly

* `server.xml` → MicroProfile Config + Vidocq Runtime extensions.
* EAR → standalone JAR + Maven plugin.
* JNDI → CDI lookup via `Vauban.bootstrap()`.
* Jakarta annotations — directly compatible, the programming model stays identical.

== From Payara Micro

Payara Micro and Vidocq Runtime share the MicroProfile target. The main difference is the build-time approach: Payara Micro embeds GlassFish; Vidocq Runtime produces a minimal jlink binary without a classical application server.

* `payara-micro --deploy app.war` → `bin/run.sh` from the `vidocq:package` `bin/` + `lib/` distribution (also attached as a `-dist.zip`).
* `payara-micro.jar` (~80 MB) → jlink image (~40 MB).
* Every enabled MicroProfile `feature.xml` is replaced by the matching Vidocq Runtime extension.

[#dev-console-dependency]
== The dev console is no longer a dependency

Before, an application declared `vidocq-runtime-devconsole-extension` itself to get the
xref:dev-console.adoc[dev console], and that dependency shipped in every binary `vidocq:package`, `jlink`,
`jpackage` and `docker` produced — off by default, but its code was there. `mvn vidocq:dev` now adds the
console itself, at the Vidocq version of the application's Chappe extension, the moment the application already has
`vidocq-runtime-chappe-webserver-extension`; no application ever needs to declare it, and no binary ever
contains it (Vidocq/vidocq#143).

* **Remove `vidocq-runtime-devconsole-extension` from the pom.** `vidocq:checkpom` already warns about it if
  you do not — a dev-only dependency declared outside `test` scope — and every packaging goal drops it anyway,
  with a warning, whether or not you remove it. Its SPI, `vidocq-runtime-devconsole-spi`, a small API jar,
  stays in the binary as long as the console, or an extension that requires the SPI, is declared.
* **Unless a test reads the console**, such as one that calls its `/api/snapshot`: keep the dependency, moved
  to `<scope>test</scope>`, together with the `-dev` module of any extension whose live panel the same test
  reads (xref:dev-console-panels.adoc#dev-module[A `-dev` module, never packaged]). `test` scope is never
  packaged, and `checkpom` accepts it.
* **An application that got `vidocq-runtime-chappe-webserver-extension` only transitively through the
  console** — the console depends on it, so declaring the console was enough to bring Chappe along — now
  declares Chappe itself. Without it, `vidocq:dev` logs `Dev tools: no dev console, it needs
  vidocq-runtime-chappe-webserver-extension` and starts without one, since nothing serves the console's page
  any more.

See xref:modules/vidocq-runtime-maven-plugin.adoc#dev-tools[Dev tools and binaries] for the whole picture,
including the six `-dev` panel modules this repository's own extensions now ship.

[#config-rest-client-codegen]
== Config and Rest Client need their codegen bundle

Two extensions now ship a `-codegen` bundle, as the others already did, and `vidocq:checkpom` fails the build
of an application that declares the extension without it:

* `vidocq-runtime-ravel-config-extension` → `vidocq-runtime-ravel-config-extension-codegen` (Vidocq/ravel#21).
  Without it, `@Inject @ConfigProperty` was reported unsatisfied at compile time, and the only way out was
  `-Avauban.validation=false`.
* `vidocq-runtime-cyrano-rest-client-extension` → `vidocq-runtime-cyrano-rest-client-extension-codegen`
  (Vidocq/vidocq#207). Without it, `@Inject @RestClient` was unsatisfied at boot.

Add each one to the compiler's `annotationProcessorPaths`, next to the inherited indexer
(`combine.children="append"`). `checkpom` prints the `<path>` to paste:

[source,xml,subs=attributes+]
----
<path>
    <groupId>io.vidocq.runtime.extensions.microprofile</groupId>
    <artifactId>vidocq-runtime-cyrano-rest-client-extension-codegen</artifactId>
    <version>{project-version}</version>
</path>
----

The bundles are jars from 0.4.0: a `<path>` written for 0.3.0 with `<type>pom</type>` still builds, and
`checkpom` warns about it so that IntelliJ's build runs the processors too; remove the line (see
xref:modules/vidocq-runtime-extensions.adoc#codegen-bundles[Codegen bundles are jars]).
`vidocq extension add ravel-config` and `vidocq extension add cyrano-rest-client` write it for you. See
xref:modules/vidocq-runtime-extensions.adoc#ravel-config-codegen[the Config extension] and
xref:modules/vidocq-runtime-extensions.adoc#cyrano-rest-client-codegen[the Rest Client extension].

[#metrics-openapi-codegen]
== Metrics, OpenAPI, Fault Tolerance and JWT need their codegen bundle

Four more extensions ship a `-codegen` bundle, so that their processor runs on the application's classes instead of
a scan by reflection when the application starts (Vidocq/vidocq-workspace#38). `vidocq:checkpom` fails the build of an
application that declares the extension without it:

* `vidocq-runtime-dirac-metrics-extension` → `vidocq-runtime-dirac-metrics-extension-codegen`;
* `vidocq-runtime-grimm-openapi-extension` → `vidocq-runtime-grimm-openapi-extension-codegen`.
* `vidocq-runtime-heisenberg-fault-tolerance-extension` → `vidocq-runtime-heisenberg-fault-tolerance-extension-codegen`
  [.tag-new]#NEW#: Heisenberg's processor writes the Fault Tolerance annotations of each bean into a companion.
* `vidocq-runtime-cervantes-jwt-extension` → `vidocq-runtime-cervantes-jwt-extension-codegen` [.tag-new]#NEW#: Vauban
  runs Cervantes' Build Compatible Extension when the application compiles.

The Metrics and OpenAPI bundles now also bring their extension's Build Compatible Extension (`DiracExtension`,
`GrimmExtension`) [.tag-new]#NEW#: without it, Vauban warned at each build that those extensions were on the module
path only and would not run.

Add each one to the compiler's `annotationProcessorPaths`, as in xref:#config-rest-client-codegen[the previous
section]; `checkpom` prints the `<path>` to paste, and `vidocq extension add` writes it. See
xref:modules/vidocq-runtime-extensions.adoc#dirac-metrics-codegen[the Metrics extension] and
xref:modules/vidocq-runtime-extensions.adoc#grimm-openapi-codegen[the OpenAPI extension],
xref:modules/vidocq-runtime-extensions.adoc#heisenberg-fault-tolerance-codegen[the Fault Tolerance extension] and
xref:modules/vidocq-runtime-extensions.adoc#cervantes-jwt-codegen[the JWT extension].

[#application-parent]
== `vidocq-runtime-parent` is an application parent, with a BOM

Until 0.4.0, `vidocq-runtime-parent` was the root of the runtime's own reactor, and an application that
inherited it got the settings of this repository with it: the SonarQube and TCK properties, the versions of
Testcontainers, Flyway, Liquibase, the bricks and the Jakarta APIs, a SNAPSHOT of langchain4j-cdi. From 0.4.0
(Vidocq/vidocq#339):

* **`vidocq-runtime-parent` is the parent of an application.** It imports `vidocq-runtime-bom`, sets Java 25,
  puts the Vauban indexer on the processor path, pins the Maven plugins, and manages
  `vidocq-runtime-maven-plugin` with `checkpom`, `check-module-info` and `package`. It writes the build identity
  the startup banner reads, and nothing else.
* **`vidocq-runtime-bom` versions every Vidocq artifact** an application declares: the runtime, the extensions,
  their `-codegen` and `-dev` modules, the Dev Services and the test support. An application that keeps a parent
  of its own imports it:
+
[source,xml,subs=attributes+]
----
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>io.vidocq.runtime</groupId>
            <artifactId>vidocq-runtime-bom</artifactId>
            <version>{project-version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
----
* **The runtime's own reactor root is `vidocq-runtime-build`.** It is published, as the parent of the runtime's
  modules, and an application never inherits it.

What to change in an application:

* **Nothing, to keep building.** The parent's name is the same; bump its version.
* **Drop the codegen paths**, if you like: the parent loads `vidocq-runtime-maven-plugin` as a build extension,
  which puts the bundle of each extension and the Vauban indexer on the processor path. A path left in the pom is
  kept and not added twice. Under a parent of your own, declare the plugin with `<extensions>true</extensions>`
  for the same result (xref:modules/vidocq-runtime-maven-plugin.adoc#codegen-wiring[The plugin wires the codegen
  bundles]).
* **Drop the `<version>` of the Vidocq dependencies and codegen paths**, if you like: the BOM gives them, and an
  upgrade then changes the parent's version only. `vidocq create` and `vidocq extension add` no longer write
  them under a 0.4.0 parent, nor under a pom that imports the BOM.
* **Declare the version of anything else you took from the old parent without one** — a Jakarta API, a brick
  such as `cassini-api`, Testcontainers, H2, Flyway: the new parent manages none of them. Maven names each one
  (`'dependencies.dependency.version' for … is missing`). The Vidocq extensions bring the bricks they need
  transitively, so most applications declare none of these.
* **Declaring `vidocq-runtime-maven-plugin` is enough.** The parent binds `checkpom`, `check-module-info` and
  `package`; the `<execution>` with `<goal>package</goal>` that `vidocq create` wrote before 0.4.0 merges with the
  parent's (both are the `default` execution), so it packages once whether you keep it or not.

[#modularize-moved]
== `vidocq:modularize` is now `vauban:modularize`

The goal moved to `io.vidocq.vauban:vauban-maven-plugin`. A pom that runs `vidocq:modularize` declares the
Vauban plugin instead, renames the `vidocq.modularize.*` properties to `vauban.modularize.*`, and drops
`<release>`; the copies are written to `target/vauban-modularized/`, where `vidocq:dev`, `vidocq:jlink` and
`vidocq:package` read them. See xref:modules/vidocq-runtime-maven-plugin.adoc#modularize[`modularize` moved to
the Vauban plugin].
