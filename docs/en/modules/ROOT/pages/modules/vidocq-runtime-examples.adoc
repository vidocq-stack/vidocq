= vidocq-runtime-examples
:description: Tour of shipped examples.

[.lead]
`vidocq-runtime-examples` groups the demo applications used as living oracles for validation and documentation. Each example is an independent Maven module, packageable via the `vidocq-runtime-maven-plugin`.

== Coordinates

[cols="1,3"]
|===
| Reactor | `vidocq-runtime-examples/`
| Build | `cd vidocq-runtime-examples/<example> && ./mvnw -ntp package`
|===

== Catalogue

[cols="2,3"]
|===
| Example | Description

| `vidocq-runtime-cassini-rest-example`
| Minimal REST application — a single Jakarta REST resource, packageable in jlink/jpackage/docker. Serves as the canonical reference to test the Maven plugin and the extension mechanism on the Chappe + Vauban + Cassini triplet.

| `vidocq-runtime-mansart-h2-example`
| Complete REST + CDI + persistence application via xref:mansart::index.adoc[Mansart] on H2 in-memory. Demonstrates `@Transactional`, `Repository<T, ID>`, constructor `@Inject`. The recommended example in xref:getting-started.adoc[Getting started].

| `vidocq-runtime-cervantes-jwt-example`
| REST application secured with MicroProfile JWT via `vidocq-runtime-cervantes-jwt-extension` — token validation and `@RolesAllowed` on Jakarta REST resources.

| `vidocq-runtime-knock-health-example`
| MicroProfile Health via `vidocq-runtime-knock-health-extension` — custom `@Liveness`/`@Readiness` checks exposed on `/health`.

| [[cyrano-rest-client-example]]`vidocq-runtime-cyrano-rest-client-example` [.tag-new]#NEW#
| MicroProfile Rest Client via `vidocq-runtime-cyrano-rest-client-extension` and its `-codegen` bundle — `/api/relay` calls the application's own `/api/greeting` through an `@Inject @RestClient` interface. Every build links it with `vidocq:jlink`.

| [[foy-servlet-example]]`vidocq-runtime-foy-servlet-example` [.tag-new]#NEW#
| Jakarta Servlet 6.1 via `vidocq-runtime-foy-servlet-extension` and its `-codegen` bundle — the Vidocq Bistro: servlets, a filter and a session listener, all CDI beans, a `@SessionScoped` basket, a `@RequestScoped` ticket shared by the filter and the servlet of a request, and a kitchen page protected by `@ServletSecurity` with BASIC authentication.

| `vidocq-runtime-petstore-example`
| The largest example — Cassini + Mansart + Champollion + H2 petstore combining REST, persistence and JSON binding.

| `vidocq-runtime-external-rest-lib`
| External library consumed by the examples — illustrates the case where a Java Modules-named dependency provides its own CDI beans. Useful for validating multi-module APT composition.
|===

== `vidocq-runtime-cassini-rest-example` — quick start

[source,bash]
----
cd vidocq-runtime-examples/vidocq-runtime-cassini-rest-example
./mvnw -ntp package -DskipTests

# standalone jlink image
./target/dist/bin/todo-app

# UI on http://127.0.0.1:8080/
# API on http://127.0.0.1:8080/api/todos
----

== `vidocq-runtime-mansart-h2-example` — quick start

[source,bash]
----
cd vidocq-runtime-examples/vidocq-runtime-mansart-h2-example
./mvnw -ntp package

# vidocq:package produced a bin/ + lib/ distribution (also zipped as *-dist.zip)
./target/vidocq-runtime-mansart-h2-example-<version>/bin/run.sh

curl -X POST http://localhost:8080/api/products \
     -H 'Content-Type: application/json' \
     -d '{"name":"cables","price":12.50}'

curl http://localhost:8080/api/products
----

In dev mode, `mvn vidocq:dev`, the example also serves the xref:dev-console.adoc[dev console] [.tag-new]#NEW#: it logs `Vidocq dev console: http://127.0.0.1:8888/`, a page with the startup report, the two pools, `@Default` and `audit`, live, and the JVM. Its `DevConsoleSnapshotTest` boots the example in a dev launch, reads that URL from the log, and checks the snapshot the page polls: both pools, the heap, and no pool password anywhere in it.

The example demonstrates the `@TransactionScoped` scope and the xref:mansart::index.adoc[Mansart] transactional bridge. It also served as the reproduction harness for bug VAU-INJ-001 (normal-scope proxy resolution) — see `vidocq/VAUBAN-BUGS.md`.

== `vidocq-runtime-foy-servlet-example` — quick start [.tag-new]#NEW#

[source,bash]
----
cd vidocq-runtime-examples/vidocq-runtime-foy-servlet-example
mvn vidocq:dev

# menu and basket on http://localhost:8080/
# kitchen on http://localhost:8080/kitchen, sign in as chef, password chef
----

Every page is written by a servlet; no JSP, no static file. `TicketFilter` and the servlet of one request inject the same `@RequestScoped` `RequestTicket`: its id is both the `X-Request-Id` header and the one in the page footer, and the next request gets a new one. The `@SessionScoped` `Basket` lives in the HTTP session, and `SessionCounter`, a `@WebListener`, counts the open sessions for the kitchen page. `KitchenServlet` carries `@ServletSecurity(@HttpConstraint(rolesAllowed = "chef"))`, and `META-INF/web.xml` holds only a FORM `login-config`: Foy forwards a visitor to `LoginServlet`'s form, which posts to `j_security_check`, and checks the user that `vidocq.servlet.users.chef.*` declares in `vidocq.properties`. The identity lives in the HTTP session, so it ends at *Sign out*, a POST to `LogoutServlet`, or after `vidocq.servlet.session-timeout` without a request; BASIC authentication, Foy's default without a `login-config`, would leave the credentials in the browser until it closes. The `module-info.java` has no exports, no opens and no hand-written `provides`. Under `vidocq:dev`, the dev console plots the active sessions.
