= vidocq-runtime-cli
:description: The Vidocq command-line interface — scaffold, run in dev mode, build, manage extensions and configuration.

[.lead]
`vidocq-runtime-cli` is the zero-dependency, JPMS-native command-line interface for the
Vidocq runtime. It scaffolds new applications, runs them in a live-reloading dev mode,
wraps the packaging goals of the Maven plugin, manages extensions and configuration, and
diagnoses your environment — all from a single `vidocq` command. This page is a complete
user guide; jump straight to <<getting-started>> for a Hello-World walkthrough.

== Coordinates

[cols="1,3"]
|===
| Artefact | `io.vidocq.runtime:vidocq-runtime-cli:{project-version}`
| JPMS module | `io.vidocq.runtime.cli`
| Main class | `io.vidocq.runtime.cli.VidocqCli`
| Dependencies | None beyond the JDK and `io.vidocq.runtime.core` (hand-rolled arg parser, pure Java 25)
|===

== Prerequisites

* **Java 25** (Temurin recommended) — the CLI refuses to run a project on an older JVM and
  `vidocq doctor` flags it.
* **Maven 3.9.16** — pinned per project via `.sdkmanrc` (`sdk env`). The build/clean commands
  reuse the project's `mvnw` wrapper, falling back to `mvn` on the `PATH`.

== Installing the `vidocq` command

The installer downloads the CLI distribution into `~/.vidocq/cli/<version>` and puts a
`vidocq` launcher on your `PATH`:

[source,bash]
----
curl -fsSL https://vidocq.dev/install.sh | sh                            # latest release
curl -fsSL https://vidocq.dev/install.sh | VIDOCQ_VERSION=0.3.0 sh       # a given release
curl -fsSL https://vidocq.dev/install.sh | VIDOCQ_VERSION=snapshot sh    # latest build of main
----

On Windows (PowerShell), set the same variable before running the script:

[source,powershell]
----
irm https://vidocq.dev/install.ps1 | iex
$env:VIDOCQ_VERSION = 'snapshot'; irm https://vidocq.dev/install.ps1 | iex
----

`VIDOCQ_VERSION=snapshot`takes the newest `-SNAPSHOT` of the CLI from the
Central snapshot repository, where every build of `main` is published. A SNAPSHOT is
downloaded again on every run, since it changes with every build; a release already
installed is kept. A CLI installed this way scaffolds projects against its own SNAPSHOT
runtime (see <<create-snapshot>>). Run the installer again to go back to the latest release.

Without the installer, download `vidocq-runtime-cli-<version>-cli.zip` from Maven Central,
unzip it anywhere and add its `bin/` directory to your `PATH`. The launcher runs the CLI
as a JPMS module:

[source,bash]
----
java -m io.vidocq.runtime.cli/io.vidocq.runtime.cli.VidocqCli <command> [options]
----

[TIP]
====
Enable tab-completion with `vidocq completion install` — see <<completion>>.
====

[#getting-started]
== Getting started — Hello World

This walkthrough scaffolds, inspects, and boots a brand-new Vidocq application in under a
minute, using only the CLI.

=== 1. Check your environment

[source,bash]
----
vidocq doctor
----

`doctor` verifies the Java version, `JAVA_HOME`, the Maven wrapper, the project layout, the
extensions in the project's runtime dependencies, and your `vidocq.properties` keys; inside a project, it also checks
the project itself (<<doctor>>). Fix any ✘ before continuing, `vidocq doctor --fix` repairs most of them;
⚠ warnings are safe to ignore for now.

=== 2. Scaffold the project

[source,bash]
----
vidocq create --name hello-world --group-id com.example
----

This generates a ready-to-build Maven project:

[source]
----
hello-world/
├── pom.xml                                  # inherits vidocq-runtime-parent, depends on core, sets vidocq.mainModule
├── mvnw, mvnw.cmd, .mvn/wrapper/            # the Maven wrapper of the Vidocq repositories
├── .gitignore, README.md
└── src/main/
    ├── java/
    │   ├── module-info.java                 # module com.example.hello.world { }
    │   └── com/example/hello/world/         # your application package
    └── resources/
        └── vidocq.properties                 # vidocq.http.port=8080
----

There is no application main class: the runtime's own main boots the application
from `vidocq.mainModule`, under `vidocq dev`, `vidocq start` and the `bin/` launchers of
`mvn package` alike. With `-x cassini-rest`, the package also gets a `HelloResource`
(`GET /hello`), and `module-info.java` opens it to JAX-RS and JSON-B. An extension that
reflects on the package without the scaffold writing a class into it (`mansart-data` alone)
gets no `opens`: the JVM refuses to open a package with no class, and `create` tells you to add
the directive once the package has one.

`--main` also writes an `@VidocqMain` trampoline, sets `vidocq.mainClass` to it and adds
`requires io.vidocq.runtime.core;`. Ask for it when you want a right-click Run in the IDE, or
logic after boot (a `VidocqApp`). `vidocq:jlink` and `vidocq:jpackage` do not need it: without a
main class they launch the runtime's own main, which re-layers `vidocq.mainModule` (see
xref:modules/vidocq-runtime-maven-plugin.adoc#jlink-without-main-class[jlink without a main class]).
The trampoline re-resolves the application into the Vauban layer, which reads
the build-time generated code through `META-INF/services` without a `provides` in your
`module-info.java`, the same way in the IDE, with `vidocq start` and in a jlink image:

[source,java]
----
package com.example.hello.world;

import io.vidocq.runtime.core.Vidocq;
import io.vidocq.runtime.spi.VidocqMain;

/**
 * Entry point. {@code main} is a trampoline: {@code Vidocq.run} resolves the application
 * into the Vauban layer and boots it there, from the IDE, {@code vidocq start} or a jlink
 * image alike. Put no code before it: it would run outside that layer.
 *
 * <p>The runtime's own main boots the application without this class. Keep it for a
 * right-click Run in the IDE, or for logic after boot (pass a {@code VidocqApp} to
 * {@code Vidocq.run(Class, String...)}).
 */
@VidocqMain
public final class HelloWorldApp {

    public static void main(String[] args) {
        Vidocq.run(args);
    }
}
----

[NOTE]
====
With `--main`, the project name is converted to a `PascalCase` class name with an `App` suffix
(`hello-world` → `HelloWorldApp`). The default package is `<groupId>.<name>` with dashes
turned into dots (`com.example.hello.world`). That package is also the module name, so every
dot-separated part must be a Java identifier that is not a keyword: `create` refuses a name such
as `ft-030` (`io.example.ft.030`) and asks for `--package`. Override the package with `--package`
and add extensions at creation time with `-x` (repeatable).
====

=== 3. Move in and build

[source,bash]
----
cd hello-world
vidocq build --skip-tests
----

`vidocq build` (no type) runs the Maven `package` lifecycle through the project wrapper and
produces a standalone distribution. Add `--dry-run` to preview the exact Maven command
without executing it.

=== 4. Run it

[source,bash]
----
vidocq start
----

The runtime boots in the foreground and awaits shutdown (Ctrl-C). To iterate with live
reload instead, use dev mode:

[source,bash]
----
vidocq dev
----

`dev` boots the runtime and watches `src/main/java`, `src/main/resources` and
`target/classes`; any `.java` / `.properties` / `.xml` / `.yml` change is debounced and
re-applies your configuration and resources in-process without leaving the CLI.

=== 5. Add an HTTP endpoint

A bare core application boots the runtime but serves no routes. To expose a REST resource,
add the Cassini REST extension and follow the full Jakarta REST + CDI walkthrough:

[source,bash]
----
vidocq extension add cassini-rest
----

See xref:getting-started.adoc[Getting started] for a complete REST + persistence example,
including the resource class, the JPMS module declarations, and `curl` calls.

== Command reference

Run `vidocq help` for the command list, or `vidocq help <command>` for per-command options; `vidocq <command> --help` (or `-h`) [.tag-new]#NEW# shows the same. After `--`, a `--help` goes to Maven.

[cols="1,3"]
|===
| Command | Description

| `vidocq version`
| Print the CLI and runtime version string. A SNAPSHOT CLI adds its build time, `0.4.0-SNAPSHOT (built 2026-10-06T09:13:13Z)`, as the help header and `vidocq info` do.

| `vidocq info`
| Display the environment (CLI, Java, OS) and, in a project, its main module, runtime version, number of extensions and active profile, read from its files without running Maven. The detailed list of extensions is `vidocq extension list`'s.

| `vidocq doctor [--fix] [--verbose]`
| Run environment & project health checks, and repair the project with `--fix` (see <<doctor>>).

| `vidocq create --name <name> …`
| Scaffold a new Vidocq Maven application (see <<create>>).

| `vidocq dev [--port] [--profile] [--debug]`
| Run the project in dev mode with live reload, `mvn vidocq:dev` (see <<dev>>).

| `vidocq start [--port] [--config] [--debug]`
| Build and run the project's application, `mvn vidocq:run` (see <<start>>).

| `vidocq test`
| Run the tests on every change, without the application, `mvn vidocq:test` (see <<test>>).

| `vidocq idea [--check\|--strict] [--kind <kind>]`
| Write, or check, the IntelliJ run configurations in `.run/`, `mvn vidocq:idea` (see <<idea>>).

| `vidocq vscode [--check]`
| Write, or check, the VS Code settings, tasks and debug configuration in `.vscode/`, `mvn vidocq:vscode` (see <<vscode>>).

| `vidocq eclipse [--check]`
| Write, or check, the Eclipse run and debug configurations in `.eclipse/`, `mvn vidocq:eclipse` (see <<eclipse>>).

| `vidocq build [type] …`
| Build/package the project, wrapping the Maven plugin goals (see <<build>>).

| `vidocq clean [--offline] [--dry-run]`
| Remove build output (`mvn clean`).

| `vidocq extension <list\|add\|remove> …`
| Manage project extensions (see <<extension>>).

| `vidocq config <get\|set\|list> …`
| Read or write keys in `vidocq.properties` (see <<config>>).

| `vidocq completion <bash\|zsh>`
| Print a shell-completion script (see <<completion>>).

| `vidocq completion install\|uninstall [bash\|zsh]`
| Set up (or remove) completion in your shell's rc file (see <<completion>>).

| `vidocq update [--check]`
| Update the CLI itself to the latest release, or the latest SNAPSHOT build (see <<update>>).

| `vidocq help [command]`
| Show the command list or detailed help for one command.
|===

[#create]
=== `vidocq create`

Scaffolds a minimal Maven project (`pom.xml`, `module-info.java` and `vidocq.properties`, plus a
`HelloResource` with `-x cassini-rest` and an `…App` trampoline with `--main`: `DemoApp` for `demo-app`, `ShopApp`
for `shop`). The project has a version of its own, `1.0.0-SNAPSHOT`, and the Maven wrapper of the
Vidocq repositories (`mvnw`, `mvnw.cmd`, `.mvn/wrapper/`), pinned to the ecosystem's Maven version
. Under a `--parent-version` before 0.4.0, whose `dependencyManagement` resolves at the project's
version, the project inherits the parent's version instead, and `create` says so. Without the CLI,
xref:modules/vidocq-runtime-maven-plugin.adoc#create-goal[`vidocq:create`] writes the same project
. The extensions are written in the order given.

From 0.4.0 the project is finished(Vidocq/vidocq#339):

* **A first test.** With `-x cassini-rest`, `src/test/java/<package>/HelloResourceTest.java` starts the application
  with xref:testing.adoc[`@VidocqTest`] and checks `GET /hello`; the pom declares `vidocq-runtime-junit` and
  `junit-jupiter` in test scope, versioned by the parent. Without it, the pom declares `junit-jupiter` alone. Under a
  parent before 0.4.0 no test is written, and `create` says why.
* **`.gitignore`**: `target/` and the files of IntelliJ IDEA, Eclipse, VS Code and macOS.
* **`README.md`**: the commands that work on the project, with the CLI and with Maven alone.
* **Questions on a console.** Without `--name`, on a terminal, `create` asks for the name, then for the group id and
  the extensions unless the command line gave them, showing the catalog first; Enter takes the default
  (`io.example`, `cassini-rest`), `none` takes no extension, and a wrong answer is explained and asked again.
  Without a terminal, `--name` stays required.

[cols="1,2"]
|===
| Option | Description

| `--name, -n <name>` | Project / artifact name; asked on a terminal when left out, required otherwise.
| `--group-id, -g <groupId>` | Maven groupId (default `io.example`).
| `--package <pkg>` | Root Java package, also the module name (default `<groupId>.<name>`, dashes turned into dots); must be a valid Java package name.
| `--extension, -x <id>` | Extension to enable; repeatable.
| `--parent-version <version>` | Version of `vidocq-runtime-parent` the project inherits (default: the runtime version of the CLI). From 0.4.0 the parent's BOM versions the Vidocq dependencies, which carry no `<version>`; under an older parent each one names this version.
| `--main`| Also write an `@VidocqMain` trampoline and set `vidocq.mainClass` to it (default: no main class, the runtime's own main boots the application). For a right-click Run in the IDE or a `VidocqApp`.
|===

[source,bash]
----
vidocq create --name my-api -g com.acme -x cassini-rest -x knock-health
----

[#create-snapshot]
==== Trying a SNAPSHOT

Every build of `main` publishes the Vidocq SNAPSHOTs to the project's own repository [.tag-new]#NEW#, `https://maven.vidocq.dev/snapshots/`, readable without an account, then copies them to Central's snapshot repository, `https://central.sonatype.com/repository/maven-snapshots/`, as before. `https://maven.bak.vidocq.dev/snapshots/` is a full copy of it on another site, synchronised every 10 minutes: declared right after it, as `vidocq-snapshots-bak`, it takes over when the first one is down, since Maven moves on to the next repository after a transfer error. The repository keeps the five latest builds of each SNAPSHOT version, and drops a SNAPSHOT version no build has touched for 30 days. When the parent version is a SNAPSHOT, the generated `pom.xml` declares both repositories, `vidocq-snapshots` then `vidocq-snapshots-bak`, for dependencies and for plugins, with releases disabled: the SNAPSHOT artifacts come from there, everything else from Maven Central. Releases are still published to Maven Central.

A project created before this change declares `central-snapshots` instead: it keeps working, and may add the two repositories above as backups. `vidocq update` looks for a SNAPSHOT CLI on `maven.vidocq.dev`; `VIDOCQ_SNAPSHOTS=https://maven.bak.vidocq.dev/snapshots` points it to the mirror.

[source,bash]
----
vidocq create --name my-api -x cassini-rest --parent-version 0.4.0-SNAPSHOT
----

A CLI installed from a SNAPSHOT (`VIDOCQ_VERSION=snapshot`, see xref:getting-started.adoc[Getting started]) scaffolds with its own SNAPSHOT runtime, so `--parent-version` is not needed there. A SNAPSHOT changes with every push to `main`: run `mvn -U package` to pick up the newest one.

[#dev]
=== `vidocq dev`

Runs `mvn process-classes vidocq:dev` in the project, through `./mvnw` when there is one: the
application starts with its dependencies and extensions on the module path, the dev console and
a debug agent on port `5005`, and restarts on every source change — exactly as
`mvn vidocq:dev` does, see xref:modules/vidocq-runtime-maven-plugin.adoc[the Maven plugin] for
its settings (continuous testing, dev services, …).

[cols="1,2"]
|===
| Option | Description

| `--port, -p <n>` | HTTP listening port, passed as `vidocq.chappe.listener.default.port` so it outranks the project's own `vidocq.http.port`.
| `--profile, -P <name>` | Config profile to activate (`-Dvidocq.profile`, default `dev`).
| `--debug` | Force the debug agent on (`-Dvidocq.dev.debug=true`); dev mode opens it by default, on this machine only.
|===

Ctrl+C stops Maven and the application; the CLI returns once both are down. `vidocq dev` and `vidocq start`
used to boot the runtime inside the CLI's own JVM, which holds neither the project's classes nor its
extensions: the runtime came up empty, with nothing listening.

[#start]
=== `vidocq start`

Runs `mvn vidocq:run` in the project, through `./mvnw` when there is one: the goal compiles the
project and starts the application with its dependencies and extensions on the module path.

[cols="1,2"]
|===
| Option | Description

| `--port, -p <n>` | HTTP listening port, over the project's own setting.
| `--config, -c <file>` | Path to an external `vidocq.properties` file.
| `--debug` | Open a debug agent on port `5005` (`-Dvidocq.run.debug=true`).
|===

[#test]
=== `vidocq test`

Runs `mvn vidocq:test` in the project, through `./mvnw` when there is one: every test, then again on each change
of the main or test sources, without starting the application. `r` runs every test, `f` the failed ones, `q`
quits. See xref:continuous-testing.adoc[Continuous testing].

[#idea]
=== `vidocq idea`

Runs `mvn vidocq:idea`: one IntelliJ run configuration per application for `vidocq:dev`, `vidocq:run` and a remote
debug, in `.run/`, never `.idea/`. Experimental, as the goal is.

[source,bash]
----
vidocq idea                      # write or update .run/*.run.xml
vidocq idea --check              # CI: fail when .run/ does not match the poms
vidocq idea --strict             # CI: also fail on files written or edited by hand
vidocq idea --kind application   # an Application run of the main class instead
----

The options map to `-Dvidocq.idea.check=true`, `-Dvidocq.idea.check=strict` and `-Dvidocq.idea.kind`; see
xref:modules/vidocq-runtime-maven-plugin.adoc#idea[the `vidocq:idea` goal].

[#vscode]
=== `vidocq vscode`

Runs `mvn vidocq:vscode`: `.vscode/settings.json` runs the Java extension's language server on Java 25 and turns its
automatic build off, `tasks.json` runs `vidocq dev`, `run` and `test`, `launch.json` attaches the debugger to
`vidocq dev`. A file it did not write is left alone.

[source,bash]
----
vidocq vscode            # write or update .vscode/
vidocq vscode --check    # CI: fail when a file is missing or out of date
----

`--check` maps to `-Dvidocq.vscode.check=true`; see
xref:modules/vidocq-runtime-maven-plugin.adoc#vscode[the `vidocq:vscode` goal].

[#eclipse]
=== `vidocq eclipse`

Runs `mvn vidocq:eclipse`: `.eclipse/` gets, per application, Maven builds of `vidocq dev`, `run` and `test` and a
debug configuration that attaches to `vidocq dev`, listed under Run Configurations once the project is imported. A
file it did not write is left alone. Turn Project > Build Automatically off while `vidocq dev` runs.

[source,bash]
----
vidocq eclipse            # write or update .eclipse/
vidocq eclipse --check    # CI: fail when a file is missing or out of date
----

`--check` maps to `-Dvidocq.eclipse.check=true`; see
xref:modules/vidocq-runtime-maven-plugin.adoc#eclipse[the `vidocq:eclipse` goal].

[#build]
=== `vidocq build` & `vidocq clean`

Thin, coloured wrappers around the real `vidocq-runtime-maven-plugin` goals. The CLI resolves
the project `mvnw` wrapper (walking the cwd and its ancestors) and falls back to `mvn`;
Maven's output streams straight to the terminal.

[cols="1,2,2"]
|===
| Type | Maven invocation | Result

| `package` _(default)_ | `mvn package` | Standalone distribution ZIP.
| `jlink` | `mvn package vidocq:jlink` | Self-contained jlink runtime image (no `java` on target).
| `jpackage` | `mvn package vidocq:jpackage` | Native installer (`.dmg`/`.deb`/`.msi`) or app-image.
| `docker` | `mvn package vidocq:jlink vidocq:docker` | Dockerfile around the jlink image, which it builds first [.tag-new]#NEW#.
|===

Shared options:

[cols="1,2"]
|===
| Option | Description

| `--offline, -o` | Run Maven offline (`-o`).
| `--skip-tests` | Skip tests (`build` only, `-DskipTests`).
| `--dry-run` | Print the resolved Maven command without running it.
| `-- <args…>` | Pass everything after `--` straight through to Maven.
|===

[source,bash]
----
vidocq build jlink --skip-tests
vidocq clean
vidocq build -- -Dvidocq.docker.build=true   # extra args after --
----

[#extension]
=== `vidocq extension`

Manages project-level extensions by editing `./pom.xml` in place (text-based, preserving
formatting; idempotent thanks to a StAX dependency scan). Without the CLI,
xref:modules/vidocq-runtime-maven-plugin.adoc#extension-goals[`mvn vidocq:add-extension` and
`vidocq:remove-extension`] make the same edits: both run the code of `vidocq-runtime-tooling`.

[cols="1,2"]
|===
| Sub-command | Description

| `list [--installed\|--available\|--all] [--refresh]` | List extensions. `--installed` (default) lists the extensions of the project in the current directory; `--available` lists the catalog built into the CLI, by family (Jakarta EE, MicroProfile, Data, Web); `--all` shows both. xref:modules/vidocq-runtime-maven-plugin.adoc#report-goals[`mvn vidocq:list-extensions`] gives the same list.
| `add <id…>` | Inject the matching `<dependency>` into `pom.xml`, the extension's APT codegen bundle into the compiler's `annotationProcessorPaths` when it ships one, and its directives into `src/main/java/module-info.java`. The dependency and the codegen path carry the parent's version, written out.
| `remove <id…>` | Remove the matching project-level `<dependency>`, its codegen path and its `module-info.java` directives — undoing `add`. The settings `add` wrote into `vidocq.properties` stay: they are the application's.
|===

[#extension-settings]
`add` also appends the settings an extension needs to `vidocq.properties` [.tag-new]#NEW#, as one block opened by
`# <id>: settings written by the Vidocq CLI, yours to edit`, written once: a second `add` finds the block, and a key the
application already sets, active or commented, is left out, so nothing is overwritten. `vidocq create -x` writes the
same blocks. `{app}` below is the project's artifactId.

[cols="1,3"]
|===
| Extension | Block

| `humboldt-telemetry`
| `otel.sdk.disabled=false`, `otel.service.name={app}`, `otel.exporter.otlp.endpoint=http://localhost:4318` and
  `otel.exporter.otlp.protocol=http/protobuf`: a local collector. Under `vidocq dev`, the OpenTelemetry dev service
  sets the endpoint and the protocol to its own, as system properties, which outrank the file.

| `cervantes-jwt`
| Comments only. The Keycloak dev service sets `mp.jwt.verify.issuer` and `mp.jwt.verify.publickey.location` under
  `vidocq dev`, `vidocq test` and `mvn test`; the block shows them, commented, for a realm named `{app}` on your
  identity provider, and `vidocq.dev.keycloak.realm-import` / `vidocq.dev.keycloak.realm`, commented too: a realm
  import naming a file not there yet would stop the dev service. `vidocq doctor` warns until a verification key is
  set (<<doctor-project>>).
|===

[#extension-codegen-path]
Under a `vidocq-runtime-parent` from 0.4.0, or a pom that declares `vidocq-runtime-maven-plugin` with
`<extensions>true</extensions>`, `add` writes no codegen path: the plugin puts the bundle on the
processor path at build time (xref:modules/vidocq-runtime-maven-plugin.adoc#codegen-wiring[The plugin wires the
codegen bundles]). `remove` still takes away a path written before. Otherwise, the codegen path goes into the compiler plugin of the project's own build: the
`maven-compiler-plugin` the pom already declares, if any, rather than a second one, and never the one of a profile
or of `pluginManagement`, which the default build does not run. Its `annotationProcessorPaths` must append to the
parent's, where `vidocq-runtime-core-codegen`, the Vauban indexer, is wired: without
`combine.children="append"`, the application's beans get no generated factory. `add` writes the attribute on the
block it fills, and warns when it adds an extension without a codegen bundle to a pom whose block still replaces
the parent's; xref:modules/vidocq-runtime-maven-plugin.adoc#goals[`vidocq:checkpom`] fails such a build.

An id may be a known short name (e.g. `cassini-rest`; the catalog now has `grimm-openapi`, `grimm-openapi-ui`,
`migration`, `flyway-migration` and `liquibase-migration` too) or an explicit `groupId:artifactId`,
for an extension outside the catalog. Any other name is refused, with the closest catalog ids, and nothing is
written:

----
$ vidocq extension add mansart-persistence
✘ Invalid extension id 'mansart-persistence': not in the Vidocq catalog. Did you mean: mansart-data, mansart-pool, mansart-transactions? An extension outside the catalog is added as groupId:artifactId.
----

A block that lists `vidocq-runtime-core-codegen` itself, as in a pom without the Vidocq parent, keeps the indexer:
`add` does not warn about it.

In `module-info.java`, `add` declares `requires` on the extension's module, which re-exports most
extension APIs (MicroProfile Health through `knock-health`, Fault Tolerance through
`heisenberg-fault-tolerance`, …). `cassini-rest` also needs Jakarta REST, JSON-B, CDI and the Cassini
API, `requires static java.compiler` for its generated adapters, and `opens` the application
package its resources live in; `mansart-data` needs the same `requires static` and `opens`. Each
added line ends with `// vidocq:<id>`, which is what `remove` takes back — never a line written by
hand, except a `requires` of the removed extension's own module, which no longer resolves.
`vidocq create -x` writes the same directives.

[#extension-descriptor]
==== For extension authors

The catalog comes from the extensions themselves. Each first-party extension ships
`src/main/resources/META-INF/vidocq/extension.properties`, and the CLI's catalog,
`META-INF/vidocq/extension-catalog.properties`, is built from those descriptors, with the groupId, artifactId
and module that each extension's `pom.xml` and `module-info.java` declare. A test of `vidocq-runtime-tooling`
rebuilds the catalog from the reactor and fails when it no longer matches; it says how to regenerate it. The
catalog lists the extensions sorted by id.

[source,properties]
----
# The short id of `vidocq extension add <id>` and `vidocq create -x <id>`
id = cassini-rest
description = Jakarta REST (JAX-RS) endpoints
# The APT bundle that goes on the annotationProcessorPaths, with the extension's groupId and version
codegen = vidocq-runtime-cassini-rest-extension-codegen
# What the application's module-info.java needs besides `requires` of the extension's module
module-info.requires.static = java.compiler
module-info.requires = jakarta.cdi, jakarta.inject, jakarta.ws.rs, jakarta.json.bind, io.vidocq.cassini.api
# Opens the application package, once it holds a class
module-info.opens-application-package = true
----

An extension with a dev service names it [.tag-new]#NEW#, and `add` declares it (xref:dev-services.adoc#declared-for-you[Declared for you]):

[source,properties]
----
# The dev service (io.vidocq.runtime) that provides what the extension connects to
devservice = vidocq-runtime-devservice-postgres
# The JDBC driver it starts on, groupId:artifactId:version, written in runtime scope
devservice.driver = org.postgresql:postgresql:42.7.10
# false keeps it out of test scope, for a service no test needs (Telemetry's collector)
devservice.in-tests = true
----

Its settings are lines, in key order, which `add` appends as a block to `vidocq.properties` [.tag-new]#NEW#
(<<extension-settings>>); `{app}` is the project's artifactId:

[source,properties]
----
config.01 = # Traces, metrics and logs leave through OTLP.
config.02 = otel.service.name={app}
----

Only `id` and `description` are required. The `module-info.*` keys are what `add` writes for a new
application. They are not checks: the directives a build must hold, which
xref:modules/vidocq-runtime-maven-plugin.adoc#goals[`vidocq:check-module-info`] enforces, go in
`META-INF/vidocq/module-requirements.properties`.

`list --installed`, `vidocq info` and `vidocq doctor` resolve the project's runtime dependencies
with Maven (`maven-dependency-plugin:list`, compile + runtime scopes, transitively) and keep every
JAR whose module provides `io.vidocq.runtime.spi.VidocqExtension`. An extension pulled in by
another one — `chappe-webserver` under `cassini-rest` — is listed and marked `(transitive)`.
Resolving takes as long as a Maven run, and may download artifacts on first use, so the answer
is cached in `~/.vidocq/cache/project-extensions/`, one file per project:

* the entry is keyed by the content of `pom.xml` — any edit resolves again;
* when nothing resolved is a SNAPSHOT, the entry is final: a release never changes;
* otherwise it records the size and modification time of every SNAPSHOT JAR and POM in the local
  repository (and of a SNAPSHOT parent POM), and resolves again as soon as one of them was
  re-downloaded. A newer SNAPSHOT still sitting in the remote repository is not seen until
  something fetches it: `vidocq extension list --refresh` forces a resolution.

[source,bash]
----
vidocq extension list --available
vidocq extension add cassini-rest knock-health
vidocq extension remove knock-health
----

[NOTE]
====
`list --available` lists the catalog built into the CLI, which every extension of the runtime describes itself
(its `META-INF/vidocq/extension.properties` names its id, description and family), so the catalog matches the
runtime the CLI belongs to. It reads no remote registry: one, for extensions released apart from the runtime,
belongs with Vidocq/vidocq#17.
====

[#config]
=== `vidocq config`

Reads and writes the project's `vidocq.properties` (project root, falling back to
`src/main/resources`). `set` preserves comments, blank lines, key order and separator
spacing, and creates the file when none exists.

The Maven plugin has no `config` goal: in a build, `vidocq.properties` is a file of the sources, edited like the
others, and xref:modules/vidocq-runtime-maven-plugin.adoc#report-goals[`vidocq:doctor`] reports the keys it does not
recognize (Vidocq/vidocq#314).

[cols="1,2"]
|===
| Sub-command | Description

| `get <key>` | Print the value bound to `<key>`.
| `set <key> <value>` | Set (or append) `<key>` to `<value>`.
| `list` | Print every `key=value` pair.
|===

[source,bash]
----
vidocq config get vidocq.http.port
vidocq config set vidocq.http.port 9090
vidocq config list
----

`set` warns at once on a `vidocq.*` key whose namespace no Vidocq module reads, and names the key you most likely
meant; the key is set all the same:

[source]
----
$ vidocq config set vidocq.htpp.port 9090
✔ Set vidocq.htpp.port = 9090  (src/main/resources/vidocq.properties)
⚠ No Vidocq module reads 'vidocq.htpp.port'. Did you mean 'vidocq.http.port'?
----

[#doctor]
=== `vidocq doctor`

Inspects the local environment and current project and prints a ✔/⚠/✘ report. It exits
non-zero when a blocking issue is found, so it doubles as a CI pre-flight gate
(`vidocq doctor && vidocq build`). Without the CLI,
xref:modules/vidocq-runtime-maven-plugin.adoc#report-goals[`mvn vidocq:doctor`] runs the same checks
.

[cols="1,3"]
|===
| Check | Meaning

| **Java version** | ✔ running JVM ≥ minimum (25); ✘ below minimum.
| **JAVA_HOME** | ✔ set and a directory; ⚠ unset / not a directory.
| **Maven wrapper** | ✔ `mvnw` in the cwd or an ancestor; ⚠ none found.
| **Vidocq project** | ✔ `pom.xml` references `io.vidocq.runtime`; ⚠ no pom / not a Vidocq pom.
| **Extensions** | ✔ the extensions in the project's runtime dependencies, none included (an application of CDI beans needs none); ⚠ Maven could not resolve them.
| **Config** | ✔ no `vidocq.properties` or all keys recognised; ⚠ unknown `vidocq.*` key(s).
|===

[#doctor-project]
In a Vidocq project, `doctor` also checks the project, from its sources, so before a compile
(Vidocq/vidocq#339). What the build checks with what Maven resolves stays with
xref:modules/vidocq-runtime-maven-plugin.adoc#goals[`vidocq:checkpom` and `vidocq:check-module-info`]: these checks
read what the pom and `module-info.java` declare.

[cols="1,3"]
|===
| Check | Meaning

| **Codegen bundles** | ✔ every catalog extension the pom declares has its `-codegen` bundle on `annotationProcessorPaths`, or the plugin puts it there (a `vidocq-runtime-parent` from 0.4.0, or the plugin declared with `<extensions>true</extensions>`); ✘ a bundle is missing; ⚠ a bundle whose extension is gone.
| **Vauban indexer** | ✔ the indexer, `vidocq-runtime-core-codegen`, is on the processor path; ✘ `annotationProcessorPaths` replace the parent's, which hold it, instead of appending (`combine.children="append"`), or, without the Vidocq parent, the pom does not declare it.
| **Module directives** | ✔ `module-info.java` declares the `requires` (and `opens`) of each extension, the `opens` of the resource packages it reads included, such as Flyway's `opens db.migration` [.tag-new]#NEW#, and, once the application is compiled, the `opens` of the packages the runtime reaches by reflection, read from `target/classes` as `vidocq:check-module-info` reads them (JPA entities, the types a REST resource returns, interceptors with a private method) [.tag-new]#NEW#; before a compile it says to compile for those; ✘ one is missing, which `vidocq:check-module-info` would fail the build on; ⚠ no `module-info.java`.
| **JWT verification** [.tag-new]#NEW# | Shown with `cervantes-jwt`. ✔ `vidocq.properties` sets `mp.jwt.verify.publickey.location` or `mp.jwt.verify.publickey`, in any profile; ⚠ none: the Keycloak dev service sets it under `vidocq dev` and the tests, and production would reject every token. Not fixable: only the application knows its identity provider.
| **Dev services** [.tag-new]#NEW# | ✔ each extension with a dev service (`mansart-pool`, `cervantes-jwt`, `humboldt-telemetry`) has its provider on `vidocq-runtime-maven-plugin`, the provider and `vidocq-runtime-devservices-junit` in test scope (not for the collector), and, for the pool, a JDBC driver; ⚠ one is missing (xref:dev-services.adoc#declared-for-you[Declared for you]).
| **Maven version** | ✔ the wrapper runs the Maven Vidocq is built with, or a newer one; ⚠ an older one. Shown when the project has a wrapper.
| **HTTP port** | ✔ the port of `vidocq.chappe.listener.default.port`, else `vidocq.http.port`, else 8080, is free; ⚠ something listens there.
|===

A fixable ✘ or ⚠ is followed by `↳ Fix: vidocq doctor --fix`. `--fix` first repairs, then reports:

* it wires the missing codegen bundles and removes those whose extension is gone, without a `<version>` when the BOM
  versions them; under a parent that wires them, it adds none;
* it makes `annotationProcessorPaths` append to the parent's, or declares the indexer without the Vidocq parent;
* it declares what the dev services of the extensions need, as `vidocq extension add` does [.tag-new]#NEW#;
* it adds the missing `module-info.java` directives, each marked `// vidocq:<id>`, as `vidocq extension add` does,
  and creates the folder of a resource package it opens, such as `src/main/resources/db/migration` [.tag-new]#NEW#;
* it opens the packages the runtime reaches by reflection, in the block `vidocq:complete-module-info` writes [.tag-new]#NEW#;
* it writes a missing Maven wrapper, and moves an older wrapper to the Maven Vidocq is built with.

A created project reports no warning. `doctor` asks for the `opens` the catalog extensions need, Flyway's
`opens db.migration` included, and for those of the packages reached by reflection, with the same code as
`vidocq:check-module-info` at `process-classes` [.tag-new]#NEW#; an extension
outside the catalog is known to the build only, through the descriptors of the resolved dependencies, and
`vidocq:complete-module-info` adds what they ask for. `doctor` does not summarise `vidocq:analyze-deps` either: that
report needs the compiled classes.

`--verbose, -v` appends a per-status summary footer and the minimum Java version. Warnings
never fail the command; only ✘ checks set a non-zero exit code.

[#completion]
=== `vidocq completion`

Prints a self-contained completion script to stdout. It completescommands, sub-commands
(`extension list|add|remove`, `config get|set|list`, …), each command's options, build types,
and values: the catalog's extension ids after `extension add` and `create -x`, less those the `pom.xml` already declares, the extensions
the current `pom.xml` declares after `extension remove`, the keys of the project's
`vidocq.properties` after `config get|set`. These values are read by the script itself, so
pressing TAB never starts a JVM.

[source,bash]
----
# bash — load for the current shell
source <(vidocq completion bash)

# zsh — install into the completion path
vidocq completion zsh > "${fpath[1]}/_vidocq"
----

`vidocq completion install`does it for you: it writes the script to
`~/.vidocq/completion/vidocq.<shell>` and adds a marked block sourcing it to `~/.zshrc` or
`~/.bashrc`. The shell comes from `$SHELL` unless named (`vidocq completion install bash`).
Running it again replaces the block instead of adding another. The script records which CLI
build wrote it, and every `vidocq` run rewrites an installed script another build wrote, so the
completion follows the CLI however it was replaced. `vidocq completion uninstall` removes the
block and the script.

NOTE: On macOS, Terminal starts bash as a login shell, which reads `~/.bash_profile`, not
`~/.bashrc`. Source `~/.bashrc` from `~/.bash_profile` if it does not already.

[#update]
=== `vidocq update`

Updates the CLI itself, from the same repositories as `install.sh`:

* a release CLI moves to the latest release on Maven Central (`0.3.0` → `0.4.0`);
* a SNAPSHOT CLI moves to the latest build of the highest SNAPSHOT line in the Central snapshot
  repository. It records the build it installed, so the next run knows whether a newer one was
  published. A SNAPSHOT CLI without that record — installed by `install.sh`, or built locally —
  takes the published build only when it was deployed after the running CLI was built: a local
  build of newer sources is never downgraded.

The new version is unpacked next to the others in `~/.vidocq/cli` and swapped in by renaming
the directory, the `vidocq` launcher in `~/.local/bin` (or `$VIDOCQ_BIN`) is pointed at it, and
an installed completion script is regenerated. Earlier versions stay where they are.

[source,bash]
----
vidocq update --check   # only report
vidocq update
----

`VIDOCQ_CENTRAL` and `VIDOCQ_SNAPSHOTS` point it at repository mirrors, as for `install.sh`.

[#update-notice]
==== The update notice

Once a day at most, a CLI installed by `install.sh` or `vidocq update` checks, while a command runs, whether
`vidocq update` would install something, and says so after the command, on the error stream:

[source]
----
A newer Vidocq CLI is available: 0.4.1. Run 'vidocq update' to install it (VIDOCQ_NO_UPDATE_CHECK=1 turns this notice off).
----

* It runs on a terminal only, never in a pipe, a script or a CI job, and never after `version`, `completion`,
  `config get` or `update`, whose output a script may read.
* A repository that does not answer within a second of the command's end is not waited for, and is asked again
  next time; a failure says nothing.
* The last check is recorded in `~/.vidocq/cache/update-check`.
* `VIDOCQ_NO_UPDATE_CHECK=1` turns it off.

== Configuration & profiles

The CLI operates on the standard Vidocq configuration model. `vidocq.properties` lives in the
project root or `src/main/resources`; profile overlays (`vidocq-<profile>.properties`) are
layered by `vidocq dev --profile`. Any key is overridable via `-Dkey=value`, environment
variables, or an external file — see xref:reference.adoc[Reference] for the full ordinal
hierarchy.

== Exit codes

[cols="1,3"]
|===
| Code | Meaning

| `0` | Success (including `doctor` runs with only ✔/⚠ checks).
| `1` | A usage error, a failed command, or a `doctor` run with at least one ✘ check.
|===

== Extending the CLI (plugin SPI)

Third-party modules can contribute extra top-level commands without forking the CLI by
implementing `io.vidocq.runtime.cli.spi.VidocqCliPlugin` and declaring it as a
`ServiceLoader` provider. Any command token that is not a built-in is matched against the
registered plugins; built-ins always win, and `vidocq help` lists discovered plugins.
