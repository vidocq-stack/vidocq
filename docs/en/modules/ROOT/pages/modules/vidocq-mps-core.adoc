= vidocq-mps-core
:description: Vidocq-MPS boot orchestrator and lifecycle.

[.lead]
`vidocq-mps-core` is the Vidocq-MPS runtime engine. It orchestrates the boot sequence, reads the extension index produced at build time, instantiates the bootstrap class generated by Class-File API, and coordinates startup phases.

== Coordinates

[cols="1,3"]
|===
| Artefact | `io.vidocq.mpserver:vidocq-mps-core:0.1.0-SNAPSHOT`
| JPMS module | `io.vidocq.mpserver.core`
| Source | `vidocq-mps-core/src/main/java/io/vidocq/mpserver/core/`
|===

== Responsibilities

* Read `META-INF/vidocq-mps/extensions.list` produced by the APT processor.
* Load the `RuntimeBootstrap` class synthesised by the Maven plugin.
* Run boot phases in order:

. **Config** — MicroProfile Config resolution.
. **Extensions init** — invoke `RUNTIME_INIT` recorders.
. **CDI start** — delegate to xref:vauban::index.adoc[Vauban] (`Vauban.bootstrap()`).
. **Transport bind** — delegate to xref:chappe::index.adoc[Chappe] via `vidocq-mps-chappe-extension`.
. **Routes register** — delegate to xref:cassini::index.adoc[Cassini], xref:foy::index.adoc[Foy] and xref:mansart::index.adoc[Mansart] depending on active extensions.

* Manage the shutdown cycle — `SIGTERM` propagates in reverse order, virtual threads drain cleanly.

== Entry point

[source,java]
----
package io.example;

public class App {
    public static void main(String[] args) {
        io.vidocq.mpserver.Vidocq.main(args);
    }
}
----

`Vidocq.main` is a simple facade. User code does not need a `@SpringBootApplication` nor an application class — the boot sequence is fully driven by the APT index.

== Lifecycle hooks

An extension can subscribe to phases through the SPI:

[source,java]
----
@BuildStep
ApplicationStartBuildItem onStart(SomeExtensionContext ctx) {
    // contribute a build step triggered at RUNTIME_INIT
    return new ApplicationStartBuildItem();
}
----

`ApplicationStartBuildItem` and `ApplicationStopBuildItem` are `SymbolicBuildItem` types — no payload, only a marker semantic.

== Threading

Boot itself is intentionally sequential on a platform thread (easier diagnosis, readable stack traces). The only virtual threads created during boot are:

* the xref:chappe::index.adoc[Chappe] HTTP I/O pool (one VT per inbound connection);
* the xref:mansart::index.adoc[Mansart] JDBC housekeeping pool;
* `StructuredTaskScope` instances opened by extensions that need them (typically `vidocq-mps-health-extension` for periodic checks).
