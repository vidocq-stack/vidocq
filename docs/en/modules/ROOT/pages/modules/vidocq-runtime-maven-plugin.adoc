= vidocq-runtime-maven-plugin
:description: Vidocq Runtime Maven plugin — generate, package, dev, run, jlink, jpackage, docker, idea.

[.lead]
`vidocq-runtime-maven-plugin` is the Maven plugin that turns an application into a deployable standalone distribution. It exposes twenty-one goals: `generate`, `analyze-deps`, `package`, `dev`, `run`, `test`, `test-path`, `checkpom`, `jlink`, `jpackage`, `docker`, `check-module-info`, `complete-module-info`, `idea`, `vscode`, `eclipse`, `add-extension`, `remove-extension`, `list-extensions`, `doctor`, `create`. (`modularize` moved to the Vauban plugin — see below.) Also see `vidocq/JLINK.md` for internal details.

== Coordinates

[cols="1,3"]
|===
| Artefact | `io.vidocq.runtime:vidocq-runtime-maven-plugin:{project-version}`
| Java module | *(none)* — Maven plugins run on Maven's class path, so the plugin intentionally has no `module-info.java`.
|===

== Goals

[cols="1,3"]
|===
| Goal | Role

| `vidocq:generate`
| Generates the CDI bean index (`META-INF/vauban-beans.list`) and the code of the dependency jars it scans — their `_VaubanComponents`, client proxies and intercepted subclasses — into an enriched copy of each jar that every launch uses. See <<generate,the `vidocq:generate` goal>>. Extension discovery itself needs no index — it is plain `ServiceLoader` over `provides` directives.

| `vidocq:package`
| Standalone distribution: `bin/run.sh` + `bin/run.cmd` launchers and `lib/*.jar` (application + module-path closure), attached as a `-dist.zip` artifact. `-Dvidocq.package.layer=false` gives the legacy layout, launched through the main class's module: see <<package-layout>>. Never a dev-only jar, even one the project declares: see <<dev-tools,Dev tools and binaries>>.

| `vidocq:dev`
| Dev/watch mode — forks a child JVM with `-Dvidocq.profile=dev`, recompiles and hot-reloads on change. The child runs a JDWP agent on `127.0.0.1:5005`, see <<debugger,the debug agent>>. With continuous testing, it also runs the tests after every reload; see xref:continuous-testing.adoc[Continuous testing]. It also adds the dev tools — the dev console and, per extension, its `-dev` panel module — to the child's module path only: see <<dev-tools,Dev tools and binaries>>.

| `vidocq:run`
| Runs the application once in a forked JVM, after compiling and indexing it: the goal forks the lifecycle up to `process-classes`, so `mvn vidocq:run` alone is a complete run. See <<run,the `vidocq:run` goal>>.

| `vidocq:test`
| Continuous testing without the application: runs the tests, then again on every change of the main or test sources, with a summary and keys in the terminal. See <<test,the `vidocq:test` goal>>.

| `vidocq:checkpom`
| Verifies every `vidocq-runtime-<name>-extension` declared in the pom is correctly wired (annotation processor paths, codegen bundles). Bound to `validate` via `pluginManagement`. A missing codegen bundle is reported with the `<path>` to paste into the compiler's `annotationProcessorPaths`, its group and version included; a `-dev` companion module is never asked for one. The bundle is the one the extension's `META-INF/vidocq/extension.properties` names, or none when it names none(xref:modules/vidocq-runtime-cli.adoc#extension-descriptor[the extension descriptor]); for an extension without that descriptor, the `vidocq-runtime-<name>-extension-codegen` its name gives, when that artifact is published. Also warns, never fails, on a dev-only jar declared in any scope but `test`: see <<dev-tools,Dev tools and binaries>>. Warns, never fails, on a codegen `<path>` still declared with `<type>pom</type>`, which IntelliJ's build cannot read(xref:modules/vidocq-runtime-extensions.adoc#codegen-bundles[Codegen bundles are jars]). Fails when an application that declares an extension has lost `vidocq-runtime-core-codegen`, the Vauban indexer the parent wires, typically to an `annotationProcessorPaths` without `combine.children="append"`; a module with `<proc>none</proc>` is left alone. Warns, never fails, when an extension with a dev service lacks a piece of it — its provider on this plugin, the test-scope pair a plain `mvn test` needs, the pool's JDBC driver — reading the effective model, so a provider a parent declares counts [.tag-new]#NEW# (xref:dev-services.adoc#declared-for-you[Declared for you]).

| `vidocq:analyze-deps`
| Explains which dependencies `vidocq:generate` scans, why, and what it does with each; prints the `<scanDependencies>` block that makes the detection explicit. See <<analyze-deps>>.

| `vauban:modularize` (Vauban plugin)
| Gives the non-modular dependency jars a `module-info` in `target/vauban-modularized/`, picked up automatically by `dev`, `jlink` and `package`. No longer a goal of this plugin — see <<modularize>>.

| `vidocq:jlink`
| Standalone Java image (`target/dist/`) with `bin/<launcher>` binary — no `java` required on target. [[jlink-modularize]]The automatic modules of the dependencies (Flyway, a JDBC driver…) first get their module descriptor, as `vauban:modularize` does in its `all-automatic` mode [.tag-new]#NEW#: jlink refuses an automatic module. A project that ran `vauban:modularize` itself keeps its own copies and options; `-Dvidocq.jlink.modularize=false` turns it off.

| `vidocq:jpackage`
| Native OS bundle (`.app` macOS, `.exe`/`.msi` Windows, `.deb`/`.rpm` Linux) or cross-platform app-image.

| `vidocq:docker`
| Generates `target/Dockerfile` distroless based on `distroless/base-debian12:nonroot`. Optional build via `vidocq.docker.build=true`. [.tag-new]#NEW# On macOS or Windows, the Dockerfile links the image inside a Linux JDK (<<docker-linux-image,details>>).

| `vidocq:check-module-info`
| Verifies the application `module-info.java` declares the Java module directives its Vidocq extensions need (e.g. `opens db.migration` for Flyway migrations); the failure names `vidocq doctor --fix`, which adds those of the catalog extensions. [[check-module-info-uncompiled]][.tag-new]#NEW# When `module-info.java` did not compile, as under `vidocq dev` after a compile error, the goal says so and checks nothing, instead of reporting a module without `module-info.java`. [[check-module-info-reflected]][.tag-new]#NEW# It also opens the packages the runtime reaches by reflection: the JPA entities, and the types a REST resource or provider takes or returns, with the types their fields and getters hold, which JSON-B binds by reflection. [[check-module-info-interceptors]][.tag-new]#NEW# The package of a CDI interceptor too when a method its container calls is `private`: Vauban calls the other interceptor methods through the provider generated in their package, which needs no directive, but a private one by reflection. Such a package that the module does not open fails the build with the line to add, for instance `opens com.acme.shop.book;   (com.acme.shop.book.Book, reached through com.acme.shop.book.BookResource)`, and names `vidocq doctor --fix` and `./mvnw vidocq:complete-module-info`, which add it; before, the first request failed with an `IllegalAccessException`. [[check-module-info-dev]][.tag-new]#NEW# Under `vidocq dev` (a `vidocq:dev` among the goals, or its recompile, which passes `-Dvidocq.moduleinfo.dev=true`), the goal opens such a package itself, in `module-info.java` and in the compiled `module-info.class`, prints `✔ module-info.java: opens com.acme.shop.book;   (…)` and lets the application start: a new package of entities or DTOs needs no step of its own. `-Dvidocq.moduleinfo.failOnMissing=false` turns the failure into a warning. xref:java-modules.adoc[Java modules in a Vidocq application] explains what the goal detects and what it cannot see.

| `vidocq:complete-module-info`
| Opt-in companion of `check-module-info` — rewrites `src/main/java/module-info.java` to add the missing directives. [.tag-new]#NEW# They include the `opens` of the packages the runtime reaches by reflection that `check-module-info` reports, so `mvn vidocq:complete-module-info` fixes what it asks for.

| `vidocq:test-path` [.tag-new]#NEW#
| Names the compile and runtime jars in `vidocq.test.runtimePath` for the application `@VidocqTest` starts, so that a driver no module requires is on its module path. Bound to `process-test-classes` by `vidocq-runtime-parent`. xref:testing.adoc#runtime-dependencies[Details].

| `vidocq:idea`
| Experimental — writes one IntelliJ IDEA shared run configuration per application of the reactor into `.run/`, or checks them in CI. See <<idea,the `vidocq:idea` goal>>.

| `vidocq:vscode`
| Writes the `.vscode/` settings, tasks and debug configuration of the project for VS Code's Java extension, or checks them in CI. See <<vscode,the `vidocq:vscode` goal>>.

| `vidocq:eclipse`
| Writes the Eclipse run and debug configurations of the project into `.eclipse/`, or checks them in CI. See <<eclipse,the `vidocq:eclipse` goal>>.

| `vidocq:add-extension`
| Adds extensions to the project, as `vidocq extension add` does: the dependency, the codegen bundle on the compiler's `annotationProcessorPaths` when the extension ships one, and its directives in `src/main/java/module-info.java`. See <<extension-goals>>.

| `vidocq:remove-extension`
| Removes extensions, undoing `add-extension`, as `vidocq extension remove` does. See <<extension-goals>>.

| `vidocq:list-extensions`
| Lists the extensions the project runs with, as `vidocq extension list` does; `-Dvidocq.extensions.available` adds the catalog. See <<report-goals>>.

| `vidocq:doctor`
| Checks the environment and the project, as `vidocq doctor` does; a failed check fails the build. See <<report-goals>>.

| `vidocq:create`
| Scaffolds a new project, as `vidocq create` does; needs no project. See <<create-goal>>.
|===

[NOTE]
.Scanned dependencies and Java Modules
====
When `vidocq:generate` scans a dependency, the classes it produces for it belong to *that
dependency's* packages. The plugin keeps the module path split-package-free end to end: `generate`
parks those classes in `target/vidocq-patches/<artifactId>/`, thenwrites an *enriched* copy of the
jar that carries them and declares its providers (<<generate>>); `dev`, `run`, `package` and `jlink`
use that copy in place of the original. Only a jar that cannot be given a module descriptor keeps
its original, its classes attached with `--patch-module`. Zero configuration. See
xref:usage.adoc#multi-module-applications-scanned-dependencies[Usage — Multi-module applications].
====

[#codegen-wiring]
== The plugin wires the codegen bundles

An extension used to take two places in the pom: its dependency, and its `-codegen` bundle in the compiler's
`annotationProcessorPaths`. From 0.4.0 it takes one. Declared with `<extensions>true</extensions>`, the plugin
puts the bundles on the processor path itself, once Maven has read the project and before any goal runs
(Vidocq/vidocq#339):

* the Vauban indexer, `vidocq-runtime-core-codegen`;
* the bundle of each catalog extension the project depends on outside the `test` scope, at that extension's
  version.

A path the pom already declares stays as it is and is not added twice, so a pom written for 0.3.0 builds
unchanged. Only a module that declares the plugin is wired: in a multi-module application, the library modules
are left alone. `vidocq:checkpom` then finds every bundle in place.

`vidocq-runtime-parent` declares the plugin that way in its `pluginManagement`: under it, declaring the plugin by
its `groupId` and `artifactId` is enough, and `vidocq create` and `vidocq extension add` write no codegen path. An
application that keeps a parent of its own declares it with the attribute:

[source,xml,subs=attributes+]
----
<plugin>
    <groupId>io.vidocq.runtime</groupId>
    <artifactId>vidocq-runtime-maven-plugin</artifactId>
    <version>{project-version}</version>
    <extensions>true</extensions>
</plugin>
----

Without the attribute, nothing changes: the paths stay in the pom, and `vidocq extension add` keeps writing them.

What was checked before the change, on a project created by `vidocq create -x cassini-rest` with its codegen path
removed:

[cols="1,3",options="header"]
|===
| Tool | Result
| Maven 3.9.16, the version of the wrapper | Same classes in `target/classes` as with the explicit path,
`checkpom` aligned.
| Maven 3.9.16, offline (`-o`) | Same.
| Maven 3.9.9, 3.9.11, 4.0.0-rc-5 | `checkpom` aligned.
| IntelliJ IDEA 2026.2, Maven import | The import runs the plugin: the processor path IntelliJ writes to
`.idea/compiler.xml` is the one an explicit path gives, entry for entry, so IntelliJ's build runs the same
processors.
| VS Code, Java extension 1.56 (jdt.ls 1.61, m2e 2.7.8) | The import runs the plugin: the `.factorypath` it writes
holds the indexer and the extension's bundle, and the IDE's build gives the classes Maven gives. The language server
must run on Java 25 (`java.jdt.ls.java.home`): JDT runs the annotation processors in its own JVM, and they are Java 25
class files. On the Java 21 the extension ships, the import succeeds and the IDE says it cannot load the processors.
| Eclipse 2026-09 (m2e 2.8) | Same m2e and JDT as VS Code's server, on the Java 25 it ships. Not run headless.
|===

An IDE build needs the Vauban processor of 0.4.0 or later: before it (VAU-APT-005), Eclipse's compiler stopped it in
its last round, and an application built by Eclipse or VS Code started without its beans.

[#extension-goals]
== `vidocq:add-extension` and `vidocq:remove-extension` goals

The two goals edit the project the way `vidocq extension add` and `vidocq extension remove` do, for a build
that has Maven and no Vidocq CLI, in CI or in an IDE. Both tools run the same code, from
`vidocq-runtime-tooling`, so they make the same edit (Vidocq/vidocq#314):

[source,bash]
----
mvn vidocq:add-extension -Dextensions=cassini-rest,knock-health
mvn vidocq:remove-extension -Dextensions=knock-health
----

* `-Dextensions` takes catalog ids, comma-separated, or `groupId:artifactId` coordinates. Any other name fails the
  goal, which names the closest catalog ids and writes nothing.
* `add-extension` writes the dependency, the codegen bundle into the compiler plugin of the project's own build,
  and the directives into `src/main/java/module-info.java`, each marked `// vidocq:<id>`. It writes no version when
  `vidocq-runtime-bom` gives it (a `vidocq-runtime-parent` from 0.4.0, or a pom that imports the BOM)
 ; otherwise it pins the version the pom's `vidocq-runtime-parent` gives, else the plugin's own. See
  xref:modules/vidocq-runtime-cli.adoc#extension[`vidocq extension`] for each of these edits.
* `remove-extension` takes back what `add-extension` wrote, the `<dependencies>`, `<build>` and `<plugins>`
  elements it created included.
* Neither goal has a phase. Each edits the project it runs on, once: in a multi-module build, run it on the
  module to change (`mvn -f app/pom.xml vidocq:add-extension …`).

[#report-goals]
== `vidocq:list-extensions` and `vidocq:doctor` goals

The two goals give the reports of `vidocq extension list` and `vidocq doctor` in a build, from the same
`vidocq-runtime-tooling` code (Vidocq/vidocq#314). Neither has a phase; each runs on every module of the build.

[source,bash]
----
mvn vidocq:list-extensions                                  # the extensions the project runs with
mvn vidocq:list-extensions -Dvidocq.extensions.available    # and the catalog
mvn vidocq:doctor [-Dvidocq.doctor.verbose]                 # the checks of vidocq doctor
mvn vidocq:doctor -Dvidocq.doctor.fix                       # repair the project first, as vidocq doctor --fix
----

* `list-extensions` keeps the runtime dependencies whose module provides `io.vidocq.runtime.spi.VidocqExtension`,
  names them by their catalog id, and marks `(transitive)` those the pom does not declare. The CLI runs Maven to
  find the same list.
* `doctor` runs the checks of xref:modules/vidocq-runtime-cli.adoc#doctor[`vidocq doctor`]: the JDK that runs
  Maven, `JAVA_HOME`, the Maven wrapper, the pom, `vidocq.properties` and the extensions, then
 xref:modules/vidocq-runtime-cli.adoc#doctor-project[the project's]: its codegen bundles, the Vauban
  indexer, the `module-info.java` directives, the wrapper's Maven and the HTTP port. A failed check (a JDK older
  than 25, a missing codegen bundle) fails the build; a warning does not. `-Dvidocq.doctor.verbose` also gives the
  hint of the checks that passed, and`-Dvidocq.doctor.fix` first makes the repairs of
  `vidocq doctor --fix` (Vidocq/vidocq#339).

[#create-goal]
== `vidocq:create` goal

Scaffolds a new Vidocq project the way `vidocq create` does, for a machine that has Maven and no Vidocq CLI.
Both run the scaffolder of `vidocq-runtime-tooling`, so they write the same `pom.xml`, `module-info.java`,
`vidocq.properties` and classes (Vidocq/vidocq#314). The goal needs no project; outside one, the plugin is named
in full, as Maven resolves the `vidocq` prefix only for a project that declares the plugin:

[source,bash]
----
mvn io.vidocq.runtime:vidocq-runtime-maven-plugin:{project-version}:create \
    -Dname=my-api -DgroupId=com.acme -Dextensions=cassini-rest,knock-health
----

[cols="1,3"]
|===
| Property | Meaning

| `name` | The project directory and artifactId. Required.
| `groupId` | The Maven groupId; `io.example` by default.
| `package` | The root Java package, which is also the module name; `<groupId>.<name>` by default. It must be a valid Java package name.
| `extensions` | The catalog ids of the extensions to enable, comma-separated, written in this order.
| `parentVersion` | The `vidocq-runtime-parent` version; the plugin's own by default. From 0.4.0 its BOM versions the Vidocq dependencies, written without a `<version>`.
| `main` | `true` also writes an `@VidocqMain` trampoline, for an IDE Run or a `VidocqApp`.
|===

The project is created in the current directory, which must not hold a directory of that name yet. See
xref:modules/vidocq-runtime-cli.adoc#create[`vidocq create`] for what each file holds.

[#generate]
== `vidocq:generate` goal

Bound to `process-classes`. Besides the application's own bean index, it generates code for the dependency jars it scans, so that their beans run generated code instead of reflection: per package a `_VaubanComponents` that creates the beans, injects their fields and calls their methods, a client proxy per normal-scoped bean, an intercepted subclass per intercepted one — the same code the Vauban annotation processor writes for a project, made with the Class-File API.

Last, it writes `META-INF/vidocq/generate.stamp`, which records the `META-INF/vauban-beans.list` it leaves: at boot, an application module whose stamp is missing or records another index was built without the goal, and the boot indexes the unprocessed bean archives itself (xref:modules/vidocq-runtime-core.adoc#vidocq-gen-001[`VIDOCQ-GEN-001`]).

=== Which jars it scans

[cols="1,3"]
|===
| Source | How

| An extension
| A jar of the project declares `Vidocq-Scan-Dependencies: <groupId:artifactId patterns>` in its manifest. The langchain4j-cdi MCP extension declares `dev.langchain4j.cdi.mcp:*`, so the server's beans are generated in every application that uses it.

| The application
| `<scanDependencies>`, `groupId:artifactId` patterns, `*` accepted at the end of either side.

| A CDI bean archive
| Any jar with a `META-INF/beans.xml` whose `bean-discovery-mode` is not `none`. On by default; `-Dvidocq.generate.autoScan=false` or `<autoScan>false</autoScan>` turns it off.

| A brick
| A brick whose codegen bundle declares `META-INF/vidocq/dependency-codegen.properties` selects the jars it can process: a jar with one of its `resources`, or with one of its `class-bytes` in a class file. See <<brick-processors>>.
|===

The dependencies considered are the compile-scope and runtime-scope ones: everything the module path holds at run time. A selected jar is left out when it already carries generated code (a Vidocq brick compiled with the Vauban processor), when `<scanExcludes>` names it, or when it is signed and `<scanDependencies>` does not name it: the build log says which, and why.

=== The enriched copy

Each scanned jar gets a copy in `target/vidocq-enriched/`, under its original file name: the jar with its generated classes, and a module descriptor that `provides io.vidocq.vauban.api.VaubanComponentProvider` with them and `requires` the Vauban modules they call. A jar without a descriptor is first given one, an `open module` synthesized as `vauban:modularize` does. `vidocq:dev`, `vidocq:run`, `vidocq:package` and `vidocq:jlink` put the copy on the module path in place of the original.

A copy is written again only when what it is made from changes — the jar, its generated classes, its providers — so a `vidocq:dev` reload leaves alone the jar its JVM holds open. On a clean build `generate` runs before `vauban:modularize`; at packaging, when that goal gave the jar a descriptor, the copy is rebuilt on it, so the module name and openness configured there are the ones shipped.

The copy is a modified third-party jar: its signature files are dropped, and its manifest records `Vidocq-Enriched-From` (the coordinates) and `Vidocq-Enriched-Digest` (`sha256:` of the original). A packaged application ships it; declare it to your SBOM tooling, or turn the detection off. A jar for which no descriptor can be synthesized — a `ServiceLoader` lookup no explicit module may declare — keeps its original and gets its generated classes through `--patch-module`, and the build says so. An IDE launch without a Maven step uses the original jars, and the beans fall back to reflection.

[cols="1,1,3"]
|===
| Parameter | Default | Role

| `scanDependencies` | none | Jars to scan, whatever else selects them; also enriches a signed jar.
| `scanExcludes` | none | Jars never scanned.
| `autoScan` (`vidocq.generate.autoScan`) | `true` | Scan every CDI bean archive.
| `cacheDir` (`vidocq.generate.cacheDir`)| `$XDG_CACHE_HOME/vidocq/depgen`, else `~/.cache/vidocq/depgen` | Where the output of the brick processors is cached. See <<depgen-cache>>.
|===

The dev console's CDI panel shows the result: a scanned jar's beans read `Class-File` or `partial` in its `codegen` column, no longer `reflection` (xref:dev-console.adoc#cdi-panel[the CDI panel]). A class that only a build-compatible extension makes a bean — a JAX-RS `@Provider` to which Cassini's extension gives `@Dependent`, say — is covered too: `generate` resolves the runtime-scope dependencies as well as the compile-scope ones, so it runs every extension the application runs.

[#brick-processors]
=== Brick processors on dependency jars

Besides Vauban's own code, `vidocq:generate` runs the annotation processors of every brick whose codegen bundle is on the project (Foy's, for instance) over the dependency jars that brick selects. A library compiled without the brick's processor, such as a `@WebListener` or a `ServletContainerInitializer` in a plain jar, then works as if it had been: the processor's output, classes and resources, goes into the jar's enriched copy, and the brick finds it at run time.

The processors see only the classes the hints point at: the top-level classes whose class file holds one of the brick's `class-bytes`, and the classes listed in the service files among its matched `resources`. The other classes of the jar are not compiled, so a class that needs an optional API missing from the build, such as a websocket endpoint without `jakarta.websocket`, does not fail it.

A jar that a brick selects is also scanned by Vauban, so that its beans get their generated code too. Vauban scans such a jar with annotated discovery, even without a `beans.xml`: its classes with a bean-defining annotation become beans. `vidocq:analyze-deps` and the scan log show the source as `selected by a brick (Foy)`. Such a jar, when it has no module descriptor, stays an automatic module in its enriched copy even when Vauban generates providers for it: the providers are listed in its `META-INF/services` files, and an automatic module may use any service, which a synthesized descriptor cannot guarantee. [[brick-automatic-packaging]]`vidocq:package` ships that automatic copy, even when `vauban:modularize` gave the jar a descriptor: it used to rebuild the copy on that descriptor, which can miss a `uses`. The copy's manifest says so with `Vidocq-Automatic: brick-selected`, and its module name is the automatic one, not a name configured for `vauban:modularize`. Only `vidocq:jlink`, which refuses automatic modules, rebuilds it on the `vauban:modularize` descriptor (Vidocq/vidocq#251).

*Not candidates.* The `io.vidocq*` jars, which are built with the processors already. For a `class-bytes` hint, a jar that itself defines the hinted classes, as the API jars do (`jakarta.servlet-api` defines `jakarta/servlet/annotation/WebListener`: it mentions it but is not a library that uses it).

*The build log.* One line per processed jar:

[source,text]
----
vidocq:generate: acme-weblib-1.0.jar — Foy (3 classes, generated)
vidocq:generate: acme-weblib-1.0.jar — Foy (3 classes, cached)
----

`Foy, Mansart` lists several bricks when several selected the jar. Warnings that a processor prints become build warnings.

*A failure.* A processor that cannot handle a library fails the build, with one line per problem. Each names the jar, the brick, the type or member, and the fix:

[source,text]
----
vidocq:generate: acme-weblib-1.0.jar — Foy cannot process acme.web.Hello: <message>. Fix the library, or leave the jar out with <scanExcludes>org.acme:acme-weblib</scanExcludes>. Full javac output: target/vidocq-depgen/acme-weblib.log
----

The whole javac output is in `target/vidocq-depgen/<artifactId>.log`. A generated file that the jar already has, and that the brick does not declare in `merge`, fails the same way.

*Signed jars.* A signed jar is skipped, with an info line (`acme-weblib-1.0.jar is signed; not processed for Foy (name it in scanDependencies to process it)`). Name it in `<scanDependencies>` to process it anyway: its signature files are then dropped from the enriched copy.

[#depgen-cache]
*The cache.* Running javac over a library costs seconds, so its output is kept. The directory is `vidocq.generate.cacheDir` (also `<cacheDir>` of the goal) if set, else `$XDG_CACHE_HOME/vidocq/depgen`, else `~/.cache/vidocq/depgen`. An entry is keyed on its content: the jar, the processors, the jar's classpath (the `groupId:artifactId:version` of each dependency, since a processor's output can depend on the types it resolves there), `--release` and the JDK, so nothing needs invalidating. It is shared between projects, survives `mvn clean`, and is safe to delete.

*In the startup report.* The `layer` headline of the startup report gains `, <k> enriched (Foy 1, Mansart 2)`: the archives of the application layer that a brick enriched, per brick. The application layer holds the dependencies only under `vidocq.app.layer=all` (xref:usage.adoc#app-layer-dependencies[Dependencies in the application layer]), so the count appears there. The archive manifests are read only when the report shows the layer.

*Limits.*

* An annotation with `SOURCE` retention is not in the class files of a library, so a processor cannot see it.
* Versioned classes under `META-INF/versions/N` are not processed.
* A Mansart repository interface compiled without `-parameters` cannot be implemented from a class file, unless its parameters use `@Param`. Mansart's hints are pending (mansart#40, mansart#41): Foy is the first brick to declare them.

[#brick-authors]
==== For brick authors

A brick opts in with `META-INF/vidocq/dependency-codegen.properties` in its codegen bundle, next to its processors. The keys are `brick`, `resources`, `class-bytes`, `markers`, `merge` and `whole-jar`; any other key fails the build. Lists are comma-separated.

[cols="1,3"]
|===
| Key | Role

| `brick`
| Required. The brick's name, as the build log prints it.

| `resources`
| Jar entries whose presence selects the jar.

| `class-bytes`
| Strings searched in the class files of a jar, typically the internal name of an annotation or a prefix of it (`jakarta/servlet/annotation/Web`). A jar that defines classes with that prefix is not selected. At least one of `resources` and `class-bytes` is required, or nothing would select a jar.

| `markers`
| Jar entries that show the jar was already processed by the brick: such a jar is skipped.

| `merge`
| Entries that several jars produce and that are merged into one, such as a `META-INF/services` file. Any other generated entry that the jar already has fails the build.

| `whole-jar`
| Generated entries that describe every class of the jar, such as an index of its classes. The processors see only the hinted classes of a dependency jar, so such an entry would be partial: it is dropped from the output, and the brick's run-time fallback covers the jar.
|===

Two limits apply to the processors of a bundle:

* They are loaded with the platform class loader as parent, so they cannot use the `jdk.compiler` internals (`com.sun.source.*`); only the `javax.annotation.processing` and `javax.lang.model` APIs are there.
* Every annotation processor in the bundle's transitive closure runs over the selected jars. A bundle must not bring other processors along, for instance `vauban-processor` at compile scope.

Foy's file:

[source,properties]
----
brick=Foy
resources=META-INF/services/jakarta.servlet.ServletContainerInitializer,META-INF/web-fragment.xml
class-bytes=jakarta/servlet/annotation/Web,jakarta/servlet/annotation/HandlesTypes
markers=META-INF/io.vidocq.foy/generated,META-INF/foy/class-index.list,META-INF/services/io.vidocq.foy.spi.gen.WebComponent
merge=META-INF/services/io.vidocq.foy.spi.gen.WebComponent
whole-jar=META-INF/foy/class-index.list
----

Foy's `merge` file is also among its `markers`: a jar that already has it was built with Foy's processor, so it is skipped rather than merged. Its `class-index.list` is a marker too, and `whole-jar`: Foy scans a jar without one for `@HandlesTypes` at run time, which a partial index would prevent.

[#analyze-deps]
== `vidocq:analyze-deps` goal

`mvn vidocq:analyze-deps` prints, for each bean archive and each named dependency, what it is — its discovery mode, an explicit or automatic module, signed or not — what selects or excludes it, and what `vidocq:generate` does with it: an enriched copy, an open module synthesized first, or nothing and why. It ends with the `<scanDependencies>` block that makes the detected bean archives explicit, to paste in the pom. It reads the same `scanDependencies`, `scanExcludes` and `autoScan` as `vidocq:generate`: configure them at plugin level so both goals see them. A jar that a brick selects reads `selected by a brick (Foy)` as its source, and the bricks that would process it are listed (<<brick-processors>>). It changes nothing.

[#package-layout]
== `vidocq:package` layouts

By default the application jar lands in `app/`, apart from the module-path closure in `lib/`, and the
`bin/` launchers boot the runtime with `-Dvidocq.app.path="$BASEDIR/app"`: the application resolves into the
module layer the Vauban class loader defines, as it does under `vidocq:dev` and `vidocq:run`.

[[launcher-java-opts]]The launchers pass the `JAVA_OPTS` environment variable to the JVM [.tag-new]#NEW#, after the
`<jvmArgs>` of the pom, so that an option set when the application starts wins; the arguments of the launcher go to
the application:

[source,shell]
----
JAVA_OPTS="-Xmx1g -Dlibrary.loan.max=3" bin/library.sh --port 8081
----

[#package-legacy-layout]
=== The legacy layout

`-Dvidocq.package.layer=false` puts everything in `lib/` and the launchers start the JVM with `--module`,
which takes a module, then a class:

* with no application main class, the runtime's own main, `io.vidocq.runtime.core/io.vidocq.runtime.core.Vidocq`;
* with an application main class, `<vidocq.mainModule>/<vidocq.mainClass>`;
* a `vidocq.mainClass` already written `<module>/<class>` is used as it is.

A plain `vidocq.mainClass` without `vidocq.mainModule` fails the build, with a message asking for one or the
other. The launchers used to pass the class name alone to `--module`, and the JVM stopped on a
`FindException` before `main` (Vidocq/vidocq#198).

[#app-layer-property]
=== The `vidocq.app.layer` property

`vidocq:run`, `vidocq:dev` and `vidocq:package` read the same two properties (Vidocq/vidocq#247).

[cols="2,1,3"]
|===
| Property | Default | Meaning

| `vidocq.app.layer`
| `classes`
| `classes`: the application layer holds the project's classes, its dependencies stay on the module path. `all`: it
  also holds every dependency outside the runtime's closure, as `WEB-INF/lib` does in a servlet container.

| `vidocq.app.layer.keep`
| _(empty)_
| Under `all`, comma-separated patterns kept in the parent layer: a module name or `groupId:artifactId`, `*` alone
  or as a suffix.
|===

`all` needs the layer mode: `vidocq.dev.layer` for `vidocq:dev`, `vidocq.package.layer` for `vidocq:package`
(both `true` by default). With the layer mode off, the goal fails.

The build logs `application layer: <n> libraries, <m> kept in the parent layer by a pin`. A dependency whose
module name cannot be derived fails the build under `all`, with a message that names the jar: give it an
`Automatic-Module-Name`, or set `vidocq.app.layer=classes`.

The parent layer also keeps the dependencies that a kept module declares in Maven: the Liquibase extension keeps
`liquibase.core` and, through Maven's dependency trails, its own dependencies. Maven records one path per
artifact, so a dependency shared with an application library and reached by a nearer path can land in the
application layer: pin it with `vidocq.app.layer.keep`.

Under `vidocq:package` with `all`, `lib/` holds the parent layer and `app/` holds the application jar and its
libraries. Both launchers boot the runtime with `-Dvidocq.app.path` pointing at `app/` and
`-Dvidocq.app.main` naming the main class, also when `vidocq.mainModule` is set: the trampoline launch would keep the
automatic libraries in the boot layer. They carry `-Dvidocq.app.layer=all`, and the pinned list when there is one.
A jar with classes parked by `vidocq:generate` ships enriched with them, so it moves to `app/` as well. The rule and the
limits are in xref:usage.adoc#app-layer-dependencies[Dependencies in the application layer].

| Before | After

[#jlink-without-main-class]
=== Without an application main class

`vidocq.mainModule` is the only setting the image needs. `vidocq.mainClass` is optional, as it is for
`vidocq:dev`, `vidocq:run` and `vidocq:package`:

* **with an application main class** (a `@VidocqMain` trampoline), the launcher runs
  `<mainModule>/<mainClass>`, and the trampoline re-layers the application, as before;
* **without one** (or with the runtime's own `io.vidocq.runtime.core.Vidocq`), the launcher runs the runtime's
  main, `io.vidocq.runtime.core/io.vidocq.runtime.core.Vidocq`, and the goal bakes two JVM options into the image
  with jlink's `--add-options`: `--add-modules=<mainModule>`, because no module of the runtime reads the
  application module and the JVM would leave it out of the boot layer, and `-Dvidocq.app.module=<mainModule>`,
  which tells `Vidocq.main` to re-layer that module the way the trampoline does.

The application boots in the same Vauban layer either way: the startup report reads
`layer … (boot-layer detection from <mainModule>)` in both. Being in the image, the options apply to every way of
starting it — `bin/<launcher>`, `bin/java -m …`, the `vidocq:jpackage` application and the `vidocq:docker` image.

A missing `vidocq.mainModule` fails the goal with a message naming the property, and so does
`vidocq.mainModule` set to the runtime's module `io.vidocq.runtime.core` without an application main class.

== `vidocq:jpackage` goal

Reuses the `jlink` image. Default type: `app-image` (cross-platform). On macOS, `.app`. On Windows, `.exe` or `.msi`. On Linux, `.deb` or `.rpm`.

Like `vidocq:jlink`, it needs `vidocq.mainModule` only. Without an application main class, the
application starts with `--module io.vidocq.runtime.core/io.vidocq.runtime.core.Vidocq`, and the goal passes the
two options of <<jlink-without-main-class>> again as `--java-options`: an image built by `vidocq:jlink` already
holds them, one given through `runtimeImage` may not.

See `vidocq/JLINK.md` §3 for the exhaustive parameter list.

== `vidocq:docker` goal

Generates a distroless `Dockerfile`. Why `distroless/base-debian12:nonroot`?

* No shell, no package manager — minimal attack surface.
* Enforced `nonroot` user (UID 65532).
* Compatible with the strictest image policies.

[source,bash]
----
./mvnw -ntp package -Dvidocq.docker.build=true
docker run --rm -p 8080:8080 example/my-app:1.0.0

# With external config
docker run --rm -p 8080:8080 \
    -e VIDOCQ_CONFIG_DIR=/etc/myapp \
    -v $(pwd)/conf:/etc/myapp:ro \
    example/my-app:1.0.0
----

[#docker-linux-image]
*An image built on macOS or Windows* [.tag-new]#NEW#. `vidocq:jlink` links against the JDK of the machine that runs
it, so on macOS or Windows `target/dist` holds a Mach-O or PE `bin/java` that a Linux container cannot start. The goal
reads that header, and then writes a two-stage `Dockerfile`: the first stage links the image again inside a Linux JDK,
`eclipse-temurin:<build JDK version>-jdk`, from the modules `vidocq:jlink` staged in `target/jlink-mods/` and the
recipe it left in `target/jlink-image/` (the host-independent jlink arguments, the entry point, the `conf/` files);
the second stage is the distroless image, as on Linux. The same `vidocq build docker` therefore gives an image that
starts, whatever the machine (BUG-20261030-17). A `target/.dockerignore` sends the daemon only what the `Dockerfile`
copies.

* `-Dvidocq.docker.linkInContainer=auto` (default) links in the container only when the image is not Linux; `true`
  always does; `false` never does, and the goal then warns about a macOS or Windows image and, with
  `-Dvidocq.docker.build=true`, fails before running `docker build`.
* `-Dvidocq.docker.jdkImage=…` names another Linux JDK image for the first stage. A JDK with `jmods/` and one linked
  without them (JEP 493, as Temurin 25) both work.

The entry point runs the image's `bin/java -m <module>/<class>`, not the launcher script of `bin/`: the distroless base
has no shell to run it. The JVM options the application needs are already in the image (`jlink --add-options`).

[#run]
== `vidocq:run` goal

`vidocq:run` runs the application once, in a JVM it forks the way the production launcher does. Before that it
forks the lifecycle up to `process-classes`, so a single command compiles the module, completes the bean index
with `vidocq:generate` and starts the application:

[source,bash]
----
mvn vidocq:run                                          # compile, index, run
mvn vidocq:run -Dvidocq.run.debug=true                  # … with a JDWP agent on 127.0.0.1:5005
mvn vidocq:run -Dvidocq.run.args="--seed data.json"     # … with application arguments
mvn vidocq:run -Dvidocq.chappe.listener.default.port=8081
----

That forked lifecycle is the reason the goal exists. An IDE that builds with its own compiler never runs
`vidocq:generate`: the bean index then misses the beans of the dependency jars and the server answers 404
(Vidocq/vidocq#83). A Run in the IDE that is a *Maven* run of this goal cannot — which is what
<<idea,`vidocq:idea`>> now writes.

[[compiler-output-check]]
[[first-build]]*A first build that does not compile* [.tag-new]#NEW#. `vidocq dev` passes `-Dmaven.compiler.failOnError=false`, so a compile error no longer stops Maven before `vidocq:dev`. When `target/classes` then holds no class (the resources are still copied), the goal says that the first build did not compile, waits for the next change of the watched sources and builds again, as a failed reload does, instead of ending the session. When an earlier build left classes there, the application starts from them and the next change recompiles (BUG-20261030-12).

*An output compiled without the processors*. Before launching, `vidocq:run` and `vidocq:dev` check that `target/classes` still holds every file the Maven compiler recorded as created in `target/maven-status/maven-compiler-plugin/compile/*/createdFiles.lst`, the output of the annotation processors included. An IDE build that compiles the same directory without the processors, as IntelliJ's does with a `-codegen` bundle still declared as a pom (see xref:modules/vidocq-runtime-extensions.adoc#codegen-bundles[Codegen bundles are jars]), leaves only the hand-written classes, and `maven-compiler-plugin` then answers "Nothing to compile": the application would start without its generated beans, web components and services. On such a gap the goal warns with the count and the first missing files, deletes the compiler's incremental state, so that the next compile is a full one with the processors, and recompiles once with `mvn process-classes`; a failed recompile, or files still missing after it, fails the goal and asks for `mvn clean` (Vidocq/vidocq#237).

The forked JVM is the one `vidocq:dev` forks, without the source watcher, the reload file and
`-Dvidocq.profile=dev`: the module path of the packaged distribution (every runtime dependency, the enriched
copy of a scanned jar, else the modularized copy of a jar when `vauban:modularize` produced one, plus the
`--patch-module` options of a scanned jar that could get no enriched copy), `--add-modules ALL-MODULE-PATH`, the application classes
handed to the runtime through `-Dvidocq.app.path` so that they boot in a Vauban-defined module layer, the
project directory as the working directory, and inherited I/O — the application writes straight to Maven's
console.

The goal blocks until the application exits:

* **Ctrl+C** stops it. A shutdown hook sends the equivalent of a `SIGTERM`, so the runtime drains as it does in
  production, and force-kills the JVM only after `vidocq.run.gracePeriodMillis`. An interrupted run is not a
  failed build.
* **The exit code is the goal's result.** Zero passes; anything else fails the build with the code in the
  message, the application's own output being just above it in the log.

=== Goal parameters

Every one of them is a property: set it on the command line, or in the module's `<properties>` for the value a
run always uses.

[cols="2,1,3"]
|===

| _(required)_

| `vidocq.mainClass`
| _(unset)_
| The application main class, typically a `@VidocqMain` trampoline. Optional: without it the runtime's own main boots the
  application; with it, the class is passed as `-Dvidocq.app.main` and run inside the application

| `vidocq.run.jvmArgs`
| _(empty)_

| `vidocq.run.debug`

| `vidocq.app.layer`
| `classes`

| `vidocq.app.layer.keep`
| _(empty)_

| `vidocq.run.skip`
| `false`

=== The properties the application sees

The application runs in another JVM, so a `-D` of the Maven command line does not reach it by itself. The goal
forwards the ones that configure the application: every `-Dvidocq.*` that is not a setting of this plugin
(`vidocq.run.*`, `vidocq.dev.*`, `vidocq.idea.*`, `vidocq.docker.*`, `vidocq.jlink.*`, `vidocq.mainClass`,
`vidocq.mainModule`, and the other packaging settings). So `mvn vidocq:run
-Dvidocq.chappe.listener.default.port=8081` listens on 8081. Anything else goes through
`vidocq.run.systemProperties`, and the forked JVM inherits Maven's environment as it is.

`vidocq:dev` forwards the same set, by the same rule. Before, a `-Dvidocq.*` of the command line
never reached the JVM it forks: `mvn vidocq:dev -Dvidocq.chappe.listener.default.port=8081` still listened on the
default port, silently. A `vidocq.dev.systemProperties` entry and the goal's own values (`vidocq.profile=dev`)
win over the command line, as `vidocq.run.systemProperties` does for `vidocq:run`.

[#run-colours]
=== Colours in the forked JVM

The forked JVM writes to Maven's own console, so it takes Maven's colour policy — `vidocq:run` and `vidocq:dev`
both pass it as `-Dvidocq.console.color`:

[cols="2,3"]
|===
| Maven's own output | The forked JVM

| coloured (`-Dstyle.color=always`, `--color=always`, a terminal, or an IDE Maven console)
| `-Dvidocq.console.color=always`
| not coloured (`-Dstyle.color=never`, `--color=never`, `-B`)
| `-Dvidocq.console.color=never`
| nothing asked either way
| nothing is passed: the runtime decides for itself, as it does outside Maven
|===

This is what brings the colours back in an IDE: IntelliJ runs Maven with `-Dstyle.color=always`, but its Maven
console is neither a terminal nor an IntelliJ Run console, so the runtime's `auto` policy would turn colours
off while Maven's own `[INFO]` lines stayed coloured. The signal read is the `jansi.mode` system property that
Maven sets for itself, with the `style.color` user property as a fallback.

Two things always win. An explicit `-Dvidocq.console.color=…` on the Maven command line is not second-guessed:
the goal passes that very value on to the forked JVM, since the property you set belongs to the Maven JVM and
the application runs in another one. And a non-empty `NO_COLOR` in the environment stops the decision — nothing
is passed, because the runtime honours `NO_COLOR` on its own, over any mode. The goal says what it decided, and
why, on one `-X` debug line.

[#test]
== `vidocq:test` goal

`vidocq:test` runs the application's tests on every change, without starting the application: no child JVM,
no dev console, no debug agent. It opens the dev services session, runs every test, then watches the main and
test directories and runs them again on each change. A run is `mvn test-compile surefire:test`, so a main
change is recompiled by the run itself. See xref:continuous-testing.adoc[Continuous testing] for the whole
behaviour, the results file and the dev services it shares.

[source,bash]
----
mvn vidocq:test
----

----
[INFO] Vidocq test — watching [src/main/java, src/main/resources] and [src/test/java, src/test/resources]
[INFO] Tests: 41 passed, 1 failed, 0 skipped in 3.2 s (run-all)
[INFO]   FAILED com.acme.OrderServiceTest#rejectsEmptyCart — AssertionFailedError: expected: <400> but was: <200>
[INFO] Log: target/vidocq-dev-tests.log   [r] run all  [f] rerun failed  [q] quit
----

With a console, `r` and Enter run every test, `f` the failed ones, `q` quits; Ctrl+C always stops the goal,
its run and its dev services.

[cols="2,1,3"]
|===
| Property | Default | Meaning

| `vidocq.dev.watchDirs`
| `src/main/java,src/main/resources`
| The main directories to watch.

| `vidocq.dev.testWatchDirs`
| `src/test/java,src/test/resources`
| The test directories to watch.

| `vidocq.dev.debounceMillis`
| `250`
| How long a burst of saves is collected into one change.

| `vidocq.dev.devServices`
| _(unset)_
| Whether the goal opens a dev services session for the tests: the explicit value, then the application's files, then on.
|===

[#dev-continuous-testing]
=== Continuous testing in `vidocq:dev`

`vidocq:dev` gains two parameters:

[cols="2,1,3"]
|===
| Property | Default | Meaning

| `vidocq.dev.continuousTesting`
| _(unset)_
| Run the tests after every reload: the explicit value, then the application's files, then on when `src/test/java` exists.

| `vidocq.dev.testWatchDirs`
| `src/test/java,src/test/resources`

[#debugger]
== The debug agent of `vidocq:dev` and `vidocq:run`

`vidocq:dev` starts its child JVM with a JDWP agent, and `vidocq:run` does when `-Dvidocq.run.debug=true` asks
for one. A JDWP agent executes what the debugger connected to it asks, so whoever can reach its port can run any
code in the application JVM. The agent therefore listens on the loopback interface, `127.0.0.1`: a debugger on
the same machine attaches to `localhost:5005` as before, and no other machine can connect.

[cols="2,2,1,3"]
|===
| `vidocq:dev` | `vidocq:run` | Default | Meaning

| `vidocq.dev.debug`
| `vidocq.run.debug`
| `true` / `false`
| Add the agent (`-agentlib:jdwp=transport=dt_socket,server=y,…`).

| `vidocq.dev.debugPort`
| `vidocq.run.debug.port`
| `5005`
| The port the agent listens on.

| `vidocq.dev.debugHost`
| `vidocq.run.debug.host`
| `127.0.0.1`
| The interface the agent listens on.

| `vidocq.dev.debugSuspend`
| `vidocq.run.debug.suspend`
| `false`
| `true` suspends the JVM until a debugger attaches, to debug the boot itself.
|===

The host is handed to the agent as it is written, so every spelling the JVM understands works:

* `127.0.0.1` (the default), `localhost`, any `127.x.y.z` address or `::1` keep the agent on this machine;
* `*`, `0.0.0.0` or `::` open it on every interface;
* any other address or host name opens it on that interface only.

The goal says where the agent listens, and warns as soon as other machines can reach it:

[source]
----
[INFO] Debug agent (JDWP) on port 5005, host 127.0.0.1 — attach any time
----

[source]
----
[INFO] Debug agent (JDWP) on port 5005, host * (every interface) — attach any time
[WARNING] vidocq.dev.debugHost=* makes the debugger reachable from the network: the JDWP agent listens on every
interface, port 5005, and whoever connects to it can run any code in the application JVM. Leave
vidocq.dev.debugHost at its default, 127.0.0.1, unless every machine that can reach this port is trusted.
----

Open it only when the debugger really runs elsewhere — a container, a VM, another machine — and only on a network
you trust: `mvn vidocq:dev -Dvidocq.dev.debugHost='*'` (quote the `*` for the shell). An empty host is the default
one, never every interface.

[#dev-tools]
== Dev tools and binaries

The dev console and every extension's `-dev` panel module (xref:dev-console-panels.adoc#dev-module[A `-dev`
module, never packaged]) are development tools: only `vidocq:dev` ever adds them, to the child JVM's module
path, and no binary this plugin produces ever contains them (Vidocq/vidocq#143). The console's SPI,
`vidocq-runtime-devconsole-spi`, is not one: an ordinary API jar, `vidocq:dev` adds it with the console, and it
ships in a binary whenever an extension that keeps the all-in-one `DevConsolePanel` form requires it.

**What `vidocq:dev` adds, and when.** After building the child's module path as it always has, the goal:

. resolves the dev console and its SPI itself, through Maven's own resolver (Aether), at the Vidocq version
  of the application's `vidocq-runtime-chappe-webserver-extension`, with a warning when that is not
  the plugin's own version, and looks in the plugin repositories as well as the project's (Vidocq/vidocq#148), the moment the application already has
  `vidocq-runtime-chappe-webserver-extension`: the console serves its page through Chappe, so without it there
  is nothing to serve the page, and nothing is added;
. for every runtime extension the project resolves, reads its `META-INF/vidocq/dev-module` descriptor, if it has
  one, and resolves that companion `-dev` module and its own dev-only runtime dependencies, plus the console SPI,
  at the extension's own `groupId` and version;
. never adds a module twice: a jar the console step already put on the path is not added again by a
  companion's own transitive dependencies, and a jar the project already resolves at runtime scope — the legacy
  declaration, kept working — is left where it is, not duplicated;
. logs one INFO line naming what it added:
+
[source,text]
----
[INFO] Dev tools: vidocq-runtime-cassini-rest-extension-dev, vidocq-runtime-mansart-pool-extension-dev
----

An application with no Chappe gets no console, and says so instead of adding one:

[source,text]
----
[INFO] Dev tools: no dev console, it needs vidocq-runtime-chappe-webserver-extension
----

Offline, or before the console was ever built locally, costs the console only — a warning, never a failed
goal, and `vidocq:dev` continues without it:

[source,text]
----
[WARNING] Dev tools: cannot resolve io.vidocq.runtime.extensions.essentials:vidocq-runtime-devconsole-extension:{project-version} (the dev console); vidocq:dev continues without it. Run the build once online, or mvn -U.
----

A companion that cannot be resolved the same way costs only that one extension's live panel — its section keeps
its boot facts, unaffected — and a descriptor that cannot be read, or that names more than one artifact or an
invalid one, costs the same, naming the jar. Both are warnings, never failures.

**`vidocq:run`, the packaging goals, and never twice.** `vidocq:run`, `vidocq:package`, `vidocq:jlink`,
`vidocq:jpackage` and `vidocq:docker` add none of this. They also drop every jar marked `Vidocq-Dev-Only: true`
in its manifest from what they launch or ship — the console, every `-dev` module, and the dev services
extension — even when the project declares one directly, at any scope but `test`. Each dropped jar logs one
WARNING per goal run, never fails the build:

[source,text]
----
[WARNING] vidocq-runtime-devconsole-extension is dev-only: not packaged; remove the dependency, vidocq:dev brings it
----

The one exception, kept from `vidocq:run`'s dev services opt-in (Vidocq/vidocq#123): `mvn vidocq:run
-Dvidocq.dev.devServices=true` still adds `vidocq-runtime-devservices-extension`, from the plugin's own
dependencies, for that one run — it is never packaged either, and it brings no console.

**`vidocq:checkpom`.** At `validate`, it warns — never fails — about a dependency on a dev-only artifact
declared in any scope but `test`, with the same message as above. The fix is either to remove the dependency
(`vidocq:dev` brings it on its own) or to move it to `test` scope.

**Tests.** `mvn test`, `vidocq:test` and the continuous tests of `vidocq:dev` get no dev tool from the plugin
either: a test that reads the console, or an extension's live panel, declares it itself, at `<scope>test</scope>`,
together with the `-dev` modules it needs. `test` scope is never packaged, and `checkpom` accepts it without a
warning. The dev services JUnit host (Vidocq/vidocq#123) is unaffected: it was already a `test`-scope
dependency.

**`vidocq:idea`.** The Dev, packaged and debug configurations it writes are covered under
<<idea,the `vidocq:idea` goal>>.

[#idea]
== `vidocq:idea` goal

*Experimental.* `vidocq:idea` writes IntelliJ IDEA shared run configurations, in `.run/`, per Vidocq application
of the reactor, from what the poms already declare. By default that is three files per application — a
**Maven** run of `vidocq:dev` suffixed ` (dev)`, the configuration a developer runs day to day (the console, hot
reload, continuous testing), one of <<run,`vidocq:run`>> suffixed ` (run)` — that one still compiles the module,
completes the bean index and starts the application, the three through Maven — and a Remote JVM Debug one
suffixed ` (debug)` that attaches to `vidocq:dev`'s own debug agent(Vidocq/vidocq#143); see
<<dev-tools,Dev tools and binaries>>.

[source,bash]
----
mvn vidocq:idea                                          # write or update .run/*.run.xml
mvn vidocq:idea -Dvidocq.idea.check=true                 # CI: fail when .run/ does not match the poms
mvn vidocq:idea -Dvidocq.idea.check=strict               # CI: also fail on files you wrote or edited
mvn vidocq:idea -Dvidocq.idea.kind=application           # an Application run of the main class instead
----

[IMPORTANT]
.Why the Maven kind is the default
====
The IDE build never runs `vidocq:generate`. IntelliJ's Make compiles the module with its own compiler, and
`vidocq:generate`, which completes the bean index with the beans of the dependency jars a build-time
annotation processor never saw, is a Maven goal bound to `process-classes`. An Application run configuration
therefore has to carry a Maven step before launch, and anything that bypasses it — a Run from the gutter, a
temporary configuration, a module IntelliJ split in two — starts an application whose bean index is
incomplete: the server answers 404 (Vidocq/vidocq#83).

A Maven run configuration has no such hole: `vidocq:run` forks the lifecycle up to `process-classes` itself,
then forks the JVM exactly as the command line does. `vidocq:dev` starts from `target/classes` as it is, so the
`(dev)` configuration runs `process-classes vidocq:dev`, as `vidocq dev` does(Vidocq/vidocq#237).
IntelliJ also disables its own Build step for a Maven configuration. A Build that IntelliJ runs on its own, from
the Build menu or automatically, still compiles `target/classes` without the processors of a `-codegen` bundle:
both goals detect it and recompile, see <<compiler-output-check,an output compiled without the processors>>.
====

Run it from the command line, in the directory IntelliJ opens as the project — usually the reactor root —
and commit `.run/`. Maven resolves the `vidocq:` prefix from the pom it is launched on: when the plugin is
only declared in the application modules, add it with its version to the root `<pluginManagement>`, or call
the goal by its coordinates (`mvn io.vidocq.runtime:vidocq-runtime-maven-plugin:{project-version}:idea`).

=== What it generates

For an application `mcp-time-server` whose pom sets `vidocq.mainClass`, with
`<vidocq.idea.jre>temurin-25</vidocq.idea.jre>` in the top-level pom, the Maven kind writes three files
(Vidocq/vidocq#143). Without `vidocq.mainClass`, they would be named after the artifactId:
`mcp-time-server (dev)`, and so on.

[cols="2,3"]
|===
| File | Runs

| `.run/McpTimeServerApp (dev).run.xml`
| A Maven run of `process-classes vidocq:dev`, the configuration a developer runs day to day.
  `process-classes` compiles and indexes first, as `vidocq dev` does, since `vidocq:dev` starts from
  `target/classes` as it is (Vidocq/vidocq#237).

| `.run/McpTimeServerApp (run).run.xml`
| A Maven run of `vidocq:run`, one run of the application as the production launcher starts it.

| `.run/McpTimeServerApp (debug).run.xml`
| A Remote JVM Debug configuration that attaches to `vidocq:dev`'s own debug agent.
|===

The first file (shortened here; it also carries the options IntelliJ leaves at their default, in the order it
writes them):

[source,xml]
----
<!-- Generated by vidocq:idea. Run "mvn vidocq:idea" to update it; once edited, it is left alone. sha256:2636c212… -->
<component name="ProjectRunConfigurationManager">
  <configuration default="false" name="McpTimeServerApp (dev)" type="MavenRunConfiguration" factoryName="Maven">
    <MavenSettings>
      <option name="myGeneralSettings" />
      <option name="myRunnerSettings">
        <MavenRunnerSettings>
          <option name="jreName" value="temurin-25" />
          <!-- … -->
        </MavenRunnerSettings>
      </option>
      <option name="myRunnerParameters">
        <MavenRunnerParameters>
          <option name="goals">
            <list>
              <option value="process-classes" />
              <option value="vidocq:dev" />
            </list>
          </option>
          <option name="pomFileName" value="mcp-time-server/pom.xml" />
          <option name="workingDirPath" value="$PROJECT_DIR$" />
          <!-- … -->
        </MavenRunnerParameters>
      </option>
    </MavenSettings>
    <method v="2" />
  </configuration>
</component>
----

The `(run)` file is the same shape with `vidocq:run` in place of `vidocq:dev`, and its own name in
`name="…"`. The `(debug)` file is a different type entirely:

[source,xml]
----
<component name="ProjectRunConfigurationManager">
  <configuration default="false" name="McpTimeServerApp (debug)" type="Remote">
    <option name="USE_SOCKET_TRANSPORT" value="true" />
    <option name="SERVER_MODE" value="false" />
    <option name="SHMEM_ADDRESS" />
    <option name="HOST" value="127.0.0.1" />
    <option name="PORT" value="5005" />
    <option name="AUTO_RESTART" value="false" />
    <RunnerSettings RunnerId="Debug">
      <option name="DEBUG_PORT" value="5005" />
      <option name="LOCAL" value="false" />
    </RunnerSettings>
    <method v="2" />
  </configuration>
</component>
----

`127.0.0.1` and `5005` are the same defaults as <<debugger,the debug agent>>'s own. Overriding them for this
file is deliberately narrower than overriding the running agent: the goal reads `vidocq.dev.debugHost` and
`vidocq.dev.debugPort` from the module's own pom `<properties>` only, never from the command line — a `-D` for
either is ignored, with a warning, the same treatment `vidocq.idea.configurationName` and the other per-module
settings already get (<<applications,Which modules are applications>>), so that the committed file does not
depend on how `vidocq:idea` was invoked. There is no `vidocq.idea.*` prefix on these two: they name the debug
agent itself, which `vidocq:dev` and `vidocq:idea` both read the same way.

* **Before launch** — nothing on any of the three files: IntelliJ disables its Build step for a Maven run
  configuration, the Dev file runs `process-classes` as its first goal and `vidocq:run` forks it; the `(debug)`
  file has no before-launch step of its own; it only attaches.
* **JDK** — `vidocq.idea.jre` writes an IntelliJ SDK *name* (such as `temurin-25`) as the Maven runner JRE for
  the first two files, which is also the JDK the application runs on: the forked JVM comes from the JVM running
  Maven. Declare it in the top-level pom, since that name must exist on every machine; an absolute path is
  accepted with a warning. Without it, IntelliJ runs Maven on the JDK of its Maven settings, which can be
  another one than the JDK you build and test with, and the goal warns. The `(debug)` file has no JDK option:
  it only attaches to a JVM already running.
* **Maven settings** — `myGeneralSettings` is left empty on purpose, on the two Maven files. A run configuration
  that carries its own replaces the user's Maven settings (settings file, local repository, offline mode,
  threads) with what the file holds, and those belong to the machine, not to the repository.
* **Format** — the one IntelliJ writes itself: the element order, the options left at their default and the
  2-space indentation of `XmlSerializer`, LF, no XML declaration. Measured against IntelliJ IDEA 2026.2.3's own
  serialiser — a generated file deserialised and serialised back comes out identical — so IntelliJ has no reason
  to rewrite it, and the marker it carries survives. The `(debug)` file carries no marker comment of its own
  kind that `Remote` configurations do not have; its ownership and drift checks are the same as the other two.
* **File name** — the configuration name (`McpTimeServerApp (dev)`, `McpTimeServerApp (run)`,
  `McpTimeServerApp (debug)`) with the characters IntelliJ replaces in file names (`/ \ ? < > : * | "`
  and control characters) turned into `_`, truncated to 255 characters. Two names that differ only by case
  fail the goal: they are one file on macOS and Windows.

==== The `application` kind

`-Dvidocq.idea.kind=application` writes what the goal wrote before: one Application run configuration per
application that declares a main class, of that main class, with two before-launch steps — IntelliJ's Make, then `vidocq:generate` on the
application's own pom. Unlike the Maven kind's three files, there is only ever this one: the application runs
in the JVM IntelliJ starts directly, never under `vidocq:dev`, so it never has the dev console or any `-dev`
module(<<dev-tools,Dev tools and binaries>>), and there is no `(debug)` file to attach a
separate debugger to — attach IntelliJ's own debugger to this configuration instead.

[source,xml]
----
<component name="ProjectRunConfigurationManager">
  <configuration default="false" name="McpTimeServerApp" type="Application" factoryName="Application">
    <option name="ALTERNATIVE_JRE_PATH" value="temurin-25" />
    <option name="ALTERNATIVE_JRE_PATH_ENABLED" value="true" />
    <option name="MAIN_CLASS_NAME" value="io.vidocq.tools.lc4jcdi.mcptimeserver.McpTimeServerApp" />
    <module name="mcp-time-server" />
    <method v="2">
      <option name="Make" enabled="true" />
      <option name="Maven.BeforeRunTask" enabled="true" file="$PROJECT_DIR$/mcp-time-server/pom.xml" goal="vidocq:generate" />
    </method>
  </configuration>
</component>
----

Apart from the marker line, this is the configuration verified in IntelliJ IDEA 2026.2: Run on the main class
built the module, completed the bean index and started the application. It runs the application in the JVM
IntelliJ starts, which is faster to launch, but every Run that bypasses the before-launch step starts it with
an incomplete bean index. When a single execution of the plugin that runs `generate` carries a configuration of
its own (for example `<scanDependencies>` on an execution rather than at plugin level), the step is written
`vidocq:generate@<execution id>`: a goal run on its own would not see that configuration. With several such
executions it stays `vidocq:generate` and the goal warns. `-Dvidocq.idea.generateBeforeLaunch=false` leaves the
step out; it does not concern the Maven kind. Here `vidocq.idea.jre` is the alternative JRE of the
configuration, and without it IntelliJ launches the application on the module SDK.

The goal never writes `.idea/`, `*.iml` or any other project file — those belong to IntelliJ's own Maven
import — nor run configuration templates, nor Eclipse launch configurations. It never deletes a file, and it
refuses to run when a pom binds it to a lifecycle phase.

[#applications]
=== Which modules are applications

A project of the build gets a run configuration when:

. its packaging is not `pom`;
. `vidocq-runtime-maven-plugin` is in its effective `<build><plugins>` (inherited declarations and active
  profiles count, `<pluginManagement>` alone does not): the before-launch step runs `vidocq:generate` on its pom;
. its pom does not set `vidocq.idea.exclude` to `true`;
. it declares `vidocq.mainModule` or an application main class. The main class is the
  plugin-level `<mainClass>` if set, otherwise the `vidocq.mainClass` property. The runtime's own
  `io.vidocq.runtime.core.Vidocq` does not count as one, and a legacy `module/Class` value keeps its class — the
  rule `vidocq:package` applies.

An application needs no main class of its own: the runtime's main boots it, and `vidocq.mainModule` is all
`vidocq:dev` and `vidocq:run` read. Such an application gets the Maven kind's three files, named after its
`artifactId`. That default also keeps apart the applications of a reactor with one application
per module, where two `App` classes would collide. Only the `application` kind runs a main class: it leaves an
application without one out, with a warning to declare `vidocq.mainClass` (a `@VidocqMain` trampoline) or to
keep the Maven kind.

A `<mainClass>` set on an execution (for example the `jlink` one) is not read; when it is the module's only main
class and the module declares no `vidocq.mainModule`, the goal warns. These values
are read from each module's pom, never from the command line: a `-Dvidocq.mainClass`, `-Dvidocq.mainModule`,
`-Dvidocq.idea.configurationName`, `-Dvidocq.idea.moduleName`, `-Dvidocq.idea.exclude`, `-Dvidocq.dev.debugHost`
or `-Dvidocq.dev.debugPort`is ignored with a warning, so that the committed files do not depend
on how Maven was invoked.

[cols="2,1,3"]
|===
| Module pom property | Default | Meaning

| `vidocq.idea.configurationName`
| simple name of the main class, or `artifactId` without one
| Run configuration name, and file name.

| `vidocq.idea.moduleName`
| `artifactId`
| IntelliJ module that holds the main class, which only the `application` kind uses. Set it when IntelliJ names the module differently, for example
  `<artifactId>.main` when it splits main and test sources into two modules, or `beta (1) (com.example)` when
  another project has the same artifactId, ignoring case.

| `vidocq.idea.exclude`
| `false`
| No run configuration for this module, nor for the modules that inherit its properties.

| `vidocq.dev.debugHost`
| `127.0.0.1`
| The host the `(debug)` file attaches to. Same key `vidocq:dev` reads for its own debug agent
  (<<debugger,the debug agent>>); blank or unset keeps the default.

| `vidocq.dev.debugPort`
| `5005`
| The port the `(debug)` file attaches to, `1`-`65535`. An invalid value is a configuration error, reported with
  the goal's other errors, and the default is used.
|===

=== Goal parameters

[cols="2,1,3"]
|===
| Property | Default | Meaning

| `vidocq.idea.check`
| `false`
| `true`: write nothing; fail when a write would change `.run/`, and list the files that belong to you as not
  verified. `strict`: also fail on those files when their content differs from what the goal writes. Any other
  value fails the goal.

| `vidocq.idea.kind`
| `maven`
| `maven`: a Maven run configuration of `vidocq:run` on the application's pom. `application`: an Application run
  configuration of the main class, with Make and `vidocq:generate` before launch. Any other value fails the goal.

| `vidocq.idea.generateBeforeLaunch`
| `true`
| Add the `vidocq:generate` step before launch. The `application` kind only.

| `vidocq.idea.jre`
| _(unset)_
| IntelliJ SDK name written as the alternative JRE.

| `vidocq.idea.projectDirectory`
| directory Maven runs in
| The directory IntelliJ opens: `.run/` is written there and the `$PROJECT_DIR$` paths are relative to it.

| `vidocq.idea.skip`
| `false`
| Skip the goal.
|===

Maven evaluates them against the top-level project of the build — the first selected project when `-pl` leaves
the root out. That is why no goal property is also a module setting: `vidocq.idea.skip` in the pom of the first
selected module would skip the goal for every application. To leave a module out, set `vidocq.idea.exclude` in
its pom; a module pom that sets `vidocq.idea.skip` gets a warning. When the goal is skipped, it says where
`vidocq.idea.skip` came from: the command line, a system property, or the properties of the top-level project.

=== Files that belong to you

The goal owns a file only while its marker matches its content. IntelliJ drops the marker when it saves a
configuration you edited, so an edited file becomes yours.

[cols="3,2,2,2"]
|===
| File in `.run/` | `mvn vidocq:idea` | `-Dvidocq.idea.check=true` | `-Dvidocq.idea.check=strict`

| absent | created | fails | fails
| marker valid, content as expected | unchanged, not rewritten | passes | passes
| marker valid, other content | updated | fails, with a line diff | fails, with a line diff
| no marker, content as expected | marker added | fails | fails
| marker whose hash no longer matches (edited since) | left untouched, warning | not verified, warning | fails with a line diff, unless the content is as expected
| no marker, other content (written by hand, saved by IntelliJ) | left untouched, warning | not verified, warning | fails, with a line diff
|===

A file of yours that pins a JDK while `vidocq.idea.jre` is not set is a special case: a regenerated file would
lose the pin, so the goal tells you to declare `vidocq.idea.jre` with that SDK name first, and adopts the file as
it is when nothing else differs. This is how a hand-written configuration moves to the goal without a change.

The default check passes when your files are the only difference, so that a configuration you customised on
purpose does not break CI; its summary is then a warning that names each file it did not verify. Use `strict` when
every file in `.run/` must follow the poms. Line endings and a trailing newline are not edits. To get a generated
file back, delete yours and run the goal again. A marked file that no application maps to any more is reported and
never deleted.

=== Multi-module builds

`vidocq:idea` is an aggregator: it runs once, for every project of the build, and writes a single `.run/` at
the project directory. Configuration errors (a main class that is not a Java class name, a pom outside the
project directory, a blank name) and name collisions fail the goal before anything is written.

When it is launched inside a module of a larger reactor — a directory that an ancestor `pom.xml` lists in its
`<modules>` — the goal fails: IntelliJ loads `.run` files anywhere in the project content, and paths written
relative to the module would resolve against the reactor root. Run it from the root, which the error names —
the outermost aggregator, when the module belongs to a nested one such as `examples/` — or set
`-Dvidocq.idea.projectDirectory` when IntelliJ really opens the module. A project directory that is not the
directory of a project of the build is accepted with a warning: IntelliJ only loads `.run` files inside the
project content.

With `-pl` or `-rf`, only the selected applications are written or checked, and the goal says so. Profiles
count: run the goal and its CI check with the same active profiles.

=== JDK

The Vidocq plugin and runtime are compiled for Java 25, and the JDK that runs each step is IntelliJ's business,
not the file's — except where `vidocq.idea.jre` says otherwise.

[cols="1,2,2"]
|===
| Step | Maven kind | `application` kind

| Build
| none (IntelliJ disables its Build step)
| Make, on the module SDK — the project SDK unless the pom declares a JDK toolchain

| Maven
| `vidocq.idea.jre` when set, else the Maven runner JRE (Settings > Build, Execution, Deployment > Build Tools >
  Maven > Runner)
| the Maven runner JRE, for the `vidocq:generate` step

| The application
| the JVM running Maven, which `vidocq:run` forks
| `vidocq.idea.jre` when set, else the module SDK (not verified in IntelliJ yet)
|===

Each of them must be JDK 25 or newer. The goal cannot see IntelliJ's SDKs and prints this reminder after a write.

=== IntelliJ limits

* **Module names** — IntelliJ names an imported module after its `artifactId`, but a renamed module, a name
  clash or a module split into `<name>.main` and `<name>.test` does not match. An unknown name fails at Run
  with "Module '<name>' doesn't exist in the project"; a split module silently gets a new temporary configuration without the Maven
  step. The goal warns when the pom shows a known split trigger (different main and test compiler levels, test
  compiler arguments, different compile and test-compile arguments or toolchains), and when a first import
  would name the module otherwise: IntelliJ numbers every module whose artifactId equals another one ignoring
  case, in any group (`beta (1) (com.example)`, `Beta (2) (com.vendor)`), and uses the directory name for the
  artifactId `Unknown`. The goal compares every project of the build, including those `-pl` leaves out. A
  module imported before keeps its earlier name, so the name can differ between machines: prefer artifactIds
  that differ by more than case, or set `vidocq.idea.moduleName` to the name IntelliJ shows.
* **Reload** — IntelliJ reloads a changed `.run` file by itself, but may miss files in a new `.run/` directory or
  several files written at once. When a configuration does not appear, use File > Reload All from Disk.
* **Same name** — a temporary or local configuration with the same name, created earlier from the gutter, can
  shadow the shared one. Delete it from the Run widget.
* **First open** — IntelliJ loads `.run` files asynchronously; a Run clicked before indexing ends may create a
  temporary configuration.

[#vscode]
== `vidocq:vscode` goal

`vidocq:vscode` writes the `.vscode/` files a Vidocq project needs in VS Code with the Extension Pack for Java
(Vidocq/vidocq#339). Run it at the directory VS Code opens, the reactor root:

[source,bash]
----
mvn vidocq:vscode                              # write or update .vscode/
mvn vidocq:vscode -Dvidocq.vscode.check=true   # CI: fail when a file is missing or out of date
mvn vidocq:vscode -Dvidocq.vscode.jdk=/path/to/jdk-25
----

[cols="1,3",options="header"]
|===
| File | What it holds
| `settings.json`
| `java.jdt.ls.java.home`: the extension's language server on the JDK running the build, Java 25. The server runs the
annotation processors in its own JVM, and Vauban's are Java 25 class files: on the Java 21 the extension ships, the
project imports and the processors do not load. `java.autobuild.enabled: false`: the extension's automatic build writes `target/classes` on every
save, as `vidocq dev` does; with it off, the editor keeps its diagnostics and completion, and `vidocq dev` compiles.
| `tasks.json`
| `vidocq dev`, `vidocq run` and `vidocq test` (Terminal > Run Task): `process-classes vidocq:dev`, `vidocq:run` and
`vidocq:test` on the application's pom, through `./mvnw` (`mvnw.cmd` on Windows) when the project has one. With
several applications, each task is suffixed with the application's name.
| `launch.json`
| `Vidocq: attach to <application> (dev)`: attaches the debugger to the agent `vidocq:dev` starts
(`vidocq.dev.debugHost` and `vidocq.dev.debugPort`, 127.0.0.1:5005 by default, as for `vidocq:idea`).
|===

Each file starts with `// Written by vidocq:vscode …`; VS Code reads these files as JSON with comments. The goal
rewrites a file that starts with that line, and leaves any other alone, printing what to add to it: delete the line
to keep a file of your own. The JDK path is this machine's: keep `settings.json` out of version control, or pass
`-Dvidocq.vscode.jdk` with the path every machine shares. Applications are found as `vidocq:idea` finds them: a
module that declares `vidocq-runtime-maven-plugin` and a `vidocq.mainModule`.

What was checked, in VS Code's language server (Java extension 1.56, jdt.ls 1.61) driven headless on a project
`vidocq create -x cassini-rest` writes: with these settings the project imports, a type error is reported in the
editor, and the server writes nothing into `target/classes`; with the automatic build on, it writes the 15 files of a
build there.

== `vidocq:eclipse` goal

`vidocq:eclipse` writes the launch configurations a Vidocq project needs in Eclipse IDE 2026-09 or newer
(Vidocq/vidocq#339). Run it at the reactor root, then import the project (File > Import > Existing Maven Projects):

[source,bash]
----
mvn vidocq:eclipse                               # write or update .eclipse/
mvn vidocq:eclipse -Dvidocq.eclipse.check=true   # CI: fail when a file is missing or out of date
----

Eclipse lists every `.launch` file of an imported project under Run > Run Configurations. Per application:

[cols="1,3",options="header"]
|===
| Configuration | What it runs
| `<application> (dev)`, `(run)`, `(test)`
| A Maven build (m2e) of `process-classes vidocq:dev`, `vidocq:run` or `vidocq:test` in the application's Eclipse
project, on the Java 25 runtime Eclipse ships. m2e's own Maven runs it; the Maven wrapper is not used.
| `<application> (debug)`
| A Remote Java Application that attaches the debugger to the agent `vidocq:dev` starts (`vidocq.dev.debugHost` and
`vidocq.dev.debugPort`, 127.0.0.1:5005 by default, as for `vidocq:idea`).
|===

The configurations name the Eclipse project after the application's artifactId, m2e's default; with another name
template in Window > Preferences > Maven, edit the working directory of each one. Each file starts with
`<!-- Written by vidocq:eclipse … -->`: the goal rewrites such a file, removes one it no longer writes (an
application renamed or removed), and leaves any other alone. Eclipse rewrites a configuration edited in its dialog
without that line: it becomes yours.

Two settings the files cannot carry:

* *Annotation processing* — m2e runs the annotation processors only when the pom asks, and Eclipse's build then
writes an application with no bean index, which starts without its beans. `vidocq-runtime-parent` asks
(`m2e.apt.activation=jdt_apt`); a project on another parent sets that property itself.
* *Build automatically* — Eclipse keeps it per workspace, so the goal cannot turn it off as `vidocq:vscode` does in VS
Code. Turn Project > Build Automatically off while `vidocq dev` runs: both would write `target/classes` on every save,
and Eclipse's compiler does not run Vauban's javac plugin, which weaves the proxies. The editor keeps its diagnostics.

What was checked, in Eclipse IDE for Java Developers 2026-09 (m2e 2.8, Java 25.0.4 bundled) driven headless on a
project `vidocq create -x cassini-rest` writes: the four configurations are listed; `(dev)` and `(run)` serve the
application, `(debug)` attaches to it; with Build Automatically on, Eclipse's build runs the processors and writes the
files of a Maven build, without the weaving.

== External override (`ExternalFileConfigSource`)

`vidocq.properties` placed in `${java.home}/conf/` (jlink image) or pointed to by `$VIDOCQ_CONFIG_DIR` is read with ordinal 250. See xref:reference.adoc[Reference] for the full hierarchy.

== Prerequisites and limitations

* **Strict Java Modules** — every dependency must be a named module; `jlink` rejects every automatic module. Give the non-modular jars a descriptor with <<modularize,`vauban:modularize`>> in `all-automatic` mode.
* [[jlink-shared-resources]]**Resource directories several jars share** — a directory that two jars both hold files in is a split package, which `jlink` refuses. Vaadin's `flow-server` and `flow-react` share `com/vaadin/flow/server/frontend/` (Vidocq/vidocq#256). `vidocq:jlink` stops before `jlink` with one line naming the jars and the directory. `-Dvidocq.jlink.mergeSharedResources=true` moves those files into one module of the image instead: the jar with classes in that package, else the one holding most files there, logged as `merged <dir> into <jar> (N files from <jars>)`. Only the staged copies change; `vidocq:package` and `target/` keep the jars as they are. Two files of one path with different contents, or classes in several jars, stop the build.
* **Records serialised over REST** — Champollion handles them via APT, not reflection. If an external dependency exposes records that are not generated, declare a JSON-B `Converter<T>`.
* **Custom `java.util.logging` Handler** — declare the module in `logging.properties` so `jlink` embeds it (`handlers=com.example.MyHandler`).
* **macOS app-image** — the bundle requires a valid `--app-version`; the plugin defaults to the project Maven version.

See `vidocq/JLINK.md` §6 and §8 for the full list of known limitations.
