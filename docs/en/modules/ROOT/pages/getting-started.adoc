= Getting started
:description: Your first Vidocq Runtime service — install the CLI, scaffold, build and run a REST app in minutes.

[.lead]
This page installs the Vidocq CLI, scaffolds a REST application, builds it with plain Maven, and serves a first endpoint — every command below is tested end-to-end against the released *0.2.x* artifacts on Maven Central. If you prefer not to use the CLI, jump to <<without-the-cli,the manual annex>>.

== Prerequisites

* **Java 25** (Temurin recommended) — check with `java -version`
* **Maven 3.9+** — check with `mvn -version`

TIP: With https://sdkman.io[SDKMAN!]: `sdk install java 25-tem && sdk install maven`.

== Step 1 — Install the CLI

[source,bash]
----
curl -fsSL https://vidocq.dev/install.sh | sh
----

On Windows (PowerShell):

[source,powershell]
----
irm https://vidocq.dev/install.ps1 | iex
----

The script downloads the latest released CLI from Maven Central into `~/.vidocq/cli` and puts a `vidocq` launcher on your `PATH`. Verify:

[source,bash,subs=attributes+]
----
$ vidocq version
Vidocq CLI {cli-version}
----

TIP: To try what is on `main` before it is released, install the latest SNAPSHOT CLI instead: `curl -fsSL https://vidocq.dev/install.sh | VIDOCQ_VERSION=snapshot sh` (PowerShell: `$env:VIDOCQ_VERSION='snapshot'; irm https://vidocq.dev/install.ps1 | iex`). The projects it scaffolds resolve Vidocq from the Vidocq snapshot repository, `https://maven.vidocq.dev/snapshots/`; see xref:modules/vidocq-runtime-cli.adoc#create-snapshot[Trying a SNAPSHOT].

NOTE: No installer needed? Download `vidocq-runtime-cli-<version>-cli.zip` from https://repo1.maven.org/maven2/io/vidocq/runtime/vidocq-runtime-cli/[Maven Central], unzip it anywhere, and add its `bin/` directory to your `PATH`.

== Step 2 — Scaffold a project

[source,bash]
----
vidocq create --name todo --group-id com.acme --extension cassini-rest
cd todo
----

`--extension cassini-rest` (short: `-x`) enables Jakarta REST — it transitively brings the Chappe HTTP server, CDI (Vauban) and JSON-B (Champollion). The generated project is a standard JPMS Maven project:

[source]
----
todo/
  pom.xml                            <1>
  src/main/java/
    module-info.java                 <2>
    com/acme/todo/HelloResource.java <3>
  src/main/resources/
    vidocq.properties                <4>
----
<1> Imports `vidocq-runtime-bom` at `{release-version}`, sets `vidocq.mainModule` and declares `vidocq-runtime-maven-plugin` as a build extension, which gives the build everything else (no parent, Vidocq/vidocq#380), so `mvn package` produces a runnable distribution.
<2> Module descriptor, pre-filled with the `requires`/`opens` a REST app needs.
<3> A first resource, written for `cassini-rest` (Step 3).
<4> MicroProfile-style configuration (`vidocq.http.port=8080`, …).

There is no main class: the runtime's own main boots the application from
`vidocq.mainModule`. `vidocq create --main` adds an `@VidocqMain` trampoline, for a right-click
Run in the IDE or logic after boot (a `VidocqApp`); a right-click Run loads the application twice and warns, see
xref:usage.adoc#ide-run-twice[the trampoline]. See
xref:modules/vidocq-runtime-cli.adoc#create[`vidocq create`].

TIP: Run `vidocq extension list --available` to see all first-party extensions, and `vidocq help create` for the options (`--package`, `--parent-version`, `--main`, …).

NOTE: From 0.4.0, `vidocq create` also writes `src/test/java/com/acme/todo/HelloResourceTest.java`, a first test that starts the application with xref:testing.adoc[`@VidocqTest`] and calls `GET /hello` (run it with `vidocq test` or `mvn test`), a `.gitignore` and a `README.md`. Run without `--name` on a terminal, it asks for the name, the group id and the extensions.

== Step 3 — Your first resource

`vidocq create` wrote `src/main/java/com/acme/todo/HelloResource.java`:

[source,java]
----
package com.acme.todo;

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.ws.rs.GET;
import jakarta.ws.rs.Path;
import jakarta.ws.rs.Produces;
import jakarta.ws.rs.core.MediaType;

/** A first REST resource: {@code GET /hello}. */
@ApplicationScoped
@Path("/hello")
@Produces(MediaType.TEXT_PLAIN)
public class HelloResource {

    @GET
    public String hello() {
        return "Hello from Vidocq!";
    }
}
----

No further wiring: the Cassini annotation processor generates the dispatch adapter at compile time — no runtime reflection. Add your own resources next to it, in the same package: `module-info.java` already opens it.

== Step 4 — Build and run

[source,bash,subs=attributes+]
----
mvn package
sh target/todo-{release-version}/bin/todo.sh
----

`mvn package` compiles, runs the code generators, and assembles a standalone distribution under `target/todo-{release-version}/` (launchers in `bin/`, module path in `lib/`). In another terminal:

[source,bash]
----
$ curl http://localhost:8080/hello
Hello from Vidocq!
----

The runtime boots in well under a second — the log line to look for:

[source]
----
INFOS: Vidocq - Started in 90.940 ms (process running for 135 ms)
----

[#last-round-warnings]
NOTE: With a Vauban older than Vidocq/vauban#251, the compilation prints one `[WARNING] File for type '…' created in the last round will not be subject to annotation processing.` per class Vauban generates (`HelloResource_ClientProxy`, `_VaubanComponents`). They are harmless: javac compiles these classes like any other. Vauban now writes them before javac's last round, once the other processors' classes are in, and the warnings are gone. It keeps the last round, and its warnings, when a bean carries an inherited annotation another processor reads, such as a class-level `@Retry` or `@Counted` (`-Avauban.generationRound`, Vidocq/vauban#216).

== Step 5 — Dev mode

[source,bash]
----
mvn vidocq:dev
----

Dev mode launches the application on its module path and watches your sources. It uses the `vidocq.mainModule` property already set in the generated pom (and `vidocq.mainClass`, when `--main` set it).

Nothing to add: since `todo` already has the Chappe HTTP server (through `cassini-rest`), `mvn vidocq:dev` also serves the xref:dev-console.adoc[dev console] on its own: `Vidocq dev console: http://127.0.0.1:8888/` opens the startup report of the running application and the live values of its extensions.

To run the application once, without the watcher, use `mvn vidocq:run`: it compiles, completes the bean index and forks the same JVM, and its exit code is the build's. See xref:modules/vidocq-runtime-maven-plugin.adoc#run[the `vidocq:run` goal].

`mvn vidocq:idea`writes IntelliJ IDEA run configurations for what an IDE should run: by
default, three files per application — a Maven run of `vidocq:dev` suffixed ` (dev)` (the one above, console
included), one of `vidocq:run` suffixed ` (run)`, and a Remote JVM Debug one suffixed ` (debug)` that attaches to
`vidocq:dev`'s own debug agent. `vidocq.mainModule` is all it needs: the files are named after the
`artifactId`, `todo (dev)` and so on. See xref:modules/vidocq-runtime-maven-plugin.adoc#idea[the `vidocq:idea` goal].

In VS Code, `mvn vidocq:vscode`(`vidocq vscode`) writes `.vscode/`: the Java extension's language
server on Java 25, which Vauban's annotation processors need, with its automatic build off so that `vidocq dev`
alone writes `target/classes`; tasks for `vidocq dev`, `run` and `test`; and a debug configuration that attaches to
`vidocq dev`. See xref:modules/vidocq-runtime-maven-plugin.adoc#vscode[the `vidocq:vscode` goal].

In Eclipse, `mvn vidocq:eclipse`(`vidocq eclipse`) writes `.eclipse/`: Maven builds of `vidocq dev`,
`run` and `test` and a debug configuration that attaches to `vidocq dev`, under Run Configurations once the project is
imported. Turn Project > Build Automatically off while `vidocq dev` runs. See
xref:modules/vidocq-runtime-maven-plugin.adoc#eclipse[the `vidocq:eclipse` goal].

NOTE: `vidocq dev` and `vidocq start` (the CLI commands, as opposed to the Maven goal) boot the runtime from the CLI's own module path and therefore do not see the extensions declared in your pom. Prefer `mvn vidocq:dev` and the packaged launcher for extension-based apps.

== Step 6 — Add extensions as you grow

[source,bash]
----
vidocq extension list --available
vidocq extension add knock-health
mvn package
----

`extension add` edits your `pom.xml` with the correct coordinates. See xref:usage.adoc[Usage] for the per-extension configuration keys, and xref:modules/vidocq-runtime-examples.adoc[the examples tour] for a full REST + persistence application (Mansart Data + H2).

== Step 7 — Package for production

[source,bash]
----
vidocq build jlink    # self-contained runtime image (no local java needed)
vidocq build docker   # container image
----

See xref:usage.adoc[Usage] for jlink/jpackage/Docker options and AOT notes.

== Annex — Without the CLI

The CLI is a convenience, not a requirement. The project above is plain Maven — here is the complete, copy-pasteable equivalent.

`pom.xml`:

[source,xml,subs=attributes+]
----
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 http://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <groupId>com.acme</groupId>
    <artifactId>todo</artifactId>
    <version>1.0.0-SNAPSHOT</version>
    <name>todo</name>

    <properties>
        <vidocq.version>{release-version}</vidocq.version>
        <maven.compiler.release>25</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
        <vidocq.mainModule>com.acme.todo</vidocq.mainModule>
    </properties>

    <dependencyManagement>
        <dependencies>
            <dependency>
                <groupId>io.vidocq.runtime</groupId>
                <artifactId>vidocq-runtime-bom</artifactId>
                <version>${vidocq.version}</version>
                <type>pom</type>
                <scope>import</scope>
            </dependency>
            <dependency>
                <groupId>org.junit</groupId>
                <artifactId>junit-bom</artifactId>
                <version>6.0.3</version>
                <type>pom</type>
                <scope>import</scope>
            </dependency>
        </dependencies>
    </dependencyManagement>

    <dependencies>
        <dependency>
            <groupId>io.vidocq.runtime</groupId>
            <artifactId>vidocq-runtime-core</artifactId>
        </dependency>
        <dependency>
            <groupId>io.vidocq.runtime.extensions.jakartaee.core</groupId>
            <artifactId>vidocq-runtime-cassini-rest-extension</artifactId>
        </dependency>
        <dependency>
            <groupId>io.vidocq.runtime</groupId>
            <artifactId>vidocq-runtime-junit</artifactId>
            <scope>test</scope>
        </dependency>
        <dependency>
            <groupId>org.junit.jupiter</groupId>
            <artifactId>junit-jupiter</artifactId>
            <scope>test</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>io.vidocq.runtime</groupId>
                <artifactId>vidocq-runtime-maven-plugin</artifactId>
                <version>${vidocq.version}</version>
                <extensions>true</extensions>
            </plugin>
        </plugins>
    </build>
</project>
----

No parent (Vidocq/vidocq#380): the plugin, loaded as a build extension, gives the build what a parent would,
the Java release, the executions of its goals, the versions of the lifecycle plugins, the processor path of the
extensions, the build identity. The application keeps a parent of its own if it has one, above the `groupId`.
`vidocq create --with-parent` writes the previous style, under `vidocq-runtime-parent`, and
xref:modules/vidocq-runtime-cli.adoc#pom-convert[`vidocq pom convert`] turns an existing pom from one style into
the other, and xref:modules/vidocq-runtime-cli.adoc#pom-upgrade[`vidocq pom upgrade`] moves it to another Vidocq version.
`maven.compiler.release` is the one line Maven does not need: IntelliJ IDEA reads the language level from
the pom alone, and the project is created in UTF-8 (`project.build.sourceEncoding`). See xref:modules/vidocq-runtime-maven-plugin.adoc#parentless[the plugin without the parent].

NOTE: This is the pom of 0.4.0. Until then, the project inherited `vidocq-runtime-parent`, pinned every Vidocq
version, bound the `package` execution and listed each extension's codegen bundle in a `maven-compiler-plugin`
block: xref:migration.adoc#no-parent[the migration page] says what became of each line. The project has a version
of its own, `1.0.0-SNAPSHOT`, and the Maven wrapper of the Vidocq repositories (`mvnw`, `mvnw.cmd`, `.mvn/wrapper/`),
so it builds with the ecosystem's Maven version and `vidocq doctor` finds it.

`src/main/java/module-info.java`:

[source,java]
----
module com.acme.todo {
    // APT-generated $$CassiniAdapter classes import @Generated (SOURCE retention).
    requires static java.compiler;

    requires jakarta.cdi;
    requires jakarta.inject;
    requires jakarta.ws.rs;
    requires jakarta.json.bind;

    requires io.vidocq.runtime.extensions.jakartaee.core.cassini;
    requires io.vidocq.cassini.api;

    // JAX-RS and JSON-B reflect on resource classes and payload types.
    opens com.acme.todo;
}
----

[TIP]
====
This `opens` works because the resources live in *this* module. In a
multi-module application (e.g. hexagonal, resources in their own Java module), the module
system only lets a module open packages it owns: the `opens` must move into the module that contains the classes,
and the runtime module scans it with `<scanDependencies>`. See
xref:usage.adoc#multi-module-applications-scanned-dependencies[Usage — Multi-module applications].
====

`src/main/resources/vidocq.properties`:

[source,properties]
----
# Vidocq application configuration
vidocq.http.port=8080
----

Then add the `HelloResource` from Step 3 and continue from Step 4 (`mvn package`) — the flow is identical.
