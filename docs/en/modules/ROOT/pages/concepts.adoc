= Concepts
:description: Build steps, build items, extensions and runtime mechanics of Vidocq.

== Build steps

A Vidocq extension declares _build steps_ — annotated methods that run at compile time, consume and produce `BuildItem` instances. The model is borrowed from Quarkus, but the engine is Vauban + Class-File API (not ArC + Gizmo).

== Build items

`BuildItem` instances are the exchange units between extensions. Planned categories:

* **`SimpleBuildItem`** — a single producer allowed (e.g. `JaxRsApplicationBuildItem`).
* **`MultiBuildItem`** — N producers (e.g. `BeanBuildItem`, `ResourceBuildItem`).
* **`SymbolicBuildItem`** — phase markers (e.g. `ApplicationStartBuildItem`).

== Shipped extensions

Modules under `vidocq-mps-core-extensions/`:

* **CDI** — wires Vauban as the injection engine.
* **JAX-RS** — wires Cassini, generates static routing.
* **JSON-B** — wires Champollion, triggers APT generation at build.
* **Servlet** — wires Foy.
* **Mansart** — initializes the JDBC pool, scans `@Repository`.
* **Mansart-transactions** — `@Transactional` handled by `mansart-transactions`.

== Runtime init vs static init

Vidocq distinguishes:

* **`STATIC_INIT`** — runs at compile time. Anything constant or pre-computable.
* **`RUNTIME_INIT`** — runs at JVM startup. External config reads, pool openings, network handshakes.

Class-File API recorders encode `STATIC_INIT` actions as bytecode so `RUNTIME_INIT` can replay them trivially.

== Bytecode generation

Recorders rely on the **Class-File API (JEP 484, finalized in Java 24)**. No ASM, no Byte Buddy. Generated bytecode targets Java 25 and is compatible with Leyden CDS.
