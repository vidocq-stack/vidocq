= Usage
:description: Packaging, configuration, profiles, deployment, AOT.

[.lead]
This page covers Vidocq Runtime usage beyond the hello world: the application entry
point, packaging via the `vidocq-runtime-maven-plugin` (jlink, jpackage, Docker),
configuration via {spec-mp-config}, observability ({spec-mp-health}, {spec-mp-metrics},
{spec-mp-openapi}), profiles, and AOT preparation.

[#entry-point]
== The application entry point

An application has no main class of its own by default. The runtime's main,
`io.vidocq.runtime.core.Vidocq`, boots it from the module that `vidocq.mainModule` names, under every goal:

* `vidocq:run` and the `vidocq:package` launchers hand the application to it as a path, `-Dvidocq.app.path`, and
  `vidocq:dev`'s hot-reload loop re-creates that layer at each reload;
* a `vidocq:jlink` image, and the `vidocq:jpackage` application built on it, start it with
  `-Dvidocq.app.module`, see xref:modules/vidocq-runtime-core.adoc#app-module-property[the `vidocq.app.module`
  property] and xref:modules/vidocq-runtime-maven-plugin.adoc#jlink-without-main-class[jlink without a main class];
* `vidocq:idea` writes its `(dev)`, `(run)` and `(debug)` configurations from `vidocq.mainModule` alone, see
  xref:modules/vidocq-runtime-maven-plugin.adoc#idea[the `vidocq:idea` goal].

`vidocq create` writes no main class either, unless asked with `--main`. Whatever the launch, the application
resolves into a **child module layer defined by the Vauban class loader**, where every class flows through the
load-time transformations (client-proxy weaving…) at definition: same layer, same transformed classes, no
instrumentation agent, no JVM warning.

[#vidocq-main-trampoline]
=== When to add a `@VidocqMain` trampoline

A main class of your own is worth having in two cases only:

* **a right-click Run on a main class in the IDE**, everything on the module path, without a Maven step (or the
  `-Dvidocq.idea.kind=application` configurations of `vidocq:idea`, which run it);
* **logic after boot, or an exit code**, through a `VidocqApp` passed to `Vidocq.run(Class, args)`.

That main is a *trampoline*: it contains nothing but `Vidocq.run(...)`, and its module `requires
io.vidocq.runtime.core` and `io.vidocq.runtime.spi`. Point `vidocq.mainClass` at it.

[source,java]
----
@VidocqMain
public final class App implements VidocqApp {

    public static void main(String[] args) {
        Vidocq.run(App.class, args);      // no business logic before this line
    }

    @Override
    public int run(String... args) throws Exception {
        // runs AFTER boot, inside the Vauban class loader, with transformed classes
        Vidocq.waitForExit();             // block for a server application
        return 0;
    }
}
----

Why a trampoline? Because Vidocq does not let the application main "own" the runtime:
`Vidocq.run()` re-resolves the application into the Vauban layer, as the runtime's main does. A plain IDE launch
then behaves exactly like a production launch.

The contract (deliberately identical to Quarkus' `@QuarkusMain`):

* **no business logic before `Vidocq.run(...)`** — the trampoline class is loaded by the
  JVM's boot layer while the application runs in the Vauban layer; code executed before
  `run()` lives in the wrong class loader and sees untransformed classes;
* application logic that must run after boot goes into a `VidocqApp` passed to
  `Vidocq.run(Class, args)` — the class is re-loaded through the layer and instantiated
  there (as a CDI bean when it is one); its return value is the exit code;
* a trampoline kept only for the IDE, without post-boot logic, just calls `Vidocq.run(args)`.

`vidocq create --main` writes such a trampoline and sets `vidocq.mainClass`, see
xref:modules/vidocq-runtime-cli.adoc#create[`vidocq create`].

=== How the application modules are chosen

When the application was resolved into the boot layer — a trampoline launched from the IDE, or a jlink image
started with `vidocq.app.module` — `Vidocq.run()` and the runtime's main pick its modules automatically, with the
policy of Vauban's xref:dev@vauban::se.adoc[Java SE launcher]: every module moves except the
Vidocq bricks, the platform and Jakarta modules, automatic modules, modules with a `javax.`,
`sun.` or `com.sun.` package, and what those kept modules read. The caller's module always
moves. CDI-agnostic libraries move too, so Vauban places the client proxies that must live in
their packages, with zero `opens`. Override with `-Dvidocq.app.modules=<name,name>` or an
explicit `-Dvidocq.app.path=<archives>`.

[#app-in-boot-layer]
When the selection finds no application module to move, the application stays in the boot
layer, and there Vidocq cannot give itself access to the `VidocqApp` class it has to instantiate. The boot
now fails with a message that names the class, its package and the two fixes, instead of a bare
`IllegalAccessException`: add `exports <package> to io.vidocq.runtime.core;` to the application's
`module-info.java`, or make the class a CDI bean (`@ApplicationScoped` or `@Dependent`), which the
container creates itself (Vidocq/vidocq#201). In the application layer, the usual case, Vidocq adds that
export by itself.

A legacy main that boots the runtime directly (through `VidocqBootstrap`) still works — unwoven beans are then
covered by the load-time weaving agent (with the JDK's dynamic-agent warning), and Vauban's warning hints at a
trampoline that re-layers the application. Delete the legacy main — the runtime's own main re-layers it too — or
turn it into a trampoline if you need one of the two cases above.

One more benefit: applications never declare generated providers in
`module-info.java`. The annotation processors emit standard `META-INF/services` files
(`_VaubanComponents`, Cassini `$$CassiniAdapter`/`$$CassiniRoutes`…), and the Vauban
layer promotes them to synthetic `provides` when it resolves the module — your
`module-info.java` stays free of any generated class name.

NOTE: custom JUL log handlers declared in the application's `logging.properties` must
live on the module path — `LogManager` instantiates handlers through the system class
loader, which cannot see the layer.

[#app-layer-dependencies]
=== Dependencies in the application layer [.tag-new]#NEW#

By default (`vidocq.app.layer=all`, since Vidocq 0.4.0) the application layer holds the project's classes and the
project's dependencies, the way `WEB-INF/lib` works in a servlet container. A framework that looks up its
resources through its own class loader, Vaadin for instance, then sees the whole application. `vidocq:run`,
`vidocq:dev`, an IDE launch of `Vidocq.run()` and `vidocq:package` all take this default: development and
production behave the same way (Vidocq/vidocq#247). `-Dvidocq.app.layer=classes` is the opt-out: the layer holds
the project's classes only, and the dependencies stay on the module path, as they did before 0.4.0.

[#app-layer-migration]
*Migrating from 0.3.x.* The default changed from `classes` to `all`. An application that worked keeps working: where
`all` cannot be honoured and nobody asked for it, the build or the launch warns and falls back, it does not fail.

* A dependency whose module name cannot be derived stays in the parent layer, and the build warns with the jar name.
  Give the jar an `Automatic-Module-Name` to move it into the application layer.
* With the layer mode off (`vidocq.dev.layer=false`, `vidocq.package.layer=false`) the goal falls back to `classes`
  with a warning.
* A pin that reads a module of the application falls back to `classes` with a warning that names both modules.
* To go back for good, set `vidocq.app.layer=classes` in the POM (`<properties>` or the plugin's `<configuration>`) or
  on the command line. An explicit `-Dvidocq.app.layer=all` keeps the strict behaviour: each of the cases above
  fails the build.
* What to pin: a library with native code (JNI), a library that must be the same class in the runtime and in the
  application, and any library that fails to load twice (see the limits below). Use `vidocq.app.layer.keep`.

*The rule.* The parent layer is the closure of the runtime: the Jakarta and MicroProfile APIs, the Vidocq
modules, the modules that provide a Vidocq extension, the modules with a `javax.`, `sun.` or `com.sun.` package,
the pinned modules, and what all of them require. Everything else belongs to the application, automatic modules
included. A module that is kept also keeps the dependencies it declares in Maven. Maven records one path per
artifact, so a dependency shared with an application library and reached by a nearer path can land in the
application layer: pin it.

*Pinning.* `-Dvidocq.app.layer.keep=<patterns>` keeps modules in the parent layer. A pattern is a module name or
`groupId:artifactId`; `*` alone, or as a suffix (`org.acme.*`), matches several. A brick pins its own modules with
the `Vidocq-Parent-Layer` attribute of its manifest. A pinned module drags what it requires into the parent layer.
The other way round, a Vidocq jar whose manifest says `Vidocq-Application-Layer: true` is not kept by
the name rule: a module that integrates an application framework, such as
xref:modules/vidocq-runtime-extensions.adoc#vaadin[the Vaadin extension], goes to the application layer with it.
A pinned module that reads a module of the application fails the build, with both names.

*The startup report.* The `layer` headline counts the libraries, for instance
`3 modules, 2 libraries (...)`. The detailed report has one `parent layer` row for each pinned module, with its
reason. The build logs `application layer: <n> libraries, <m> kept in the parent layer by a pin`.

*Enriched libraries.* `vidocq:generate` runs the brick processors (Foy's, for instance) over the dependency jars they select, so a `@WebListener` of a library works without a workaround. The `layer` headline then counts them: `, 1 enriched (Foy 1)`. See xref:modules/vidocq-runtime-maven-plugin.adoc#brick-processors[Brick processors on dependency jars].

*Dev reload.* The libraries are reloaded with the application. The JDBC drivers that the old layer defined are
deregistered at each reload. A thread that a library leaves running keeps the old layer in memory; the reload names
such threads in a warning, `Hot reload: N thread(s) still hold the previous application layer ...`. Virtual threads
are not detected. A library with native code (JNI) cannot be loaded twice by the JVM: keep it in the parent layer
with `vidocq.app.layer.keep`.

*Packaging.* Under `vidocq:package`, `lib/` holds the parent layer and `app/` holds the application jar and its
libraries. Both launchers hand `app/` to the runtime through `-Dvidocq.app.path`, also for an application with a
main class, and carry `-Dvidocq.app.layer=` with the mode the build settled on (`classes` too: a runtime that finds
the property unset takes the default, `all`) and the pinned list. `all` requires the layer mode
(`vidocq.dev.layer`, `vidocq.package.layer`). Left to the default, a goal without the layer mode falls back to
`classes` with a warning; asked for with `-Dvidocq.app.layer=all`, it fails. In the same way a dependency whose module
name cannot be derived stays in the parent layer with a warning by default, and fails the build when `all` was asked
for, with a message that names the jar: add an `Automatic-Module-Name` to it, or use `vidocq.app.layer=classes`. See xref:modules/vidocq-runtime-maven-plugin.adoc#app-layer-property[the plugin properties].

[[app-layer-jdk-modules]]*JDK modules.*Only the boot layer can define a JDK module, so a JDK module that only an
application module requires, such as `java.sql` for Vaadin's `flow-data`, must be resolved there. `vidocq:run`,
`vidocq:dev` and the `vidocq:package` launchers add these modules to `--add-modules`, read from the descriptors of
the application path. A `java` command written by hand needs the same option; without it the runtime fails with
`Cannot create the application layer (...): Module java.sql not found, required by flow.data. A JDK module can
only be resolved in the boot layer: add --add-modules java.sql to the java command (...)` (Vidocq/vidocq#254).
A `requires` on a JDK module added while `vidocq:dev` runs needs a restart of `vidocq:dev`: a hot reload keeps the
boot layer.

*Known limits.*

* A plain IDE run of `main` (the `Vidocq.run` trampoline) keeps the automatic libraries in the boot layer. The
  `(dev)` configuration that `vidocq:idea` writes has no such limit.
* `vidocq:jlink`, `vidocq:jpackage` and the Docker image built on the jlink image follow the same default. The image is
  linked as one boot layer, and at start the runtime re-layers the application from it (`vidocq.app.module`, or the
  `@VidocqMain` trampoline), the way it does for an IDE launch: the application and its libraries go into the
  application layer, and the runtime and the bricks stay. The build bakes `-Dvidocq.app.layer=` with its mode into
  the launcher (`--add-options`, and `--java-options` for jpackage), so the image keeps the mode it was built under:
  build it with `-Dvidocq.app.layer=classes` to opt out.
* A library with native code (JNI) cannot be loaded twice by the JVM, and the dev reload loads the application
  layer again: pin it with `vidocq.app.layer.keep`.
* A thread that a library leaves running keeps the previous layer in memory; the dev reload warns, as above.
* The libraries of the layer are listed in the `layer` section of the startup report.
* The IDE launch and the build-time split share the rule for explicit modules (the runtime, the bricks, what they
  read). They differ on automatic modules only, see the first limit of this list.
* Jar signatures are not verified in the layer.
* An automatic module declares no `requires`, so the JDK modules it uses are not added for it. One that needs
  `java.sql` or `java.desktop` fails with `NoClassDefFoundError`: add the module with `--add-modules` in
  `vidocq.dev.jvmArgs` or the package's `jvmArgs`, or give the jar a descriptor with `vauban:modularize`.

== Packaging with `vidocq-runtime-maven-plugin`

The Maven plugin exposes three packaging targets. See xref:modules/vidocq-runtime-maven-plugin.adoc[the dedicated page] for the full inventory and the internal `JLINK.md` details.

[cols="1,1,3"]
|===
| Goal | Output | Typical startup

| `vidocq:jlink`
| `target/dist/` (binary + embedded Java runtime, ~40 MB)
| ~4 s

| `vidocq:jpackage`
| `target/installer/<name>.app` or `.exe`/`.msi`/`.deb`/`.rpm`
| ~1 s (CDS)

| `vidocq:docker`
| `target/Dockerfile` distroless based on `distroless/base-debian12:nonroot`
| ~50 MB image
|===

Quick start (from `vidocq-runtime-cassini-rest-example`):

[source,bash]
----
cd vidocq-runtime-examples/vidocq-runtime-cassini-rest-example
./mvnw -ntp package -DskipTests
./target/dist/bin/todo-app
----

`jlink` and `jpackage` require every dependency to be a *named* module. When some third-party jars ship without `module-info.class`, run `vauban:modularize` beforehand: it generates their descriptors into `target/vauban-modularized/`, where `dev`, `jlink` and `package` pick them up automatically. See xref:modules/vidocq-runtime-maven-plugin.adoc#modularize[the `vauban:modularize` goal].

== Multi-module applications (scanned dependencies)

Hexagonal and multi-module applications typically keep their business and adapter modules
*spec-only* — Jakarta EE / MicroProfile APIs only, no Vidocq dependency, no Vidocq APT — and
concentrate everything runtime-specific in a small main module. That main module asks
`vidocq:generate` to scan the app modules and produce the CDI/REST glue for them. The id `generate` is the one of the
execution the plugin binds as a build extension, or `vidocq-runtime-parent`: the configuration below merges into it,
and the goal still runs once.

[source,xml]
----
<execution>
    <id>generate</id>
    <goals><goal>generate</goal></goals>
    <configuration>
        <scanDependencies>
            <scanDependency>com.acme:my-rest-adapter</scanDependency>
            <scanDependency>com.acme:my-domain</scanDependency>
        </scanDependencies>
    </configuration>
</execution>
----

Two rules for each *scanned* module's `module-info.java` — and remember that the Java module
system only lets a module `opens` (or `exports`) packages it *owns*: you cannot open another module's package from
the main module, which is why the single-module `opens` shown in
xref:getting-started.adoc[Getting started] must move into the module that contains the classes.

[source,java]
----
module com.acme.rest.adapter {
    exports com.acme.rest;          // resource classes
    exports com.acme.rest.dto;      // JSON-B reads records via their public accessors
    requires jakarta.cdi;
    requires jakarta.ws.rs;

    // The consuming runtime generates/reflects the CDI plumbing for these beans.
    // Unqualified `opens` names no runtime module: the module stays spec-only,
    // and classpath-based runtimes ignore it entirely.
    opens com.acme.rest;
}
----

[NOTE]
.New in 0.3.0
====
The classes that `vidocq:generate` produces for scanned dependencies (client proxies,
interceptors) live in packages *owned by those dependencies*. Since 0.3.0 the plugin keeps them
out of the main module automatically:

* `vidocq:generate` parks them in `target/vidocq-patches/<artifactId>/`
  (log line: `JPMS: parked N generated class(es) of '…'`);
* `vidocq:generate` then writes an *enriched* copy of each such jar in `target/vidocq-enriched/`,
  carrying its own generated classes, with a module descriptor that declares its providers — the
  packages already exist in those jars, so the module path never sees a split package;
* `vidocq:dev`, `vidocq:run`, `vidocq:package` and `vidocq:jlink` use that copy in place of the
  original; only a jar that cannot be given a descriptor keeps its original, and `vidocq:dev`
  attaches its classes with `--patch-module`.

No configuration is needed: see
xref:modules/vidocq-runtime-maven-plugin.adoc#generate[which jars `vidocq:generate` scans].
====

[WARNING]
.On 0.2.0 (released)
====
Vidocq 0.2.0 leaves the generated classes in the main module's `target/classes`, which creates
an illegal *split package* on the module path: the boot layer fails with
`ResolutionException: Module <main> contains package <pkg>, module <dep> exports package <pkg>`
— or, if the dependency is not `requires`-ed, its beans are silently absent (HTTP 404).
The workaround on 0.2.0 is to do by hand what 0.3.0 does natively:

. move the foreign-package classes out of `target/classes` *before* the jar is built
  (e.g. `maven-antrun-plugin` at `prepare-package` — moving them after the fact is not enough,
  because `maven-jar-plugin` records the packages in the `ModulePackages` attribute of
  `module-info.class`);
. launch with `--patch-module <dep.module>=<dir>` for each dependency, e.g. via the
  `<jvmArgs>` of the `package` goal for the generated launch scripts.
====

[#several-applications]
== Several applications in one reactor

A reactor can hold one application per module, next to the library modules they share. Each application module
is an ordinary Vidocq application: `vidocq-runtime-maven-plugin` in its `<build><plugins>`, and its own
`vidocq.mainModule`. None of them needs a main class (<<entry-point>>).

[source,xml]
----
<!-- orders/pom.xml -->
<properties>
    <vidocq.mainModule>com.acme.orders</vidocq.mainModule>
</properties>

<!-- billing/pom.xml -->
<properties>
    <vidocq.mainModule>com.acme.billing</vidocq.mainModule>
</properties>
----

Run `mvn vidocq:idea` once from the reactor root: it writes `orders (dev)`, `orders (run)`, `orders (debug)` and
the same three for `billing`, named after each module's `artifactId`, so two applications never collide. A
module pom that sets `vidocq.idea.configurationName` gets that name instead, and `vidocq.idea.exclude=true` leaves
a module out. Each `(dev)` and `(run)` configuration runs Maven on its own module's pom, so the sibling modules
it depends on must be resolvable: `mvn install` the reactor once. When the plugin is only declared in the
application modules, add it to the root `<pluginManagement>` so that the `vidocq:` prefix resolves there. See
xref:modules/vidocq-runtime-maven-plugin.adoc#idea[the `vidocq:idea` goal].

Give each application its own HTTP port in its `vidocq.properties` if you run them side by side.

== MicroProfile configuration

Vidocq Runtime implements {spec-mp-config}. Source hierarchy, highest to lowest priority:

[cols="1,2,3"]
|===
| Ordinal | Source | Description

| 400 | `SystemPropertiesConfigSource` | `-Dkey=value`
| 300 | `EnvConfigSource` | Environment variables (`KEY_NAME`)
| 250 | `ExternalFileConfigSource` | `${java.home}/conf/vidocq.properties` (jlink image)
| 100 | `PropertiesFileConfigSource` | classpath `vidocq.properties`
|===

`ExternalFileConfigSource` lets you override a deployed jlink/jpackage binary without rebuilding, simply by editing the `conf/vidocq.properties` file next to the launcher. A boot log line traces the effective load.

== Health

[source,java]
----
@Liveness
@ApplicationScoped
public class DatabaseHealth implements HealthCheck {
    @Inject DataSource ds;

    @Override
    public HealthCheckResponse call() {
        try (Connection c = ds.getConnection()) {
            return HealthCheckResponse.up("database");
        } catch (SQLException e) {
            return HealthCheckResponse.down("database");
        }
    }
}
----

Endpoints exposed by `vidocq-runtime-knock-health-extension`: `/health`, `/health/live`, `/health/ready`, `/health/started` (see xref:tck.adoc[TCK]).

== OpenAPI

The `vidocq-runtime-grimm-openapi-extension` extension serves the OpenAPI document, generated from Jakarta REST + MicroProfile OpenAPI annotations, at `/openapi`; the companion `vidocq-runtime-grimm-openapi-ui-extension` serves Swagger UI at `/openapi/ui`.

[#dev-console]
== Dev console

While you develop, run `mvn vidocq:dev`: it adds the console itself when the application has `vidocq-runtime-chappe-webserver-extension`, and never packages it. The application logs `Vidocq dev console: http://127.0.0.1:8888/`, a read-only page with the startup report of the running boot and the live values of the extensions — the connections of each Mansart pool, the heap, the threads, the garbage collectors. It is on in a dev launch only, on the loopback address. See xref:dev-console.adoc[Dev console]; an extension adds its own panel as xref:dev-console-panels.adoc[Writing a dev console panel] describes.

== Profiles

MicroProfile convention: prefix a key with `%<profile>.` to scope it.

[source,properties]
----
vidocq.http.port=8080
%dev.vidocq.http.port=8081
%prod.vidocq.http.port=80
----

Activate via the `-Dvidocq.profile=dev` system property (there is no environment-variable equivalent).

[#property-expressions]
== Property expressions [.tag-new]#NEW#

A value may refer to other keys with the {spec-mp-config} property expressions, which every Vidocq key and the extensions read, with or without Ravel:

[source,properties]
----
vidocq.chappe.listener.default.port=${DASHBOARD_PORT:8080}
orders.url=jdbc:postgresql://${db.host}:${db.port:5432}/orders
----

* `${key}` is the value of `key`, from any source — an environment variable `DASHBOARD_PORT` above — and is itself expanded; `${key:default}` is `default` when no source has `key`. The key and the default may hold expressions: `${url.${target}}`.
* `\${key}` is kept as written, `${key}`.
* An expression without a default whose key has no value leaves the property without a value: the extension that reads it applies its own default.
* An expression that comes back to its own key, or a `${` without its closing brace, fails the read with an `IllegalArgumentException`.
* `mp.config.property.expressions.enabled=false` turns the expansion off: values are read as written.

With Ravel, `ConfigProvider.getConfig()` and `VidocqConfig` expand a value the same way.

== Docker deployment

Minimal distroless image produced by `vidocq:docker`:

[source,bash]
----
./mvnw -ntp package -Dvidocq.docker.build=true
docker run --rm -p 8080:8080 \
    -e VIDOCQ_CONFIG_DIR=/etc/myapp \
    -v $(pwd)/conf:/etc/myapp:ro \
    example/my-app:1.0.0
----

The `distroless/base-debian12:nonroot` base image has no shell, no package manager — minimal attack surface. The `nonroot` user (UID 65532) is enforced.

== AOT — GraalVM and Leyden

* **Leyden CDS** — supported out of the box. Static Class-File API codegen produces bytecode that archives perfectly.
* **GraalVM native-image** — Vidocq Runtime's zero-reflection + zero-proxy strategy minimises `reachability-metadata`. See `vidocq/JLINK.md` for runtime prerequisites (logging.properties, named Java modules, serialised records).
