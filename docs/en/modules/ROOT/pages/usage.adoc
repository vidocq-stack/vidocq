= Usage
:description: Packaging, configuration, profiles, deployment, AOT.

[.lead]
This page covers Vidocq Runtime usage beyond the hello world: the application entry
point, packaging via the `vidocq-runtime-maven-plugin` (jlink, jpackage, Docker),
configuration via {spec-mp-config}, observability ({spec-mp-health}, {spec-mp-metrics},
{spec-mp-openapi}), profiles, and AOT preparation.

[#entry-point]
== The application entry point

An application has no main class of its own by default. The runtime's main,
`io.vidocq.runtime.core.Vidocq`, boots it from the module that `vidocq.mainModule` names, under every goal:

* `vidocq:run` and the `vidocq:package` launchers hand the application to it as a path, `-Dvidocq.app.path`, and
  `vidocq:dev`'s hot-reload loop re-creates that layer at each reload;
* a `vidocq:jlink` image, and the `vidocq:jpackage` application built on it, start it with
  `-Dvidocq.app.module`, see xref:modules/vidocq-runtime-core.adoc#app-module-property[the `vidocq.app.module`
  property] and xref:modules/vidocq-runtime-maven-plugin.adoc#jlink-without-main-class[jlink without a main class];
* `vidocq:idea` writes its `(dev)`, `(run)` and `(debug)` configurations from `vidocq.mainModule` alone, see
  xref:modules/vidocq-runtime-maven-plugin.adoc#idea[the `vidocq:idea` goal].

`vidocq create` writes no main class either, unless asked with `--main`. Whatever the launch, the application
resolves into a **child module layer defined by the Vauban class loader**, where every class flows through the
load-time transformations (client-proxy weaving…) at definition: same layer, same transformed classes, no
instrumentation agent, no JVM warning.

[#vidocq-main-trampoline]
=== When to add a `@VidocqMain` trampoline

A main class of your own is worth having in two cases only:

* **a right-click Run on a main class in the IDE**, everything on the module path, without a Maven step (or the
  `-Dvidocq.idea.kind=application` configurations of `vidocq:idea`, which run it);
* **logic after boot, or an exit code**, through a `VidocqApp` passed to `Vidocq.run(Class, args)`.

That main is a *trampoline*: it contains nothing but `Vidocq.run(...)`, and its module `requires
io.vidocq.runtime.core` and `io.vidocq.runtime.spi`. Annotate it `@VidocqMain`: `vidocq:dev`, `vidocq:run` and the
packaging goals then launch it without a setting, and say so. Set `vidocq.mainClass` only to choose among several
annotated classes, or to launch another one.

[#ide-run-twice]
A right-click Run leaves the application on the module path, so in the JVM's boot layer, and `Vidocq.run` loads it
again into the application layer: each class of the application, and under `vidocq.app.layer=all` of its libraries,
exists twice. The runtime's own lookups prefer the copy of the layer, but a library that looks its services up
itself finds twice each provider that these modules declare in their `module-info.java`: Vaadin stops with "multiple
eligible instantiator implementations" when the application `provides` an `InstantiatorFactory`. The start warns with
xref:modules/vidocq-runtime-core.adoc#vidocq-lay-001[`VIDOCQ-LAY-001`] and names the modules loaded twice. The
`(dev)` and `(run)` configurations that `vidocq:idea` writes by default run `vidocq:dev` and `vidocq:run`, which hand
the application to the runtime without the module path, and load it once (BUG-20261114-10).

[source,java]
----
@VidocqMain
public final class App implements VidocqApp {

    public static void main(String[] args) {
        Vidocq.run(App.class, args);      // no business logic before this line
    }

    @Override
    public int run(String... args) throws Exception {
        // runs AFTER boot, inside the Vauban class loader, with transformed classes
        Vidocq.waitForExit();             // block for a server application
        return 0;
    }
}
----

Why a trampoline? Because Vidocq does not let the application main "own" the runtime:
`Vidocq.run()` re-resolves the application into the Vauban layer, as the runtime's main does. A plain IDE launch
then behaves exactly like a production launch.

The contract (deliberately identical to Quarkus' `@QuarkusMain`):

* **no business logic before `Vidocq.run(...)`** — the trampoline class is loaded by the
  JVM's boot layer while the application runs in the Vauban layer; code executed before
  `run()` lives in the wrong class loader and sees untransformed classes;
* application logic that must run after boot goes into a `VidocqApp` passed to
  `Vidocq.run(Class, args)` — the class is re-loaded through the layer and instantiated
  there (as a CDI bean when it is one); its return value is the exit code;
* a trampoline kept only for the IDE, without post-boot logic, just calls `Vidocq.run(args)`.

`vidocq create --main` writes such a trampoline and sets `vidocq.mainClass`, see
xref:modules/vidocq-runtime-cli.adoc#create[`vidocq create`].

[#shutdown]
=== Stopping the application from its own code

An application ends itself with `Vidocq.shutdown()`, never with `System.exit`: closing the last window of a desktop
application, a batch whose work is done. The call returns at once and the stop runs on a virtual thread of its own,
exactly as on Ctrl+C: the extensions stop in reverse start order, the container closes and fires the CDI
`jakarta.enterprise.event.Shutdown` event, and `Vidocq.waitForExit()` returns. It is safe from any thread, a UI
thread, an HTTP request, a CDI observer or an extension's `onStart`; a request made during the boot is honoured once
the boot completes. `Vidocq.shutdownAndWait()` runs the stop on the calling thread and returns once it is done, with
the failure of the container's close if any: never call it from a thread the stop needs (a UI thread, a request
thread, an executor of the application).

`System.exit` stops the runtime from a JVM shutdown hook, where some libraries no longer work (JavaFX on macOS runs no
`Platform.runLater` there), and ends the JVM of a test run with it. Under `vidocq:dev`, an application that stops
itself ends the whole dev session; a crash or a failed boot keeps it waiting for a fix.

=== How the application modules are chosen

When the application was resolved into the boot layer — a trampoline launched from the IDE, or a jlink image
started with `vidocq.app.module` — `Vidocq.run()` and the runtime's main pick its modules automatically, with the
policy of Vauban's xref:dev@vauban::se.adoc[Java SE launcher]: every module moves except the
Vidocq bricks, the platform and Jakarta modules, automatic modules, modules with a `javax.`,
`sun.` or `com.sun.` package, and what those kept modules read. The caller's module always
moves. CDI-agnostic libraries move too, so Vauban places the client proxies that must live in
their packages, with zero `opens`. Override with `-Dvidocq.app.modules=<name,name>` or an
explicit `-Dvidocq.app.path=<archives>`.

[#app-in-boot-layer]
When the selection finds no application module to move, the application stays in the boot
layer, and there Vidocq cannot give itself access to the `VidocqApp` class it has to instantiate. The boot
now fails with a message that names the class, its package and the two fixes, instead of a bare
`IllegalAccessException`: add `exports <package> to io.vidocq.runtime.core;` to the application's
`module-info.java`, or make the class a CDI bean (`@ApplicationScoped` or `@Dependent`), which the
container creates itself (Vidocq/vidocq#201). In the application layer, the usual case, Vidocq adds that
export by itself.

A legacy main that boots the runtime directly (through `VidocqBootstrap`) still works — unwoven beans are then
covered by the load-time weaving agent (with the JDK's dynamic-agent warning), and Vauban's warning hints at a
trampoline that re-layers the application. Delete the legacy main — the runtime's own main re-layers it too — or
turn it into a trampoline if you need one of the two cases above.

One more benefit: applications never declare generated providers in
`module-info.java`. The annotation processors emit standard `META-INF/services` files
(`_VaubanComponents`, Cassini `$$CassiniAdapter`/`$$CassiniRoutes`…), and the Vauban
layer promotes them to synthetic `provides` when it resolves the module — your
`module-info.java` stays free of any generated class name.

NOTE: custom JUL log handlers declared in the application's `logging.properties` must
live on the module path — `LogManager` instantiates handlers through the system class
loader, which cannot see the layer.

[#app-layer-dependencies]
=== Dependencies in the application layer [.tag-new]#NEW#

By default (`vidocq.app.layer=all`, since Vidocq 0.4.0) the application layer holds the project's classes and the
project's dependencies, the way `WEB-INF/lib` works in a servlet container. A framework that looks up its
resources through its own class loader, Vaadin for instance, then sees the whole application. `vidocq:run`,
`vidocq:dev`, an IDE launch of `Vidocq.run()` and `vidocq:package` all take this default: development and
production behave the same way (Vidocq/vidocq#247). `-Dvidocq.app.layer=classes` is the opt-out: the layer holds
the project's classes only, and the dependencies stay on the module path, as they did before 0.4.0.

[#app-layer-migration]
*Migrating from 0.3.x.* The default changed from `classes` to `all`. An application that worked keeps working: where
`all` cannot be honoured and nobody asked for it, the build or the launch warns and falls back, it does not fail.

* A dependency whose module name cannot be derived stays in the parent layer, and the build warns with the jar name.
  Give the jar an `Automatic-Module-Name` to move it into the application layer.
* With the layer mode off (`vidocq.dev.layer=false`, `vidocq.package.layer=false`) the goal falls back to `classes`
  with a warning.
* A pin that reads a module of the application falls back to `classes` with a warning that names both modules.
* To go back for good, set `vidocq.app.layer=classes` in the POM (`<properties>` or the plugin's `<configuration>`) or
  on the command line. An explicit `-Dvidocq.app.layer=all` keeps the strict behaviour: each of the cases above
  fails the build.
* What to pin: a library with native code (JNI), a library that must be the same class in the runtime and in the
  application, and any library that fails to load twice (see the limits below). Use `vidocq.app.layer.keep`.

*The rule.* The parent layer is the closure of the runtime: the Jakarta and MicroProfile APIs, the Vidocq
modules, the modules that provide a Vidocq extension, the modules with a `javax.`, `sun.` or `com.sun.` package,
the pinned modules, and what all of them require. Everything else belongs to the application, automatic modules
included. A module that is kept also keeps the dependencies it declares in Maven. Maven records one path per
artifact, so a dependency shared with an application library and reached by a nearer path can land in the
application layer: pin it.

*Pinning.* `-Dvidocq.app.layer.keep=<patterns>` keeps modules in the parent layer. A pattern is a module name or
`groupId:artifactId`; `*` alone, or as a suffix (`org.acme.*`), matches several. A brick pins its own modules with
the `Vidocq-Parent-Layer` attribute of its manifest. A pinned module drags what it requires into the parent layer.
The other way round, a Vidocq jar whose manifest says `Vidocq-Application-Layer: true` is not kept by
the name rule: a module that integrates an application framework, such as
xref:modules/vidocq-runtime-extensions.adoc#vaadin[the Vaadin extension], goes to the application layer with it.
A pinned module that reads a module of the application fails the build, with both names.

*The startup report.* The `layer` headline counts the libraries, for instance
`3 modules, 2 libraries (...)`. The detailed report has one `parent layer` row for each pinned module, with its
reason. The build logs `application layer: <n> libraries, <m> kept in the parent layer by a pin`.

*Enriched libraries.* `vidocq:generate` runs the brick processors (Foy's, for instance) over the dependency jars they select, so a `@WebListener` of a library works without a workaround. The `layer` headline then counts them: `, 1 enriched (Foy 1)`. See xref:modules/vidocq-runtime-maven-plugin.adoc#brick-processors[Brick processors on dependency jars].

[[dev-recompile]]*Dev recompile.* At each change, `vidocq:dev` recompiles with a Maven run of its own, and says
which:

[source]
----
Changes detected — recompiling: ./mvnw -ntp -q process-classes -DskipTests -Dvidocq.moduleinfo.dev=true (MAVEN_ARGS: -U)
----

That run inherits the environment of `vidocq:dev`, so the `MAVEN_ARGS` it shows apply to every recompile: with
`-U` there, each one checks the remote repositories and takes seconds more.

[[dev-save-seen]]*How soon a save is seen.* [.tag-new]#NEW# The JDK's file watcher of macOS looks at the directories
every 2 seconds, so a save could wait up to 2 s before the recompile started. Where the JDK's
watcher polls, `vidocq:dev` and `vidocq:test` read the modification time and size of the watched files themselves,
every 200 ms by default (`vidocq.dev.watchPollMillis`; `0` keeps the JDK's watcher). The debounce
(`vidocq.dev.debounceMillis`, 250 ms) comes after, as before. On Linux the JDK's watcher is told of each save by the
kernel: it is kept, and the property changes nothing. The wait before the recompile starts is in no log line:
`Hot reload signalled after … ms` counts from the start of the recompile.

[[dev-save-while-compiling]]*A save while a recompile runs.* [.tag-new]#NEW# The compiler reads every source, then
writes the classes, seconds later on a real module. A source you save in between gets a class that is newer than the
source, compiled from what the compiler read before your save, and Maven takes a source with a newer class for
compiled. So `vidocq:dev` notes the time of each source when a recompile starts, and the classes the recompile leaves
when it ends. The recompile that your save starts deletes the class of that source, Maven compiles the module again,
and the log names the source:

[source]
----
Menu.java was saved since the previous recompile started and its class is not older: compiling it again.
----

* A source saved before the compiler read it is compiled a second time. The output does not change, and nothing
  reloads.
* A class written after the recompile ended stays: your IDE compiled it from the save.
* When a file time cannot be read, or a class cannot be deleted, a warning says so and the recompile goes on. If a
  save does not show then, save the file again.

The test runs do the same for the sources they compile: see
xref:continuous-testing.adoc#saved-while-compiling[A save while a run compiles].

[[dev-save-while-starting]]*A save while `vidocq:dev` starts.* [.tag-new]#NEW# `vidocq:dev` watches the sources last:
after the build, the dev services and the rest of its start. A file you save before that begins no recompile, and a
source saved while the build compiles it gets a class that looks up to date. So, once it watches, `vidocq:dev` looks
for the watched files saved since Maven started. When there is one, it recompiles before the application starts, and
the log names the file:

[source]
----
Menu.java was saved while vidocq:dev started: compiling it before the application starts.
----

* A start with no save compiles nothing more: only a file that is not older than the start of Maven counts.
* A source whose class looks up to date loses that class first, as above, and a second line names it:
  `Menu.java was saved since the build started and its class is not older: compiling it again.`
* When the save does not compile, a warning says so and `vidocq:dev` compiles again at the next change. The
  application starts once the sources compile.

[[dev-changed-while-stopped]]*A change made while `vidocq:dev` did not run.* [.tag-new]#NEW# `mvn vidocq:dev` alone
runs no phase of the build: the goal starts the application from the classes of the last build. So it first looks
for what changed since that build: a watched file saved since the compiler last ran, or a source it compiled that
is gone. When there is one, it builds the project before the application starts, and the log names the file:

[source]
----
Since the last build, Menu.java changed: building the project first (mvn process-classes).
----

* A start with no change builds nothing: `mvn vidocq:dev` stays the short way to start again.
* The compiler keeps a record of its last run in `target/maven-status`, and `vidocq:dev` reads the time of that
  record, not the times of the classes. A class your IDE compiled from the save does not hide the change.
* A changed source whose class looks up to date loses that class before the build, and a second line names it:
  `Menu.java was saved since the last build started and its class is not older: compiling it again.` It is a source
  your IDE compiled, or one you saved while the last build compiled it. Without its class, the build compiles it,
  with the annotation processors.
* `vidocq dev` and the IDE configurations run `mvn process-classes vidocq:dev`. The build of that command saw every
  change, and `vidocq:dev` builds nothing more.
* When the build fails, a warning says so and `vidocq:dev` builds again at the next change. The application starts
  once the project builds.
* Three changes are not seen: a change of the `pom.xml`, a file restored with an older date, and a deleted resource.
  Run `mvn process-classes vidocq:dev` then, after `mvn clean` for a deleted resource.
* A pom that sets `useIncrementalCompilation` to `false` leaves no record of the compiler. `vidocq:dev` then compares
  with the newest file of the classes, and a class that is not older than its source is taken for compiled.

[[dev-preload-classes]]*The application while a recompile runs.* [.tag-new]#NEW# `vidocq:dev` loads every class of
the application's directories as soon as the application layer starts, at the first start and at each layer swap.
The application then needs no class file from `target/classes`. It keeps running on the classes it loaded during a
recompile, and while a save does not compile:

[source]
----
Compile failed (exit 1); keeping previous JVM up.
----

The reason is in the compiler plugin: before it compiles the module again, it removes the classes it created. They
are back when the recompile ends, and stay out while your sources do not compile. An application that reads a class
when it first uses it then misses the classes no request asked for yet: the page fails with a
`NoClassDefFoundError`, and keeps failing once the class is back, until the application layer is swapped.

* Loading a class runs none of its code: a static initializer still runs when your application first uses the class.
* The jars of the application are left alone: no build writes them while the application runs.
* A class that cannot be loaded at that time is left to its first use, for instance one whose supertype comes from an
  optional dependency that is absent.
* A file that an annotation processor writes next to the classes, such as a generated resource, is still read from
  `target/classes` when the application asks for it.
* The logger `io.vidocq.runtime.core.VidocqDevReloadLoop` at DEBUG counts the classes and gives the time they took:
  `Application layer: 71 classes of the application's directories loaded ahead of their first use (15 ms)`.
* It comes with the reload inside the JVM, the default. With `-Dvidocq.dev.hotReload=false` or
  `-Dvidocq.dev.layer=false`, a change restarts the JVM, and until then the application reads each class when it
  first uses it.
* `-Dvidocq.dev.preloadClasses=false` reads each class when it is first used, as before.

*Dev reload.* The libraries are reloaded with the application. The JDBC drivers that the old layer defined are
deregistered at each reload. A thread that a library leaves running keeps the old layer in memory; the reload names
such threads in a warning, `Hot reload: N thread(s) still hold the previous application layer ...`. Virtual threads
are not detected. A library with native code (JNI) cannot be loaded twice by the JVM: keep it in the parent layer
with `vidocq.app.layer.keep`. A layer swap carries the HTTP sessions of the servlet application over to the new
layer, unless a rule drops them: see <<dev-swap-sessions,HTTP sessions across a swap>>. A change in method bodies only
keeps them too: see <<dev-hot-swap,hot swap>>.

[[dev-reload-reasons]]*Why a change reloads.* After each recompile, `vidocq:dev` compares the compiled output with the
one the application runs, class by class, with the JDK's Class-File API. When nothing changed, for instance an edited
comment, nothing is reloaded and the tests of the change still run:

[source]
----
Recompiled in 210 ms: the compiled output did not change, nothing reloaded.
----

When the change touches method bodies only, the application keeps running (<<dev-hot-swap,hot swap>>). Otherwise
both sides of the log say why the application layer is swapped:

[source]
----
Hot reload signalled after 1210 ms (layer swap: MainView gained a method lambda$new$1).
Hot reload - restarting on a fresh application layer: MainView gained a method lambda$new$1
----

The reasons, in the order they are checked:

* a class added or deleted: `MainView$1 is a new class`;
* a resource or `module-info` changed: `application.properties changed`. The files of `META-INF/vidocq/build-info/`,
  rewritten by every build, are left out, and so are the files an extension declares as written by its build tool,
  such as Vaadin's `flow-build-info.json`
  (xref:modules/vidocq-runtime-extensions.adoc#start-time-code[Declaring start-time code]);
* a class generated rather than compiled from the project's own sources (the compile source roots outside
  `target/`): `_VaubanComponents is not compiled from this project's sources`;
* a change of shape, such as a field, a method, a signature, a modifier, a supertype or an annotation: `Order lost a
  field total`, `GreetingResource changed an annotation on hello()`;
* a change in code that ran at start: `Greeter's constructor ran at start`, `Hello.init() ran at start`. That code
  is the static initializers, what each extension
  xref:modules/vidocq-runtime-extensions.adoc#start-time-code[declares as start-time], and every application method
  they call;
* otherwise, method bodies only: the classes are redefined in place, unless hot swap is off. Then the reason says
  why: `2 classes changed in method bodies only; class redefinition is off: vidocq.dev.hotSwap=false`.

A generated class changes because a class of the project did: a bean that gains a method changes its client proxy.
So when a class of the project is new or changed its shape, the reason names it, `Probe gained a method refresh`,
rather than `Probe_ClientProxy is not compiled from this project's sources`.

The next recompile waits until the application has confirmed the previous reload. A reload that is not confirmed
within two minutes, or a child JVM started again, makes the next one a swap: `the previous reload was not confirmed`.
The startup log says where the start-time declarations come from: `Hot swap: start-time declarations from 4 jars`.
With a runtime that declares none (one older than this check), the startup log says `Hot swap off: no dependency
declares its start-time code (...)`, and every change swaps the layer, with the log lines of earlier versions.

[[dev-swap-sessions]]*HTTP sessions across a swap.* [.tag-new]#NEW# A layer swap stops the application and starts it
again on the new classes, and the HTTP sessions of the servlet application move with it: during the stop, each
deployment writes its sessions out, and the new deployment at the same context path reads them back before it serves.
An open page keeps its session, and its next request finds what the session held. An object read back keeps what the
code that built it did: a listener that a constructor now registers is only on the objects built after the swap. The
log gives the count:

[source]
----
Hot reload - restarting on a fresh application layer: MainView gained a method lambda$new$1
Hot reload - kept 1 HTTP session across the reload
----

A session moves when Foy can write each of its attributes and read it back with the new classes; it drops one that it
cannot, with a WARNING of its own, and that client starts a new session. `vidocq:dev` drops all the sessions of a
swap, and says why, in four cases. Each looks only at what a session can hold, what Java serialization writes:
serializable classes, serializable lambdas such as Vaadin's listeners, serializable anonymous classes. A field added
to a REST resource or to a service keeps the sessions.

* a changed serializable class gained, lost or retyped an instance field, or changed its superclass or its
  interfaces, stopping being serializable included, so an instance written before the change would not match the
  class after it: `Hot reload - HTTP sessions not kept: Order gained a field total, so a restored instance would not
  match the new class`;
* [[dev-swap-serial-version-uid]]a changed serializable class whose `serialVersionUID` moved, where Java would refuse
  to read it back [.tag-new]#NEW#. The UID is the one the class declares, or else the default one Java computes, a
  hash of the class that a method or a constructor added, removed or changed moves, unless it is private: a lambda
  does not move it. A moved default UID keeps the sessions: Foy reads them with the new class, whose fields and
  superclass the case above found unchanged. It drops them when the class declares a `serialVersionUID`, before or
  after the change, is `Externalizable` or declares `writeObject`, whose data Foy cannot check: `Hot reload - HTTP
  sessions not kept: Order changed its serialVersionUID from 1 to 2, so a restored instance would not match the new
  class`. The other reasons say `declared serialVersionUID 1, not its default -3497372159402628655`, `no longer
  declares serialVersionUID 1`, and `changed its default serialVersionUID and declares writeObject` (or `is
  Externalizable`). To declare a `serialVersionUID` without losing the sessions, declare the value the class had,
  the one `serialver` gives for the class before the change. Records and enums are left out: Java ignores their
  `serialVersionUID`;
* a changed class gained or lost a serializable lambda while the code of one it kept changed: the compiler numbered
  its lambdas again, and a listener read back from the session could run the code of another one. `Hot reload - HTTP
  sessions not kept: MainView's lambdas moved, and a restored listener could run another one's code`. A lambda added
  after the others, a lambda body edited in place, or the last lambda removed keeps the sessions;
* a class gained or lost an anonymous class while a serializable one it kept changed, for the same reason: the
  compiler numbers them `MainView$1`, `MainView$2`, ... in source order. `Hot reload - HTTP sessions not kept:
  MainView's anonymous classes moved, and a restored listener could run another one's code`.

`-Dvidocq.dev.keepSessions=false` drops them at every swap: `Hot reload - HTTP sessions not kept:
vidocq.dev.keepSessions is false`. Dropped sessions end as before: `sessionDestroyed` fires, and the log gives their
count, `Undeploying the servlet application invalidated 1 HTTP session: its client starts a new one on its next
request`. The sessions are also dropped, without a line of their own, when the change is not classified (`Hot swap
off: no dependency declares its start-time code`), when the JVM refused a redefinition and the layer is swapped
instead, and when the context path changed between the two starts. An application without a servlet deployment gets no
line at all. Sessions the new deployment cannot read are dropped with one WARNING, and it starts anyway: `Hot reload -
the HTTP sessions of the previous deployment could not be imported, starting without them: ...`.

A session the rules above let move but that Foy cannot read back stays behind alone, and its client starts a new
session. Foy's WARNING names the first class it could not read, and why: a `serialPersistentFields` that changed, for
instance, gives `Importing the HTTP sessions dropped 1 session(s) that could not be restored, as new ones start
instead; first cause: class app.Order: its default serialVersionUID changed and its serializable fields changed`. Foy
gives the first reason that applies, in this order: `its declared serialVersionUID changed`, then `its default
serialVersionUID changed and` `it is Externalizable`, `it declares writeObject`, `its serializable fields changed`,
`its serializable superclass changed`, `its interfaces changed` or `its shape could not be read`, then `the class is
missing`, and otherwise the message of the exception the read threw (`an unreadable value: ...` when the stream fails
before it names a class).

A session that holds `@SessionScoped` beans moves with them [.tag-new]#NEW#: each instance keeps its state and belongs
to the new container, the client proxies it holds and the `Event`, `Instance`, `Provider` or `BeanManager` it injects
read back as the new container's, and the
xref:modules/vidocq-runtime-extensions.adoc#servlet-built-in-beans[`@Inject HttpSession` bean] gives the session
read back. This is CDI passivation: no `@PreDestroy` runs on the old side, no `@PostConstruct` on the new one
(xref:foy::internals.adoc#sessions-across-redeploy[Foy, Sessions across a redeploy]). A session that holds an
intercepted `@SessionScoped` instance, or one that is not `Serializable`, stays behind whole: Foy drops it at the
stop with its WARNING, and its client starts a new session.

[[dev-hot-swap]]*Hot swap.* A change in method bodies only is applied to the running application: the JVM redefines
the changed classes in place, through the agent `vidocq:dev` starts its child with, `vidocq-runtime-dev-agent`. The
application is not restarted: its beans, its HTTP sessions and the open browser pages keep their state, and the next
call runs the new code.

[source]
----
Hot reload signalled after 640 ms (class redefinition: 2 classes).
Hot reload - redefined 2 classes in 14 ms, the application keeps running: MainView, MainView$Row
----

* A method that is running when the class is redefined, such as a loop, finishes with its old code; its next call
  runs the new one.
* A class changed before it was ever loaded loads the new code when first used: `Hot reload - 2 classes changed in
  method bodies, none of them loaded yet: they load the new code when first used`. The classes of the application's
  directories are <<dev-preload-classes,loaded when the layer starts>>, so this is a class that could not be loaded
  then, or any class under `-Dvidocq.dev.preloadClasses=false`.
* The JVM checks the new classes against the loaded ones and redefines all of them or none. When it refuses, the
  layer is swapped and the log gives the JVM's reason: `Hot reload - redefinition refused (... add a method ...):
  restarting on a fresh application layer`. `class redefinition failed: invalid class` is its reason for a loaded
  class it cannot link, for instance one whose code needs a class of an optional dependency that is absent.
* The JVM clears the breakpoints of a class it redefines. With a debugger attached, the log says so: `...; breakpoints
  in MainView no longer stop: set them again, or debug with -Dvidocq.dev.hotSwap=false`.

The agent is a dev tool. `vidocq:dev` resolves it at the version of the application's `vidocq-runtime-core` and adds
it to the child only, never to a package; no binary contains it. It is added only in the layer mode with the in-JVM
reload (`vidocq.dev.layer` and `vidocq.dev.hotReload`, both on by default). `-Dvidocq.dev.hotSwap=false` starts the
child without it, and every change swaps the layer. Without the agent, the startup log says why: `Hot swap off:
vidocq.dev.hotSwap=false, every change swaps the application layer`, or `Hot swap off: vidocq-runtime-dev-agent 0.3.0
not found, ...` with a runtime older than the agent.

*Packaging.* Under `vidocq:package`, `lib/` holds the parent layer and `app/` holds the application jar and its
libraries. Both launchers hand `app/` to the runtime through `-Dvidocq.app.path`, also for an application with a
main class, and carry `-Dvidocq.app.layer=` with the mode the build settled on (`classes` too: a runtime that finds
the property unset takes the default, `all`) and the pinned list. `all` requires the layer mode
(`vidocq.dev.layer`, `vidocq.package.layer`). Left to the default, a goal without the layer mode falls back to
`classes` with a warning; asked for with `-Dvidocq.app.layer=all`, it fails. In the same way a dependency whose module
name cannot be derived stays in the parent layer with a warning by default, and fails the build when `all` was asked
for, with a message that names the jar: add an `Automatic-Module-Name` to it, or use `vidocq.app.layer=classes`. See xref:modules/vidocq-runtime-maven-plugin.adoc#app-layer-property[the plugin properties].

[[app-layer-jdk-modules]]*JDK modules.*Only the boot layer can define a JDK module, so a JDK module that only an
application module requires, such as `java.sql` for Vaadin's `flow-data`, must be resolved there. `vidocq:run`,
`vidocq:dev` and the `vidocq:package` launchers add these modules to `--add-modules`, read from the descriptors of
the application path. A `java` command written by hand needs the same option; without it the runtime fails with
`Cannot create the application layer (...): Module java.sql not found, required by flow.data. A JDK module can
only be resolved in the boot layer: add --add-modules java.sql to the java command (...)` (Vidocq/vidocq#254).
A `requires` on a JDK module added while `vidocq:dev` runs needs a restart of `vidocq:dev`: a hot reload keeps the
boot layer.

*Known limits.*

* A plain IDE run of `main` (the `Vidocq.run` trampoline) keeps the automatic libraries in the boot layer, and
  loads the application and its other libraries twice: the start warns with `VIDOCQ-LAY-001`, see
  <<ide-run-twice,above>>. The `(dev)` configuration that `vidocq:idea` writes has no such limit.
* `vidocq:jlink`, `vidocq:jpackage` and the Docker image built on the jlink image have no application layer: an
  image has one layer, the JVM's own, with every module linked into it, and `vidocq.app.layer` does not apply
  (xref:modules/vidocq-runtime-maven-plugin.adoc#jlink-one-layer[one layer], BUG-20261114-11). The same application
  runs in both; xref:modules/vidocq-runtime-maven-plugin.adoc#jlink-differences[five things differ]. An encrypted jar
  needs the application layer, so the `vidocq:package` distribution.
* A library with native code (JNI) cannot be loaded twice by the JVM, and the dev reload loads the application
  layer again: pin it with `vidocq.app.layer.keep`.
* A thread that a library leaves running keeps the previous layer in memory; the dev reload warns, as above.
* The libraries of the layer are listed in the `layer` section of the startup report.
* The IDE launch and the build-time split share the rule for explicit modules (the runtime, the bricks, what they
  read). They differ on automatic modules only, see the first limit of this list.
* Jar signatures are not verified in the layer.
* An automatic module declares no `requires`, so the JDK modules it uses are not added for it. One that needs
  `java.sql` or `java.desktop` fails with `NoClassDefFoundError`: add the module with `--add-modules` in
  `vidocq.dev.jvmArgs` or the package's `jvmArgs`, or give the jar a descriptor with `vauban:modularize`.

== Packaging with `vidocq-runtime-maven-plugin`

The Maven plugin exposes three packaging targets. See xref:modules/vidocq-runtime-maven-plugin.adoc[the dedicated page] for the full inventory and the internal `JLINK.md` details, and xref:shipping.adoc[Choosing how to ship an application] for which one fits which situation.

[cols="1,3"]
|===
| Goal | Output

| `vidocq:jlink`
| `target/dist/` (binary + embedded Java runtime, ~40 MB)

| `vidocq:jpackage`
| `target/installer/<name>.app` or `.exe`/`.msi`/`.deb`/`.rpm`

| `vidocq:docker`
| `target/Dockerfile`: around the jlink image on `distroless/base-debian12:nonroot` (~50 MB image), or the `vidocq:package` distribution on a JDK base image (`-Dvidocq.docker.kind=jdk`)
|===

Quick start (from `vidocq-runtime-cassini-rest-example`):

[source,bash]
----
cd vidocq-runtime-examples/vidocq-runtime-cassini-rest-example
./mvnw -ntp package -DskipTests
./target/dist/bin/todo-app
----

`jlink` and `jpackage` require every dependency to be a *named* module. When some third-party jars ship without `module-info.class`, run `vauban:modularize` beforehand: it generates their descriptors into `target/vauban-modularized/`, where `dev`, `jlink` and `package` pick them up automatically. See xref:modules/vidocq-runtime-maven-plugin.adoc#modularize[the `vauban:modularize` goal].

== Multi-module applications (scanned dependencies)

Hexagonal and multi-module applications typically keep their business and adapter modules
*spec-only* — Jakarta EE / MicroProfile APIs only, no Vidocq dependency, no Vidocq APT — and
concentrate everything runtime-specific in a small main module. That main module asks
`vidocq:generate` to scan the app modules and produce the CDI/REST glue for them. The id `generate` is the one of the
execution the plugin binds as a build extension, or `vidocq-runtime-parent`: the configuration below merges into it,
and the goal still runs once.

[source,xml]
----
<execution>
    <id>generate</id>
    <goals><goal>generate</goal></goals>
    <configuration>
        <scanDependencies>
            <scanDependency>com.acme:my-rest-adapter</scanDependency>
            <scanDependency>com.acme:my-domain</scanDependency>
        </scanDependencies>
    </configuration>
</execution>
----

Two rules for each *scanned* module's `module-info.java` — and remember that the Java module
system only lets a module `opens` (or `exports`) packages it *owns*: you cannot open another module's package from
the main module, which is why the single-module `opens` shown in
xref:getting-started.adoc[Getting started] must move into the module that contains the classes.

[source,java]
----
module com.acme.rest.adapter {
    exports com.acme.rest;          // resource classes
    exports com.acme.rest.dto;      // JSON-B reads records via their public accessors
    requires jakarta.cdi;
    requires jakarta.ws.rs;

    // The consuming runtime generates/reflects the CDI plumbing for these beans.
    // Unqualified `opens` names no runtime module: the module stays spec-only,
    // and classpath-based runtimes ignore it entirely.
    opens com.acme.rest;
}
----

[NOTE]
.New in 0.3.0
====
The classes that `vidocq:generate` produces for scanned dependencies (client proxies,
interceptors) live in packages *owned by those dependencies*. Since 0.3.0 the plugin keeps them
out of the main module automatically:

* `vidocq:generate` parks them in `target/vidocq-patches/<artifactId>/`
  (log line: `JPMS: parked N generated class(es) of '…'`);
* `vidocq:generate` then writes an *enriched* copy of each such jar in `target/vidocq-enriched/`,
  carrying its own generated classes, with a module descriptor that declares its providers — the
  packages already exist in those jars, so the module path never sees a split package;
* `vidocq:dev`, `vidocq:run`, `vidocq:package` and `vidocq:jlink` use that copy in place of the
  original; only a jar that cannot be given a descriptor keeps its original, and `vidocq:dev`
  attaches its classes with `--patch-module`.

No configuration is needed: see
xref:modules/vidocq-runtime-maven-plugin.adoc#generate[which jars `vidocq:generate` scans].
====

[WARNING]
.On 0.2.0 (released)
====
Vidocq 0.2.0 leaves the generated classes in the main module's `target/classes`, which creates
an illegal *split package* on the module path: the boot layer fails with
`ResolutionException: Module <main> contains package <pkg>, module <dep> exports package <pkg>`
— or, if the dependency is not `requires`-ed, its beans are silently absent (HTTP 404).
The workaround on 0.2.0 is to do by hand what 0.3.0 does natively:

. move the foreign-package classes out of `target/classes` *before* the jar is built
  (e.g. `maven-antrun-plugin` at `prepare-package` — moving them after the fact is not enough,
  because `maven-jar-plugin` records the packages in the `ModulePackages` attribute of
  `module-info.class`);
. launch with `--patch-module <dep.module>=<dir>` for each dependency, e.g. via the
  `<jvmArgs>` of the `package` goal for the generated launch scripts.
====

[#several-applications]
== Several applications in one reactor

A reactor can hold one application per module, next to the library modules they share. Each application module
is an ordinary Vidocq application: `vidocq-runtime-maven-plugin` in its `<build><plugins>`, and its own
`vidocq.mainModule`. None of them needs a main class (<<entry-point>>).

[source,xml]
----
<!-- orders/pom.xml -->
<properties>
    <vidocq.mainModule>com.acme.orders</vidocq.mainModule>
</properties>

<!-- billing/pom.xml -->
<properties>
    <vidocq.mainModule>com.acme.billing</vidocq.mainModule>
</properties>
----

Run `mvn vidocq:idea` once from the reactor root: it writes `orders (dev)`, `orders (run)`, `orders (debug)` and
the same three for `billing`, named after each module's `artifactId`, so two applications never collide. A
module pom that sets `vidocq.idea.configurationName` gets that name instead, and `vidocq.idea.exclude=true` leaves
a module out. Each `(dev)` and `(run)` configuration runs Maven on its own module's pom, so the sibling modules
it depends on must be resolvable: `mvn install` the reactor once. When the plugin is only declared in the
application modules, add it to the root `<pluginManagement>` so that the `vidocq:` prefix resolves there. See
xref:modules/vidocq-runtime-maven-plugin.adoc#idea[the `vidocq:idea` goal].

Give each application its own HTTP port in its `vidocq.properties` if you run them side by side.

== MicroProfile configuration

Vidocq Runtime implements {spec-mp-config}. Source hierarchy, highest to lowest priority:

[cols="1,2,3"]
|===
| Ordinal | Source | Description

| 400 | `SystemPropertiesConfigSource` | `-Dkey=value`
| 300 | `EnvConfigSource` | Environment variables (`KEY_NAME`)
| 250 | `ExternalFileConfigSource` | `${java.home}/conf/vidocq.properties` (jlink image)
| 100 | `PropertiesFileConfigSource` | classpath `vidocq.properties`
|===

`ExternalFileConfigSource` lets you override a deployed jlink/jpackage binary without rebuilding, simply by editing the `conf/vidocq.properties` file next to the launcher. A boot log line traces the effective load.

[#property-expressions]
== Property expressions [.tag-new]#NEW#

A value may refer to other keys with the {spec-mp-config} property expressions, which every Vidocq key and the extensions read, with or without Ravel:

[source,properties]
----
vidocq.chappe.listener.default.port=${DASHBOARD_PORT:8080}
orders.url=jdbc:postgresql://${db.host}:${db.port:5432}/orders
----

* `${key}` is the value of `key`, from any source — an environment variable `DASHBOARD_PORT` above — and is itself expanded; `${key:default}` is `default` when no source has `key`. The key and the default may hold expressions: `${url.${target}}`.
* `\${key}` is kept as written, `${key}`.
* An expression without a default whose key has no value leaves the property without a value: the extension that reads it applies its own default.
* An expression that comes back to its own key, or a `${` without its closing brace, fails the read with an `IllegalArgumentException`.
* `mp.config.property.expressions.enabled=false` turns the expansion off: values are read as written.

With Ravel, `ConfigProvider.getConfig()` and `VidocqConfig` expand a value the same way.

[#jvm-options]
== JVM options of each binary

Options every start needs go in the pom, as `vidocq.jvmArgs`: the build writes them into the `vidocq:package`
launchers and bakes them into the `vidocq:jlink` image, so the `vidocq:jpackage` application and the `vidocq:docker`
image built on it get them too (xref:modules/vidocq-runtime-maven-plugin.adoc#jlink-jvm-args[JVM arguments of the
image]).

Options for one start go in a variable, and each launcher reads a different one. An option set there wins over the
same option of `vidocq.jvmArgs`:

[cols="1,2"]
|===
| Binary | Where its JVM options go at start

| `vidocq:package` distribution
| The `JAVA_OPTS` variable, read by `bin/<app>.sh` and `bin/<app>.bat`.

| `vidocq:jlink` image
| The `JDK_JAVA_OPTIONS` variable, read by the image's `java` launcher. `JAVA_OPTS` is not read.

| `vidocq:jpackage` application
| The `JAVA_TOOL_OPTIONS` variable, or the `[JavaOptions]` section of the launcher's `.cfg` file. `JDK_JAVA_OPTIONS`
and `JAVA_OPTS` are not read.
|===

A jpackage launcher is a native program, not the `java` launcher, so it ignores `JDK_JAVA_OPTIONS`. Two ways remain:

* `JAVA_TOOL_OPTIONS`, read by the JVM itself, which then prints `Picked up JAVA_TOOL_OPTIONS: …` on standard error.
  The options of the launcher come after it: for a system property both set, the launcher's value wins.
+
[source,bash]
----
JAVA_TOOL_OPTIONS="-Xmx512m" target/installer/my-app.app/Contents/MacOS/my-app
----
* The launcher's `.cfg` file, one `java-options=` line per option under `[JavaOptions]`. These lines apply at every
  start, without a variable: `my-app.app/Contents/app/my-app.cfg` on macOS, `my-app/lib/app/my-app.cfg` on Linux,
  `my-app\app\my-app.cfg` on Windows.
+
[source,ini]
----
[JavaOptions]
java-options=-Xmx512m
----

[#aot]
== Ahead of time: the JDK's AOT cache, and GraalVM

[#aot-cache]
*The JDK's AOT cache works, and you record it yourself.* Since JDK 25, a first run records the classes it loaded and linked into a cache, and the next runs start from it (JEP 483, 514, 515). No Vidocq goal records or ships that cache yet: pass the JDK's own options.

On a `vidocq:package` distribution, through `JAVA_OPTS`:

[source,bash]
----
# 1. A training run: start the application, use it, stop it. The cache is written when the JVM ends.
JAVA_OPTS="-XX:AOTCacheOutput=app.aot" bin/my-app.sh

# 2. Every later run starts from the cache.
JAVA_OPTS="-XX:AOTCache=app.aot" bin/my-app.sh
----

On a jlink image, whose launcher reads no `JAVA_OPTS`, through the `JDK_JAVA_OPTIONS` variable the `java` launcher reads itself:

[source,bash]
----
JDK_JAVA_OPTIONS="-XX:AOTCacheOutput=app.aot" target/dist/bin/my-app
JDK_JAVA_OPTIONS="-XX:AOTCache=app.aot" target/dist/bin/my-app
----

On a `vidocq:jpackage` application, through `JAVA_TOOL_OPTIONS` or the launcher's `.cfg` file (see <<jvm-options>>).

What to know:

* **The cache matches one build on one JDK.** Record it again after each build of the application and each change of JDK: classes that no longer match are loaded the usual way, silently.
* **The two launches do not gain the same.** In a jlink image, which has one layer, every class of the application is stored loaded and linked. In the application layer of a `vidocq:package` distribution, the classes of that layer are stored too, but not linked: they gain less (xref:shipping.adoc#why-two-ways[why two ways of loading]).
* **Never add `--limit-modules`** to the JVM options of an application: the JVM then turns CDS and the AOT cache off.
* **Do not record a cache over an encrypted jar (sjar).** The cache holds the classes as the JVM received them, so decrypted (Vidocq/vauban#304).

Start times are not given here: a figure belongs in `BENCH.md`, with its machine and its command (Vidocq/vidocq#579).

[#aot-graalvm]
*A GraalVM native image is not available yet.* What is in place is its groundwork: no reflection where code can be generated, no dynamic proxy, and, for an image, a launch in one layer with nothing defined at run time. The reachability metadata, the build goal and the tests are not done.
