= Java modules in a Vidocq application
:description: Why a Vidocq application opens some of its packages, what the tooling detects and writes for you, what it cannot see, and what the runtime says when a package is missing.

[.lead]
A Vidocq application is a named Java module: its `src/main/java/module-info.java` says which modules it reads (`requires`) and which of its packages other modules may reach. Most of the time you do not touch the `opens` part of it: the tooling writes it. This page explains what happens underneath, for the day you need it.

[#why]
== Why `opens` exists

Some libraries of the runtime look inside your classes by reflection: JSON-B reads and fills the fields of the DTOs it has no generated binding for (see <<json-b-at-build-time>>), Jakarta Persistence builds your entities, Vauban calls a `private` interceptor method. Reaching private fields and constructors of a named module is *deep reflection*, and the Java module system only allows it on a package the module **opens**:

[source,java]
----
module com.example.library {
    requires io.vidocq.runtime.extensions.jakartaee.core.cassini; // vidocq:cassini-rest
    // added by vidocq: the runtime reaches these packages by reflection
    opens com.example.library.book; // vidocq:reflection
}
----

Without that line nothing fails at build time: the first request that serializes a `Book` fails with an `IllegalAccessException` or an `InaccessibleObjectException`.

[#what-is-written-for-you]
== What the tooling writes for you

[cols="1,3"]
|===
| When | What happens

| `vidocq create`, `vidocq extension add`
| The `requires` and `opens` an extension needs (for instance `opens db.migration;` for Flyway, its folder created) are written at once, each line marked `// vidocq:<extension id>`.

| `vidocq dev`
| After each compile, a package the runtime will reach by reflection and the module does not open is opened, in `module-info.java` and in the compiled `module-info.class`; the console prints `✔ module-info.java: opens com.example.library.book;   (…)` and the application starts.

| `./mvnw package`, the CI
| `vidocq:check-module-info` fails the build with the exact line to add, and names `vidocq doctor --fix` and `./mvnw vidocq:complete-module-info`, which write it. A build never rewrites your sources.

| `vidocq doctor`
| Runs the same check after a compile; `--fix` writes the missing lines.
|===

The lines the tooling adds for reflection go in one block, last in the file, each marked `// vidocq:reflection` (see xref:modules/vidocq-runtime-cli.adoc#module-info-layout[the layout of `module-info.java`]). A line you wrote yourself is left where it is.

[#what-is-detected]
== What the build check detects

`vidocq:check-module-info` and `vidocq doctor` read the compiled classes of `target/classes` (nothing is loaded or run) and start from three kinds of classes:

* an entity (Jakarta Data), embeddable or mapped superclass (`@Entity`, `@Embeddable`, `@MappedSuperclass`) that Mansart has no model generated at build time for: its package (xref:#entities[below]);
* a REST resource or provider (`@Path`, `@Provider`): the types its methods take and return, which JSON-B binds — not the resource itself, whose dispatch is generated;
* a CDI interceptor with a `private` interceptor method (`@AroundInvoke`, `@AroundConstruct`, a lifecycle callback): its package. Other interceptor methods are called through code generated in their package and need nothing.

From each type reached, the check follows the declared types of its fields and of its getters, generic arguments included, as long as they are classes of the application.It also follows the superclass of each type it reaches, whose fields and getters JSON-B, and Mansart when it falls back to reflection, read too, and, for a type that is an interface or an abstract class, the application classes that implement or extend it directly, one of which is what the field actually holds:

----
BookResource ──returns──▶ List<Book> ──▶ Book ──field──▶ Author ──field──▶ Address
 (not listed)                       com.example.book   com.example.author   com.example.common
----

Three packages must be opened here, and each is reported with the type that brought it in — unless JSON-B maps those types without reflection, below.

[#json-b-at-build-time]
== JSON-B without reflection

The REST extension's codegen bundle runs Champollion's processor: every **record**, and every **class** with a no-argument constructor — `final` or not, with a superclass or not — that a resource takes or returns gets its JSON-B binding generated at build time, with the types it holds. JSON-B then reads and writes it through plain generated code, with no reflection, so its package needs no `opens` for JSON-B, and the check does not ask for one. Classic DTOs work as they are:

[source,java]
----
public class BaseEntity {                       // com.example.shop.common
    private Long id;
    public Long getId() { return id; }
    public void setId(Long id) { this.id = id; }
}

public class Product extends BaseEntity {       // com.example.shop.catalog
    private String name;
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
}
----

Neither `com.example.shop.catalog` nor `com.example.shop.common` is opened: the binding of `Product` calls the public getters and setters, inherited ones included, and writes the superclass's properties first, as the reflective mapping does.

*Subclasses.* JSON-B maps a value by its declared type: a resource declared to return `Product` that returns a `SpecialProduct` writes `Product`'s properties, by reflection or by the binding alike. So a subclass needs nothing either. A subclass compiled with the application gets its own binding too, used where it is the declared type. One case escapes the check: a method that returns a `Response` — JAX-RS then hands JSON-B the class of the entity it holds, which the build cannot know; the runtime message below names its package if it lacks a binding.

A type the generated code cannot map keeps the reflective mapping, and the compiler says why, as an `[INFO]` line of the build:

----
Champollion: com.example.shop.Shape keeps the reflective JSON-B mapping at run time: abstract
----

The usual reasons, and what to do:

* an abstract class, an interface or `Object` as a property type — or a JSON-B customisation the generated code cannot honour (a `@JsonbCreator` parameter without a `@JsonbProperty` name in a dependency compiled without `-parameters`, `@JsonbTypeInfo` on an interface that is not sealed, `@JsonbVisibility`, `@JsonbPropertyOrder`…): keep it, and keep the `opens` the check asks for.Date and number formats, arrays, adapters, serializers and deserializers, creators, and `@JsonbTypeInfo` on a sealed interface over records are generated;
* a property declared on several classes of a hierarchy (a getter overridden in a subclass), an interface with a default getter: same;

An adapter, serializer or deserializer that is a CDI bean — injections included — is called by the generated binding too: the REST extension brings `champollion-jsonb-cdi`, whose registry hands the bindings the container's instances, one per application, destroyed when it stops, and whose build compatible extension, run by Vauban at build, fails the build when such a class is ambiguous or injects without being a bean (its injections would stay null) — xref:champollion::reference.adoc#jsonb-cdi[JSON-B and CDI].

A type of a dependency — a DTO jar your resources return — cannot get its binding in your compilation. The processor lists it, with the types it holds, in `META-INF/champollion/dependency-types`, and `vidocq:generate` runs the processor over that jar: the bindings go into the jar's enriched copy (xref:modules/vidocq-runtime-maven-plugin.adoc#brick-processors[brick processors]), so the library's packages need no `opens` either, not even a package it does not export.

The output is the same as the reflective mapping, character for character (`@JsonbProperty`, `@JsonbTransient` and `@JsonbNillable` included). The details are in Champollion's reference, xref:champollion::reference.adoc#rest-bindings[Bindings for the types REST resources exchange].

[#entities]
== Entities and repositories (Jakarta Data)

Mansart's processor, run by the `mansart-data` extension's codegen bundle, generates each entity's model (`_Book`), each repository's implementation (`BooksImpl`), the code that builds the records a JDQL query projects into, and, per package, a `_MansartComponents` service that hands them to Mansart by plain calls. Mansart reaches none of them by reflection, so a package of entities, repositories or projection records needs no `opens` for Jakarta Data, and `vidocq:check-module-info` and `vidocq doctor` do not ask for one when the generated `_MansartComponents` names the entity.

They still ask for it when Mansart falls back to reflection: an entity no generated model covers (a module compiled without the processor), which Mansart then reads by reflection, as it does under another container (Weld, Open Liberty). The reason line says so: `opens com.acme.shop.data;   (com.acme.shop.data.Loan, an entity (Jakarta Data) without a model generated at build time)`. An entity a REST resource returns is a plain class to the JSON-B processor like any other: it gets its generated binding (`Product$$Binding`) and needs no `opens` for JSON-B either, unless one of the reasons above applies. The details are in Mansart's reference, xref:mansart::reference.adoc#application-modules[Your entities and repositories need no `opens`].

[#limits]
== What it cannot see

The check works from the declared types it finds in your compiled classes. It cannot see a use decided while the application runs:

* JSON-B called by hand, `JsonbBuilder.create().toJson(report)`, on a type no resource takes or returns;
* `Class.forName(…)`, or a resource read with `getResource(…)` from a package of the application;
* a third-party library that does its own reflection;
* the actual class behind a field typed by `Object` or by a JDK or library interface (`Serializable`, `Comparable`…): the check follows the declared type and, for an application interface or abstract class, its implementations;
* the entity of a `Response` whose static type is `Object`:Champollion's processor reads the method bodies for the entity given to `Response.ok(…)`, `accepted(…)`, `ResponseBuilder.entity(…)` and `GenericEntity<T>`, generates its binding and lists it (`META-INF/champollion/rest-entity-types`); the check reads that list, so it covers a `Response` entity it cannot bind. Only an entity typed `Object`, whose class is known at run time only, escapes it.

For these cases, the runtime tells you what to add, below.

[#runtime-message]
== What the runtime says

When a library fails to reach a package of your application by reflection, the failure the runtime logs — a request's `500`, a failed start-up — is followed by one error that names the package and the line, once per package:

----
[ERROR] Module com.example.library does not open package com.example.library.report to
io.vidocq.champollion.jsonb, which reached class com.example.library.report.Report by reflection
at run time. The build checks cannot see this use: add `opens com.example.library.report;`
to module-info.java (or make it an `open module`). See "Java modules in a Vidocq application"
in the documentation.
----

Under `vidocq dev` you have nothing to do: the plugin writes `opens com.example.library.report; // vidocq:reflection` to `module-info.java`, prints `✔ module-info.java: opens com.example.library.report;   (reached by reflection at run time)`, and the application reloads; retry the request once it has. Only a package of your application is named: a denial between two libraries, or into the JDK, is left to its stack trace.

[#open-module]
== Or: an open module

If you would rather never think about `opens`, make the application an **open module**:

[source,bash]
----
vidocq create --name library --group-id com.example -x cassini-rest --open-module
----

[source,java]
----
open module com.example.library {
    requires io.vidocq.runtime.extensions.jakartaee.core.cassini; // vidocq:cassini-rest
}
----

An open module opens every one of its packages to reflection, at run time. Nothing else changes: `requires` and `exports` work as before, and code outside the module still compiles only against the packages you export. The tooling follows it: `vidocq extension add`, `vidocq dev`, `vidocq doctor --fix` and `vidocq:complete-module-info` write no `opens` line (javac refuses one inside an open module), the build check has nothing to ask for, and the runtime message above cannot happen.

The trade-off is encapsulation: any library may reflect into any package of the module. For an application that is usually fine — it is the end of the chain, nothing depends on it. For a library others use, keep a plain module and its `opens` lines.

To make an existing application open, change `module` to `open module` in `module-info.java`, then run `vidocq doctor --fix`: it removes the `opens` lines javac now refuses, and names those you wrote yourself. To go back, remove `open` and run `vidocq doctor --fix` again (or let `vidocq dev` and the build check ask for the lines again).
