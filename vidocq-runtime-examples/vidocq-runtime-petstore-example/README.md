# Vidocq Runtime — Petstore Example

An end-to-end demo of a "petstore" REST API (inspired by the Swagger petstore), built with the
Vidocq stack alone:

| Layer             | Brick                                                         |
|-------------------|---------------------------------------------------------------|
| HTTP transport    | **Chappe** (HTTP/1.1 + H2/H3, zero dependencies)              |
| REST / JAX-RS 4.0 | **Cassini** via `vidocq-runtime-cassini-rest-extension`       |
| Persistence       | **Mansart** Data 1.0 + Pool + Transactions on in-memory **H2** |
| JSON-B / JSON-P   | **Champollion** (`champollion-jsonb` / `champollion-jsonp`)   |
| Config            | MicroProfile Config 3.1 via **Ravel** (opt-in)                |
| Packaging         | `vidocq-runtime-maven-plugin` → jlink + jpackage + Docker     |

The model has three **flat** entities — `Pet`, `Category`, `Tag` — linked by foreign keys and
a `pet_tags` join table. Mansart Data does not handle JPA associations: the relations are
**put back together by hand in `PetService`** (resolving or creating the category and the tags,
assembling the `PetView`).

## How the application starts

There is **no `main` class**: the runtime's main, `io.vidocq.runtime.core.Vidocq`, starts the
`VidocqBootstrap`, which discovers every extension on the module path (through `ServiceLoader` /
`provides VidocqExtension`) and orchestrates them in priority order:

1. `mansart-pool` (200) — opens the H2 pool from `vidocq.pool.*` and publishes the `DataSource`.
2. `mansart-data` (300) — wires the `@Repository` interfaces (implementations generated by APT).
3. `cassini` (500) — mounts the JAX-RS resources on the Chappe listener.
4. `chappe-bootstrap` (10000) — starts the listener on `0.0.0.0:8080`.

`SchemaInitializer` (an `@Observes @Initialized(ApplicationScoped.class)`) creates the schema
and the demo data once the CDI container is ready.

The application module is declared once in the `pom.xml` and used by every goal
(`vidocq:dev`, `vidocq:package`, `vidocq:jlink`, `vidocq:jpackage`):

```xml
<properties>
    <vidocq.mainModule>io.vidocq.runtime.examples.petstore</vidocq.mainModule>
</properties>
```

## Build

Like every example, the petstore resolves the runtime (and the H2 extension below) from the
local repository: build the runtime workspace first, then the example.

```bash
# from the root of the vidocq/ project: installs core + extensions (including the H2 repackage)
./mvnw -ntp -DskipTests install

# then the example alone
./mvnw -ntp -DskipTests -pl vidocq-runtime-examples/vidocq-runtime-petstore-example clean package
```

The `dist` profile (active by default) produces:

- `target/dist/` — a self-contained **jlink** image (JVM + application, next to no external dependency);
- `target/installer/petstore-app.app` — a native **jpackage** app-image (`petstore-app` v1.0.0);
- `target/Dockerfile` — a Docker image (distroless), not built by default.

For a quick compile + test cycle without native packaging: `-P'!dist'`.

> **Why `vidocq-runtime-h2-module-repackaged`?** H2 is only an *automatic module*
> (`Automatic-Module-Name` in its manifest, no `module-info`), which `jlink` refuses. The
> `io.vidocq.runtime.extensions.module.repackaged:vidocq-runtime-h2-module-repackaged` artifact
> (in `vidocq-runtime-extensions/vidocq-runtime-extensions-module-repackaged/`) republishes H2
> **unchanged** as the named Java module `com.h2database` (`module-info` generated by `jdeps`,
> `provides java.sql.Driver with org.h2.Driver`), which makes the jpackage possible. The petstore
> depends on it instead of the plain `com.h2database:h2`. The H2 classes keep their original
> licence (MPL 2.0 / EPL 1.0, see `META-INF/NOTICE.txt`); only the added `module-info` is under
> the Vidocq licence.

## Run

```bash
# 1) jlink binary
./target/dist/bin/petstore-app

# 2) jpackage app-image (macOS)
./target/installer/petstore-app.app/Contents/MacOS/petstore-app

# 3) In development, straight from Maven
../mvnw -pl vidocq-runtime-petstore-example vidocq:dev
```

Then open the UI: <http://localhost:8080/>

## API

| Method  | Path                         | Effect                                           |
|---------|------------------------------|--------------------------------------------------|
| `GET`   | `/api/pets`                  | Lists the pets (filter `?status=available\|pending\|sold`) |
| `GET`   | `/api/pets/{id}`             | One pet (404 otherwise)                          |
| `GET`   | `/api/pets/count`            | Number of pets (`text/plain`)                    |
| `POST`  | `/api/pets`                  | Creates a pet (category + tags resolved or created) |
| `PUT`   | `/api/pets/{id}`             | Updates a pet and resynchronises its tags        |
| `DELETE`| `/api/pets/{id}`             | Deletes a pet and its links                      |
| `GET` / `POST` | `/api/categories`     | Lists / creates a category                       |
| `GET` / `POST` | `/api/tags`           | Lists / creates a tag                            |

Examples:

```bash
curl http://localhost:8080/api/pets
curl 'http://localhost:8080/api/pets?status=available'

curl -X POST -H 'content-type: application/json' \
     -d '{"name":"Rex","category":"Dog","status":"available","price":120.0,"tags":["friendly","trained"]}' \
     http://localhost:8080/api/pets

curl -X PUT -H 'content-type: application/json' \
     -d '{"name":"Rex","category":"Dog","status":"sold","price":130.0,"tags":["trained"]}' \
     http://localhost:8080/api/pets/1

curl -X DELETE http://localhost:8080/api/pets/2
curl http://localhost:8080/api/categories
curl http://localhost:8080/api/tags
```

## Configuration

`src/main/resources/vidocq.properties` — the Chappe listener, the REST mount (`/api`), the static
mount (`/`), and the H2 pool (`jdbc:h2:mem:petstore;DB_CLOSE_DELAY=-1`). The database is
**in-memory**: `SchemaInitializer` recreates the schema and the demo data at every start.
